# MCP through OpenShell and the middleware: the D98 prototype

Status: prototype built and tested offline (2026-10-23, backlog A2); the offline prerequisites for retiring the proxy built (2026-10-24): the production check of held calls, the workspace's cards for the middleware's requests, listings without denied tools, and binary results as artifacts; the two remaining offline gaps closed (2026-10-26): where the client runs in the confined runtime, with binary results handed to the host over `publish_mcp_binary`, and canaries that need no proxy (`list_mcp_tools`). The 2026-10-26 babbage lab found OpenShell 0.1.5 never offers the middleware an event-stream listing whole: such listings now pass unread, and the runtime's client filters and reports them (`report_mcp_listing`, below). Native rules and the middleware's call decisions worked in that lab. The decision it informs is D98's ([decisions](../DECISIONS.md)); the proxy stays as built until the owner decides.

Today every MCP call goes through the MCP proxy, a service in its own sandbox that holds the servers' credentials and decides each call ([MCP connectors](../MCP-CONNECTORS.md)). D98 would drop it: the agent's MCP client calls the server's own URL, and OpenShell's proxy, which already carries every sandbox request, checks it twice: its native `protocol: mcp` rules allow or deny each tool by name, and the policy middleware decides the rest, as it decides research sandboxes' HTTP ([policy middleware](../POLICY-MIDDLEWARE.md)). D98 names five proofs, plus response inspection; if all pass, the proxy retires; if holds do not fit, it stays, slimmed to MCP only.

## What was built

- **Compiler.** `compile_agent_mcp` (`policy/openshell.py`) gives a sandbox one inspected `protocol: mcp` endpoint per declared server, the same endpoint the proxy sandbox's fence has, from the same code, plus the policy middleware for the servers' hosts. The config names the policy revision, the project and the caller (`{"mcp": {"project": "crypto", "caller": "agent-runtime"}}`). Escalated tools are admitted by name at the fence, since the middleware holds them; denied tools are never admitted.
- **Middleware.** For a sandbox with that config (`policy_middleware/mcp.py`, `evaluator.py`), every request must be one POST of one strict JSON-RPC message to a declared endpoint, read with the code the proxy uses (`policy/mcp_wire.py`, moved from the proxy: strict JSON, the parameters MCP defines, the parameters' digest, placeholders in bodies, tool listings, event streams). The library's tool rules decide it with the orchestrator as origin, and every message gets an `mcp-call` record.
- **Harness.** `DirectClient` (`orchestrator/mcp_direct.py`) speaks Streamable HTTP to the server's URL through OpenShell's proxy, with placeholders from its environment as credential headers, and turns OpenShell's refusals into the errors the proxy's client raises, so `Connectors` is unchanged. A refusal naming a request is trusted only once the worker confirms it over the middleware's records (below). In the confined runtime it runs in the agent runtime's sandbox (below); the agent's connector calls do not use it yet.
- **Responses.** A direct-path sandbox needs `mcp_listings = true` in the middleware's settings (refused with `mcp_listings_off` otherwise); the service declares `HTTP_RESPONSE` before return and reads each JSON `tools/list` answer whole, rewriting it by the proxy's rule (below). An event-stream listing OpenShell does not offer whole passes unread, recorded (`mcp-tools-listing-unread`); the runtime's client filters and reports it.

## How holds behave

The middleware cannot hold a request until a person answers: one evaluation has at most 30 seconds, and OpenShell's default is 500 ms. It refuses instead, as it does for HTTP, and the harness calls again, as it does with the proxy (every 3 s for a minute, then every 10). The same arguments make the same request, since the client sorts keys and the key holds the digest of the parameters as MCP defines them; `_meta`, which passes to the server on this path, is not part of it.

OpenShell returns to the sandbox only the middleware's reason code, never its other words, so a refusal that concerns a request names it in the code: `approval_required_r12`, `approval_denied_r12`, `escalation_timed_out_r12` (`reasons.with_request`). Approving with `sandbox-science-policy-middleware approve --request 12` works for these requests as for network ones, with the scopes `call`, `tool` and `server`. The session and run are attribution only: they are in no key, so an approval made for one session covers the same call from another, as through the proxy.

Holds therefore fit.

## What the proxy did that this path now does

- **Listings without denied tools** (lab 39, B5). The middleware reads each `tools/list` answer whole (`WHOLE_BODY_BYTES`), JSON or an event stream that ends with the response, since a stream's 64 KiB pieces cannot be rewritten one by one, and passes it on by the proxy's rule (`policy.mcp_answers.callable_tools`, which the proxy now calls too): each tool judged as a call by name alone, with the hint its page gives it; denied tools dropped; the rest marked with their class and, when they escalate, `sandbox-science/escalates`, over the server's own `_meta`. An event-stream listing OpenShell does not offer whole passes unread instead: the runtime's client drops the tools the compiled native rules deny before the model sees any, and reports the server's own listing for the drift check (below). Any other listing it cannot read, of another media, or JSON that OpenShell cannot offer whole is blocked (`tool_listing_unreadable`). Drift is still judged on the server's own listing.
- **Binary results.** The harness withholds images, audio and blobs by the proxy's rule (`policy.mcp_answers.withhold_binary`) and keeps each as an artifact through control: the decoded bytes are written to `mcp-results/` in the session's workspace through the worker and published with the run's publisher; the model sees a note naming the artifact. The middleware does not touch `tools/call` answers. The proxy still drops them, having no route to control's stores. In the confined runtime the client and the publisher are on two sides of the boundary, and the runtime hands each item to the host over `publish_mcp_binary` ([below](#where-the-client-runs-binaries-and-canaries)).
- **A server's 403.** A server can answer with a body that reads as OpenShell's denial and name any request number. `DirectClient` trusts a refusal that names a request only when its `RequestCheck` confirms it: the request exists, stands as the code says, and is this call's by project, server, method, tool and parameters' digest (`Approvals.confirms`). The production check reads the middleware's own records the way the workspace reaches them, through the worker, which holds the middleware's event store: `WorkerRequestCheck` asks `POST /v1/permission-requests/{seq}/confirm` with the client's own token, and the worker answers any client, for its own projects, yes or no about one MCP request, never its record, so the run service's token gains nothing broader (the run service still cannot list or answer requests). The confined runtime holds no worker token: its check is the attempt's `confirm_request` capability (`confinement.requests.ControlRequestCheck`), which carries no project; the host binds the attempt's and asks the worker. Anything unconfirmed is the server's error (`server_error`, the number kept as `unconfirmed_request`): no card, no wait. Through the proxy the same holds for `fence_denied`.
- **The tool index** is the harness's already (`Connectors`), as D98 has it.
- **Canaries** (D103). The proxy's canaries list through it from the trusted side; on this path the control service asks the runtime to list through its client over `list_mcp_tools` ([below](#where-the-client-runs-binaries-and-canaries)), so a deployment without the proxy keeps its canaries.

## What the proxy still does that this path does not

- **Only advertised tools.** The proxy refuses a tool missing from the server's latest listing (`tool_not_advertised`); here the native rules and the policy decide by name alone.
- **Its own bytes upstream.** The proxy re-serializes what it decided; here the server gets the client's bytes, which the middleware has read strictly.
- **Answers.** The proxy bounds answers (`max_response_bytes`), answers a server's `ping` and refuses its other requests in a stream, and records each call's outcome. Here the harness bounds answers at 8 MiB and declares no capabilities, which the middleware requires.
- **Callers.** The proxy tells callers apart by token and applies `worker_access` and `worker_tools` to worker code. This path covers the agent runtime only; research sandboxes still cannot reach MCP hosts.
- **Credentials.** The provider is attached to the agent runtime's sandbox, whose processes hold placeholders, never values; the compiled endpoint admits only the interpreter named as its binary.

## Recommendation

Holds fit, and each proof passes offline, so by D98's rule the proxy should retire, not stay slimmed. Of the three prerequisites set on 2026-10-23, the two that could be met offline are met (2026-10-24):

- **Met:** the workspace reads and answers the middleware's MCP requests through the worker, with the proxy's card fields and scopes, its grants answer the middleware's later calls through the relay, and the harness's `RequestCheck` reads the same records (`WorkerRequestCheck`, and `confirm_request` in the confined runtime).
- **Met:** listings lose denied tools in the middleware by the proxy's rule, and binary results become artifacts in the harness.

Retire it only after a babbage lab runs `DirectClient` in an agent runtime sandbox against the attack-catalog server through a real OpenShell 0.1.5 gateway, showing:

1. the native rules: an allowed and an escalated tool admitted by name, a denied one refused before the middleware;
2. the middleware on an mcp endpoint, and a reason code with its request number reaching the client, which the runtime's `confirm_request` confirms against the worker before the card appears, and a person's answer in the workspace letting the retried call through;
3. listings without denied tools, reframed after the 2026-10-26 lab (OpenShell 0.1.5 never offers an event stream whole): a JSON listing read and rewritten by the middleware; an event-stream listing passing unread with its `mcp-tools-listing-unread` record, the runtime's client showing none of the denied tools and its report recording a drift that holds the server's non-read calls; and an error answer passing;
4. placeholders substituted in the credential headers;
5. a binary result (an image from a server that returns one) kept as an artifact through `publish_mcp_binary` (below): only the live run is left.

Until then the proxy runs as built and the agent's connector calls do not take the direct path.

## Where the client runs, binaries and canaries

*As built 2026-10-26:* in the confined runtime the direct client runs in the agent runtime's sandbox, as this spec framed it: that is where OpenShell's proxy is, where the provider's placeholders are attached and where the compiled `protocol: mcp` endpoints admit the runtime's interpreter. The trusted host has none of these, and gets none: no MCP credential or placeholder reaches it, as none reached it through the proxy. Two capabilities of the confinement's catalog ([confinement](orchestrator-confinement.md#capability-operations)) carry what the host still needs:

- **`publish_mcp_binary`, runtime to host.** The runtime withholds each binary item of a `tools/call` answer by the proxy's rule and sends it with the model's call ID, its media type and the SHA-256 of its decoded bytes (`confinement.binaries.ControlBinaries`). The host (`CallBinaries`) keeps it exactly as the proxy path's items are kept (`mcp_binaries.ArtifactBinaries.keep_bytes`: written to `mcp-results/` through the worker, published with the run's publisher, one operation per run and content) and answers the artifact, revision, SHA-256 and the note that replaces the item. It takes the call's tool and server from its own records, never from the runtime: the call must be the attempt's logged, unexecuted tool intent and a connector tool's. It refuses a digest mismatch (`conflict`), an item over 8 MiB decoded or a call over 8 MiB or 100 items (`invalid_request`: the harness's answer bound and the recorder's per-call file bound), a media type other than `image/*`, `audio/*` or `application/*`, and any other call ID (`denied`). The same item of the same call again is answered as before, nothing kept twice. The items kept go into the call's tool record (`mcp_binaries`, `binary_results`).
- **`list_mcp_tools`, host to runtime.** The canaries need a trusted-side listing, and no trusted service can reach a server on this path. The confinement already has requests in this direction for what only the runtime can reach, its model gateway (`model`, `embedding`), so the control service asks the connected runtime for one server's listing the same way, rather than giving the runtime a way to pull work. The runtime lists through its own `DirectClient` with `mcp_canaries.list_tools`, `tools/list` only, at most 32 pages within 15 s, and answers the outcome (status, count, digest, error kind), never the tools; the policy middleware records the listing, and so its drift, as any other. The control service's runner (`[canaries]` without `[mcp_proxy]`, from the runtime's first handshake) stores each outcome in `mcp_canaries` as the proxy's canaries do; no runtime connected is `unavailable` (`runtime_unavailable`), no answer within 20 s `timeout`. The runtime's word on a canary is a monitor's: a lying runtime hides only an outage.

- **`report_mcp_listing`, runtime to host** (owner, 2026-10-26, after the lab). The runtime's `DirectClient` filters every listing page by its server's compiled native rules (`DirectServer.tools`, `policy.openshell.tool_admission` of the compiled endpoint: an allow pattern matches and no deny pattern does, as OpenShell matches them; a server whose rules are not given shows no tool), so no denied tool reaches the model. When a listing is complete it sends the server's own listing (each tool's name, `tool_digest` and hint, at most 2,048, and the listing's digest) over `report_mcp_listing`. The host binds the project, session and run, the attempt's (only one of the attempt's connector servers) or for the canaries' client the canaries' project (only their servers), and forwards it to the worker (`POST /v1/mcp-listings`, any client for its own projects, a server of the project's policy). The worker compares it with the pin of the project's classification in force with the library's `listing_drift` and appends the same `mcp-tools-drift` record with source `runtime`, once per listing digest; the middleware's `DriftLedger`, which rereads the store at most once a second when deciding a non-read call, then holds the server's non-read calls until re-accepted, as for a drift it read. A listing the host or worker refuses or cannot take is not shown (`unavailable`). The canaries list through the same client, so a canary listing reports drift too. The operator's `mcp_tool_pins` apply only to the listings the middleware reads.

Not built: the agent's connector calls through the runtime's client (the runtime's toolbox runs every tool on the host today), and the launcher's compile of the runtime sandbox's MCP egress (`compile_agent_mcp`, the policy middleware and the provider) for `[mcp_direct]`; the lab supplies both.
