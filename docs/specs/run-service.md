# Run service: GUI chat and live run events

Date: 2026-10-14. **Status: Approved and built** (`sandbox-science-harness serve`, the workspace's chat routes and the session page's chat panel; [workspace](../WORKSPACE.md#chat)). Waking a session when a detached job ends is not built, nor are the amendments of 2026-10-15 for the [context management](context-management.md) spec RS-9, RS-6c and RS-14; RS-7's, the message's archive header, is built, and so are RS-10's session view and RS-12's message named once, before folds ([as built](context-management.md#as-built)). The owner decided the outline (refactoring plan, decision 5): a small orchestrator run service, one active run per session, messages queued to the run's next safe point, a new run carries earlier tasks and final answers, and a message may start a run within the project's model budget. The questions below were decided on 2026-10-14 by the coordinator under the owner's autonomy mandate, each as recommended. Conventions in the [index](README.md).

## Scope

This spec covers:
- chatting with a session's main agent from the GUI;
- the process that runs the agent for the GUI;
- the run events the GUI shows while a run is in progress.

The browser's views are E-06 and E-07 in the refactoring plan. Waking a session when a detached job ends ([tools](tools.md#background-jobs), item 8) comes later, in the same process.

## Behavior

### The process

- RS-1. `sandbox-science-harness serve` is a long-lived orchestrator process for one state directory (new). It holds what `run` holds today: the worker's token, the gateway key and the model roles. It builds each run with the same `Harness` as `run`. The workspace server gets no worker or agent authority (CONVENTIONS, W4 exception).
- RS-2. The workspace and the service communicate through the control store (decided, question 1). This departs from the plan's wording, which has the workspace proxy the service: a message is durable before anything acts on it, and there is no listener and no second token. The workspace writes USER rows, as it already writes work requests and review requests. The service polls for them, at least once a second, and writes the results back. The service does not listen on any port.
- RS-3. The service renews a heartbeat row. The GUI shows whether chat is available from that row's age: more than 30 s old means no service is running.

### Messages and runs

- RS-4. A user message is a row of the session's message queue: its ID, the text (Markdown with LaTeX, at most 64 KiB), the USER author, the time and a state. The states are `queued`, `delivered` with the run ID, `refused` with a reason, and `held`: left by an interrupted run (RS-12).

  *Amended 2026-10-15 (coordinator decision, which the owner can reverse):* while the run that holds the session waits for the user's answer to a question it asked ([plans and delegation](plans-and-delegation.md), PD-23), a message is not queued: it answers the oldest such question in the user's own words, and the question keeps the message's ID ([questions to the user](../QUESTIONS.md)).
- RS-5. **One active run per session.** A run holds a per-session run lease in the control store, which it renews while it runs. `run` from the command line takes the same lease. A second run for a session that holds the lease is refused (`busy`). A lease whose renewal stops for 60 s has expired; its holder died.
- RS-6. **Starting a run.** When a session has queued messages and no active run, the service starts a run. The run's task is the queued messages, oldest first. The run is refused when the project has a daily cost limit and has reached it (RS-6a). The messages are then `refused` with the reason `budget`, and the GUI shows it.
- RS-6b. **Work requests** (added 2026-10-15, lab 38). A work request, a comment the user addresses to the session's main agent ([living documents](living-documents.md), LD-22), starts a run as a queued message does when the session has no active run, within the project's cost limit, if it has one. Queued messages go first: a run started for them is offered the requests too. A run started for requests alone has no task message: its conversation begins with the requests, as the run's hook offers them, and its record's task says that it answered work requests. A request also ends a job wait, as a message does (RS-7). A request has no `held` or `refused` state. Where a message would be held (RS-9, RS-11, RS-12), the service keeps the request from starting a run by itself until the session's next run, which is offered it, or until the service restarts. When the cost limit is reached, the service looks at the request again after 15 minutes. A request does not reopen a closed session: it waits for the session's next run.
- RS-6a. **The project's cost limit** (decided, question 3; amended 2026-10-15 by the owner: "I would expect budget to mostly be enforced upstream by LiteLLM", and "doing it as cost instead of tokens seems better, too"). Spending is enforced upstream, by the gateway's own budget for the key, its user or its team (RS-6d). A project has no limit of its own by default. It may have a daily cost limit, a project setting in the gateway's currency (normally US dollars): `project budget --daily-cost-limit AMOUNT`, or the launcher's `[model] daily_cost_limit`. Spending is what the gateway reported the project's calls cost, in the runs that started over the last 24 hours: from the saved records' `usage`, and for a run without a saved record (one in progress, or one that ended `interrupted`), from the `usage` of its `assistant` events, so neither a crash nor a long run hides what was spent. The reviewer's and the job watcher's calls made over the last 24 hours count too, each with the cost the gateway reported for it (amended 2026-10-15, lab 40, B5: they were about 30% of the lab's tokens, and the limit left them out). *Amended 2026-10-16 (lab 43, B2: LiteLLM 1.102.1 prices no call on `/v1/responses`, so GPT's runs counted for nothing and a limit could not stop them):* a call the gateway reports no cost for, or a cost of 0 for though it used tokens, is priced from the gateway's own price list, its model information (`GET /model/info`: the alias's per-token input, cached-input, cache-write and output costs, the dearest of its deployments'), at the tokens the call's usage reports. The record marks such a cost `cost_source: "model_info"`, one the gateway reported `"gateway"`; so do the reviewer's, the job watcher's and the import pass's calls, each in its table (control store version 53). It is the gateway's price, not an estimate. A call with neither stays without a cost, never 0. With a daily cost limit, such a call in the window, a run's or the reviewer's, the job watcher's or the import pass's, means the spending cannot be known, so the limit counts as reached until the call leaves the window: runs are refused with `budget`, and a run stops at its next safe point. Without a limit, nothing changes. The limit is checked when a run starts (RS-6) and at the run's safe points (RS-6c). The token budget it replaces, 2,000,000 MAIN tokens a day by default, is gone, with its table.
- RS-6c. **The limit during a run** (amended 2026-10-15, lab 39: a run that answered a finding while it ran went 370,000 tokens past its project's cap, which was checked only at the start; and by the owner the same day, as RS-6a says). Before each model call after the first, a run of a project with a daily cost limit checks it. It stops there, before the call and before that safe point's notices, when:
  - the project's calls over the last 24 hours, its own included, reached the limit: `stopped="budget"`;
  - or the run's own calls reached its part of the limit, when it has one: `stopped="run_budget"`. A run has none by default; `serve --run-share PERCENT` gives it one, and the launcher's `[run_service] run_share`.

  Without a limit, nothing stops a run for spending but the gateway.

  A delegated run is bounded by its own tokens, not by a share of its root's: nothing is reserved for it ([plans and delegation](plans-and-delegation.md), PD-38).

  The run ends as at its context limit. *Amended 2026-10-15 ([context management](context-management.md), CM-43 to CM-45; built 2026-10-16, `research_state` with step (f2b), for main runs with stores):* a run reaches its context limit only after a context error it could not fold its way past (`overflow`), a breaker that stopped folding (`breaker`), a view that cannot fit (`irreducible`), or current decisions that cannot fit (`research_state`), and the stop records which; until then, it is a conversation over `--max-input-chars`, or the gateway's context error. An answer that a closing round was taken for stands, and the run keeps its reason. The record, the `stopped` event and the GUI say why. A tool call already made finishes first, and its result is kept. Messages, work requests and notices that no model call saw wait for the next run, as at a run's start: with the limit reached, the messages are `refused` with `budget` and the requests wait (RS-6, RS-6b). `run` on the command line keeps no limit.
- RS-6d. **The gateway's budget** (the owner, 2026-10-15: spending is mostly enforced upstream, by LiteLLM's budget for the gateway key, its user or its team). When the gateway refuses a call because such a budget is spent, the call is not tried again, though LiteLLM may send the refusal as a 429. The model client knows it by the error object's `type`, `budget_exceeded`, or by its message, which names a spent budget as LiteLLM's do ("Budget has been exceeded", `ExceededBudget`, `ExceededTokenBudget`), never by the status alone. The run ends there, `stopped="gateway_budget"`, as at its context limit: an answer a closing round was taken for stands, and what no model call saw waits. The record, the `stopped` event and the GUI say why. The session's queued messages and work requests stay queued, and no run starts for them for 15 minutes, since every call would be refused until the budget is raised or resets.
- RS-7. **A message during a run.** A message queued while the run is active is delivered at the run's next safe point: before the next model call, or at once when the agent is waiting on jobs, which ends the wait with `user_message` ([tools](tools.md#background-jobs), item 6). It is not attached to a tool result. It goes in as a user message with the user's text as written. Unlike document text and notices, it is the user's instruction. *Amended 2026-10-15 by the owner, with the [context management](context-management.md) spec (CM-4a); built 2026-10-16:* a one-line header naming the message's archive ID comes before the user's text, which follows as written, a line of it that begins like a header escaped.
- RS-8. A message queued when the run is about to end is not lost. If the message is there at the run's closing, the run continues and answers it. If it arrives after the closing, it starts the next run (RS-6).
- RS-9. **Delivery follows the record.** A message counts as delivered once a successful model call has seen it. It is marked `delivered` only after the run's record is saved, the rule every notice source follows (A-02). A message that a failed or interrupted run saw stays `queued` and goes to the next run. A session whose runs keep failing waits longer before each next one, doubling from 30 s up to 15 minutes; after five failures in a row, its queued messages are `held` with the reason that the runs failed, until the user resumes or writes again (amended 2026-10-14, review of the run service). *Amended 2026-10-15 ([context management](context-management.md), CM-45; built 2026-10-16):* after a run stops with `context_limit` for the reason `research_state`, the session's queued messages, and those written later, are `held` with that reason until the ledger changes or the user resumes, since the next run would stop the same way.
- RS-10. **Earlier conversation.** *Amended 2026-10-15 by the owner, with the [context management](context-management.md) spec (CM-25 to CM-30); built 2026-10-16 before folds, which leave out the oldest messages instead of folding them until step (f1) ([as built](context-management.md#as-built)).* A new run starts from the session's view: the system message; the state block, holding the user's words from the folded part of the session and the research-state digest; fold records of older work; the raw tail, which holds the end of earlier runs with their tool calls and results; and the new task. The user's messages stay word for word, in the raw tail where they were written and in the state block once folded, within CM-30's limits: past their share, the oldest become pointers that `history_read` returns whole, so they are no longer never cut. The comments addressed to the session count as the user's messages, each after a line naming its document. Before it was built, a new run's messages were:
  1. the system message;
  2. the session's earlier runs, oldest first: each run's task and user messages and its answer, within a character budget, with tool calls and their results left out (decided, question 4). The user's messages are what the agent most needs to keep, so they give way last (amended 2026-10-15 by the coordinator, from lane K's triage of the prompt research, D3):
     - every run's task and user messages are kept as written, never cut;
     - the user's messages are the chat messages and the comments addressed to the session (work requests, RS-6b) that the run delivered, in the order they were written, each comment after a line naming its document: a comment addressed to the agent is the user's instruction, as a chat message is. A run started for comments alone shows them in place of its stand-in task (amended 2026-10-15 by the coordinator);
     - the agent's answers give way first: the newest that fit are kept whole, and each of the others is replaced by a line saying that it was left out and how long it was;
     - when even the user's messages do not fit, the oldest runs are left out whole, and a line says how many, with the user's messages in them;
  3. the new task.

  *Amended 2026-10-16 by the coordinator (lab 42, B4):* a run's answer is its answer to the user, the text of the turn that answered, which a closing let stand: not a text the plan's veto held back, and not the texts of the closing rounds after it, such as its responses to review findings or a turn for new input. The run's record keeps it as `answer`, beside `final_text`, its last text; a record from before has its `final_text` in its place. The chat and the record keep every text. Under CM-29 the raw tail holds every text of the earlier runs in its place, so the session view needs no choice among them; the record's `answer` still says which one answered the user.
- RS-11. **Cancel.** The user can cancel the active run. The cancel is a USER row the service reads. The run stops at once: a model call or tool call in progress is abandoned, as the CLI's interrupt does. Its background jobs keep running, since jobs outlive their run (D83). The record is saved with `stopped="cancelled"` (decided, question 5).
- RS-12. **Restart.** When the service starts, and at every look after, it finds every lease whose holder died, other than its own runs' (a lease can look expired while its holder lives, as after a suspend), and removes it only if it is still expired. It ends each run by writing a `stopped` event with `interrupted`; a run whose record was saved before its process died is acknowledged from the record instead. No record is written for that run (decided, question 6). The messages it was offered, which each run marks as it offers them, and that no saved record delivered become `held`, so no run starts for them by itself. They are queued again when the user resumes or sends another message, and then go to that run. *Amended 2026-10-15 ([context management](context-management.md), CM-29a; built 2026-10-16):* a held message the next run's view already holds, where the interrupted run received it, is not repeated: the new run's task is a line that names it. The run's delegations still running end `interrupted`, and its children's runs get their `stopped` events ([plans and delegation](plans-and-delegation.md), PD-40).

### Run events

- RS-13. **Events as they happen.** While a run runs, the harness appends events to the control store, numbered from 1 within the run. Each event is committed before the run goes on to the next model or tool call. The final `RunRecord` is written once at the end, as now. Events are observations for display. Acknowledgements still follow the saved record (RS-9).
- RS-14. **The event format.** Each event is a row `(run_id, seq, at, kind, data)`, with `data` a JSON object of at most 64 KiB. Longer text keeps its head and tail with a marker; the record keeps the whole text. The kinds are:

  | Kind | `data` |
  | --- | --- |
  | `started` | `project`, `session`, `run_id`, `message_ids` (the messages it answers), `prompt_provenance` (the pins), and the run tree's `role`, `parent` and `delegation` (PD-32) |
  | `user` | `message_id` (null for a CLI task), `text` |
  | `model` | `turn`: a model call started (the GUI shows that the agent is thinking) |
  | `assistant` | `turn`, `text`, `tool_calls`: `[{id, name, arguments}]`, `usage`: `{model, input_tokens, output_tokens, characters, cost, cost_source}` as the record keeps it (RS-6a); `cost` is what the gateway reported the call cost (LiteLLM's `x-litellm-response-cost`, or the answer's `usage.cost`), null when it reported none |
  | `tool` | `turn`, `call_id`, `name`, `result` (the text the model read, bounded), `outcome` (state, error kind and exit code when there is one) |
  | `notice` | `source`, `ids`: notices added to the conversation, such as jobs or reviews |
  | `waiting` | `job_ids`, `mode` while the agent waits on jobs; `null` when the wait ends |
  | `fold` | *Amended 2026-10-15 ([context management](context-management.md), CM-46); not built:* a fold or another change of the view: its ID, level and span, its state (`started`, `applied`, `skeleton_only`, `code_merge`, `failed` or `rejected`), the tokens it freed, its stubs and spills, a wall wait and how long it took, and why it failed |
  | `stopped` | `stopped` (`answered`, `turn_limit`, `context_limit`, `user_message`, `plan_unread`, `cancelled`, `budget`, `run_budget`, `gateway_budget`, `interrupted` or `error`), with `context_limit`'s `reason` and `detail` for a run that folds (CM-43 to CM-45: `overflow`, `breaker`, `irreducible`, or `start` for a run whose geometry refused it), `failure`, `final_text`, `record` (the saved record's name, or null) |

- RS-15. **Reading events.** The workspace reads a run's events by cursor, `after=seq` and a `limit`, from the control store, as it reads run records now. Its route returns them with the run's state: active, or ended with the `stopped` event; a delegated run, which holds no lease, is active while its root holds the session (PD-42). The browser polls with the generic `Poller`. SSE can come later without changing the format.
- RS-16. **Retention.** A run's events stay after its record is saved. The GUI shows the record for ended runs and the events for the active one and for interrupted ones. Interrupted runs have no record.

## Contracts used

- `RunRecord` gains `cancelled` as a `stopped` value. Its other fields are unchanged.
- The control store keeps each project's optional daily cost limit (RS-6a).
- The control store gains tables for messages, run leases, cancel requests, the service heartbeat and run events, each in one migration step (B-02).

## Acceptance fixtures

All are `scripted`, through the workspace's routes and the service, with the scripted gateway.

1. **A first message.** A message to an idle session starts a run. Its events arrive in order (`started`, `user`, `model`, `assistant`, `stopped`). The record names the message as delivered.
2. **A message during a tool call.** The second model call sees the message as a user message, after the tool result, and its answer covers it. Both messages end `delivered` to the one run.
3. **A message during a job wait** ends the wait with `user_message`. The agent answers it and waits again. The job is not disturbed.
4. **A message after the last answer** starts a second run. That run's conversation holds the first run's task and answer, and none of its tool calls. *Amended 2026-10-15 ([context management](context-management.md), CM-F17); not built:* it holds the first run's tool calls and results too.
5. **Busy.** `run` on the command line for a session whose run is active is refused, and the active run is unaffected.
6. **Cancel** during a tool call stops the run. A `cancelled` record is saved with the partial conversation, and a job it started keeps running.
7. **Restart.** The service is killed during a model call. On restart, the run ends `interrupted`. Its message is `held`, and nothing it saw is acknowledged. Resuming queues it, and a new run answers it.
8. **Budget.** With the project's cost limit reached, a message is `refused` with `budget`, and no model call is made. Without a limit, nothing is refused for spending.
9. **A comment** (RS-6b). A work request to an idle session starts a run that begins with it and delivers it. A work request ends a job wait. After a cancel, an interruption or five failed runs, the request starts no run until a message does, and that run delivers it. With the cost limit reached, it waits, and no model call is made.
10. **The limit during a run** (RS-6c). A run whose first call reaches the project's cost limit stops before its second, `budget`, with its tool call's result kept. A message that arrived while it ran waits, and is then `refused` with `budget`. A run whose calls reach its part stops, `run_budget`, while the project's limit is not reached. A limit the gateway reports no cost against stops nothing.
11. **The gateway's budget** (RS-6d). A gateway that refuses a call for its budget, whether as a 400 or a 429, is asked once: the run stops, `gateway_budget`, with its earlier tool results kept, and its message stays queued with no other run for it. A rate limit is still tried again.
12. **The user's messages give way last** (RS-10). *Replaced, once the session view is built, by the context-management spec's CM-F2 and CM-F17 (amended 2026-10-15).* Three earlier runs whose answers do not all fit keep every task as written: the newest answer whole, and a line for each other. When the tasks alone do not fit, the oldest run is left out whole, and a line says so. A comment a run delivered with a message is in the next run's earlier conversation, before the message it was written before, and is kept as the message is while the answer gives way.

## Decided questions

Each was decided on 2026-10-14 by the coordinator, under the owner's autonomy mandate, as recommended in the draft.

1. **How the workspace reaches the service.** The plan says the workspace proxies the service. *Decided 2026-10-14:* they share the control store instead (RS-2). The workspace writes messages and cancels as USER rows, as it already queues review requests, and reads events as it reads records; the service polls. This departs from the plan's wording on purpose: a message is durable before anything acts on it, so it survives a crash of either process, and there is no listener, no second token and no proxy route. The cost is up to a second of latency, and a refusal arrives on the message row instead of as the reply to the POST. A proxied HTTP API (loopback, a token file only the workspace reads) can come with W5's control API.
2. **Messages and document work requests.** E-06 suggests one table for both. *Decided 2026-10-14:* separate tables. Work requests carry anchors and are answered with `document_reply`; chat messages are plain. Both are turn hooks with the same delivery rule (RS-9).
3. **The project's model budget.** MAIN had none; the gateway key's spending limit was the only monetary cap. *Decided 2026-10-14:* tokens per project over a rolling 24 hours, 2,000,000 by default, a project setting, checked when a run starts (RS-6a). *Amended 2026-10-15 by the owner:* the gateway's own budget is the default cap, and a project's optional limit is a daily cost, as the gateway reports it. Runs that end `interrupted` count too, from the per-call usage their `assistant` events keep.
4. **The earlier conversation's size.** *Decided 2026-10-14:* 100,000 characters, a quarter of the run's input budget, without tool calls (RS-10). Runs that do not fit are left out, newest kept, and a line says how many were left out. Compaction comes later. *Superseded 2026-10-15 by the owner, with the [context management](context-management.md) spec: the session view replaces the character budget (CM-29); not built.* *Amended 2026-10-15 by the coordinator:* the agent's answers give way before the user's messages, which are kept as written; whole runs are left out, oldest first, only when the user's messages alone do not fit.
5. **Is a record saved on cancel?** Today an interrupted CLI run saves nothing. *Decided 2026-10-14:* yes, with `stopped="cancelled"` and no failure, so the GUI shows what happened (RS-11). Notices a successful model call saw are acknowledged, as for any saved record.
6. **Recovering an interrupted run.** *Decided 2026-10-14:* it ends as RS-12 says, without a record, and its messages become `held`. They are not run again automatically: a run that died once may die again, and each try spends budget. The GUI offers "resume", which queues the held messages again.
7. **Who may start runs.** *Decided 2026-10-14:* the workspace's one USER (E-17), any logged-in user of it. Spending is bounded by the gateway's budget, the project's cost limit if it has one, and the turn limit.
