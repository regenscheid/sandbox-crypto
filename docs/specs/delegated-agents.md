# Delegated agents

Date: 2026-10-21. **Status: Draft, owner direction (2026-10-21).** Delegated agents should do nearly everything the main agent does: call connectors, read and write files, and use skills. Only the user's conversation and the main run's duties stay with the main agent. To be built after `agent-context-refactor` is merged into `dev`: tool selection by role now lives in that branch's `capabilities.py` role factories (its `docs/specs/capability-assembly.md`, which this page links once merged), and the references below are to that branch unless marked `dev`. This draft proposes amendments to [plans and delegation](plans-and-delegation.md) (PD-11, PD-16, PD-33, PD-34, the check paragraph and PD-F8) and to [skills](skills.md) (SK-8, SK-9), listed in [Amendments](#amendments). Until they are built, that spec describes the behavior. Conventions in the [index](README.md).

## Scope

What a delegated run (role `delegated`, kind `task` or `check`) may use: connector tools and their approvals, files in the session and the project's shared area, skills, and the PDF sources it reads as citation evidence. It also covers what the run is told about itself. Out of scope: the delegate tools' limits, outcomes and lifetimes (PD-15, PD-17 to PD-19, PD-38 to PD-40, D87), which do not change, and questions to the user, which stay with the main run (DA-15).

Terms:

- **Child**: a delegated run; **parent**: the run that delegated it; **root**: the main run at the top of its tree.
- **File grant**: a file the parent names in a brief, pinned by the platform at the version it had when the delegation started.
- **Write area**: the directory of the session a child's file tools may write in, `work/<delegation_id>/`.

## As built (2026-10-21)

What a child cannot do today, and where:

- **Connectors.** The harness builds connectors only for a run that is not delegated (`harness.py`, `connectors=… and not delegated`). `Toolbox` refuses them as well ("a delegated run gets no connector tools", `tools.py`). PD-33's check paragraph lists connectors among the tools a check does not get. No spec gives a reason beyond PD-16's rule on permission requests. *Superseded 2026-10-24: children get connectors (DA-3, DA-7 as built).*
- **Approvals.** A held connector call is keyed by project, caller, policy, server, method, tool and parameters (then `mcp_proxy/proxy.py`, `_escalation`; since the proxy retired, the policy middleware's request key). It is attributed to a session only, by the `Sandbox-Science-Session` header. `PendingApproval` (`workspace/approvals.py`) names the session, not the run, and the workspace lists requests by session. *Superseded: requests name the run (DA-4), and a child's are its own (DA-9, DA-10).*
- **Skills.** A skill is main-only unless listed otherwise (`skills/builtin.py`). Computation, environment setup, figures, literature search, PDF reading and recording results are main-only. Children get delegating-work, writing-documents and scientific-writing. *Since 2026-10-24 children also get computation, literature search and PDF reading.*
- **Files.** A child shares its parent's session directory (`_child_admitted` copies the session). The worker resolves `shared/…` to the project's shared area and any other path to `sessions/<session>/…` (worker `executor.py`). A child that writes `sessions/main/sources/a.pdf` therefore reaches `sessions/main/sessions/main/sources/a.pdf` and gets `not_found`, as observed on 2026-10-21. A brief's `inputs` are up to 20 free-text strings (`delegation/specs.py`, `MAX_INPUTS`), not pinned files. No path is read-only to a child, and a child may write anywhere its parent may. *Superseded 2026-10-31: a child's file tools write in its write area and `shared/` only (DA-19 as built); and 2026-11-01: its processes write only in its write area and its scratch directory (DA-20 as built).*
- **Citations.** Only a main run has a review controller. A child's `pdf_pages` and ePrint reads are therefore never recorded as `source` observations (`consistency/controller.py`, `_source`). A quote the child found then fails the citation check, which looks sources up by project and session (`consistency/quotes.py`).
- **Prompts.** The delegated prompts say "You are a delegated research agent" and "You cannot talk to the user" (`delegation/prompt.py`). They mention neither connectors nor skills. *Since `sandbox-delegated-task-13` and `sandbox-delegated-check-13` they mention both (DA-26).*

## Behavior

### What stays with the main run

- DA-1. A task child is offered every capability its parent has, except those that act for the user or own the session's work: questions to the user (`ask_user`), the plan's authoring and status tools, the review tools (responding to findings, claiming fixes), and deciding permission requests. PD-16's prohibitions are unchanged. A check child keeps PD-33's read-only rule for the ledger, documents and memory. It also gets connector tools classed `read` (DA-7) and the reading skills (DA-21).
- DA-2. The selection is made by the trusted role factories (`main`, `task`, `check`). No agent text selects a factory or widens a scope. A parent may narrow what a child gets (DA-6, DA-23), never widen it beyond its own.

### Connectors

- DA-3. Task and check children are offered `mcp_tools` and the connector tools it loads, under the same project policy as the main run. The harness builds the run's connectors for every role whose factory offers them. `Toolbox`'s refusal for delegated runs is removed. *Built 2026-10-24 ([D99](../DECISIONS.md)):* a child's connectors are built as its root's, through the same client (the proxy's or the direct one) and the same index, `mcp_tools` and on-demand schema loading; a tool called before it was loaded is loaded and called, not refused for the role. The policy decides each call by class exactly as for the main run; a task's tools are not narrowed by class. A check is offered only the tools classed `read` (DA-1, question 3), by the classes the host gives a direct listing's tools (DA-7, built 2026-10-31). A task's brief may narrow them (DA-6, built 2026-10-27).
- DA-4. Every connector call names the run that made it. The run service sends a `Sandbox-Science-Run` header with the run's name next to `Sandbox-Science-Session`. The proxy accepts the header only from the run service's caller, never from a worker or sandbox caller, and records it in the escalation event and the pending request. The run is attribution only: it is not part of an approval's key or scope. Approvals stay once or for the whole project (the existing `once`, `project` and `server` decisions), never for one run (owner, 2026-10-21). *Built 2026-10-24:* every request of a run's connectors, the listings included, names its run (`connectors.RUN_HEADER`), a main run's as a child's; the MCP session with each server is shared by the runs of one client. The proxy believes the header from the run service's caller only: a worker caller's run is kept as `run_claim`. The attribution in every `mcp-call` and escalation record carries `run`, and the operator listing of waiting requests gives it (`PendingApproval.run` in the workspace). A request's key does not hold it: the same call from another run is the same request.
- DA-5. A child's MCP sessions are its own, or shared with its tree with the run named on each call; which is an implementation choice. A child's connector calls count toward the project's daily cost limit and the proxy's rate limits, together with every other run of the project.
- DA-6. A task brief may name the connector servers, or `server/tool` names, the child may use (`connectors`; default: all its parent may use). The child's `mcp_tools` index lists only those, and loading any other is refused with `not_permitted_for_role`. *Built 2026-10-27 (`delegation/narrowing.py`):*
  - **Entries.** At most 32, each a configured server (`crypto-research-mcp`), a server behind it as the index names it (`crypto-research-mcp/e-print-mcp`, or `e-print-mcp` alone when the parent's index has it under one configured server, recorded with the server), a tool by its full name (`SERVER/TOOL`), or a shell-style pattern of tool names (`SERVER/e-print-mcp_search_*`). A check takes none: its connectors are the platform's (DA-1), and a check brief that names some is refused with `not_permitted_for_role`.
  - **Only narrowing.** At delegation, an entry whose server no configured connector is, or that is malformed, refuses the brief with `invalid_request` (`unknown_connector`). An entry that admits nothing the parent is offered refuses it with `not_permitted_for_role`: a server the parent lacks (the user turned it off, or the parent's own brief left it out), or, where the parent's listing of the server came, a tool, a server behind it or a pattern none of the parent's tools matches. Where the parent's listing failed, an entry of that server is taken and the child's own listing decides.
  - **Recorded.** The delegation's brief keeps the entries as normalized (`connectors`) and every narrowing above them (`inherited_connectors`, a narrowed task's children's), and the child's connectors are built from that record, so a resumed or reopened run gets the same tools. A record the platform cannot read narrows to nothing.
  - **Enforced where the child's connectors are built** (`Connectors`, with the root's client and index settings): a tool is offered only when every level admits it, the brief's own and each inherited one, on top of the child's default (the servers the user did not turn off; for a check, the tools classed `read`); a server no level names is not listed. The index opens with the narrowing, `mcp_tools` answers a load of a listed tool it leaves out under `not_permitted`, a call of one is refused with `not_permitted_for_role`, and the run's record keeps the narrowing (`summaries.connectors.narrowing`). Tests: `test_connector_narrowing.py`.
  - The delegated task prompt (`sandbox-delegated-task-17`) says a brief may narrow its connectors: `mcp_tools` then lists only those it names, any other is not permitted, and a task that needs one tells its parent with `message_parent`.
- DA-7. A connector tool is an effect, as today, unless the project policy classes it `read`. The policy can class a whole server `read` and name the tools that are effects. Most research servers' methods only read (search, fetch, records, full text), so a server is usually classed `read` with a few exceptions. A server's own `readOnlyHint` is not trusted. The plan fence (`ChildFence`) lets read-classed connector calls through while the plan is a draft or after the user changed it, as it does other reads. *Amended 2026-10-23 ([D96, D99](../DECISIONS.md)):* a tool the classification does not mention takes its `readOnlyHint`; the fence gates outward effects only, and a plan in draft is a UI signal, not a block. *Built 2026-10-23 (D99, interim until D96's classes):* under a draft or user-edited plan `ChildFence` refuses only outward calls. The built-in tools whose effects stay in the session pass (`delegation/effects.py`: `shell`, `python`, `sage`, `restart_kernel`, `write_file`, `edit_file` (added 2026-10-24), `pdf_render`, `start_job`, `provision`), `pdf_info`, `pdf_pages` and `pdf_search` are `read`, as `read_file`, `list_files`, `glob` and `grep` are, and every other `effect` tool is outward: connector tools, `publish`, `admit_hosts`, `delegate`, ledger and document writes. A session closed or opened again still refuses both. HTTP from a child's code is gated where it leaves the sandbox (the middleware's escalations), not by the fence. The main run's plan gate is unchanged. *Built 2026-10-24 (D96's classes):* the fence reads each connector tool's class and escalation mark as the MCP proxy listed them (`sandbox-science/effect`, `sandbox-science/escalates`; a client that does not classify gives neither). A tool the proxy classes `read`, which no argument can make more, passes as computation does. A tool the proxy says asks a person first also passes under a draft or user-edited plan: the proxy holds the call, and the user decides it from the child's card (DA-9), so the plan is a signal there, not a block. Any other connector call, one the policy would let through unasked, is refused under a draft or user-edited plan. A session closed or opened again refuses all of them.
  *Built 2026-10-31 (classes on direct listings, A6):* the agent runtime's client passes the server's own listing, whose word on a class is not taken, so the host gives each listed tool its class itself, on the trusted side:
  - **The join.** The run service digests each listed tool as the pins do (`mcp_wire.tool_digest`: name, description and input schema; a tool whose text cannot be digested, such as one with a lone surrogate, gets no class) and asks the worker (`POST /v1/mcp-tool-classes`), for every server at once within one 10 s deadline, for the class the project's classification in force (its accepted revision, else the checked-in file) gives each name with that digest. Nothing else of the listing is taken: no `_meta`, hint or class the runtime or the server wrote.
  - **Under the middleware's policy.** The worker answers under the policy revision the project's agent runtime sandboxes are bound to, which the policy middleware decides their calls under, not the project's own binding, which may have moved since the sandbox was bound. While no runtime sandbox is bound, or two are bound to different revisions (a replacement beside the runtime it replaces), no tool has a class (`unbound`).
  - **Only a pinned match has a class.** A tool gets a class only when the classification in force names it with a pin equal to its digest. A tool it does not name (one the policy's `classify` alone names included), one it names without a pin, one whose digest differs from its pin (drift), and one the policy denies by name get none, which the fence treats as outward, as before.
  - **Which class.** The class a call by name without arguments resolves to under that policy, `read` only when no argument rule can make a call of it more (`listed_effect`, as the proxy marked its listings). The tool asks first (`escalates`) only when every call of it asks the user: the policy escalates a call by name, and every class an argument rule can resolve a call to is escalated or denied, none allowed. A user's grant in force (D97) that would answer such a call, for the project or the run's session, also clears the mark: a granted call goes out without a card, so for the fence it is a call the policy lets through unasked, refused under a draft or user-edited plan. The grants are the control store's, which the host reads (the worker cannot), so the worker names each escalated class a call can resolve to with its grant ceiling (`asks`) and the host checks the grants against them.
  - **At every fenced call.** The classes are taken at the listing and again before each call the fence decides, so a classification or policy revision, or a grant given or revoked, during a run applies from the run's next call. A worker that does not answer gives no class (outward), and the tools it did not answer for at the listing are asked again at their calls rather than left without a class for the run. A check's own call asks again too, whether or not the fence did: a tool that is no longer `read` is refused with `not_permitted_for_role`, though the check was offered it, and one whose class could not be confirmed (the worker did not answer) is refused saying so. A check is offered only `read` tools, and, while the worker does not answer at the listing, the tools it could not ask about, which it calls only once they are confirmed as reads.
  - **Main runs** get the same classes, which their call records keep (`effect_class`, `reach`); their plan gate is unchanged.
  Tests: `test_connector_classes.py` (the orchestrator's: a drifted digest, an unclassified tool, a revision changed during a run, a child and a check seeing only reads, the narrowing) and `test_classification_routes.py` (the worker's route).

### Approvals

- DA-8. A child's call that needs approval takes the main run's path. The proxy refuses it with `approval_required`, the run service retries it while the request is pending (`Connectors.call`), and the workspace shows the card. Only the user decides (PD-16, D76). No agent, child or parent, can answer, relay or restate the request: an attempt to answer one is refused with `not_permitted_for_role`.
- DA-9. The card says who asked. `PendingApproval` gains `run` and `delegation` (null for a main run). The card names the agent (its brief's title, kind and depth), links to its activity, and takes the call's arguments from that run's transcript. Cards stay in the session's chat with the main run's, oldest first. *Built 2026-10-23 ([D99](../DECISIONS.md)), backend first:* a child's wait (`Connectors`' `on_approval`, `delegation/requests.py`) records the request in `child_requests`: the proxy's request number, delegation, run, server, tool and the child's own words (2,000 characters). The parent's brief, its task or its check and note (2,000 characters), is read from the delegation. The workspace's listing adds `child` (delegation, run, kind, brief, words), and the card says a delegated agent asked and shows its brief and words as agent text. Attribution comes from that record; the proxy's record also names the run (DA-4). *Since 2026-10-24* children have connectors, and a child's held call takes this path end to end: the card, the parent's notice, its withdrawal and the proxy's denial.
- DA-10. The parent is told, not asked. While a child's call waits, the parent's context gets a notice like a job notice: the delegation, the server and tool, and since when. A second notice says when the request was answered, denied or timed out. The parent may go on, cancel the child, or send it a message (`message_child`, PD-44). The delegation's status reads `waiting_for_user` in its record and in the Agents pane. *Built 2026-10-23 (D99):* the parent is told through the agent mailbox, one platform notice per request, sent as the child's. A run that may message its children is offered `withdraw_child_request` (class `cancel`), for its direct children's requests only. A withdrawal only refuses: the workspace stops showing the card, refuses to approve it, and denies that one call at the proxy, so the child's call ends as a denied one. No agent tool approves (DA-8). Not built: the settled notice, `waiting_for_user`, and a withdrawal-specific message to the child (the middleware reports a denial). *On the direct path (2026-10-27):* the same record, notice and withdrawal, since the wait is the host's (`Connectors.call` with the run's `ChildApproval`, whatever its client): a child's call the policy middleware holds is recorded under the middleware's request number, once the host confirmed the request for that very call; the parent is told; a withdrawal hides the card, the workspace refuses to approve it, and its relay denies the request at the middleware, so the child's retry ends `approval_denied`. A session that spans the proxy's retirement can hold an older record of the same number for another call: that wait tells no parent and cannot be withdrawn, and its card names the child from the delegation alone. A detection hold of the session (D103) is not a child's request: it refuses the call (`session_held`), and only the user clears it. Tests: `test_mcp_direct.py` and the workspace's `test_routes_direct_approvals.py`, with the real middleware and worker.
- DA-11. Time spent waiting for the user does not count toward the child's turn, token or wall-time limits. A parent's `wait_delegations` is unaffected.
- DA-12. A denial or timeout returns the proxy's refusal to the child's call, as for a main run. The child goes on without it, and its outcome lists the refused calls.
- DA-13. Approvals the user remembered for the project or a server cover every run of the project, children included, so a child is not asked again for what the user already allowed. *Built (D97 grants):* a child's call is the agent's (caller kind `agent`) in its root's session, so a class grant for the project covers it as it covers the main run's, and a session grant covers the session's children.
- DA-14. *Alternative considered:* routing a child's request through its parent agent, which would decide or ask the user itself. Rejected:
  - A parent deciding is forbidden by PD-16.
  - A parent asking would put an agent's restatement in front of the user, the self-escalation the threat model names (A3: "Agent text never authorizes anything").
  - The parent is often waiting or working, and relaying costs model calls.

  DA-10 gives the parent what it needs to plan, without the authority.

### Questions to the user

- DA-15. Unchanged. `ask_user` is main-only (PD-41). A child that needs the user's input tells its parent, either with `message_parent` while it goes on (PD-44) or by ending with result status `blocked` and its `open_questions` (PD-17). The parent decides whether to ask the user, in its own question, which the user reads as the parent's. *Amended 2026-10-24 by the owner:* a child that lacks context asks its parent the same way, and the parent's answer may carry `references` to its own records (PD-44, CM-37b), which widen what the child's state block holds and its `history_read` may read; the parent need not retell them. *Built 2026-10-24 (`sandbox-delegated-task-14`):* the task prompt says so; a check takes no references.

### Files

- DA-16. A path a child passes to a file, PDF or artifact tool that starts with `sessions/<its own session>/` is refused with `path_outside_session`. The message names the path relative to the session. The worker does not guess, since `sessions/` may be a real subdirectory.
- DA-17. **File grants.** A brief's `inputs` may name files, by path in the session or `shared/…`, as well as free text. At delegation the platform resolves each named file to its path, sha256 and size, and records it as a recorded file's revision (RA-27) if it is not one already. The child reads a granted file at that revision, even after the parent changes it. A grant is not a copy: an unchanged file is the same content-addressed revision. A directory grants the files in it, up to the brief's 20 inputs counted per file. A path that does not exist refuses the brief with `invalid_input`.
- DA-18. A child may still read any file in the session and in `shared/`, as today. A grant pins a version and tells the child what to read first. It is not the only file the child can see.
- DA-19. **Write area.** A child's file tools (`write_file` and `edit_file`) write only in its write area, `work/<delegation_id>/`, and in `shared/` with the existing `expected_sha256` or `create_only` guard. A write elsewhere in the session is refused with `outside_write_area`. Its parent and the rest of the session can read the write area. The results a child declares in its outcome (RA-36, RA-38) are paths there or in `shared/`. A check gets a write area for scratch work, and its read-only rule for ledger, documents and memory is unchanged.

  *Built 2026-10-31:*
  - **Where it is enforced.** The worker, which holds every route to a sandbox's files. The harness gives a delegated run's `Toolbox` its write area, its research work's (below), and the run's `write_file` and `edit_file` requests carry it in their `ExecutionContext` (`write_area`; the contract takes only the shape `work/<identifier>`). The field is the platform's, like `authority`: no tool argument reaches it. The worker's file requests (`Files.write`, `Files.edit`) refuse any other path than one below the area or in `shared/`, before the environment is reached, with `policy_denied` and the message `outside_write_area: '<path>' is outside your write area…`, which names the area and `shared/` with its guard and suggests the same path in the area. A worker that predates the field refuses the request whole, so an older worker fails closed. The main run's requests carry none, nor do the platform's own writes for a child (saved output, kept MCP binaries, hand-backs, staged inputs, job deliveries).
  - **Paths.** The check is exact on the path as given, after the contract has refused absolute paths and empty, `.` and `..` segments, so `..`, a leading `/` or `./`, and a trailing slash are `invalid_request`. Case counts (`Work/…`, `work/DLG-…` are outside), as do longer or other delegations' names; the area itself is not a file in it. A symlink the child's shell put in or in place of its write area is refused by the executor, which follows none; an edit replaces the file atomically, so a hard link leads nowhere either. In `shared/` the executor's guard is unchanged.
  - **Reads.** Unchanged (DA-18): the parent, siblings and later runs read, list and search the write area; a sibling cannot write it, and the parent, whose requests carry no write area, can.
  - **What the agent is told.** The brief's last paragraph is the platform's line naming the area ("Your write area: work/<id>/. write_file and edit_file write only there and in shared/ …"), for a check's brief and a task's, and `delegate`'s answer gives the parent `write_area`. The line is true of the child's placement: a child in the session's environment is told it reads every file of the session and its parent reads the area; a child in an environment of its own ([child environments](child-environments.md)), which has only its copied inputs and `shared/`, is told it reads its own environment's files, not the session's other files, and that the files of its area are copied to the same paths in the session when its task ends (`write_area_text`). The pinned prompts are unchanged: the line is part of the brief, not of a pinned section.
  - **A child in its own environment** ([child environments](child-environments.md)) has the same write area, in its own environment: the same field and check, so the path rule does not depend on placement, and its `inputs/` (CE-7) is not writable by its file tools. Its brief's last paragraph, after the write area's line, is the platform's line mapping each input's session path to its copy under `inputs/`. Its hand-back (CE-6) copies a file of the write area to the same path in the session's environment, and any other file below the write area (`out/x` to `work/<id>/out/x`), so a path the child names in `result_files` is the path its parent reads; of two files that would land on one path, the first listed is copied and the other left out with that reason.
  - **One area a research work** (amended 2026-10-31 by the coordinator). A write area is its research work's (D100): `work/<first>/`, where `first` is the delegation the work was first admitted for, as its blueprint names it (`DelegationRecords.write_area`). A reopened task is the same delegation (PD-46) and keeps it. A Resume's continuation is a delegation of its own for the same work (CE-12), and so writes where the work's earlier attempts wrote: a resumed child edits the files it was working on. Its brief, which a continuation takes from the work's blueprint, already names that area. Another work's area, a sibling's included, is still refused. Only one attempt of a work runs at a time: `WorkRecords.admit` makes one attempt current and running, from `waiting`, in one write transaction of the control store, and a stale attempt's calls are refused by the worker's recovery fence (its epoch). As the run's tools are built, the harness checks it again (`held_write_area`): an attempt that is not its work's current, running one is refused with `conflict` (`write_area_held: …`, naming the area, the work and its current attempt), so two attempts never hold one area. A continuation in a child environment hands back into the work's area too (`HandBackRequest.write_area`, set when it is not the delegation's own), so the paths its files had stay the paths its parent reads; the session's `.handback/manifest.json` there is the latest hand-back's copy, and each manifest is kept whole in the worker's records.
  - **Decided** (safer reading; the spec did not settle them): `pdf_render`'s PNG and a job's delivered outputs are written where the platform places them, as a process's files are (DA-20), not under the write area.
  - **Not built here:** DA-16 (`path_outside_session`) and DA-17 (file grants), so DA-F4's first and third cases are not yet built. DA-20 was built on 2026-11-01.
  - Tests: the worker's `test_write_area.py` (paths, symlinks, `shared/`, the parent's and a sibling's reads) and `test_child_environments.py` (the hand-back's paths, a continuation's into its work's area); `test_continuation_write_area.py` (a resumed child edits its earlier file and is refused a sibling's area; only the current, running attempt holds the area); `test_parent_review.py` (a reopened task edits its earlier file); end to end through the CLI and a real worker, `test_delegation_write_area.py` (DA-F4's writes, the brief, the parent's read, the main run) and `test_delegation_environments.py` (a child in its own environment).
- DA-20. **A child's processes.** A child's shell commands, its background jobs in its environment and its Python and Sage cells (in its own kernels, PD-37) start in its write area, which `$RUN_WORK` names, and can write only there and in the run's scratch directory, `$TMPDIR`. They read what the sandbox lets them read, as before, and change nothing else: its parent's and the session's other files, its own `inputs/` (CE-7), a sibling's write area, `shared/`, the installed packages (the Python and Conda prefix; a child installs with `provision`, whose steps are the platform's), the home directory and the executor's files. DA-19 holds its file tools to the same area, and to `shared/` with its guard. The owner requires this (question 1). A draft or user-edited plan does not hold these executions (DA-7, D99).

  *Decided and built 2026-11-01:*
  - **A Landlock ruleset per execution.** The worker's executor starts each of the child's processes through `sandbox_confine.py`, which adds a Landlock ruleset to itself and then becomes the command; a kernel's command is prefixed the same way at every start and restart. The ruleset is nested in the one OpenShell gives every sandbox, covers the process and everything it starts, and cannot be lifted or widened. It handles every right that changes the file system (write, truncate, create, remove, rename, link) and allows them only below the write area, below the run's scratch directory (outside the session; it holds `TMPDIR`, `IPYTHONDIR`, `MPLCONFIGDIR`, `XDG_CACHE_HOME` and `DOT_SAGE`) and on the devices the sandbox grants (`/dev/null`, `/dev/zero`, `/dev/full`, `/dev/tty`, `/dev/ptmx`, `/dev/pts`, `/dev/shm`). Reading stays the sandbox's rule. Its scopes (Landlock ABI 6) refuse the process a connection to an abstract Unix socket made outside it, such as another run's kernel, which is not held, and a signal to a process outside it (the calls the kernel carries out for the process; the seccomp filter below refuses those a sandbox's supervisor would carry out instead); Landlock also refuses it ptrace-like access (`ptrace`, `process_vm_writev`, `pidfd_getfd`, `/proc/<pid>/mem`, `fd`, `environ`) to processes outside. Without the scopes a child could drive its parent's kernel, so ABI 6 is required ([worker](../WORKER.md#a-delegated-runs-processes)). The ruleset also has TCP rules: binding a port is refused, and so is connecting to any port but an egress proxy's (the ports in `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` where the sandbox sets them; OpenShell 0.1.5 sets none; the rule is per port, on any address), so that a child cannot reach a server another run opens on a TCP port. They hold where the kernel makes the process's sockets, as on the `local` backend, and not under OpenShell 0.1.5, which makes them in its supervisor (*Not covered*). It also refuses ioctls on devices other than the terminals. Landlock's TCP rules see only plain TCP sockets, so the seccomp filter below admits no other way to carry TCP.
  - **A seccomp filter beside it**, added by the same wrapper after the ruleset (it stacks on OpenShell's filter; `prctl(PR_SET_SECCOMP)` is what OpenShell 0.1.5 leaves open), for what Landlock does not cover: `prlimit64`, `setpriority` and `ioprio_set` act only on the calling process (pid 0 or its own), else `EPERM`, so a child cannot set its parent's kernel's CPU limit or the executor's file limit; the scheduling calls (`sched_setaffinity`, `sched_setscheduler`, `sched_setparam`, `sched_setattr`) on another process or thread succeed doing nothing, since libzmq aborts when a thread cannot set its own; file locks (`flock`, and `fcntl`'s `F_SETLK`, `F_SETLKW`, `F_OFD_SETLK`, `F_OFD_SETLKW`) succeed doing nothing, since a read-only descriptor of a file the child cannot write (the package commands' lock, say) could otherwise hold every execution of the session; leases (`F_SETLEASE`) are `EPERM`; `kill` and `rt_sigqueueinfo` are `EPERM` whatever they name, and so are making a process a descriptor's owner or choosing its signal (`fcntl`'s `F_SETOWN`, `F_SETOWN_EX` and `F_SETSIG`, the `FIOSETOWN` and `SIOCSPGRP` ioctls), because OpenShell 0.1.5's supervisor carries out an allowed `kill` or `rt_sigqueueinfo` itself (a seccomp user notification, answered with its own `pidfd_send_signal`), outside the caller's Landlock domain, where the signal scope never sees it, and this filter's refusal takes precedence over the notification; the thread-directed calls (`tkill`, `tgkill`, `rt_tgsigqueueinfo`), which OpenShell lets the kernel carry out, and `pidfd_send_signal` pass, and Landlock checks them; a socket is created only of the families `AF_UNIX`, `AF_NETLINK`, `AF_INET` and `AF_INET6`, and an Internet one only as a stream or datagram socket of TCP, UDP or ICMP (`EAFNOSUPPORT` or `EPROTONOSUPPORT` otherwise: MPTCP, SCTP and `AF_SMC` carry TCP past Landlock's rules); io_uring is `ENOSYS`, since its socket and connect operations pass no socket call; a call of another architecture (x86's i386 and x32) ends the process. "The calling process" is pid 0 or the run's first process, whose pid the filter holds: a process that process starts gets `EPERM` naming its own pid, as `resource.prlimit(os.getpid(), …)` does, and succeeds with 0, as `setrlimit` does. The executor applies the ruleset and the filter in a probe process of its own before it reports that it can hold a run. The probe then tries every way it has to signal the executor, which is outside them: `kill`, `tkill`, `tgkill`, `rt_sigqueueinfo`, `rt_tgsigqueueinfo` and `pidfd_send_signal` with the signals 0 and `SIGCONT` (which a running process ignores, and which OpenShell's supervisor handles apart), `kill` of its own process group, of the executor's and of every process with 0, and making the executor a socket's owner. If one goes through, the executor reports that it cannot hold a run, with the call that did. It also tries to bind a loopback TCP port, and reports in `hello` whether TCP is held there (`tcp_held`); that only informs.
  - **Signals within the run.** A held process's own programs still signal their own processes through the signal shim (`shim/signal_self.c`, `libsandbox-science-signal.so`), which the executor preloads (`LD_PRELOAD`) in every held process, and in no other. It replaces C library functions with calls Landlock checks: `kill(pid > 0)` becomes `tgkill(pid, pid)`, so the signal goes to the process's main thread rather than to any thread not blocking it; `kill(0)`, `kill(-pgid)` and `killpg` signal each member of the group that `/proc` lists, the caller last, reading the list again until it shows no new member; `kill(-1)` signals every process but the caller and init; `sigqueue` becomes `rt_tgsigqueueinfo`. Every one of these reaches the process's own execution (each held shell command, job and kernel starts in a Landlock domain, session and process group of its own) and is refused outside it, process by process, so Python's `subprocess` and `os.kill`, the shell's `kill`, `timeout`, `multiprocessing` and `concurrent.futures` pools and joblib's work as before. The research images ship the shim beside the scheduler shim, and the worker validates it and names it to the executor as it does that one; the `local` backend builds it with the host's compiler. A program that makes the system call itself, or is linked statically (Go programs, a static busybox), gets `EPERM` from `kill` even for its own children; and where the shim is missing (`own_signals: false` in `hello`), so does every program.
  - **Why not per-run mounts or a uid per run.** OpenShell 0.1.5's seccomp filter refuses `mount`, the new mount API, `pivot_root`, `setns`, and `unshare` and `clone` with a new user namespace, and its sandboxes run with no capabilities, so no per-run bind mount, mount namespace or separate uid can be made inside a sandbox, on the VM driver or on Kubernetes. File modes would not hold: the run owns the files and could change them back. Landlock needs no privilege, and OpenShell 0.1.5 itself requires it: its VM driver's guest kernel (6.12) has ABI 6, and Kata's guest on the cluster ABI 7. A child environment of its own (CE) separates a child from its parent's files but not from its own `inputs/`, and is a placement a project turns on, not every child's.
  - **Both placements.** In the session's environment and in a child environment of its own the request carries the same `write_area` (DA-19), so the rule does not depend on placement; in its own environment it is what keeps `inputs/` read-only (CE-7). A job in a job sandbox of its own (D93) is not held: that sandbox holds only copies of its inputs, its results come back where the platform places them, and it is discarded.
  - **Where it cannot hold, nothing runs.** The executor reports in its `hello` what Landlock offers (`confinement`: its ABI, or why it cannot hold a run). On an executor that cannot, that says nothing (one from before), whose confinement protocol is older than 2 (its filter leaves the supervisor's signal calls open, and its probe does not check that a signal stays in), or that offers an ABI below 6, the worker refuses the child's shell, job, cell and kernel restart with `unsupported` before anything runs, and the executor refuses them again on its own. A child's code never runs with a lower guarantee: an unconfined child could rewrite its parent's files or drive its parent's kernel, the harm DA-20 exists to prevent, and recording a lower guarantee would not undo it. The refusal reaches only the developer's `local` backend on a Linux kernel before 6.12 or on macOS, where a child's file tools still work. The wrapper fails closed too: a ruleset it cannot make in full runs nothing (exit status 126).
  - **The requests.** The harness sends `ExecutionContext.write_area` (DA-19) on the child's shell, job, cell and kernel restart requests, and on the restart and replay of its kernel when a Resume rebuilds it (the work's area, by DA-19's continuation rule). A cell naming a write area runs in its run's own kernel (`invalid_request` otherwise); a kernel keeps the area it was started with, and a request naming another, or none, is refused with `conflict` (`kernel_confinement`). The platform's requests for the child (the PDF helper, saved output, provisioning steps, hand-backs) name none. Worker protocol 19; executor protocol 4; the `hello`'s confinement protocol 2.
  - **What the child is told.** The brief's write-area line (DA-19) adds that its shell, jobs and cells start in the area (`$RUN_WORK`) and write only there and in `$TMPDIR`, not `inputs/`, `shared/`, other files or the installed packages, which it installs with `provision` when offered; and that it reads the session's files (in its own environment, that environment's) at `$SESSION_WORKSPACE`. The pinned prompts are unchanged. A package command its processes run (`pip`, `uv pip`, `conda`, `micromamba` install) is refused, since the prefix is read-only to them, and the refusal adds that a delegated run installs packages with the `provision` tool.
  - **Not covered.**
    - *A file's mode, owner, times and extended attributes.* Landlock governs paths, not these, and refusing `chmod`, `utimensat` and `setxattr` outright would break ordinary work on the child's own files (`touch`, `tar`, `cp -p`, `chmod +x`). So a child's process can make a file it cannot write unreadable to its parent (`chmod 000`) until the parent sets the mode back: a denial of service, never a change of content. The shared files' sync stamps a file with the later of its modification and status-change times, which the kernel sets, so a child that sets a modification time back cannot hide another run's change from the sync.
    - *Shared memory and terminals.* A child's process can write any segment in `/dev/shm` and any pseudo-terminal of the sandbox, which Python's `multiprocessing` and Sage's interfaces need. Another run's shared-memory data and POSIX semaphores can therefore be corrupted, and data another run unpickles from `/dev/shm` would run the child's code there: joblib's memory-mapped pickles, which its worker processes load, are the known route, so the executor points `JOBLIB_TEMP_FOLDER` for every run at a directory a child cannot write (a held run's at its scratch directory). Code that shares pickles through `/dev/shm` by other means is not protected. Through another run's pseudo-terminal (opened by its `/dev/pts` name, as Sage's pexpect interfaces' are) a child's process can also write to it and change its settings or window size; the last makes the kernel send `SIGWINCH` to the processes using that terminal, a signal the kernel itself sends and no ruleset checks (most programs redraw or ignore it).
    - *TCP under OpenShell.* OpenShell 0.1.5 makes each sandbox process's sockets in its supervisor and passes the descriptor in, so the ruleset's TCP rules never see them. A child's process can therefore bind and listen on a loopback port, and connect to a TCP server that another run in the same sandbox opened on loopback (and, as before, to whatever the sandbox's network policy lets out). Kernels' channels are abstract Unix sockets, which the scope covers, so a parent's kernel stays out of reach; a server the parent's code opens on a TCP port does not. The executor's `hello` says `tcp_held: false` there.
    - *Other channels.* A Unix socket with a path, or UDP, that another run's process opens is reachable as before; the platform's own use abstract sockets, which the scope covers. `listen()` on a socket never bound still takes an ephemeral TCP port, so a child can serve on one that other runs' processes may choose to reach. System V IPC (`shmctl`, `semctl`, `msgctl`, `ipcrm`) and POSIX message queues are the user's: a child can remove or change another run's objects.
    - *Shared resources.* A child's processes share the sandbox's memory, processes, CPU and disk with its parent: one can exhaust them, and the kernel's out-of-memory killer may then end the parent's kernel. The sandbox's own limits bound the whole, not a run.
    - *Modification times elsewhere.* Besides the shared files' sync, which uses the status-change time too, three checks read modification times, which a child can set on any file it can read without changing its content. The package fingerprint reads the times of `.dist-info` folders and Conda records: a child touching one records a spurious revision of the packages, unmanaged and attributed to the call that saw it, whose lockfile is unchanged. A call's written-files report compares modification time, size and inode (its observation report names the time as `mtime_ns`): a same-size change made in place by another run's process, with its time set back by a child during that call, is left out of that call's report. A write's check that the file it replaces did not change meanwhile compares the same, over the milliseconds of the swap. None of these lets a child change content.
    - *Locks within the child.* Its file locks do nothing, so an SQLite database or an HDF5 file shared by two of the child's own processes at once is not protected by locking; each of its kernels has an IPython directory of its own, so their history databases are not shared.
    - *Leftover processes.* A process the child starts that rewrites its own owner mark (`SANDBOX_SCIENCE_OWNER`) is not ended with the call, as for any run ([worker](../WORKER.md#leftover-processes)); it stays held.
    - *The platform's operations.* The executor's own work for the child (the file tools under DA-19, the PDF helper, `provision`'s steps, hand-backs) is not held. Network access beyond TCP to the proxy is the sandbox policy's, unchanged.
  - **Decided** (the safer reading; the spec did not settle them): `shared/` is read-only to a child's processes, which write there only with `write_file` and its guard; the installed packages are read-only to them, so a child installs through `provision`; its processes start in its write area, so a relative path is in the area; where their TCP rules hold (the `local` backend) they cannot bind a TCP port or connect to one other than an egress proxy's, so a local cluster such as Dask's does not run in a child, and with no proxy set a child has no TCP (under OpenShell 0.1.5 the rules do not hold: *Not covered*); MPTCP and SCTP are refused everywhere; a process's `kill` reaches its own execution's processes through the signal shim, and a statically linked program, or one making the system call itself, cannot signal even its own children (`EPERM`); their file locks do nothing, so two of a child's processes cannot lock a file of its own against each other; `/dev/shm` stays writable, since `multiprocessing` needs it.
  - Tests: the worker's `test_held_processes.py` (DA-F9 and DA-F10, with real commands and kernels, and the review's findings: another process's limits, priority, I/O priority and scheduling, ptrace, a lock and a lease on the package commands' lock, TCP, a device ioctl, joblib's folder and the shared files' stamp; and the signals: the filter's answers to each signal call, the probe refusing where a signal leaves, a child's shell signalling its own processes, `timeout` and pools, and never the parent's kernel, the executor or their group); `test_signal_shim.py` (the shim's `kill`, `killpg`, `kill(0)`, `kill(-1)` and `sigqueue` in a held process, and `kill` refused without it); `test_provisioning.py` (a held package command names `provision`); the image checks' `signal-shim` and `held-run`, in each research image as a container and inside an OpenShell-like Landlock ruleset, with Sage's pexpect interfaces and the shell's `kill` and `timeout`; the harness's `test_held_requests.py` (which requests name the area); and end to end through the CLI and a real worker, `test_delegation_write_area.py` (a child's shell and cell).

## Questions

All decided by the owner on 2026-10-21.

1. **Holding a child's processes to its write area.** DA-19 binds the file tools only; a child's shell can still write anywhere the session's sandbox can. *Decided:* required, but after the first build. *Built 2026-11-01* (DA-20) with a Landlock ruleset per execution rather than per-run mounts, which OpenShell's sandboxes cannot make.
2. **Per-run approval scopes**, such as an approval for one child only. *Decided:* no. Approvals stay once, for the session or project-wide (grants, D97), and the run is attribution (DA-4).
3. **Check children and connectors.** *Decided:* only tools classed `read` (DA-1, DA-7). Most connector methods only read.
4. **A connector budget per delegation.** *Decided:* no separate budget. Calls count toward the project's cost limit, and the outcome reports how many the child made.
