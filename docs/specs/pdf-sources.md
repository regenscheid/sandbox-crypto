# PDF sources: pages, search, renders and anchors

**Status.** Approved as drafted, with the recommended answers to its open questions, adopted on 2026-10-14 under the owner's instruction to proceed with the refactoring plan's recommendations. It is written from the [research workspace](../RESEARCH-WORKSPACE.md) requirements and D59. The worker implements it (`PdfRequest`, [worker](../WORKER.md#pdfs)), and the harness offers it as the tools `pdf_info`, `pdf_pages`, `pdf_search` and `pdf_render`.

## Scope

This spec covers how the agent reads a PDF in its workspace, and how it cites a place in one:
- page facts and outline;
- page text with line anchors;
- search;
- page and region renders, for checking what extracted text cannot show faithfully (equations, matrices, figures).

These belong to other specs or later work: importing PDFs as artifact revisions with import attribution ([research artifacts](research-artifacts.md), RA-F*), the GUI viewer, annotations on a PDF ([research artifacts](research-artifacts.md), RA-21), OCR, tables, and caching parsed results by document hash.

## Principles

- **Parsing is untrusted work.** PDFs are untrusted input. They are parsed inside the sandbox, by the environment's pdf_oxide (D59), in a process of their own with the time and output limits of a tool call. Nothing parses a PDF beside the orchestrator or the worker service.
- **The source is the bytes.** Every result names the file's path and its SHA-256. An anchor that names a hash stays meaningful after the file changes or moves.
- **Two page numbers.** Pages are numbered by their physical position (`index`, from 1) and also carry the label the document prints (`label`, such as `iv` or `12`). Without page labels, the label is the index. An anchor keeps both, so a printed page number never silently points at the wrong page.
- **Extraction is not proof.** Results say which parser and version produced them, and whether a page has a text layer. Extracted text of equations and matrices may be wrong; a render shows the page as drawn.

## Operations

1. **`pdf_info`** returns:
   - the page count, and each page's index, label, size in points, rotation and whether it has a text layer;
   - the outline (bookmarks), each with its title, level and target page;
   - the parser's name and version, and the source's path, size and SHA-256.
2. **`pdf_pages`** returns the text of selected pages (for example `"3-5,9"`), at most 20 per call, as numbered lines. Each line carries its bounding box. A page over the output limit is cut, and the result says so.
3. **`pdf_search`** finds a case-insensitive string. Each hit gives its page index and label, line number, the line's text and its box. Hits stop at a limit, and the result says so.

   **One line numbering** (amended 2026-10-15 by the coordinator, from the `pdf-reading` skill's writing). Both tools number a page's lines one way: every line with text, from 1, in the parser's order. Running headers, footers and page numbers (tagged `/Artifact`) are counted and marked as such. `pdf_pages` leaves them out unless asked, and says which numbers it left out, but never renumbers the rest. A line cited from either tool is therefore the same line, and the citation check (CR-4) finds a quote by either tool's numbers. A line that mixes such text with the body's is body text.
4. **`pdf_render`** renders one page, or one region of a page, to a PNG in the session workspace. It returns the PNG's path, size in pixels and SHA-256, so the agent can publish it as evidence beside the text it checks.

## Anchors

A `PdfAnchor` names:
- the source's SHA-256 and the path it was read from;
- the page index and the page label;
- an optional box `[x0, y0, x1, y1]` in PDF points, in the page's coordinate space (origin at the bottom left, before any page rotation);
- an optional quote, which is the text the box held when the anchor was made.

The agent cites a line as `p<index>:<line>` from `pdf_pages` or `pdf_search`. The harness turns that into an anchor with the line's box and text.

## Errors

| Case | Kind |
| --- | --- |
| The environment lacks pdf_oxide | `unsupported`, naming the package to install |
| The file is missing, a directory, outside the workspace or not a PDF | `invalid_request` |
| An encrypted PDF that needs a password | `unsupported` |
| A malformed PDF that the parser rejects | `exception`, with the parser's message |
| More pages asked for than allowed, or a page out of range | `invalid_request` |
| Parsing outlasts the call's time limit | `timed_out` |

## Acceptance fixtures

The fixtures use small PDFs generated by the tests, whose text and positions are known.

**PDF-F1 Page facts** (`scripted`)
- *Given* a four-page PDF with page labels `i`, `ii`, `1`, `2` and an outline of two entries.
- *When* the agent calls `pdf_info`.
- *Then* it gets four pages with those labels and the outline's titles and target pages; the source's SHA-256 matches the file.

**PDF-F2 Line anchors** (`scripted`)
- *Given* a page whose first line, "A Note on GF(17)", is drawn at a known position.
- *When* the agent calls `pdf_pages` for page 1.
- *Then* line 1 is that text, and its box contains the drawn position.

**PDF-F3 Search** (`scripted`)
- *When* the agent searches for a word that appears on pages 1 and 3.
- *Then* each hit names the right page index and label and a box on that page.

**PDF-F4 Region render** (`scripted`)
- *When* the agent renders the region around a known line at 150 DPI.
- *Then* a PNG of the expected pixel size appears in the workspace, and its SHA-256 is reported.

**PDF-F5 No text layer** (`scripted`)
- *Given* a page that is only an image.
- *Then* `pdf_info` reports it without a text layer, and `pdf_pages` returns no lines for it while saying why.

**PDF-F6 Bad input** (`scripted`)
- *Given* a file that is not a PDF, and a page range past the end.
- *Then* both calls fail with `invalid_request`, and nothing else in the session changes.

**PDF-F7 One line numbering** (`scripted`)
- *Given* a page with a running header, two lines of text and a page number, the header and page number tagged `/Artifact`.
- *When* the agent reads it with `pdf_pages` and searches it with `pdf_search`.
- *Then* the two lines are 2 and 3 in both. `pdf_pages` names 1 and 4 as left out, and a search hit on the header is marked as one. A quote of line 3 cited from either tool is found in the other's result.

## Open questions

The recommended answers below were adopted with the spec on 2026-10-14.

- Should `pdf_pages` default to excluding running headers and footers (tagged artifacts)? Recommended: yes, with a switch, since they repeat on every page and waste context. *Amended 2026-10-15:* excluded from the text, but still counted in the line numbers (tools item 3).
- Should parsed pages be cached by the document hash and parser version in the session workspace, or in the worker? Recommended: in the workspace, since the parse already ran there, and the cache is then visible and disposable.
