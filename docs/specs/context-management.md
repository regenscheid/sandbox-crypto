## Scope

A research session runs for days. Its runs together read and produce millions of tokens: papers, tool output, computations and decisions. A model reads far less in one call, and reasons best over context that is curated. This spec says how the platform keeps everything, what each model call sees, how older work is folded into shorter records, how the research state is kept outside the conversation, and how the agent gets exact values back.

**Today.** A run is one user turn of at most 30 model calls, and each call sends the whole conversation. Past 400,000 characters (about 100,000 tokens), or on the gateway's context error, the run stops with `context_limit`. A new run sees only the earlier runs' tasks, user messages and final answers, within 100,000 characters; their tool calls and results are dropped ([run service](run-service.md), RS-10). So on day 3 the agent sees none of the evidence it gathered on day 1, unless it was written into an answer, the ledger, a document or memory.

**The design.** It follows Claude Science's rolling folds (CScience): keep everything in an archive, show the model a bounded view, fold the oldest work in chunks, clear old bulky tool output when it folds, and let the agent get exact values back from the archive. It changes four things:

1. Code carries state forward at every fold: the user's messages word for word, and a digest of the research state, from the ledger and the plan. Claude Science keeps such carries only in its fallback path.
2. The view spans the whole session, not one run. It replaces RS-10's earlier conversation.
3. Code checks that the values and search keys in a fold occur in the span it covers.
4. Two native model adapters: Claude through the gateway's `/v1/messages`, with the rules that bind thinking to its history, and GPT through `/v1/responses`, with reasoning items.

The spec has six layers: the archive, the research state, folds, the working view, retrieval and the model adapters. The [residual risks](#residual-risks) follow the requirements.

**The ceiling.** 600,000 tokens is the owner's default for how much context a call may carry. It is a setting, not a finding. Studies of long contexts find that models reason less well as the context grows (Chroma's "Context Rot"; the Graphwalks results at 256,000 and 1,000,000 tokens), so more context is not always better. And no proven system runs rolling folds at this size: Claude Science folds in pieces only on windows of 200,000 tokens or less; on 1,000,000-token windows it lets the context grow to about 600,000 tokens and then writes one summary of the whole history. The first lab round runs the probes at the default itself, and the owner lowers it if the larger context does worse (CM-27, question 7).

**Out of scope.** Project memory, which stays as it is ([project memory](project-memory.md)). The consistency reviewer's and the job watcher's inputs, which are bounded on their own. Provider-native compaction (question 3). A session scratchpad, which comes only if the continuity probes find state that neither the ledger nor the plan holds.

Terms:

- **Archive**: every original message of a session, kept for as long as the project exists.
- **View**: what one model call receives.
- **Ceiling** (C): the most tokens a call's input may hold.
- **Raw tail**: the newest messages, shown word for word, except old bulky tool results, which become stubs at folds.
- **Fold**: the replacement, in the view, of the oldest part of the raw tail by a fold record. Its **span** is the run of archive messages it covers.
- **Fold record**: a span header, a skeleton and marker lines built by code, a narrative written by a model, and search keys. A first-level fold covers raw messages; an **overview** covers earlier fold records.
- **State block**: one message, rebuilt by code, holding the user's own words and the research-state digest.
- **Research state**: where the research stands, kept in the ledger, the session plan and the read register.
- **Rebuild**: a moment when code recomposes the view: a fold, a run's start, and a change of model.
- **Safe point**: a moment in a run when no tool call waits for its result: before a model call, and while the run waits on jobs, delegations or a question.

## Behavior

### General

- CM-1. **Which runs.** Main runs get the session view (CM-29). Delegated runs fold within their own run (CM-37). The consistency reviewer and the job watcher keep their own bounded inputs and have no view.
- CM-2. **Both model families** (owner, 2026-10-15). The archive, the research state, fold records, the state block and the retrieval tools are plain text and records that any model reads. A session may switch between Claude and GPT models. Only native items, such as thinking and reasoning, stay with the model family that made them (CM-42).
- CM-2a. **One replaceable subsystem** (new). The view builder, the fold engine (scheduling, skeletons, enrichment, validation, overviews and marker retention) and the retrieval tools sit behind one interface. The loop calls it at its safe points: it hands over each appended message and each call's usage, and asks for the next call's view. The interface lives outside the loop's own module, as a turn hook does (refactoring plan, working rule 7). The archive and the research state are stable stores that the subsystem reads and does not own. Replacing the subsystem, with a plain summary, a provider's compaction or a library, changes neither store, nor the loop, nor the model adapters.

### Layer 1: the archive

- CM-3. **What it holds.** Every message of every run of the session, delegated runs included: tasks, the user's messages and the comments addressed to the session (RS-6b), notices, the assistant's text and tool calls, tool results, delegation outcomes as the parent received them, and the state blocks and fold records the platform sent. Each message has a stable ID, `msg-` and 16 hexadecimal digits, unique in the project; its position in the session (an integer that only grows); its run; its role and kind; and its time. A tool result also has its call ID and tool (new). Positions interleave the runs of a delegation tree; CM-29a says which messages the main view holds.
- CM-4. **Written as the run goes.** Each message is appended before the next model call, as run events are (RS-13), but whole: unlike an event, it is never cut. An interrupted run keeps every message it appended. Nothing is changed or deleted while the project exists (CScience keeps a whole-session log; Codex keeps its rollout file).
- CM-4a. **ID headers** (new). Every message the platform appends to a conversation (a user message, a comment, a notice, a tool result, a delegation outcome) begins with a one-line header naming its full archive ID and kind, such as `[msg-5f0c2e9a41d7b386 · tool result · sage]`. The header is written once, when the message is appended, and never changes, so it keeps the cache and Claude's thinking binding intact. The user's text follows its header as written (RS-7). A line inside a message's own content that begins like a header is escaped when the message is appended, with a marker before it, so that only the platform's headers read as headers. Assistant messages keep the model's own content: the agent cites them by the IDs of the tool calls they hold, or finds them by search. So the agent can cite any recent message by its ID (CM-9).
- CM-5. **Native payloads.** Beside each assistant message's provider-neutral copy, the archive keeps the provider's native response byte for byte: Claude's content blocks, including thinking blocks with empty visible text, their signatures, redacted thinking and progress-update text (CM-38); GPT's output items, with encrypted reasoning, `phase` and the item IDs as the gateway gave them. It also records the provider model and the gateway's version (CM-39). Claude's progress-update text counts as the assistant's text for skeletons and search.
- CM-6. **Files and outcomes.** A tool result links to the files its call saved: the whole output behind a sample ([tools](tools.md), Shell 5) and the artifact revisions the call recorded ([research artifacts](research-artifacts.md), RA-27). A delegation outcome links to its delegation (PD-17).
- CM-7. **The search index.** The archive keeps two SQLite FTS5 indexes over the same content: one with the `unicode61` tokenizer, for words and quoted phrases ranked by BM25, and one with the `trigram` tokenizer, for substrings, so that part of a hash or of a long number finds it. They cover messages' text, tool calls (names and arguments), tool results, notices, delegation outcomes, and the saved output files behind samples, up to 1 MiB each. The index knows its coverage: the positions it indexed, and the files it left out, with the reason. When the service starts, it checks that its SQLite has FTS5 and the trigram tokenizer (SQLite 3.34 or later), and refuses to start without them, saying which is missing. CScience also ranks by BM25 with a bonus for exact substrings, but over an index it holds in memory; this one is on disk beside the archive.

### Layer 2: the research state

- CM-8. **What it is.** An explicitly kept record of where the research stands, not a by-product of summaries. It lives in the [ledger](ledger.md), the session plan ([plans and delegation](plans-and-delegation.md)) and the read register (CM-12):

  | Item | Kept as | New here |
  | --- | --- | --- |
  | Open questions | An `issue` of kind `question`, `open` | The issue's kind |
  | Active hypotheses | An `issue` of kind `hypothesis`, `open`, resolved by a claim that `answers` it | The kind |
  | Assumptions, and what depends on them | An `assumption`, the `assumes` links to it, and the platform's flags (LG-27, LG-28) | Nothing |
  | Decisions, including rejected and reversed ones, with their reasons and the conditions that would justify reopening them | A `decision`, its status, the reason of the revision that gave it that status, and its reopen condition, stated as an issue | The reopen condition and its links (CM-10) |
  | The user's standing constraints | A `decision` in effect with the basis `user` or `user_quoted`, anchored on the user's words, for the project or for one session | The basis (CM-9); the session scope (CM-10) |
  | Unresolved contradictions between sources or results | An `issue` of kind `contradiction`, `open`, which `concerns` the entries that disagree | The kind; it concerns at least two entries |
  | Findings, with evidence type, scope and caveats | A `claim` or `result`, its evidence links' types and scope notes (LG-8, LG-9), and its caveats | The caveats |
  | Attempts, and how they ended | Work records (LG-6): `limit`, `obstruction_claimed`, `produced`, `assessment` | Nothing |
  | Which sources were read completely, and which only in part | The read register (CM-12), shown on `reference` entries | All of it |
  | Where the session's work stands | The session plan: its steps, their statuses and notes; a step may name the ledger task it advances (LG-40) | Nothing |

- CM-9. **Provenance** (new). Every entry revision and work record an agent writes keeps its basis and its anchors:
  - the basis: `user` for the user's own changes; `user_quoted` for an agent's record of what the user said or decided; `observed` for an agent's record that restates what the platform observed (a tool result, an artifact, a line of a PDF); `interpreted` for the agent's reading or inference, and for a change that names no basis. The digest shows them as `[user]`, `[user, quoted]`, `[observed]` and `[interpreted]`, so an agent's statement about the user never looks like the user's own change;
  - the anchors: at least one place the item comes from, besides the change's own tool call: an archive message by its ID (CM-4a), or a tool result by its call ID; a PDF anchor (LG-8); an artifact revision; a document block at a revision; or an entry revision. The evidence links a revision holds, those kept from its earlier revisions included, count as its anchors.

  An agent's change that creates an entry, changes its statement, fields or caveats, or moves a decision to `in_effect`, `rejected` or `reversed`, and every work record, has at least one anchor. A change of another status, a title or links alone needs only its reason. So a revision that rewords a statement and keeps the entry's evidence, as LG-F6's does, needs nothing more. Code checks, and refuses with `provenance_required`, naming what failed:
  - `user_quoted` needs an anchor on a message the user wrote (a USER row, or a comment addressed to the session) with a quote of at least 20 characters, or the whole message if it is shorter, which code finds verbatim in that row, its line ends normalized;
  - `observed` needs an anchor on a tool result (whole, or a range of its output), an artifact revision or a PDF anchor. Every number in the change's statement and fields must occur, with the notation normalized as CM-20 says, in one of the observation targets: the anchors of those kinds that the change names, and the revision's evidence targets of those kinds;
  - every anchor must exist in the project.

  **What this verifies, and what it does not.** It verifies that a quoted user message holds those words, that an observed item's numbers appear in its sources, and that every anchor exists. It does not verify that a quote means what the record says, that a source supports a statement beyond its numbers, or anything about an `interpreted` item. The basis is a structural check, not a proof. The gate (LG-17) still reads only evidence links.

  Records the platform makes on an agent's behalf are anchored automatically: an import from a results file (LG-35, LG-41) is `observed`, anchored on the file's artifact revision and line, so the pack's records (gate 5, LG-F9) import as before; a check's outcome recorded as work (LG-F8) is `observed`, anchored on its delegation's outcome. The user's own changes have the basis `user` and need no anchor. Entries written before this change show their basis as not recorded.

  *Built 2026-10-16 (step b2, control store version 51; [ledger](../LEDGER.md#what-is-built)), with these decisions of the coordinator, which the owner can reverse:*
  - *An import is `observed` only when its results file is an artifact revision an execution produced:* the worker reported it written by an execution that succeeded (RA-34, RA-11). It is anchored on that revision and the line. A file without that lineage, such as one written with `write_file`, imports as `interpreted`; one that is no artifact revision yet is recorded as one at the import, and a file the project does not record is anchored on its path, SHA-256 and line.
  - *The user's words are what the user wrote:* a chat message the run received (a `user` row), the chat messages a run's task names (a `task` row; a delegation's brief and the stand-in task for comments name none), each matched apart, the task the operator typed with `run --task` (a `task` row naming its own run as `cli:<run>`), and a comment notice's `request_text` values, read by the payload's structure whatever the framing's version, never its framing, its JSON or the document text beside them, which an agent may have written. Every quote a `user_quoted` record holds must be such words, found verbatim: one real quote does not carry an invented one, or one on a tool result. On another basis a quote says only that its text appears where it points, which code checks too (the coordinator, 2026-10-16, found reviewing the digest).
  - *Anchors resolve where their author may look* (CM-37, PD-13): a main agent's within its session, its delegated runs included; a delegated agent's within its own run and the messages its brief names as inputs. A call ID is looked for in the author's own run first; one that two other runs share is refused as ambiguous, and the message ID is named instead. What an agent may not see reads as missing.
  - *The number check reads digits wherever they stand,* next to letters too (`80bit`, `AES-128`), with powers however spaced or bracketed (`2 ^ 80`, `2^(80)`), scientific notation as one number (`1e24` is `10^24`; `1.2e-5` and `1.2 \times 10^{-5}` are one), and thousands set apart by spaces (`1 000 003`). Digits and numerals it cannot read (`①`, `½`, `Ⅷ`), and powers whose exponent is no plain number (`2^{80+1}`), refuse `observed`.
  - *Departures accepted:* a work record's references to a delegation, an artifact or a document count as its anchors, as a revision's evidence does; a PDF passage is anchored as a quote evidence link (LG-8), whose quoted text the number check reads.
- CM-10. **What the ledger gains** (new; the [ledger](ledger.md) is amended accordingly):
  1. An issue has a kind: `question`, `hypothesis`, `idea`, `experiment`, `contradiction` or `reproduction` (a failed reproduction). Older issues read as `question`. A `contradiction` `concerns` at least two entries, findings or document blocks, and its statement says what disagrees, with an anchor on each side.
  2. A decision has a reopen condition: a short text, and `reopen_on` links to what it watches. A condition about something the ledger does not yet hold is stated as an open issue of kind `question`, such as I-14, "Is assumption Y available for the target group?", which the decision links to. A link may also name an existing assumption, claim or result whose change would matter. A decision moved to `rejected` or `reversed` needs a reason; its reopen condition may say "none".
  3. When a linked issue is resolved, or a linked entry changes status or statement, the platform flags the decision for reconsideration, as LG-28 flags dependents. Reopening changes nothing by itself: the digest shows the flag with its cause, and the main agent or the user either clears it with a reason (the condition is not met after all) or records a new decision. A rejected or reversed decision stays so: trying the approach again is a new decision that cites the old one (LG-4).
  4. A claim or result has caveats: up to 10 short lines, each at most 300 characters, that qualify it in ways its scope notes and assumptions do not, such as "heuristic: assumes the reduced basis behaves like a random one" or "estimated from 2^20 samples".
  5. Entry revisions and work records keep their basis and anchors (CM-9). An anchor on an archive message is a transcript anchor, the contract addition the index approved ([addition 3](README.md#proposed-contract-additions-new)).
  6. A decision may be scoped to one session. Ledger entries are project-wide (LG-3), but a user's constraint can be meant for one session only, such as "in this session, try only the small parameter sets". Such a decision names its session; only that session's digest shows it among the standing constraints, and other sessions' digests count it with that session's decisions.
- CM-11. **Failure is not impossibility.** The research state keeps three things apart, and the digest labels them differently (CM-16):
  - an attempt that did not succeed: a work record ending `limit`, which says what ran out (time, tools, context or ideas), or a claim of kind `observation` with `numerical_experiment` or `finite_test` evidence and its scope, such as "no collision in 2^40 trials";
  - a claimed obstruction or negative result that is not settled: a work record ending `obstruction_claimed` that no assessment has accepted, or a claim of kind `negative result` that is `proposed` or `disputed`, whatever evidence it holds. An agent can propose such a claim and attach its own proof before anyone checks it;
  - a settled impossibility, in the ledger's settled statuses only: an issue `obstructed` by a decision in effect that names its excluded scope and an accepted assessment (LG-7); a project claim of kind `negative result` that is `established`, which only a decision in effect makes it, either the user's own or the main agent's that passes the gate (LG-17); or a published one that is `recorded` and confirmed as LG-16 says, labelled as its source's claim.

  Only the last is called impossible, always with its scope (the excluded scope, or the claim's statement and evidence scope notes) and the assumptions it rests on (its `assumes` links). A settled entry with an open flag (LG-28), such as one whose assumption changed, renders as unresolved, with the flag's cause, until the flag is cleared. A proposed, disputed or flagged negative result never renders as impossible: the digest says "claimed, not established", "disputed" or "flagged", with its handle. A failed numerical experiment never becomes an impossibility by being folded or summarized.

  *Built 2026-10-15 (step b1; [ledger](../LEDGER.md#what-is-built)):* CM-10's items 1 to 4 and 6 as fields and the `reopen_on` link kind (control store version 47), with the flag cause `reopen_condition`; CM-11's labels as each entry's and work record's `standing` in the ledger's reads, the agent's and the workspace's. A decision's reopen condition other than `none` needs a `reopen_on` link to an open question or an entry, the user or the main agent may record a rejected decision at once, a decision in effect, rejected or reversed keeps its research state unless a decision changes it, an agent never changes the user's, and an agent names its own session as `this`. Caveats are not part of what checks and reviews cover, and only the user removes one; a user's obstruction settles without an assessment, and every obstruction names its scope (the coordinator, 2026-10-15, which the owner can reverse). Weakening a settled state needs no authority (the owner, 2026-10-15): the main agent reopens an obstructed issue with its reason, recorded as work (`reopened`). CM-10's item 5 is built with step (b2) (CM-9, control store version 51). Not built: the digest that renders these (CM-16, step e2).
- CM-12. **The read register** (new). The platform records, from the tool records, how much of each source a session read. It is an observation, not the agent's statement. A source is a PDF artifact revision, an ePrint paper, a fetched web page, a connector's document or a saved output file. Its extent is one of:
  - `whole`: every page of a PDF returned whole by `pdf_pages`; every byte of a file read with `read_file`, counted as PD-18 counts a whole read; a fetch or connector read that returned all of it;
  - `partial`: part of it, saying which, such as pages 3–7 of 21, a byte range, or the first part of a fetched page;
  - `abstract_only`: a catalog record or abstract, such as an ePrint entry's metadata;
  - `preview_only`: a sample or preview whose whole the session never read;
  - `unknown`: a tool that does not say what it returned.

  A `pdf_search` hit reads lines, not pages. A `reference` entry shows the extents recorded for its PDF and its identifiers. The agent may add its own statement of how far it read a source the register cannot observe; that is kept as the agent's, with the basis `interpreted`. This settles the backlog's request that a reference record how much of its source was read (LG-15).
- CM-12a. **Extents for connector tools** (new). Most of the owner's papers arrive through crypto-research-mcp's tools (D64), not through the PDF tools. So the first build ships an extent descriptor for each of its reading tools, written against the tool's published schema: how to tell, from a result's fields, what part of the source it returned (a page range, a continuation cursor, a truncation flag, a length against the source's total). At least: the e-print server's `get_eprint` (a catalog record: `abstract_only`), `eprint_file` (the PDF, which becomes an artifact that the PDF tools then read) and `eprint_fulltext`; the web-fetch server's `fetch_page`, `web_fetch` and `fetch_continue` (`partial` until the continuation reports the end); firecrawl's `firecrawl_scrape` and `firecrawl_research_read_paper`; and the NIST servers' `nist_read`, `nist_get_pdf` and `csrc_fulltext`. A tool without a descriptor gives `unknown`, and the register reports the share of reads it could not place, so the labs show where a descriptor is missing.
- CM-13. **Authority** (LG-13, LG-17; owner, 2026-10-15). Agents propose; only the user, or a decision that passes the gate, settles. The research state adds no authority: the user, the main agent and delegated agents keep LG-13's, and a fold's proposals have none of their own (CM-15).
- CM-14. **The agent keeps it current.** As it works, the agent records the research state with the ledger and plan tools, within its role's authority. Its system prompt says when (CM-48 to CM-48b): when the user sets a standing constraint, when it abandons an approach, chooses a method or a scope, gets a result, relies on something unproven, finds two sources or results that disagree, or fails at an attempt, and before it marks a plan step done.
- CM-15. **Folds propose updates** (new). Each fold's enrichment call (CM-19) also proposes research-state updates for its span, as typed operations:
  - a new issue: a question, a hypothesis or a contradiction that the span shows and the ledger lacks;
  - a decision that the span shows made but that nobody recorded: an approach abandoned, to be recorded `rejected` with its reason and reopen condition, or a method or scope chosen;
  - a work record on an existing issue, claim or result: what was tried, and how it ended;
  - a caveat on an existing claim or result;
  - an assumption the span relied on, with the entries that rely on it.

  Each proposal names its basis and its anchors, which lie in the span. Code validates each one: its form; that the handles it names exist; that its anchors lie in the span and pass CM-9's checks; that its numbers and identifiers occur in the span (CM-20); and that its text holds no hidden character (`check_agent_text`). It keeps the valid ones, at most 20 per fold, as the fold's proposals, recorded as agent-proposed. Nothing is written to the ledger. A session holds at most 50 waiting proposals, as project memory holds at most 50 (PM-3); a fold that would pass that keeps none of its own and records how many it dropped, which a later fold may propose again. A proposal waits, shown in the digest, until the main agent or the user accepts it or dismisses it with a reason. The main agent accepts proposals with one tool call, as it imports a results file (LG-41), with its own authority: a status that needs a decision still needs one, and the gate still applies. Accepting is idempotent: it names the proposal and an operation ID, and accepting again returns the first result and creates nothing (LG-31). The user accepts or dismisses them in the GUI. A fold's proposals change no entry and settle nothing (owner, 2026-10-15).
- CM-16. **The digest.** At every rebuild, code renders a digest of the research state into the main run's state block (CM-26). Its sections, in order, with their shares of the digest's budget:

  | Section | Share |
  | --- | --- |
  | 1. The session plan: its goal and version, each step's status and note, and the current step | 10% |
  | 2. Decisions: first the user's standing constraints, which are decisions in effect with the basis `user` or `user_quoted`, the project's and this session's (CM-10). Beside each `user_quoted` one, code copies the verified quote from the user's message, with its ID, so that the user's words stand next to the agent's statement of them. Then rejected and reversed decisions, and decisions in effect that exclude an approach or a scope, which stop repeated work; then the others in effect, and proposed ones. Each with its handle, statement, status, reason, reopen condition and any open flag | 30% |
  | 3. Open questions and hypotheses, and open contradictions with what they concern | 10% |
  | 4. Active assumptions, each with the entries that rely on it, and their open flags | 10% |
  | 5. Findings: claims and results with their status, evidence types, scope notes and caveats; then attempts that did not succeed, unsettled obstructions and negative results, and settled impossibilities with their scope and assumptions, each under its own label (CM-11) | 20% |
  | 6. Sources: references with their read extents (CM-12) | 5% |
  | 7. The session's open items, by ID with one line each: unresolved review findings addressed to it, jobs and delegations still running, questions to the user not yet answered, and approvals its tool results said it waits for (`approval_required`) | 5% |
  | 8. Fold proposals waiting (CM-15) | 5% |
  | 9. An index of delegation outcomes and recorded artifacts: IDs and titles only | 5% |

  A section's unused share passes to the sections after it, in order, and what is left at the end goes to decisions. Every line ends with its basis (`[user]`, `[user, quoted]`, `[observed]`, `[interpreted]`) and the handles and archive IDs to retrieve it with (`ledger_read`, `history_read`). Within a section, the entries the session touched come first, then the most recently changed and the most linked. A section over its share ends with a line saying how many entries it left out and how to list them. A current decision, caveat or incomplete read of this session's folded work that its section leaves out is shown in the fold region instead (CM-21b). The main run's digest is project-wide, since the ledger is (LG-3); delegated runs get what CM-37a gives them.

### Layer 3: folds

- CM-17. **A fold record** holds (CScience; new where marked):
  - a span header: the first and last archive positions and IDs, the runs and the dates;
  - the skeleton, built by code (CM-18);
  - marker lines, built by code: each incomplete read, each caveat, each decision line and each aggregate of failed calls in the span, with its kind and its subject: the entry's handle, the source, or the tool (CM-18) (new);
  - the narrative, written by the enrichment call (CM-19);
  - search keys: literal strings that occur in the span (CM-20);
  - its level: 1 for a fold of raw messages, and for an overview one more than the highest level among its parts; and its size in tokens.

  The record is archived (CM-3) as it was built, its marker lines whole, and is never changed afterwards. What the view shows of it is rendered from the stored record at each rebuild (CM-21b), in place of its span. The span's messages stay in the archive.
- CM-18. **The skeleton** (CScience's design, with this platform's own record lines and budgets). Code builds a chronological, labelled outline of the span. Each item has a budget in tokens:

  | Item | In the skeleton | Budget |
  | --- | --- | --- |
  | A user message | Its ID and first words; its text is in the state block (CM-26) | 60, never squeezed |
  | Assistant text, progress-update text included | Its head and tail | 120 |
  | A tool call and its result | The tool, its key arguments, the outcome (state and exit code), the output's size and the message ID; the result's text only when there is room | 80, and up to 200 of the result |
  | A ledger, plan or memory change | One line: the handle, the change and its reason, such as `D-4 → rejected: needs assumption Y (REF-2 p. 7); reopen if I-14 resolves` | Whole |
  | A delegation outcome | Its verdict, status, ID and the head of its summary | 150 |
  | A retrieval (CM-33, CM-34) | The query or the IDs read, and the IDs returned | 60 |
  | A notice | Its source and IDs | 30 |
  | A file written | Its path and revision | 30 |

  Code builds the marker lines from the records, never from model text, in three tiers (CM-21b):
  - **decision lines**: each decision change in the span, with its reason and reopen condition;
  - **caveats and incomplete reads**: an evidence scope note; evidence of type `finite_test` or `numerical_experiment`; a caveat line (CM-10); a work record ending `limit` or `obstruction_claimed`; a check that ended `inconclusive`; and a source the span read only in part, or a sample whose saved file the span never read whole, with its path and extent (CM-12);
  - **failure aggregates**: the failed and timed-out calls of one tool in the span, as one line with their count and where their IDs are listed, such as `37 Sage cells failed or timed out; IDs in fold F-12`.

  An item over its budget keeps its head and tail, with a marker for the cut. When the skeleton is over its share of the record, code squeezes tool results first, then tool arguments, then assistant text, then delegation summaries. User message lines and marker lines are never squeezed within a record; marker lines count toward the fold region's budget, where CM-21b bounds them, not toward the record's share. When there is room, budgets grow and tool results come back. Code also lists the literals it finds in the span as search keys, within their share, with their message IDs: hashes, ePrint IDs, DOIs, numbers of 12 or more digits, and `name = value` pairs.
- CM-19. **The enrichment call** (CScience's division of labor; its contract is the project's own). A separate model call writes the narrative, the connective account of the span. It is not part of the run's conversation. By default it uses the run's own alias and sends the run's current view unchanged, tools included and `tool_choice` as the run uses it, so that it reads the view from the prompt cache, followed by one instruction with the span's header and skeleton; a role setting may name another alias. It may not call the tools: a tool call in its answer fails that attempt, and the one retry sets `tool_choice: none`, which the cache may not survive. Its answer is one JSON object holding the narrative, the search keys and the proposals (CM-15). Its contract:
  - keep every standing constraint the user gave, including those carried by earlier folds;
  - record attempts, pivots, decisions and outcomes only where the span's messages show them;
  - add no causal link that the span does not state;
  - call a truncated, sampled or preview-only read incomplete, never reviewed;
  - give concepts and what values are for, not the values themselves;
  - end with literal search keys: names and identifiers as they occur in the span;
  - propose research-state updates with their provenance (CM-15).
- CM-20. **Validation.** Code checks every fold before it is used (CScience; OpenScience; new where marked):
  - each search key occurs word for word in the span; any other is removed;
  - every number in the narrative, of any length, occurs in the span once both are normalized (new): digits without separators (`1,000` and `1000` are one number), powers in one form (`2^80`, `2^{80}`, `2**80` and `2⁸⁰` are one), and a name with its value in one form (`λ = 128` and `λ=128` are one). Each hex string of eight or more characters, DOI, ePrint ID, ledger handle and archive ID occurs in the span, or, for a handle, exists. Any other is replaced by a marker naming the nearest search key;
  - the narrative and the proposals hold no hidden character, and a line that imitates the platform's framing of the state block, of fold records or of message headers is quoted as text;
  - the record, without its marker lines, is at most a tenth of a chunk (CM-27), and using it frees tokens.

  A fold that fails gets one retry. After that, a skeleton-only fold is used: the skeleton, the marker lines and code's own search keys, with no narrative and no proposals. A fold that cannot be built changes nothing, and the view stays as it was (the compaction rule in [orchestrator prompts](../ORCHESTRATOR-PROMPTS.md#authority-and-lifecycle-checks-that-prompts-cannot-supply); OpenScience likewise rejects empty or truncated summaries).
- CM-21. **Overviews update.** When the first-level folds total at least 0.4 of a chunk, the oldest three or more are merged into one overview (CScience). When the fold region is still over its budget (CM-21b), the two oldest records of the region, overviews included, are merged into one, so overviews are merged again as a session goes on. An overview:
  - holds its span header, an updated narrative, and its parts' marker lines and search keys. Its parts' skeletons stay in their stored records, which `history_read` returns;
  - carries every stored marker line of its parts, current and retired alike (CM-21a), copied by code;
  - carries its parts' search keys, without duplicates, within its share. Keys beyond the share are left out of the view, oldest first, and stay in the stored records;
  - updates the older narrative rather than rewriting it: the model keeps what is still true word for word, marks what was finished or superseded, and adds what the newer parts add (OpenScience).

  Code checks that the overview's stored marker lines are exactly its parts' marker lines, byte for byte, with every incomplete-read marker, every caveat marker and every decision line with its reason. An overview that drops or changes one is rejected, and the folds stay as they were. The model never writes marker lines. What the view shows of them is decided when the view is rendered (CM-21b), never by changing a stored record.
- CM-21a. **Current and retired markers** (new). At each rebuild, code decides from the records whether each stored marker is current or retired. Nothing a model wrote enters the decision:

  | Marker | Current while | Retired when |
  | --- | --- | --- |
  | An incomplete read | the read register shows the source's extent short of `whole` | the register shows the source read `whole` later; the retirement names the message that completed the read |
  | A caveat from a ledger entry: a scope note, an evidence type or a caveat line | the entry's current revision still holds it, and the entry is not `superseded`, `withdrawn` or `refuted` | a later revision dropped or changed it, or the entry was set aside |
  | A work record ending `limit` or `obstruction_claimed` | its issue is `open`, and no assessment decided the claimed obstruction | the issue is resolved, obstructed, split or withdrawn, or an assessment decided the claim |
  | An inconclusive check | the entry keeps the material it checked, and no later check of it ended | the entry's statement, fields or evidence changed, or a later check ended |
  | A failure aggregate | it is in a first-level fold, and no later call of the same tool with the same arguments succeeded for every call it counts | such calls succeeded, or its fold was merged into an overview and no work record cites the calls |
  | A decision line | it is the newest change of its decision, and the decision is `proposed`, `in_effect` or `rejected` | a later change of the same decision exists, or the decision was `reversed`; the reversing decision's own line is then current |

  "Superseded" thus means that a later record concerns the same subject: a later read of the same source, a later revision of the same entry, a later identical call, a later change of the same decision. The rules compare IDs, handles, statuses and revisions, never text.
- CM-21b. **Rendering markers within a bound** (new). At each rebuild, code renders each fold record from its stored form, together with the new state block. A request's view holds until the next rebuild, so each request decides for itself:
  - a current marker is shown in its short form (its handle or source, and the words "in the state block") only when that view's state block holds the same information exactly: the same handle, status, reason and reopen condition for a decision; the same text for a caveat; the same source and extent for a read. Otherwise it is shown in full. When newer entries push an entry out of the digest, the next view therefore shows its marker in full again;
  - a retired marker is shown only as a line in its record's index of retired markers: its kind, its subject, what retired it, and the archive IDs of both, such as `read: REF-2 PDF pp. 1–3 of 21 → read whole later (msg-…, msg-…)`.

  The tiers bound what the fold region shows:
  - **decision lines** with their reasons are not squeezed, spilled or shortened, except to the short form when that request's state block holds them exactly, and, as the last step before a stop, to one short line each (step 5 below);
  - **failure aggregates** may be squeezed and spilled first;
  - **caveats and incomplete reads** take the short form when the digest shows their entry or source; otherwise they are shown in full until the region must spill them, lowest priority first.

  When the rendered fold region would pass its budget (CM-27), code reduces it in this order, stopping as soon as it fits:
  1. it merges records into overviews (CM-21), without a model call at the hard wall (CM-21c);
  2. it collapses each record's index of retired markers into one count per kind, oldest records first;
  3. it spills, oldest records first, retired markers and failure aggregates into a spill record in the archive, which one pointer line replaces, such as `spilled: 212 retired markers and 4 failure aggregates of F-1 to F-9 → history_read spill-…`;
  4. it spills current caveats and incomplete reads that the digest does not show, lowest priority first, the pointer line listing their handles. Priority, highest first: those on entries that the current plan step or an open issue names; incomplete reads of sources that a ledger entry cites; then the rest, newest first;
  5. if current decision lines alone still pass the budget, the region may grow past it only while the steady state still allows a useful fold (CM-27: the system message and tools, the state block's budget, the region as grown, the raw floor and half a chunk stay under the trigger), so that decisions never crowd out the folding that would make room. Past that, the least relevant of this session's decisions (the lowest in the priority above, the oldest first) are shown as one short line each: the handle, the status, the first 100 characters of the reason, and a pointer (`ledger_read D-…`). The user's standing constraints are never shortened. A `fold` event records each step. If even the short lines do not fit, the run stops (CM-45, reason `research_state`).

  So every current decision of this session's folded work is shown, in the state block or in the fold region, in full until step 5 shortens the least relevant ones; every current caveat and incomplete read is too, until the region must spill some, which it records and names by handle. Decisions made in other sessions appear only in the digest, which may leave the least recent out with a count (CM-16). The stored records, the spill records, the ledger and the archive keep everything whole (CM-46).
- CM-21c. **A merge without a model call** (new). At the hard wall, and after a context error, there is no time for an enrichment call. Code then merges the oldest records into an overview of its own: their span headers joined, their marker lines and search keys copied as CM-21 says, and their narratives cut to their heads within the overview's share. The overview is marked as built by code; when the next fold's enrichment runs, it may rewrite that narrative as an update.
- CM-22. **The narrative is lossy.** Every narrative leaves things out, and an overview more so. The research state, the marker lines and the archive are what make reasons, caveats and values survive; the narrative only connects them. No requirement here relies on a narrative being complete.
- CM-23. **Where a span ends.** Never between a tool call and its result, nor between the calls of one assistant message and their results. A span takes the oldest messages of the raw tail, about a chunk's worth (CM-27). It ends at the boundary nearest to that size where a plan step changed or a user message arrived, when one lies within a quarter of a chunk, and at the nearest call boundary otherwise (SelfCompact's evidence favors task boundaries).
- CM-24. **When folds happen.** Code measures the view (CM-28) at every safe point:
  - past the fold trigger, it starts a fold of the oldest span, unless one is running. The enrichment call runs while the agent goes on, and the fold is applied at the first safe point after it is ready (CScience applies folds a call late the same way);
  - when a fold is applied, tool results in the raw tail that are older than the newest five and longer than 5,000 characters become stubs: the tool, its key arguments, the output's size, whether its saved file was read whole, and the message ID, which `history_read` returns whole (CScience clears old large tool output at the same moments). The user's and the agent's messages, notices, the newest five results, retrieval results (CM-35) and short results stay word for word. Stubs are made only at folds, so the view stays append-only between them;
  - past the hard wall, if a fold is running, the run waits for it, at most 10 minutes, and applies it, or a skeleton-only fold if it is not ready by then; if none is running, it applies a skeleton-only fold at once. It folds again, skeleton-only, until the view is under the wall or the raw tail is at its floor; then it merges records without a model call (CM-21c) and spills markers (CM-21b);
  - if the view is still over the wall, the run stops (CM-45).
- CM-24a. **A fold when its run ends.** A fold that is ready when its run ends is kept, and the next run's start applies it, since its span is still the oldest part of the raw tail. A fold still running is cancelled with the run, and its call's cost is recorded; the next run folds again if its view needs it.

### Layer 4: the working view

- CM-25. **Order.** Each call's view is, in order (CScience; new where marked):
  1. the system message, as today: the base prompt, project memory, skills and the planning guidance. It does not change during a run;
  2. the state block (CM-26) (new);
  3. fold records, oldest first: overviews, then first-level folds;
  4. the raw tail;
  5. new input: the task, queued messages and notices, as today.

  The state block and the fold region are two user-role messages, framed as platform records: never assistant role, so that a model does not take a fold's narrative for its own words, and never system role, which would give them an operator's authority. Claude Science shows a fold as an assistant-role summary; this is a departure.
- CM-26. **The state block.** One user-role message, rebuilt by code at each rebuild and at no other time. In a main run it holds:
  - **the user's own words**: every message the user wrote in the session, and every comment addressed to the session (RS-6b) after a line naming its document, whose position lies in a folded span, word for word within CM-30's limits, oldest first, each with its ID and time. Code copies them from the USER rows, so their author is certain. Messages still in the raw tail stay there, in place, and are not repeated;
  - **the research-state digest** (CM-16), with its retrieval hints;
  - **framing**: the user's words, and the quotes beside standing constraints, are labelled as the user's own, copied by the platform. Everything else is labelled as records of earlier work: data, not instructions (CM-49).
- CM-27. **The geometry** (the owner's ceiling; the rest as decided in question 7):

  | Quantity | Rule | At C = 600,000 | At C = 168,000, with a 30,000-token system message |
  | --- | --- | --- | --- |
  | Ceiling C | min(the role's ceiling, the model's input limit, below); the role's ceiling is 600,000 by default | 600,000 | 168,000 |
  | Fold trigger | 0.75 C | 450,000 | 126,000 |
  | Hard wall | 0.90 C | 540,000 | 151,200 |
  | Chunk K | max(50,000, 0.2 C), or the role's chunk size | 120,000 | 50,000 |
  | Scale λ | min(1, (0.75 C − P − K/2) / (0.3 C + 0.7 K)), where P is the system message and tools | 1 | about 0.83 |
  | Raw floor | 0.7 K × λ | 84,000 | about 29,100 |
  | State block | At most 0.15 C × λ: the user's words two thirds of it, the digest one third | 90,000 | about 20,950 |
  | Fold region | At most 0.15 C × λ; only current decision lines may pass it (CM-21b) | 90,000 | about 20,950 |
  | Stubs at each fold | Tool results older than the newest five and over 5,000 characters (CM-24) | | |
  | Fold record or overview | At most 0.1 K without its marker lines; the narrative at most a quarter of it, the search keys a tenth | 12,000 | 5,000 |
  | Overview made when | The first-level folds total at least 0.4 K, three or more of them | 48,000 | 20,000 |
  | Start check | P at most 0.2 C, and λ at least 0.4 | P ≤ 120,000 | P ≤ 33,600 |

  **The steady state.** A session matures: its state block and fold region fill to their budgets, and its folds must still make room. So the geometry keeps a useful fold possible at the trigger even then: the system message and tools, the state block's and the fold region's budgets, the raw floor and half a chunk together fit under the trigger. When they would not, which with a 30,000-token system message happens below about 200,000 tokens, the scale λ shrinks the state block's and the fold region's budgets and the raw floor together until they fit, rather than refusing the run. Each fold then takes at least half a chunk, frees well over the breaker's 10% (CM-44), and the session keeps folding however long it runs. A run whose λ would fall below 0.4, or whose system message and tools pass 0.2 C, does not start, and says which part failed: with so little room, folding cannot keep up.

  **The model's input limit.** The owner's rule caps the ceiling by the model's window less its maximum output. When the gateway's model information gives a window that input and output share, the limit is that window less the call's maximum output (the role's setting, or the model's maximum when the role sets none). When it gives an input limit that already excludes the output (LiteLLM's `max_input_tokens`, for a model whose input and output limits are separate), the limit is that figure, and the output is not subtracted again. Where the gateway says neither, the role's setting gives it. An unknown limit never turns folding off: C is then the role's ceiling, and a context error folds and retries (CM-43). OpenCode never compacts when it does not know the window, which is the failure this avoids.

  A fold takes the oldest K of the raw tail, or less when K would leave the raw tail below its floor. The floor counts the raw tail's messages as they stand before that fold's stubs: it bounds how much a fold takes, not what the stubs free. At the default, the model works with between about 0.4 C and 0.75 C of context between folds, most of it recent work word for word and the rest stubs of old bulky output.

  **Departures from Claude Science's geometry**, which this one scales from its small windows: the triggers are fractions of C, where Claude Science folds when its raw part passes about 85,000 tokens; the trigger is 0.75 C; the chunk and the floor keep its minimum of 50,000 and its ratio of 0.7, scaled by λ on small ceilings; the hard wall is its 0.9; stubbing at each fold follows its clearing of old large output, with this spec's own thresholds. Claude Science folds in pieces only on windows of 200,000 tokens or less, so nothing here has been run at 600,000. OpenScience caps its budget at a pricing-tier boundary when one exists, such as GPT's 272,000 tokens; this geometry does not, so GPT calls over that size pay the long-context rate ([Cost](#cost)).
- CM-28. **Counting tokens** (Codex's accounting, made precise):
  - **total input** is every token a call's input occupies, cached or not. Each adapter normalizes its provider's usage to it. Claude's Messages API reports `input_tokens` without the cache's tokens, so the total is `input_tokens` + `cache_read_input_tokens` + `cache_creation_input_tokens`. OpenAI's Responses API counts the cached tokens inside `input_tokens` (and breaks them out in `input_tokens_details.cached_tokens`), so the total is `input_tokens`. The chat-completions client (CM-41) takes `prompt_tokens` as the gateway reports it; the first lab round checks that figure against the native counts for both families (CM-F31);
  - **between rebuilds**, the view's size is the last call's total input, plus an estimate of what was added since: the call's answer as it will be sent back, the tool results and the new input. A native item whose size its text does not show, such as encrypted reasoning or signed thinking that will be replayed, counts as the output tokens the provider reported for it; the rest counts as its characters divided by the characters per token of the session's recent calls on that model, or 4 until there are any;
  - **after a rebuild** (a fold, a run's start or a change of model), the baseline resets: the size is a fresh estimate of the whole new view, part by part, never the old count carried forward. The first call after it reports the true total, which becomes the new baseline. Without the reset, the view just folded would still measure as before the fold, and would fold again at once.
- CM-29. **The view spans the session** (new; replaces RS-10). A new run starts from the session's view: the system message, a rebuilt state block, the folds, the raw tail, which now holds the end of earlier runs with their tool calls and results, and the new task. It folds as any run does (question 1).
- CM-29a. **Which messages the main view holds** (new). The main view holds the main runs' messages, and delegation outcomes as their parent received them (handback notices and wait results). It never holds a delegated run's own messages, which the archive keeps and the main run may search (CM-33). An interrupted run's messages stay in the view in their place, the message it was answering among them. When RS-12 delivers that message again, the new run's task does not repeat its text: it is a platform line that names the message's ID, says that the run that first received it was interrupted, and asks for an answer. The text stays where it first appeared, or in the state block once folded. Before any adapter renders the view, code normalizes it for every adapter, not only GPT's (Codex): a tool call without a result, as an interrupted run leaves, gets a synthetic result saying it was aborted; a result without its call is left out; calls and results are removed in pairs.
- CM-29b. **Skills in the view.** A skill body that the view still holds counts as loaded, whichever run loaded it: loading it again returns the short note (SK-12). When a fold or a stub takes a body out of the view, the harness records it, and the next load returns the body whole (SK-12). The skills a discovery notice skips as already shown or loaded (SK-35), and the 100,000 characters of bodies a run may hold (SK-39), count what the view holds, not what one run loaded.
- CM-29c. **Earlier runs' kernels.** The raw tail can hold cells of earlier runs whose kernel has since restarted, so that their variables are gone. At a run's start, code puts a line before each earlier run's part of the raw tail, naming the kernels its cells used and whether each is still the one running, from the worker's records of kernel starts ([kernel revisions](../KERNEL-REVISIONS.md)). The lines are added only at that rebuild, and the cells stay as they were.
- CM-30. **The user's words and their budget.** The user's folded messages fit in their share of the state block. One message takes at most a quarter of that share; a longer one shows its head and tail, with a marker for the cut and a pointer to the whole, so that one pasted 64 KiB message cannot fill the share at C = 168,000. When the messages do not fit, the oldest become one-line pointers: the message's ID, time, length and first words, which `history_read` returns whole. A message that a standing constraint anchors (a decision in effect with the basis `user_quoted`, CM-16) becomes a pointer only after every other message has, and its pointer names that decision, which the digest shows first, with the user's quote beside it. The newest folded message is never a pointer. This changes RS-10's rule that the user's messages are never cut (question 2).
- CM-31. **Switching models.** When a session's next call is on another model, the raw tail is sent in the new provider's format, native items following CM-42, and the folds and the state block carry over unchanged. When the new model's ceiling is smaller, the whole view is first refitted to the new geometry: the state block to its new budget, the fold region by merges and spills, and the raw tail by folds and stubs, until the view is under the new trigger. The old model writes the narratives (Codex compacts with the old model when the new window is smaller); when the old model is not available, the folds are skeleton-only and the merges are built by code. If the refitted view would still be irreducible under the new model (CM-45), the switch is refused with the reason, and the session stays on the old model if it can.
- CM-32. **The prompt cache.** Between rebuilds the view only grows at its end, so each call reads the earlier part from the provider's cache. At a rebuild the state block, the fold region and the stubs change, so the next call writes the cache again from the state block on; the system message and tools stay cached. The Claude adapter marks cache breakpoints after the system message, after the fold region and on the last message. A run that waits longer than the cache's lifetime (five minutes by default on Claude) pays the full input price once when it resumes. The enrichment call reads the run's cached view (CM-19).

### Layer 5: retrieval

- CM-33. **`history_search(query, scope, from, to, kind)`** (CScience's ranking; OpenScience's `recall` as a reference):
  - scope: `session` by default, `run`, or `project` for the project's other sessions; never another project. A main run's `session` scope includes its delegated runs' messages, each labelled with its run;
  - matching: words and quoted phrases ranked by BM25, with a bonus when the trigram index finds the exact substring (CM-7);
  - each hit gives the message ID, position, run, role, tool, score and a snippet of about 400 characters. It returns 10 hits by default, at most 30;
  - diagnostics: the scope searched, the index's coverage (CM-7) and the total number of hits. With no hits it says "no match in this scope", never that something does not exist, and suggests other words, a substring or a wider scope;
  - results are framed as untrusted data, each naming its session and run (CM-49).
- CM-34. **`history_read(message or range, offset)`** returns whole content: a message, a tool result whole, a stored fold or spill record, or the saved file behind a sample, in pages of at most 20,000 characters (the tool output budget the ledger's tools use), with where the next page starts. A range of positions returns its messages in order.
- CM-35. **Retrieval stays.** A retrieval result in the raw tail is never stubbed (CM-24), and its skeleton line names the IDs it returned.
- CM-36. **Cues.** The state block's lines and the fold records carry handles, archive IDs and search keys, which tell the agent what to retrieve. A search key such as `twist order` leads `history_search("twist order")` to the tool output holding the 135-digit group order computed on day 1.
- CM-37. **Delegated runs.** A delegated run folds within its own run, with the delegated role's settings (PD-27). Its state block holds what CM-37a says, never the main run's digest. Its retrieval tools read only its own run: a check must not read its parent's reasoning, which could carry the verdict (LG-17; question 8). Today a delegated run's token limit, at most 400,000 tokens over all its calls (PD-38), ends it long before its view nears the ceiling, so its folds matter only once those limits rise.
- CM-37a. **What a delegated run's state block holds** (new). A delegated run starts with a fresh context (PD-13): its role's instructions, the brief, its track of the plan, its skills and the inputs the brief names, not its parent's transcript. Its state block keeps to that:
  - **a check** gets no digest at all. Its state block holds its brief, labelled as written by the platform (LG-17), with the parent's note inside it, labelled as the requester's note, not evidence. Nothing else from the session or the ledger: no decisions, entries, findings, work records, earlier checks' outcomes, fold proposals or delegation outcomes. Its limits and jobs reach it as notices, as today;
  - **a task** gets its brief, labelled as the parent's; the user's standing constraints, the project's and its session's, each with the user's quote beside it (CM-16), since they are the user's instructions, not the parent's conclusions; the steps of its track with their statuses (PD-9); the entries its brief names; the entries and work records its own run made; and its running jobs. Not the rest of the project-wide digest, since a task may assess a claimed obstruction, which LG-7 asks another agent to do;
  - neither gets the user's messages: the user writes to the root only (PD-41).

  This closes the view's path by which a checker could see its parent's conclusion or an earlier check's outcome. What a check may read with its own ledger tools is LG-13's and PD-34's rule, which a later change will narrow (question 10).

### Layer 6: model adapters

- CM-38. **Claude through `/v1/messages`** ([D61](../DECISIONS.md), amended):
  - each response's content blocks are archived byte for byte (CM-5);
  - on the models whose documentation offers it (Claude Fable 5 and 5.1, Mythos 5.1, Opus 5.5 and Sonnet 5.5), requests set `thinking: {type: "adaptive", display: "updates"}`, with the beta header `thinking-display-updates-2026-08-18`. Under the default `display: "omitted"`, those models return their text between tool calls as progress-update thinking blocks with empty text, so the agent's own account of its work would be lost. With `updates` it comes back as short notes, which the archive keeps and indexes as the assistant's text (CM-38a). On other Claude models the adapter asks for `display: "summarized"`, and archives and indexes the summary without rendering it into the conversation. Whether LiteLLM 1.102.1 passes the beta header and the setting through is not verified; the first lab round confirms it (CM-F31);
  - between rebuilds the history is append-only, and the run's thinking blocks are sent back unchanged, when replay is on (CM-39);
  - at a rebuild, no thinking block from the history is sent, and the model thinks again. Removing all thinking is valid; changing or removing a block in the middle is not (Anthropic's rule binding thinking to the history before it; CScience strips thinking the same way when it rewrites history);
  - tools added during a run, such as connector tools loaded mid-run, are added without changing the request's tool list, which the binding rule treats as an edit: declared from the start with `defer_loading: true`, which keeps a tool out of the comparison until something references it, or appended as a `tool_addition` under the beta `mid-conversation-tool-changes-2026-07-01` (by reference) or `inline-tools-2026-09-15` (by value). A change the adapter cannot make that way is a rebuild;
  - `thinking.block_binding` with `prefix_mismatch_behavior: "error"`, and its beta header, are sent only when replay is on; then the response's `input_transformations` are logged. `drop_block` is only a temporary fallback, if the labs show the check firing;
  - no server-side compaction and no context editing (question 3).
- CM-38a. **The agent's progress notes stay in view** (new). Progress notes arrive inside thinking blocks, which are not always sent back: never with replay off, the default; not after a rebuild; and not on a switch to GPT. Whenever a thinking block is not sent, its progress text is sent instead as assistant text, in a text block marked as the agent's progress note, so the model still sees its own account of its work. The choice is made when the message is first sent back, and kept until the next rebuild, so the request's prefix stays stable; at a rebuild that drops thinking, the notes become text from then on. Only progress notes are rendered this way, never a summary of reasoning.
- CM-39. **Thinking replay is a deployment setting** (new). The owner's gateway runs LiteLLM 1.102.1, which drops Claude's signed thinking blocks whose visible text is empty; the newest Claude models return such blocks by default. The two fixes (commits `897bfea38d` and `f470e418ea`) are only in development builds (`v1.107.0-dev.3`), not in a stable release or the 1.106.0 release candidates. The version header cannot tell them apart: `x-litellm-version` reads 1.107.0 on dev.1 and dev.2, which lack the fixes. So:
  - replay is on only when the deployment's setting turns it on. The setting records the gateway image it was verified on (its digest, as the operator deployed it), the version string that image reports, the date, and the ID of the CM-F30 run that passed against it. By default replay is off, and the Claude adapter sends no thinking block from the history;
  - the platform cannot see the image, only the version header. So any change to the gateway, even one that keeps the version string, needs CM-F30 run again before replay may stay on: the operator re-runs it and updates the setting. Replay also turns itself off 30 days after the setting's date, until the fixture is run again;
  - each call records the `x-litellm-version` header, or unknown when it is missing, and the run record keeps it. A call that reports another string than the setting names (a release candidate, another build, or a version that changes during the run) turns replay off for the rest of the run, recorded with both strings;
  - LiteLLM may answer a thinking-related 400 by stripping all thinking and retrying, which would hide a binding error. The platform catches it in two ways. The conformance fixture sends a deliberately edited history, which must fail with the binding error rather than succeed. And each replaying call's reported total input is compared with the platform's estimate of the request, replayed thinking included (CM-28): a call whose reported input falls short by about the replayed thinking's size is recorded as thinking dropped by the gateway, and replay turns off for the rest of the run.

  The fold design and the GPT adapter do not wait for this. LiteLLM 1.102.1 also has none of LiteLLM's own clearing or compaction stand-ins, which this design does not use.
- CM-40. **GPT through `/v1/responses`** ([D61](../DECISIONS.md), amended):
  - requests set `store: false`, with which, by OpenAI's current documentation, encrypted reasoning comes back by default. They also send `include: ["reasoning.encrypted_content"]`, an older form of the same request, kept so that the request says so explicitly; the fixture checks it in the request (CM-F11), and the first lab round confirms that real responses through the gateway carry encrypted reasoning (CM-F31);
  - each output item is archived byte for byte: `encrypted_content`, `phase`, and the item IDs as the gateway rewrote them. They are replayed only through the same gateway;
  - between rebuilds, every reasoning item, function call and output since the last user message is sent back unchanged. In a platform run, that is the whole run;
  - at a rebuild, reasoning items before the fold boundary are dropped and those in the raw tail are kept. A reasoning item is kept or dropped together with the item that follows it, the call or message it led to. OpenAI does not document whether reasoning is bound to the history before it, as Claude's thinking is: a fixture and the labs test it. If replaying the tail's reasoning after a rebuild is refused or does worse, all reasoning is dropped at rebuilds, as on Claude;
  - calls and outputs are normalized as CM-29a says;
  - no compaction item (question 3), and never `truncation: "auto"`, which drops the oldest items silently.
- CM-41. **Other models.** An alias whose provider is neither keeps today's `/chat/completions` client, without reasoning replay, its messages normalized as CM-29a says. The adapter is chosen for each alias from the gateway's model information, or by a deployment setting.
- CM-42. **Native items and model switches.** Between Claude models, thinking blocks are sent as they are, when replay is on, and the API leaves out those the current model cannot read: stripping them would lose that reasoning for good when the session returns to the model that made them. Between providers, native items (thinking, reasoning, compaction items) are left out, and replayed only to the provider that made them; Claude's progress notes are sent as assistant text (CM-38a) (CM-31).

### Guards and limits

- CM-43. **Overflow.** A gateway context error starts a skeleton-only fold, with merges built by code if they are needed (CM-21c), and one retry of the call. A second context error in a row stops the run with `context_limit`, reason `overflow` (OpenScience; OpenCode's error classifier is a reference).
- CM-44. **Breaker.** After three folds in a run that each freed less than 10% of the view, the run folds no more (OpenScience). If the view then passes the hard wall, the run stops with `context_limit`, reason `breaker`. The steady state (CM-27) keeps a mature session's folds above that.
- CM-45. **Irreducible context.** If the system message, the state block, the fold region and the raw floor together still pass the hard wall after merging, stubbing, spilling and shortening (CM-21b, CM-24), the run stops with `context_limit` instead of looping (OpenCode's loop bugs). Its reason is `research_state` when current decision lines are what will not fit, and `irreducible` otherwise.

  A `research_state` stop is not a dead end. The run's record, its `stopped` event and the GUI tell the user that the session holds more current decisions than its view can show, which are the least relevant, and how to consolidate them, in the GUI or with the ledger command: record one decision that replaces several, reversing them with a reason that sums them up; or reverse decisions that no longer matter. Reversed decisions' lines retire (CM-21a). Until the user consolidates or raises the role's ceiling, the session's next run would stop the same way, so the service holds the session's queued messages with the reason `research_state`, as RS-9 holds them after failed runs, and queues them again when the ledger changes or the user resumes.
- CM-46. **Records and events.** Each fold is a run event of kind `fold` (RS-14): its ID, level and span, its state (`started`, `applied`, `skeleton_only`, `code_merge`, `failed` or `rejected`), the tokens it freed, the stubs it made, and why it failed. The run record keeps each call's view by its parts: the state block's archive ID, the fold record IDs, how each record was rendered (which markers were short, retired, spilled or shortened, CM-21b), the stubs, and the raw tail's first and last positions. What a call saw can therefore be rebuilt from the archive. Each wall wait (with how long it took), each spill, each growth of the fold region past its budget and each shortening of decisions is also a `fold` event, so the GUI and the labs see when the research state outgrows the view.
- CM-47. **Settings.** Per role (PD-27): the ceiling, the fold trigger and hard wall fractions, the chunk size, the stub threshold and the enrichment alias. The shares of the user's words, of the digest and of the digest's sections are deployment settings, and so is thinking replay with its verified gateway image (CM-39). Each run records the values it used, λ included (PD-29).

### Prompt rules

Written in the project's own words when built (new); each role's rules keep to its authority under LG-13.

- CM-48. **The main run's rules:**
  - when the user sets a standing constraint, such as "only attacks with memory below 2^64", record it as a decision in effect with the basis `user_quoted`, anchored on the user's words with a quote, so that it stays in view after the message is folded (CM-16, CM-30). Scope it to the session when the user meant it only for this session (CM-10);
  - when you abandon an approach, record a decision with its reason and its reopen condition, stating the condition as an open question when the ledger does not hold it yet, and a work record on its issue;
  - record an attempt that fails as a work record ending `limit`, saying what ran out. Call nothing impossible that the ledger has not settled (CM-11);
  - record what a finding rests on: its evidence type, scope and caveats. When two sources or results disagree, record a contradiction issue that concerns both;
  - give each record its basis and anchors (CM-9); cite recent messages by the IDs in their headers (CM-4a);
  - copy exact values from a search result, a read, a saved file or a ledger entry, never from a fold;
  - a search with no hits found nothing in that scope; it is not proof of absence. The MAIN prompt already says this of external sources; it now covers the archive too;
  - call a source read only as far as the read register shows (CM-12);
  - accept or dismiss the folds' proposals listed in the state block (CM-15).
- CM-48a. **A delegated task's rules.** Under LG-13 a task run creates entries only in their first status, adds work records and evidence, and changes no status. So: record an approach it abandons as a `proposed` decision to exclude that approach, with its reason and reopen condition, which the main agent or the user puts in effect or not; record failed attempts as work records ending `limit`; record findings as `proposed` claims with their caveats, and disagreements as contradiction issues; give each its basis and anchors; keep to the user's standing constraints in its state block; and copy values, search and judge reads as the main run's rules say.
- CM-48b. **A check's rules.** A check writes nothing to the ledger (PD-34). It puts what it found in its result instead: what it did not examine in its coverage, caveats and contradictions in its open questions, and a refutation's step, value or counterexample, each with the archive ID, PDF anchor or artifact it rests on. It copies values from its reads, and treats a search with no hits as no proof of absence.

### Authority of text

- CM-49. **Only the user's words carry the user's authority** (threat model, A3 and T2). In the view, only the user's messages and the comments addressed to the session, copied by code from USER rows, and the user's quotes that code copies beside standing constraints, are the user's words. Fold records, the digest's other lines, notices, search results and retrieved content are records and data, and are framed as such. No model can place text in the state block's user section, which code fills only from USER rows, by ID. An instruction-shaped string inside a tool result reaches fold records and search results only inside data framing, and a header-like line inside a message is escaped (CM-4a). Fold text and proposals are agent text: they are checked for hidden characters, and they authorize nothing.

  Injected text can persist. An agent may copy instruction-shaped text from a paper or a tool result into a ledger entry, which every later digest then shows, and `project`-scope search can carry it into other sessions. The mitigations:
  - digest lines, fold records and search results are framed as records and data, never instructions;
  - every digest line shows its basis, so an agent's record never reads as the user's;
  - agents' ledger text is checked for hidden characters (`check_agent_text`);
  - search results name their session and run;
  - the user sees every entry in the GUI and can withdraw it;
  - nothing in a record grants authority: policy, approvals and grants are enforced in code (threat model, A3).

  A persistent injected instruction can still steer the agent. The threat model rates that a lower concern (T2) and records it as a residual risk; CM-P5 probes it.

## Worked examples

### Day 3 at the default ceiling

Claude Opus 5.5 has a 1,000,000-token window and up to 128,000 tokens of output, so C = min(600,000, 872,000) = 600,000. With a 30,000-token system message λ is 1, and the fold trigger is 450,000, the hard wall 540,000, a chunk 120,000 and the raw floor 84,000.

Day 3, run 14. The request holds:

1. the system message and tools, 30,000 tokens;
2. the state block, 35,000 tokens: the user's folded messages, 15,000, among them "only attacks with memory below 2^64", and the digest, 20,000. The digest's first decision is that constraint, D-2 `[user, quoted]`, with the user's words beside it; among the rejected ones is `D-4 [rejected] index calculus for the target group: paper A needs assumption Y (REF-2 p. 7); reopen if I-14 resolves [interpreted] msg-…`;
3. one overview and three folds, 40,000 tokens, covering days 1 and 2;
4. a raw tail of 350,000 tokens, reaching back into run 12;
5. the new message.

That is about 455,000 tokens, past the trigger. A fold of the oldest 120,000 tokens of the raw tail starts, and the agent goes on. Two calls later the agent's work has added 10,000 tokens, the view is at 465,000, and the fold is ready. At that safe point it is applied:

| Change | Tokens |
| --- | --- |
| The view before the fold | 465,000 |
| The span leaves the raw tail | − 120,000 |
| The new fold record joins the fold region | + 10,000 |
| The span's user messages move into the state block; they were part of the 120,000 | + 2,000 |
| 36 tool results older than the newest five, each over 5,000 characters and 100,000 tokens in all, become stubs of about 60 tokens each | − 98,000 |
| The rebuilt digest, the same size; no thinking is dropped, since replay is off by default (CM-39) | 0 |
| The view after the fold | 259,000 |

The size after the fold is a fresh estimate of the new view, not the old count carried forward (CM-28), so nothing folds again until the view passes 450,000, about 190,000 tokens of work later. The first-level folds now total 38,000 tokens, under the 48,000 that starts an overview.

The agent needs the 135-digit group order it computed on day 1. The overview's search keys include `twist order`. `history_search("twist order")` returns the tool result's ID, and `history_read` returns the whole output, from which the agent copies the number. If the agent starts to propose index calculus again, D-4 with its reason and its reopen condition is already in front of it. While the digest shows D-4, the overview shows D-4's marker in its short form. On day 5, newer decisions push D-4 out of the digest's share; from that rebuild on, the overview shows D-4's marker in full again, so the reason stays in view (CM-21b). On day 2 the agent had read only pages 1–3 of paper A; that marker stays current until the read register shows the paper read whole, and then becomes one line in the overview's index of retired markers (CM-21a).

### Day 10 at the default ceiling: a mature session

By day 10 the state block (85,000) and the fold region (88,000) are near their budgets of 90,000 each. At the trigger, the raw tail holds 450,000 − 30,000 − 85,000 − 88,000 = 247,000 tokens, so a full chunk of 120,000 still leaves 127,000, above the floor.

| Change | Tokens |
| --- | --- |
| The view before the fold, after two more calls of work | 460,000 |
| The span leaves the raw tail | − 120,000 |
| The new fold record | + 10,000 |
| The region passes its 90,000: the three oldest first-level folds are merged into an overview | − 10,000 |
| The span's user messages move into the state block | + 2,000 |
| 20 old tool results over 5,000 characters, 55,000 tokens in all, become stubs | − 53,800 |
| The view after the fold | 288,200 |

The fold freed more than a third of the view, and the next comes about 160,000 tokens of work later. The model now works with about 0.48 C to 0.75 C between folds.

### A smaller window, mature

A model with a 200,000-token window shared by input and output, run with 32,000 tokens of maximum output, has an input limit of 168,000, so C = 168,000. With a 30,000-token system message and tools, the steady state does not fit at full budgets (30,000 + 25,200 + 25,200 + 35,000 + 25,000 = 140,400, over the 126,000 trigger), so λ = (126,000 − 30,000 − 25,000) / (50,400 + 35,000), about 0.83. The state block and the fold region get about 20,950 tokens each, the raw floor about 29,100; the trigger stays 126,000, the wall 151,200 and a chunk 50,000. The start check holds: 30,000 is under 0.2 C (33,600), and λ is over 0.4.

A mature session, its state block at 20,000 and its fold region at 20,500:

| Change | Tokens |
| --- | --- |
| The view before the fold: system message and tools 30,000, state block 20,000, folds 20,500, raw tail 60,500 | 131,000 |
| The span leaves the raw tail: 31,400, since a full chunk would leave the raw tail under its floor; at least half a chunk, as the steady state promises | − 31,400 |
| The new fold record | + 2,500 |
| The region passes its budget: an overview merge | − 2,500 |
| The span's user messages move into the state block | + 500 |
| 3 old tool results over 5,000 characters, 8,000 tokens in all, become stubs | − 7,800 |
| The view after the fold | 92,300 |

The fold freed about 30% of the view, far above the breaker's 10%, and the next comes about 34,000 tokens later. Without λ, the same session would have only about 10,600 tokens above its floor at the trigger, and its folds would stall at the wall.

## Cost

The owner does not treat cost as a driver. In plain terms, at the prices published on 2026-10-15, per million tokens:

- **Claude Opus 5.5:** $4 input, $5 to write the cache, $0.20 to read it, $20 output, with no long-context surcharge. A 600,000-token request costs about $2.40 uncached, $3.00 when it writes the cache, and $0.12 when it is read from the cache.
- **GPT-5.5** (a 1,050,000-token window), for requests over 272,000 input tokens: $10 input and $1 cached, twice its rate below that size. A 600,000-token request costs about $6.00 uncached and $0.60 cached. **GPT-5.6 Sol**, over 272,000 tokens: $8 input, $10 to write the cache, $0.80 cached, so a 600,000-token request costs $4.80 uncached, $6.00 when it writes the cache, and $0.48 cached.
- **Between folds**, nearly all of each call is read from the cache. A call near the trigger, at 450,000 tokens, costs about $0.14 of input on Opus 5.5 (440,000 read and 10,000 written) and about $0.54 on GPT-5.5, plus its output.
- **A fold** adds the enrichment call, which reads the run's cached view once more (about $0.09 on Opus 5.5 and $0.45 on GPT-5.5 at 450,000) plus its output. It also makes the next call write the cache again for everything after the system message: about 230,000 tokens in the day-3 example, about $1.15 on Opus 5.5 and on GPT-5.5, whose request is then under 272,000 tokens and at the lower rate.
- Before each fold, requests reach four to five times today's 100,000-token limit, and cost that much more per call. OpenScience keeps its requests under a pricing-tier boundary; this geometry does not (CM-27). The gateway reports what each call actually cost (RS-6a).

## Contracts used

- `Anchor`: transcript anchors ([addition 3](README.md#proposed-contract-additions-new), approved) name archive messages and tool results, with an optional quote or output range, for provenance (CM-9) and pointers.
- `Mutation`: the ledger's changes gain the basis and anchors, issue kinds, reopen conditions, `reopen_on` links, caveats and a decision's session scope (CM-10). A fold's proposals are mutations as LG-30 gives them, imported as LG-41 imports a results file.
- `Event`: the run event `fold` (CM-46); `context_limit` keeps its reason.
- `RunRecord`: each call's view by its parts and how its fold records were rendered, each call's total input as normalized (CM-28), the gateway's version, whether thinking replay was on and why not, and the context settings used, λ included (CM-39, CM-46, CM-47).
- Fold records and spill records are stored once and never changed: their marker lines whole, each with its kind and subject (CM-17). Whether a marker is current or retired is computed at each rebuild, never stored in the record (CM-21a).
- The control store gains tables for the archive and its two indexes, fold records, spill records, fold proposals and the read register, each in one migration step.

## As built

Step (a) is built (2026-10-16; `orchestrator/history`, control store version 46): the archive (CM-3 to CM-7, CM-4a) and the history tools (CM-33, CM-34). How it reads the requirements where they leave a choice:

- **Writing** (CM-3, CM-4). The loop hands each message it adds to the run's message log (`hooks.MessageLog`), which archives it, one change each, before the next model call. A write that finds the control store busy is tried again, waiting longer each time, for about a minute (a busy change wrote nothing); any other failed write fails the run. Delegated runs archive into their session too, naming their parent run. The kinds are `task`, `user` (the user's chat messages, each naming its chat message ID), `comment` (the work requests' notices), `notice`, `outcome` (delegation handbacks), `assistant` and `tool_result`; a task names the chat messages it stands for, if any. State blocks and fold records come with their steps. The earlier conversation that RS-10 gives a run, until the session view replaces it, is not archived again: it copies earlier runs' messages.
- **Headers** (CM-4a). `[msg-… · kind]`, with the source of a notice or the tool of a result. The archive keeps each message's content as the run added it, and renders the header and the escaping each time it gives the message as it was sent, the same each time; changing either needs a new scheme, since the prompt cache and Claude's thinking bind to what was sent. A line gets a backslash before it when, read as compatibility characters (NFKC) without invisible formatting characters and with any dash taken for a hyphen, it begins with `[msg-` after any characters that are not letters or digits (spaces of any kind, quote markers, bullets, a backslash), however many, in any case and with spaces inside; every line break Python knows ends a line. Known limits: a combining mark on a letter of `msg`, or a letter from another script that looks like one, such as a Cyrillic em, is not caught. This holds for every message the platform writes, the user's included; the session's message row and the archive keep the user's text as written. A JSON result's strings hold no lines, so nothing in them is escaped.
- **Native payloads** (CM-5). The chat-completions client keeps its whole answer, as the format `chat_completions`, the Responses adapter, step (c), its whole response, as `responses`, and the Messages adapter, step (d), its whole response, as `messages`. Each call's `x-litellm-version` is in its usage in the run record and on the archived answer.
- **Files** (CM-6). A tool result links to its saved files and its recorded revisions. The archive keeps a saved file's text up to 1 MiB, with the artifact revision its call recorded it as (RA-27); a larger file is not kept, and its row names that revision to read instead.
- **Indexes** (CM-7). Two FTS5 tables hold no copy of the text (contentless), so SQLite cannot rebuild them from themselves: a rebuild deletes their rows and inserts each document of `archive_docs` again under its number, a saved file's kept text or a message's text. The control store checks for FTS5 and the trigram tokenizer whenever it is opened, so the run service, the command line and the workspace all refuse to start without them, saying which is missing. The retrievals' own calls and results are archived but not indexed: they copy what the indexes cover, and would answer every search with the searches made before it.
- **Search** (CM-33). Hits come in this order, each saying how it matched: texts that hold every word and quoted phrase of the query, ranked by BM25, those that also hold the whole query (case aside) before the others; then texts that hold the whole query inside longer words, such as part of a hash, newest first; and, when those are fewer than asked for, texts that hold any of the words, by BM25. The answer counts what each way of matching found. Ranking every word first keeps a query's own texts on top; any-word hits rescue questions worded unlike their answers. On an archive of labs 40 to 42's 1,031 messages, every word found nothing for 3 of 12 natural queries, and any word found relevant hits for 2 of those 3; for a common word, the top ten are BM25's top ten. `project` covers every session of the project, this one included. The coverage names the scope's messages and positions, the saved files indexed and those left out with why, and the scope's runs with no archived message, which ran before the archive existed.
- **Reads** (CM-34). Whole text as the run added it, in pages of at most 20,000 characters within the run's tool output budget; a range of at most 1,000 positions comes in pages by message and offset.
- **Delegated runs** (CM-37, question 8). Their history tools search and read their own run, whatever scope they ask for; another run's message reads as one that does not exist.
- **Prompt rules** (CM-48 to CM-48b, the archive's part). `sandbox-main-7`, `sandbox-delegated-task-5` and `sandbox-delegated-check-6`: cite messages by their headers' IDs, copy exact values from retrievals, and a search with no hit shows nothing absent.
- **What it leaves to later steps.** A held message that RS-12 delivers again is archived twice, once by each run that received it; the session view (e1) shows it once, where it first appeared, as CM-29a says. Runs recorded before the archive existed have no archived messages, and the history tools' coverage counts them. A backfill from their saved records could archive their messages, though not as they were sent (no headers, no native payloads, no saved files beyond what the records hold); it is not built. The session view (e1) reads the user's words from those records instead.
- **Token accounting** (CM-28; step (e1), 2026-10-16). `tokens.py` normalizes each API's usage to total input: Claude's `input_tokens` with both cache counts, the Responses API's `input_tokens`, and the chat-completions client's `prompt_tokens`, which it uses. A view's size before a call is a fresh estimate until a call reports, then that call's input and output tokens and what was added since, at the characters per token of the session's last calls on the run's alias (4 until there are any). Each main run's record keeps, under `summaries.view`, its view's parts at the start and each call's estimate beside the input the gateway reported. Until folds are built, the run's context limit is still in characters (`--max-input-chars`).
- **The session view** (CM-25, CM-29, CM-29a; step (e1)). Every main run with the project's stores, from the run service and from the command line, starts from its session's view, built by the harness from the archive: the main runs' messages as they were sent, the outcomes they received among them, never a delegated run's own messages or an earlier state block. It replaces RS-10's earlier conversation. Each call is followed by its result, found by its call ID among its own run's later results, whatever came between them in the archive; a call without a result gets one saying it was aborted, a result no call claims is left out, and calls and results stay together. A chat message the view already holds, as one an interrupted run received, is not given again: the run gets a notice naming it (`sandbox-notice-redelivered-1`), and its delivery is acknowledged as the message's own. Runs from before the archive have no messages in it; the state block counts them, and holds the user's words from their saved records (below).
- **Until folds** (step (f1)). A view that would pass half of the run's input (`--max-input-chars`) leaves out its oldest messages at a boundary that splits no call from its results, newest kept. Its newest unit (a message, or an answer with its calls' results) is kept even when it alone passes that room, and so is the user's latest message, a chat message or a task, when it falls before the messages kept; the block then names it as kept. It then begins with a state block (`sandbox-state-block-1`), archived as a message of the kind `state_block` that later views and the indexes leave out. The block names the positions left out and holds the user's own words from them within a tenth of the input: the user's messages, the comments addressed to the session after a line naming their document, and the tasks, but the stand-in task of a run started for comments, oldest first, each with its ID and time; one longer than a quarter of that share as its head and tail; the oldest, past it, as one line each with its length and first words, never the newest; and when even those lines pass it, the oldest of them as one line naming how many and the first and last IDs, which the history tools find. With about 2,000 of the user's messages left out, the words stay within their tenth. Runs from before the archive come first: their tasks and the chat messages they delivered, as their saved records keep them, under each run's name (RS-10's earlier conversation, as far as the user's words go; the comments they delivered are not included). This is the fallback rather than a backfill: a backfill would place those runs after the archived ones and would have to run once per session. The block has no digest until step (e2), and a constraint's message is not kept from becoming a pointer until the ledger records constraints (steps (b1), (b2), (e2)). A run whose view still does not fit stops with `context_limit`, as before.
- **Skills and kernels** (CM-29b, CM-29c; step (e1)). The skill bodies the view holds count as loaded, whichever run loaded them, and toward the run's 100,000 characters; the skills its discovery notices showed are not shown again. A body or notice the view leaves out counts for nothing. Before each earlier run's part that ran cells, a line (`sandbox-kernel-lines-1`) names the kernels its cells used and whether each runs now, from the worker's existing-connection observation, or unknown when it cannot say. These lines are not archived; the run's record keeps the view's parts and the lines' text (`summaries.view.kernel_lines`, CM-46). The state block's write waits for a busy control store as a run's archive writes do.

With replay on, its thinking blocks go back unchanged while the request before it, as it is rendered now, has the answer's `prefix`, whether the answer is the run's own or rebuilt from the archive. - *Then* every original message, the interrupted run's included, reads whole by its ID with `history_read`; every request stays under C; folds are contiguous and never overlap; each call's view rebuilds from the archive as the record names it. Each appended message begins with its full ID header, and a tool output line that begins like a header is escaped. A service whose SQLite lacks FTS5 or the trigram tokenizer does not start.

**CM-F2 The user's words survive** (CM-26, CM-30)
- *Given* a constraint in run 1's first message, and 20 runs.
- *Then* the constraint is byte for byte in every request after every fold, in the raw tail or in the state block. With the user's words over their budget, the oldest become pointers that `history_read` returns whole, and the newest folded message is never a pointer. A 64 KiB message at C = 168,000 shows its head and tail within a quarter of the share.

**CM-F3 The research state survives, and changes only at rebuilds** (CM-16, CM-26)
- *Given* decision D-4, rejected in run 2 with a reason and a reopen condition.
- *Then* D-4, its reason and its reopen condition are in the state block of every later request. A change to D-4 appears at the next rebuild, never between rebuilds. Each digest section stays within its share, unused shares passing on as CM-16 says.

**CM-F4 Exact values** (CM-7, CM-20, CM-33, CM-34)
- *Given* the 12 values the earlier evaluation planted (64-hex-digit hashes and numbers of 30 or more digits), one of them past the sample, only in the saved file.
- *Then* all 12 are found by value, by a substring of 12 characters, and by words near them; `history_read` returns each whole output and the saved file. No fold's narrative holds a number or identifier missing from its span: a wrong number planted in the scripted narrative, of two digits and of 30, and one written `2**81` where the span says `2^80`, are each replaced by a marker naming a search key, while `2^{80}` for `2^80` passes.

**CM-F5 A failed fold changes nothing** (CM-19, CM-20, CM-44)
- *When* the enrichment call fails, answers empty, answers too large, or calls a tool.
- *Then* the view is unchanged; one retry follows, with `tool_choice: none` after a tool call, then a skeleton-only fold. After three folds that each free less than 10%, the run folds no more.

**CM-F6 The geometry** (CM-24, CM-27, CM-44)
- *Given* C = 600,000 and a 30,000-token system message.
- *Then* nothing folds below 450,000. Past it, a fold of about 120,000 tokens starts at a boundary that splits no tool call, and is applied at the next safe point. A fold never leaves less than 84,000 tokens of messages unfolded, counted before stubs. Tool results older than the newest five and over 5,000 characters become stubs, retrieval results never, and `history_read` returns each whole. Past 540,000 with a fold running, the run waits for it, at most 10 minutes, and applies it, or a skeleton-only fold if it is not ready by then; with none running, it applies a skeleton-only fold at once.
- *And* with a 200,000-token shared window and 32,000 of output, C is 168,000, the trigger 126,000 and the chunk 50,000. With an input limit that already excludes the output, the output is not subtracted again. With no limit known, C is the role's ceiling, and a context error folds.
- *And* the steady state: at C = 168,000 with 30,000 tokens of system message and tools, λ is about 0.83, the state block's and the fold region's budgets about 20,950 and the floor about 29,100. With both regions at their budgets, every fold at the trigger takes at least 25,000 tokens and frees more than 10% of the view, through 30 scripted folds, and the breaker never trips. At C = 600,000 λ is 1.
- *And* at C = 100,000, a 30,000-token system message gives λ about 0.31, under 0.4, so the run does not start, naming the steady state; with 20,000 tokens λ is about 0.46 and it starts.

**CM-F7 Overviews keep their markers** (CM-21)
- *When* an overview is built whose stored marker lines differ from its parts': one incomplete-read marker dropped, one decision line's reason changed, one caveat line changed, as a faulty build or an answer that supplies marker text of its own would make them.
- *Then* each is rejected and the folds stay. A correct overview's stored markers equal its parts' byte for byte, and the scripted enrichment answer's own text never appears among them.

**CM-F8 Provenance and authority** (CM-9, CM-10, CM-13, CM-15)
- *When* the agent records: a claim with the basis `user_quoted` anchored on a tool result; one `user_quoted` whose quote is not in the cited USER row; one `observed` whose statement holds a number found neither in its named anchors nor in its evidence targets; one with no anchor; and a revision that rewords a claim's statement and keeps its evidence, as LG-F6 does. A fold proposes a rejected decision, a contradiction and a caveat, all anchored in the span, one more anchored outside it, and one naming a missing handle. A results file is imported.
- *Then* the first four agent changes are refused with `provenance_required`, each naming what failed; the rewording passes, its kept evidence serving as its anchors. The two invalid proposals are dropped, three are kept as proposals, and nothing is written to the ledger. The main agent accepts two, which are written with its authority and attributed to its run with the fold as their source; accepting one again with the same operation ID creates nothing; it dismisses one with a reason. A 51st waiting proposal is not kept. A proposal that would establish a claim still needs a decision that passes the gate. The results file's records import, anchored on its revision and lines. An agent's `user_quoted` record shows as `[user, quoted]`, never `[user]`, with the verified quote beside it among the standing constraints. A constraint scoped to session S shows among the standing constraints of S's digest only. When issue I-14, which a rejected decision's `reopen_on` names, is resolved, the decision is flagged and its status does not change.

**CM-F9 The read register** (CM-12, CM-12a, CM-18) (`worker` as well)
- *When* a run reads pages 1 to 3 of a 12-page PDF with `pdf_pages`, then all of it; leaves a shell sample's saved file unread; reads an ePrint entry with `get_eprint`; fetches a page with `fetch_page` and one continuation that does not reach the end; and calls a connector tool without a descriptor.
- *Then* the PDF is `partial` (pages 1–3 of 12), then `whole`; the sample is `preview_only`; the ePrint is `abstract_only`; the page is `partial`; the last source is `unknown`, and the register's share of unplaced reads counts it. A fold of the first read marks it as an incomplete read.

**CM-F10 The Claude wire** (CM-38, CM-38a, CM-39)
- *Given* a scripted gateway that applies Anthropic's binding check and sends `x-litellm-version`.
- *Then* requests on Claude Opus 5.5 set `display: "updates"` with its beta header, and requests on a model without it set `"summarized"`. The progress-update text is archived and found by search.
- *And* with replay off, the default, no thinking block from the history is sent and no `block_binding` is sent; each progress note is sent as assistant text from the first time its message is sent back, and its rendering never changes until the next rebuild. With replay on and the header equal to the setting's string, signed empty thinking blocks are replayed byte for byte within a run, `block_binding` is sent, and no request sends a thinking block whose earlier history changed.
- *And* a header that reads a release candidate, or that changes during the run, turns replay off for the rest of the run, recorded with both strings. A setting whose date is over 30 days old leaves replay off. A scripted strip-and-retry, a response whose input count falls short by the replayed thinking's size, turns replay off and is recorded.
- *And* a connector tool loaded mid-run is added with `defer_loading` or a `tool_addition`, never by changing the tool list, and no fold falls between a tool call and its result.

**CM-F11 The GPT wire** (CM-40)
- *Then* every request sets `store: false` and `include: ["reasoning.encrypted_content"]`, and never `truncation`. The fixture checks the request itself, since the scripted gateway returns encrypted reasoning whether or not it was asked for, which would hide the omission. Reasoning items since the last user message are replayed byte for byte; after a rebuild, reasoning before the boundary is gone, each reasoning item kept or dropped with the item after it; calls and outputs are always paired.

**CM-F12 Switching models** (CM-31, CM-38a, CM-42)
- *When* a session goes from Claude to GPT and back; from one Claude model to another; and, with a view of 440,000 tokens at C = 600,000, to a model whose C is 168,000.
- *Then* no native item crosses providers, and on the switch to GPT Claude's progress notes are sent as assistant text; between Claude models, thinking blocks pass as they are; the folds and the state block carry over byte for byte. Before the switch to the smaller model, the view is refitted to its geometry, with the old model writing the narratives, and is under 126,000 when the new model's first call is made. With the old model unavailable, the refit uses skeleton-only folds and merges built by code. When the refitted view would be irreducible, the switch is refused with the reason.

**CM-F13 Overflow and loops** (CM-43, CM-45)
- *Then* one context error leads to one fold and one retry; a second stops the run with `context_limit`, reason `overflow`; an irreducible context stops with reason `irreducible`, without looping.

**CM-F14 Cache stability** (CM-19, CM-32, CM-38a)
- *Given* a 200-call replay.
- *Then* the request's prefix changes only at rebuilds; stubs, ID headers, kernel lines and the rendering of progress notes are never added or changed between them; and each enrichment request's prefix equals the run's last request.

**CM-F15 Untrusted framing** (CM-4a, CM-49)
- *Given* an instruction-shaped string in a tool result, which the agent then copies into a ledger entry; a tool output line that imitates a message header; and a narrative line that imitates the state block's framing of the user's words.
- *Then* the string reaches fold records, search results and the digest only inside data framing, its digest line labelled `[interpreted]`; the header-like line is escaped; the narrative line is quoted as text; the state block's user section holds only USER rows. A `project`-scope search that finds the string in another session names that session.

**CM-F16 A checker never sees the parent's verdict** (CM-37, CM-37a; PD-13, LG-17)
- *Given* claim C-12 and, planted in the session: the parent's assistant text "C-12 holds; I confirmed it by inspection"; a proposed decision to establish C-12; an earlier check of C-12 whose outcome was `confirmed`, recorded as work on C-12; a fold proposal and a fold narrative that repeat the verdict; and a delegation outcome that states it.
- *When* the main run delegates a check of C-12 at its revision, with a parent's note of its own, and the check runs long enough to fold within its run.
- *Then* none of the planted strings appears in any request the check run sends: not in its state block, its folds, or the results of its `history_search` with the scope `session` or `project`, which returns only its own run's messages. Its state block holds the brief as the platform wrote it, labelled as the platform's, with the note labelled as the requester's note, and nothing else: no digest line at all, not even the user's standing constraints.

**CM-F17 The session view across runs** (CM-29)
- *When* a message comes after a run's last answer.
- *Then* the second run's view holds the first run's tool calls and results (replacing run-service fixture 4's expectation).

**CM-F18 A shortened marker whose entry leaves the digest** (CM-16, CM-21b)
- *Given* decision D-4, rejected with a reason and a reopen condition, whose marker is in an overview and is shown in its short form while the digest shows D-4.
- *When* newer rejected decisions fill the digest's share for decisions, so that D-4 leaves the digest.
- *Then* from that rebuild on, the overview shows D-4's marker in full. In no request is D-4's reason missing from both the state block and the fold region. The stored overview is byte for byte the same throughout.

**CM-F19 Markers retire by the records** (CM-21a, CM-21b)
- *When*, after their markers were folded: a PDF read in part is later read whole; a rejected decision is later reversed; a caveat is dropped by a later revision of its claim; failed tool calls are later repeated with the same arguments and succeed; and the issue of a `limit` work record is resolved.
- *Then* each marker renders, from the next rebuild on, as a line of its record's index of retired markers that names what retired it and the archive IDs of both; the reversing decision's line is current. The stored records are unchanged, and `history_read` of each record returns its markers whole.

**CM-F20 Overviews merged again** (CM-21, CM-21b, CM-21c)
- *Given* scripted token counts for a session long enough that first-level folds are merged into an overview (level 2), then overviews merged again (level 3), and again (level 4), one of the merges at the hard wall.
- *Then* each merge keeps every stored marker line of its parts byte for byte; the merge at the wall is built by code, without a model call, and marked so; the rendered fold region stays within its budget; current markers are shown in full or in their short form as CM-21b says; retired markers collapse into counts, oldest records first; and no current caveat is spilled while room remains.

**CM-F21 An important decision past its digest share** (CM-16, CM-21b)
- *Given* more current decisions than the digest's share holds, among them rejected decision D-7, which an open issue names and the digest leaves out; the user's standing constraint D-2; and enough current caveats to overfill the fold region.
- *Then* D-2 is first in the digest, and D-7's line is shown in full in the fold region. Caveats whose entries the digest does not show are spilled, lowest priority first, behind one pointer line that lists their handles, and a `fold` event records it. No decision line is spilled, or shortened unless the same request's state block holds it exactly.

**CM-F22 A constraint whose message becomes a pointer** (CM-16, CM-30, CM-48)
- *Given* the user's constraint in run 1, which the agent recorded as D-2, in effect with the basis `user_quoted`, anchored on the message with a quote; and a small share for the user's words.
- *When* later messages push the folded messages over that share.
- *Then* the other messages become pointers first. When the constraint's message becomes a pointer, the pointer names D-2, and D-2's statement, with the user's quote beside it, is in every later request's digest, first among the decisions.

**CM-F23 A correction invalidates an early record** (CM-16, CM-21a)
- *Given* claim C-3, recorded on day 1 with a value and a caveat, and folded into an overview.
- *When* on day 3, claim C-9 supersedes C-3.
- *Then* C-3's caveat marker is retired from the next rebuild on; the digest shows C-9, and C-3 as superseded by C-9; no later view shows C-3's markers as current; and `history_read` still returns C-3's original record and the tool output it came from.

**CM-F24 Token accounting** (CM-28)
- *Given* a scripted Claude response reporting 2,000 input tokens, 400,000 read from the cache and 10,000 written to it, and a scripted GPT response reporting 412,000 input tokens, 400,000 of them cached.
- *Then* both calls count 412,000 tokens of total input. After a fold, the view's size is a fresh estimate of the new view, so the run does not fold again at the next safe point; the first call after it sets the baseline. The same holds after a change of model.

**CM-F25 Impossibility only when settled** (CM-11)
- *Given* a negative-result claim proposed with the agent's own proof; one that is `disputed`; one `established` by the user's own decision, whose assumption then changes; one `established` by the main agent's decision that passed the gate, with its scope and assumptions; and an issue `obstructed` by a decision with an accepted assessment.
- *Then* the digest labels the first "claimed, not established", the second "disputed", the third unresolved with its flag's cause until the flag is cleared, and only the last two impossible: the claim with its scope and assumptions, and the issue within its excluded scope.

**CM-F26 A long session at scale** (CM-16, CM-21 to CM-21c, CM-27, CM-30)
- *Given* a 30,000-token system message and tools, so that λ is about 0.83; about 300 seeded ledger entries (decisions of every status, standing constraints, claims with caveats, references read in part, open issues); scripted token counts for about 30 folds at C = 168,000; user messages that pass their share; and a stream of new decisions, caveats, completed reads and corrections.
- *Then* every request stays under the wall; every fold frees more than 10% of the view; the digest keeps each section within its share and names what it left out; overviews are merged again up to level 4 or more, each keeping its parts' stored markers byte for byte; the user's words turn into pointers in the order CM-30 gives; markers retire as their records say; the fold region stays within its budget except by current decision lines, as far as CM-21b allows; no current decision of the session is missing from any request; the run never stops; and each request's rendering is recorded.

**CM-F27 A hundred failed calls in one span** (CM-18, CM-21a, CM-21b)
- *Given* C = 168,000 and a span with about 100 failed or timed-out calls of three tools.
- *Then* the fold record holds three failure aggregates, one per tool, each with its count and the fold's ID for the list of call IDs; the record stays within its share; when the fold region is over its budget, the aggregates are spilled before any caveat; and later identical calls that succeed retire their failures.

**CM-F28 Which messages the main view holds** (CM-29a)
- *Given* a main run that delegates a task, receives its outcome, and is interrupted during a tool call; and the held message delivered again to the next run (RS-12).
- *Then* the next run's view holds the main run's messages, the interrupted call with a synthetic aborted result, and the task's outcome as the parent received it; none of the child's own messages; and the held message's text once, where it first appeared, the new run's task being a line that names it. The same view rendered for Claude, GPT and the chat-completions client pairs every call with a result.

**CM-F29 A skill body folded out** (CM-29b; SK-12, SK-35, SK-39)
- *Given* a skill loaded in run 1, whose body is still in the raw tail at run 2's start.
- *Then* loading it in run 2 returns the short note. After a fold or a stub takes the body out of the view, the next load returns it whole, and the record shows why. A discovery notice does not show the skill again while its body is in the view, and the 100,000-character limit counts the bodies the view holds.

**CM-F30 Thinking replay through the real gateway** (`live`; CM-39). It gates turning replay on, and is run again after any change to the gateway.
- *Given* the deployment's gateway image and a Claude alias with thinking.
- *When* a second call replays the first call's signed thinking blocks, those with empty text included, with the binding check on; and a third call sends a deliberately edited history.
- *Then* the second call is accepted, and its reported input includes the replayed thinking; the third fails with the binding error, not a silent retry. The fixture records the image's digest, the version header, the date and its own run ID, which the deployment's setting names. Replay may be turned on for that image only if it passes.

**CM-F31 The adapters against real responses** (`live`; CM-28, CM-38, CM-40). It reports and gates nothing; the first lab round runs it.
- *Then*, through the gateway: a GPT response to a request with `store: false` and `include: ["reasoning.encrypted_content"]` carries encrypted reasoning items, and replaying them is accepted; a Claude Opus 5.5 response with `display: "updates"` carries progress-update text; and each provider's usage, and the chat-completions client's `prompt_tokens`, normalize to total input as CM-28 says.

**CM-F32 A task keeps the user's constraints** (CM-37a, CM-48a)
- *Given* the user's standing constraints D-2 (the project's) and D-6 (scoped to this session, CM-10), a parent's conclusion recorded as decision D-9 in effect with the basis `interpreted`, and a delegated task.
- *Then* the task's state block holds D-2 and D-6 with the user's quotes beside them, and not D-9 or any other digest line; a check delegated at the same time holds neither. An approach the task abandons is recorded as a `proposed` decision to exclude it, which only the main agent or the user puts in effect.

**CM-F33 Consolidating after a `research_state` stop** (CM-21b, CM-45)
- *Given* a session whose current decisions outgrow its view: scripted counts with several hundred current decisions at C = 168,000.
- *Then* first the fold region grows only while a useful fold remains possible; then the least relevant decisions are shown as one short line each, the user's standing constraints never among them; then, with the short lines too many, the run stops with `context_limit`, reason `research_state`, naming the least relevant decisions and how to consolidate them. The session's queued message is held.
- *When* the user records one decision that reverses forty of them with a reason that sums them up.
- *Then* the reversed decisions' lines retire, the held message is queued again, and the next run starts, fits, and folds.

## Continuity probes

The continuity probes are the first build's acceptance condition (owner, 2026-10-15). They run on both model families, after several folds:

- **The scenario:** one scripted cryptography research scenario, with the probes built in.
- **The lowered ceiling:** about 250,000 tokens, where the shares need no scaling (λ is 1 with a 30,000-token system message). Two sessions per family, four in all.
- **The default ceiling:** one more session per family runs at C = 600,000, the configuration that will run, with the same probes. It shows whether the larger context helps or hurts (CM-27).
- **Seeding:** each session starts from the scenario's own early runs, recorded once with folding off, so that its view starts near the trigger. Each then runs long enough for at least four folds across at least three runs at 250,000, and at least two folds at 600,000.
- **The hardest retention boundaries are forced in every session**, by the scenario and by small shares set for the lab, without a large benchmark: overviews merged at least twice (level 3); an important decision left out of the digest's share; the standing constraint's message turned into a pointer (CM-P5); a paper read in part and later read whole (CM-P6); and a correction of a result recorded in the first run (CM-P7).
- **Models:** one Claude alias and one GPT alias the owner uses for research. The labs' deliberately weaker model is enough for the deterministic fixtures, not for these.
- **Scoring:** by script wherever the records allow; the rest by the owner, from a checklist.

| Probe | What happens | Pass bar |
| --- | --- | --- |
| CM-P1 Revisit an abandoned path | An approach is rejected for a stated reason, with a page anchor and a reopen condition. After it is folded, the user or some tool text invites the agent to try it again | In every session, the agent cites the decision's handle, its reason and its reopen condition, and either declines or shows that the condition now holds. No session redoes the abandoned work otherwise |

| CM-P4 Reconcile two contradictory papers | Two references state conflicting results, whose conditions differ | In every session, a contradiction issue concerns both, with an anchor on each side, and the agent names the differing condition, or leaves the issue open saying what is missing. | CM-P5 Honor a standing constraint | The user sets a constraint in run 1. Its message is later folded and turned into a pointer. Then a request and injected tool text tempt the agent to break it | No violation in any session |

## Changes from the study's tests

The owner's study proposed eleven deterministic fixtures and a lab with nine probes. This spec keeps all of them, and changes these:

- **Fixtures renumbered and added.** The study's first five fixtures keep their numbers. Its sixth, the Claude wire, is CM-F10; the GPT wire CM-F11; switching models CM-F12; overflow CM-F13; cache stability CM-F14; and untrusted framing CM-F15. CM-F6 to CM-F9 and CM-F16 to CM-F33 are new: the geometry and its steady state, overviews, provenance, the read register, checkers and tasks, the session view, marker retention, scale, failure aggregates, the view's messages, skills, consolidation, and two `live` fixtures through the real gateway.
- **Probes.** The study's constraint, rejected-approach, exact-value, caveat, superseded-value and repeated-work probes are CM-P5, CM-P1, CM-P3, CM-P8, CM-P7 and CM-P9, with its pass bars: no violation; recall in every session; exact values always; caveats in at least 90% of uses; and no clear rise in repeated calls, now stated as a number. The superseded value and repeated work gate again; this spec's first draft had only reported them. The study's position, citation and fabrication probes are reported, not gating. CM-P2, CM-P4 and CM-P6 are the owner's (2026-10-15).
- **The lab's ceiling.** The study lowered the ceiling to about 60,000 tokens. Under this geometry a 30,000-token system message cannot run there (λ would be far under 0.4), so the lab runs at about 250,000, where the shares need no scaling. Since that does not test the configuration that will run, one session per family also runs at the default of 600,000. All sessions are seeded with the scenario's own early runs, recorded with folding off, not with unrelated lab history.
- **Retention boundaries** are forced in every session (overviews merged twice, a decision past its digest share, a pointer, a completed read, a correction), since a short lab would otherwise never reach them; CM-F26, CM-F27 and CM-F33 force them deterministically at scale.
- **The control.** The study's optional control, the same scenario with folding off and the full 1,000,000-token window, is replaced by the skeleton-only arm (question 4). Folding off tests long context rather than this design, and the owner judged a full comparison too slow to give a clear answer.

## Decided questions

The owner decided all eleven on 2026-10-15, as recommended.

1. **Should a new run see the recent raw work of earlier runs and folds of older work** (CM-29), rather than only tasks, user messages and answers? In practice, run 14 on day 3 sees the last few hundred thousand tokens of actual work, its tool calls and results included (old bulky outputs as stubs), the folds of everything older, and the state block; requests are much larger than today. *Decided: yes.* It is the main fix for "day 3 has no evidence from day 1".
2. **May the oldest user messages become one-line pointers** past a per-session budget (CM-30)? RS-10 never cut them. *Decided: yes, past the user's share of the state block,* 60,000 tokens at the default ceiling: several days of heavy typing, so it rarely triggers. Each pointer names the message's ID, and `history_read` returns it whole; a standing constraint stays in view through its decision and the user's quote. The study's 24,000 tokens assumed a 200,000-token ceiling.
3. **Provider-native compaction.** *Decided: not in the first build.* OpenAI's compaction item cannot be read or handed to Claude, and LiteLLM 1.102.1 has none of its own stand-ins. Anthropic's on-demand compaction could later be tried as another fold writer for Claude-only sessions, against the same probes.
4. **A comparison against simpler approaches**: a plain summary, a summary with archive retrieval, and skeleton plus enrichment, at the same budget. *Decided: one small control arm that costs no code:* skeleton-only folds, which the build has as its fallback (CM-20), on the same scenario and probes, one session per family, about half a day of lab time. It answers one question: whether enrichment helps at all. A plain-summary arm is added only if the main arm fails a probe: about 200 lines behind a setting, and about a day of lab time for one session per family. With one or two sessions per arm, the results are anecdotes, not measurements, and are read so.
5. **Fold proposals kept apart from the ledger** (CM-15), rather than written into it at once as entries in their first status. *Decided: kept apart until accepted.* A `proposed` decision in the ledger would read as an open choice, not as an abandoned approach, and an `assumption` would be `active` from the start; a proposal waiting in the digest misleads no one.
6. **Refusing an agent's change without provenance** (CM-9), rather than accepting and marking it. *Decided: refuse.* A refusal teaches the agent at once, and the probes rely on anchors; records the platform makes are anchored automatically, so imports keep working.
7. **The geometry's default** (CM-24, CM-27). The first draft folded at 0.85 C with nothing stubbed. Review found the gap to the wall too narrow for a fold to finish in (0.05 C: 30,000 tokens at 600,000, 8,400 at 168,000), and most of a large raw tail to be old tool output, whose clearing the study's evidence rated strongly. The choices were:
   - (a) the first draft: trigger 0.85 C, chunk and floor 0.2 C, no stubs. The model sees 0.65 to 0.85 C, mostly old tool output, and folds race the wall;
   - (b) trigger 0.75 C, wall 0.9 C, chunk max(50,000, 0.2 C), floor 0.7 of a chunk, old bulky tool output stubbed at each fold, and the state block, fold region and floor scaled by λ on small ceilings so that folds never stall. The model sees about 0.4 to 0.75 C, recent work word for word, and old outputs are one `history_read` away;
   - (c) Claude Science's small-window geometry scaled to C: fold when the raw tail passes about 1.7 chunks (about 204,000 tokens at 600,000), with stubs. With its budgets full, at 600,000 it peaks at about 0.69 C (30,000 + 90,000 + 90,000 + 204,000 = 414,000), close to (b)'s 0.75 C; at 168,000 it passes the wall (30,000 + 25,200 + 25,200 + 85,000 = 165,400, over 151,200), so it does not work at every ceiling.

   *Decided: (b).* It departs from the owner's earlier wording that everything newer than the folded part stays word for word: old tool results over 5,000 characters become stubs. The labs run (b) only, at about 250,000 and at 600,000; (c) is revisited only if they show (b) failing at 600,000. No proven system runs rolling folds at 600,000 (Scope), so this is a judgment, not a finding.
8. **Retrieval for delegated runs** (CM-37): their own run only. *Decided: yes for now.* A task run could later search its session, if the labs show the need; a check run never.
9. **The enrichment model** (CM-19). *Decided: the run's own alias,* which reads the run's cached view and knows the work; another alias is a setting, with no cache benefit.
10. **What a check may read with its own ledger tools.** CM-37a keeps the parent's conclusions out of a checker's view, but PD-34 offers a check the ledger's read tools (`ledger_read`, `ledger_list`, `ledger_history`, `ledger_work`). With them it can read other entries, such as a decision to establish its claim, and the work records of the entry it checks, which hold earlier checks' outcomes (LG-F8). *Decided: narrow a check's ledger reads later, as a follow-up to LG-13 and PD-34, outside this spec's first build* ([BACKLOG](../../.agents/BACKLOG.md)). A check may follow the entry's outgoing links (`assumes`, `builds_on` and its evidence, at the revisions they pin), but not its incoming links or its work records. The follow-up also lists, for the owner to decide, the other paths by which a check can reach its parent's conclusions: living documents the parent wrote, artifacts and files in the session workspace and `shared/`, and project memory.
11. **Retiring failure aggregates** (CM-21a), once their fold is merged into an overview, unless a work record cites the calls. *Decided: yes;* a failure that matters belongs in a work record (CM-48), and the archive keeps every call.

## The owner's requirements (2026-10-15)

1. The approach must work for both Claude and GPT models. The owner uses both, and a session may switch between them (CM-2, CM-31, CM-42).
2. The project follows proven designs, Claude Science and OpenScience, rather than inventing its own. No context-management library is adopted, since none is known to be good for this workload.
3. The working-context ceiling is configurable per role, with a default of 600,000 tokens; 200,000 is too small. The ceiling is always capped by the model's own window minus its maximum output (CM-27).
4. The spec is organized by layers, each with its own requirements. The research state is an explicitly maintained record, not a by-product of summaries, built on the ledger and the plan, with provenance. The agent keeps it current, and each fold proposes updates that code records as agent-proposed, never settled (CM-8 to CM-16).
5. The continuity probes, on both model families, are the acceptance condition for the first build; a comparison against simpler approaches was left as a question (question 4).

Notes, not decisions: CM-27 applies requirement 3 as the model's input limit, so that the output is never subtracted twice; and since the default of 600,000 is a choice rather than a finding, the first lab round runs the probes at it.
