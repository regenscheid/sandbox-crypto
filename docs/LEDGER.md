# Project ledger

The project ledger as built, against its specification, [the ledger spec](specs/ledger.md). It records the project's research state as typed entries in the control store (`orchestrator/ledger/`).

## What is built

**Entries (LG-1, LG-2).** An entry has an ID (`entry-…`), a type, a handle unique in its project (`I-3`, `C-12`, `REF-2`: one counter per project and type), and, for claims and results, its origin (`project` or `published`). The type, handle and origin never change. Each revision holds the title, the status, the statement, the type's own fields and the outgoing links, with who made it, the reason, the operation ID, and where it came from when it was imported (LG-41). The seven types and their statuses:

| Type | Handle | Statuses | Fields |
| --- | --- | --- | --- |
| `issue` | `I-` | `open`, `resolved`, `obstructed`, `split`, `withdrawn` | none |
| `claim` | `C-` | `proposed`, `established`, `recorded`, `disputed`, `refuted`, `superseded`, `withdrawn` | `kind` (lemma, theorem, observation, counterexample, negative result, other) |
| `result` | `R-` | as a claim | `kind`, `category`, `conditions`, `measures` |
| `assumption` | `A-` | `active`, `withdrawn` | none |
| `decision` | `D-` | `proposed`, `in_effect`, `rejected`, `reversed` | none |
| `task` | `T-` | `todo`, `in_progress`, `blocked`, `done`, `dropped` | none |
| `reference` | `REF-` | `active`, `withdrawn` | `identifiers` (DOI, ePrint, arXiv, NIST, ISBN, URL), `authors`, `published`, `version`, `retrieved`, `pdf` (an artifact revision, pinned by its SHA-256); its statement is the citation text |

A new entry starts in its type's first status: `proposed` for a project claim or result, `recorded` for a published one. A reference names at least one locator (an identifier or its PDF, which must be a revision of an artifact of the project; the link records the revision's SHA-256, and a hash the change gives must be that one) and a date: published, versioned or retrieved (LG-15). An entry's fields are at most 64 KiB as UTF-8 JSON, and a result's measures are finite numbers or text.

**Hidden text (threat model, A3).** An agent's ledger text holds no character the user may not see, as it is or as a character reference (`check_agent_text`): a change's reason, an entry's title and statement, every text in its fields (keys too), a link's note and an evidence scope. The user reads and decides on entries, and agents read them again. The check runs when the text is written, after its line ends become line feeds, so stored text still reads; a refusal names the place, and a results file's line. The user's own text is kept as written.

**Statements.** A statement is Markdown with LaTeX, saved in the dollar form (LD-42). Its revisions are `text_revisions` of kind `statement` under the entry's ID, with their block map and block owners, as comment bodies and explanations keep theirs; an entry revision names the statement's text revision, and a revision that leaves the statement unchanged names the same one.

**Math checks (LG-1, LD-53 to LD-55).** Each new text revision of a statement is queued for the math check documents, comments and explanations have ([math checks](MATH-CHECKS.md)), with the project's macros, since a statement belongs to no document; a project macro change checks it again. A formula KaTeX rejects becomes a `math` finding anchored to the entry's statement at that text revision, for the session of the agent that last changed the formula's block, with the repair as its remedy; text the user wrote gets none. The agent fixes it with `ledger_change`, and the next revision's check confirms the finding fixed, or confirms it when the formula is gone. A revision that keeps the statement is not checked again.

**Links (LG-5).** A revision's links replace the revision before's when a change gives them, and are kept otherwise; a change that gives the links the entry already holds changes nothing. Each kind has the types that may hold it and the targets it may name:

| Kind | Held by | Points to |
| --- | --- | --- |
| `answers` | claim, result | issue |
| `assumes` | claim, result, decision | assumption, pinned to a revision (when none is named, its revision as the change leaves it) |
| `builds_on` | claim, result, issue | claim, result |
| `restates`, `supersedes` | claim, result | claim, result |
| `compares_to` | claim, result | claim, result, with the stated difference |
| `dominates` | result | result, with the reason (see the best known results) |
| `split_into` | issue | issue |
| `affects` | decision | any entry |
| `concerns` | issue | any entry, a review finding of the project, or a document block at a revision |

An entry the same change revises is linked as the change leaves it, so an assumption revised and pinned in one change is pinned at its new revision (LG-F5). A finding link reads with the session the finding is in now, since the workspace opens a finding in its session and a math finding can move to another. A block link keeps the document's ID even when the change names the document, since a name can later name another document. An entry's current revision also shows the links other entries' current revisions hold to it, 200 at a time in the order those entries were made, with their count.

**Evidence (LG-8 to LG-11).** A claim, result or decision holds evidence links; a reference holds only the user's checks of it, which vouch for its PDF (LG-16). Each has a role (`supports`, `contradicts`, `derivation`, or `independent_check` with the revision of the entry it checked), a type (`proof`, `exact_computation`, `finite_test`, `numerical_experiment`, `source_claim`, `synthetic`; `unclassified` is for imports), a scope note saying what it covers, and one pinned target, checked to exist in the project: an entry revision (its revision as the change leaves it by default), an artifact revision with its SHA-256, whose bytes the control store keeps as it captured them (a tombstone or a revision that keeps only the sandbox's hash pins no content, and neither is a reference's PDF), a document block or math span at a revision (by the document's ID, even when the change names it), a review, the outcome of a delegation of the project that checked the entry (`delegation`, only for an `independent_check` of the revision its brief named, once it ended, and linked by the user or by a main run of its session; the link records the checking run, its model alias and models, how it ended, its verdict and status, whether it read the entry and its proofs' targets, the SHA-256 of its brief and the parent's note, which the entry view shows), or a quote of a reference (`quote`, with `entry` naming the reference): of its PDF, pinned by the PDF's SHA-256, with the page as `pdf_pages` or `pdf_search` numbered it, its printed label and the lines, or of its ePrint, with the date stamp the e-print tools gave; and the text, as it was read (at least 20 characters besides white space and at most 2,000, an agent's checked for hidden characters). A quote is `source_claim` evidence and cites its reference for LG-15; the reference names the PDF or the ePrint identifier, at the revision the quote pins. An ePrint quote is named by the paper's identifier and the date stamp the e-print tools gave (such as `2015-06-30T18:41:29Z; 2015-06-30T20:25:17Z`), as the server reports them: the tools take no version and give no hash of the text they quote from, so a quote is tied to the paper as the server dated it, not to exact bytes, until the server gives a version and a SHA-256 with each result. A PDF quote confirms a result by the consistency reviewer's check alone only when the PDF's SHA-256 is vouched for: by the e-print server, when a recorded e-print result names that hash (today none does), or by the user's check of a revision of the reference that names the PDF (`ledger check`, or the workspace's), which pins the PDF's SHA-256 through that revision; vouching is explicit, so no other revision of the user's vouches, and a reference holds no evidence but such checks; the platform cannot yet tell a downloaded paper from a PDF an agent made, so otherwise a PDF-quoted result stays unverified until the user confirms it. An ePrint passage quote can confirm a result by the check alone. The target is the platform's record; the role, type and scope are the author's assertion. A change adds links (`evidence`) and removes them by their IDs (`evidence_removed`); a revision keeps the links of the one before, each with its ID and the revision that added it, whose author added it. An entry revision's scope notes are at most 32 KiB in all. A claim or result with no evidence links shows as asserted only (`asserted_only`, in lists too). Execution targets are refused until they are built.

**Published claims and results (LG-15).** A published claim or result starts `recorded` and cites its reference through a `supports` link of type `source_claim` to a reference entry, which may be one the same change records; a change without one, or one that removes the last, is refused.

**Work records (LG-6, LG-7, LG-12, LG-13).** A work record says what was tried on an issue, a claim or a result, by whom, and how it ended: `limit` (time, tools, context or ideas ran out; the issue stays `open` for new work), `obstruction_claimed` (with its evidence in its references), `produced` (the entries it created: ones its change creates, or ones the delegation it cites created, never its own entry) or `assessment` (a critique of other work, which may name the work record it assesses, on the same entry, with its verdict: `accepted`, `rejected` or `inconclusive`). It cites pinned references, each with an optional note: a delegation of the project that has ended, for its outcome; an artifact revision whose bytes the platform keeps, with its SHA-256; a document block at a revision, by the document's ID; or another work record. Its references' notes hold 16 KiB in all. It may be `part_of` another record, as a dismissal is part of a delegation outcome's record. A change appends work records (`work`, at most 32) after its entries are written, so that a record may be on, or name as produced, an entry the change creates (`new:<key>`), and may name another record of the change by its `key`; a change may hold work alone. The user, the main agent and a delegated agent record work; the reviewer records none. A record changes no status, never conflicts with another or with the entry's revisions, and is never changed, removed or replaced; an entry holds at most 5,000 records. It keeps the entry's revision when it was recorded, the change's author, reason, operation ID and provenance (a results file's line, as a revision does), and its position among the project's records; each is a `ledger.work_recorded` event. `ledger_work` lists an entry's records, newest first, a page at a time (and so does the workspace's `GET …/ledger/{entry}/work`, [workspace](WORKSPACE.md)), shortening one too long for its budget, notes first; a results file's lines carry work records too, and `ledger_import` names those each line recorded.

A delegation that checks an entry records its outcome as work on that entry, the platform writing it as the outcome is kept and attributing it to the delegated run, with the delegation as its provenance (LG-F8): what was tried (an independent check of the entry at its revision), its ending, `assessment` for a check that returned a result, its note giving the verdict, the status and the head of the summary, or `limit` for one that returned none (`context` when its conversation outgrew its limit, `time` for a turn or budget limit, `tools` for a failure, a cancel or an interruption), and a reference to the delegation, whose outcome stays as returned. Its operation ID is the delegation's (`work-<delegation>`), so writing it again replays it; a record that cannot be written leaves the outcome as it is. A check changes no entry itself (PD-34). Delegations on issues, with their dismissals and claimed obstructions as records `part_of` the outcome's, come with general briefs.

**Decisions (LG-4, LG-30).** An entry becomes `established`, `obstructed` or `refuted`, leaves `refuted`, `withdrawn` or `superseded`, and a decision becomes `reversed`, only in a change that puts in effect a decision that `affects` it: a new decision recorded `in_effect` (by the user or the main agent; a delegated agent's decision is `proposed`), or a proposed one moved to `in_effect`. Only a project claim or result is `established`. The main agent's decision that brings a claim or result back from `refuted`, `withdrawn` or `superseded` passes the gate, whatever status it brings it back to, since through `disputed` it could otherwise be `recorded` again with nothing checked. While an entry is `established`, `refuted` or `obstructed`, or a claim or result that was once `established` or `recorded` is `disputed`, its statement, fields, `assumes` links and evidence change only with its status, or in a change that puts in effect a decision that affects it, which for the main agent's establishing passes the gate again. A proposed decision may be `rejected`; a decision in effect is reversed by a new decision, which states its own changes, and nothing returns to a status by itself; a rejected or reversed decision stays so. Other status changes need no decision.

**The gate (LG-17).** The user's decision establishes a project result as it is. The main agent's needs the gate to hold (the reviews below decide its review and finding clauses), and a refusal (`policy_denied`, `gate_not_met: …`, with the entry and the clause in its details) names the first clause that does not:

| Clause | Holds when | Pending, and why |
| --- | --- | --- |
| `evidence` | a `supports` or `derivation` link whose type is neither `synthetic` nor `unclassified`, to anything but a review or an entry that is `refuted`, `withdrawn` or `superseded` | No record says which of a target's inputs were synthetic (RA-17), so the link's type alone is read |
| `independent_check` | when evidence that counts is a `proof`, an `independent_check` of a revision whose statement, fields, `assumes` links and evidence that bears on it (`supports`, `derivation`, `contradicts`) the change keeps: one the user added themselves at the revision they checked, which the user records with the workspace's check ("I checked this revision…" on the entry, after reading its exact text) or `sandbox-science-harness ledger check`; or one whose target is the outcome of a delegation that checked that revision in a fresh context ([plans and delegation](specs/plans-and-delegation.md)), from the brief the platform wrote, and returned `confirmed` and `complete`, met no plan fence, read the entry at that revision with `ledger_read`, its whole statement and the evidence that holds its proofs, and the target of each proof whole at the revision its link pins (an entry's whole statement with `ledger_read`, the document's block with `document_read`, an artifact's whole file with `read_file`, from its start to its end), and was run by none of the runs that added the entry's proofs; while no delegation that checked a revision with the same statement text, fields, `assumes` links and `supports` and `derivation` evidence returned `refuted`, or `inconclusive` from a complete check, or is still running, linked or not, whatever `contradicts` evidence was added or removed since. A check is linked only while no other check of the entry runs. The same model in a fresh context counts, and the user's check counts whatever a delegation said (coordinator, 2026-10-15) | Verification reviews are not built. A delegation's run is told apart from a proof's author by the run that added the proof to the entry, not by who wrote the block it cites |
| `computation` | computational evidence (`exact_computation`, `finite_test`, `numerical_experiment`) pinned to an artifact revision | Execution targets are not built, so the producing execution is not pinned |
| `review` | a completed checkpoint or terminal review (`passed` or `findings`) whose coverage was complete held, whole, in its snapshot a revision of the entry whose statement, fields, `assumes` links and evidence that bears on it the change keeps; an entry shortened to fit one review item is not held whole; when a fix was confirmed of a `fail` finding raised on that material, the review started after the confirmation, so the review that raised it does not count | None |
| `finding` | no `fail` finding anchored to the entry is unresolved: open, claimed fixed or unaddressed, or superseded until a completed review that started after the supersession has covered the entry as the change leaves it. A confirmed fix or a withdrawal (an accepted rebuttal, or the user's dismissal) resolves it only for the material it was decided for: while a `fail` finding of any status is anchored to a revision with the material the change leaves the entry, the entry must have kept that material at every revision since, so returning to failed material holds the gate; the user can still establish it | No record says which revision a decision on a finding saw, so the gate reads that the entry kept the material since the finding, over at most 256 revisions |
| `flags` | the entry has no open flag, and the change raises none on it (see Flags below) | Flags from document blocks, block bindings and artifact revisions are not built, so only entries raise them |

The gate can be read for an entry without deciding anything (`Ledger.gate`, the workspace's `GET …/ledger/{entry}/gate`): each clause, in order, as the main agent's decision to establish the entry as it reads now would meet it, whether it holds and why, every clause rather than only the first that does not hold; whether all hold; and the decisions whose current revisions affect the entry, newest first, as many as 50, each with its status, revision and author. For an entry the gate does not apply to, anything but a project claim or result, it lists no clauses. The read changes nothing and takes no write lock.

The main agent's decision makes or keeps an issue `obstructed` only when it names the scope it excludes (`fields.excluded_scope`), its evidence (an evidence link) and the assessment (`fields.assessment`) that accepted an obstruction claimed on the issue (a work record ending `obstruction_claimed`): an assessment on the issue that the user recorded, the latest of the user's on that claim (LG-7, LG-F8). It holds only for the content it was made on: the issue's statement and fields at the claim's and the assessment's revisions are those it has, and the change leaves them as they are, so a reworded issue, or an obstructed one rewritten, needs a fresh acceptance. Otherwise it is refused (clause `assessment`). LG-7 also counts an assessment from a delegation started to assess the claim and run by another agent; delegations are briefed only to check entries so far, so an agent's assessment counts for nothing yet. The user's own decision makes an issue obstructed without one. The user records an assessment at the issue's revision read (`ledger assess`, or the workspace's `POST …/ledger/{entry}/assessments`); a later rejection by the user of the claim an obstruction rests on flags the issue (`evidence_changed`). A project setting that reserves decisions to the user is not built; by default it reserves none.

**Flags (LG-28, LG-29).** A change flags the entries that rest on what it changed, as their current revisions say:

- an assumption whose statement changes flags the entries whose `assumes` link pins an earlier revision of it (`assumption_revised`);
- an entry that becomes `disputed`, `refuted`, `superseded` or `withdrawn`, or moves from one of these to another, flags the entries that build on it, assume it or hold evidence pinned to it (`dependency_status`, or `assumption_withdrawn` for a withdrawn assumption);
- an entry whose statement changes flags the entries with evidence pinned to an earlier revision of it (`evidence_changed`).

An entry is flagged in the same way when a change makes it rest on such an entry: an `assumes` or `builds_on` link or evidence it gains to an entry that is set aside, that pins a revision older than the target's statement, or to an entry with an open flag (`spread`). Pins that were already stale when flags were built (migration 25) are not flagged. A flag passes on to the entries that rest on a flagged entry through `assumes`, `builds_on` and evidence links, once each (`spread`, naming the flag it came from). Each flag names its cause, the entry and revision it came from, the revision of the flagged entry it was raised on, and the reviews whose snapshots held that revision; an entry has one open flag per cause and source (the entry at the revision that raised it, or the flagged entry it spread from), and its check of itself flags nothing. A flag changes no statement, status or revision, and the main agent's change that would establish an entry it also flags is refused (clause `flags`).

A flag stays until the user or the main agent clears it with a reason; a delegated agent clears none. A change clears up to 256 flags, by ID (`flags_cleared`), or all the open flags on an entry, or those of one cause (`flags_cleared_on`), and may revise nothing else; the user clears with the workspace's `POST …/ledger/{entry}/flags` or `sandbox-science-harness ledger clear`. The user, and only the user, opens a cleared flag again (`flags_reopened`, `POST …/ledger/{entry}/flags/reopened` or `ledger reopen`): a new flag that names the one it reopens. An entry's read lists its open flags, newest first, as many as 50, and a list counts them (`open_flags`); the first page of its history lists the flags cleared on it, latest first, as many as 50, with who cleared each and why. A change's result lists as many as 50 of the entries it flagged and the flags it cleared, and counts them all (`flagged_total`, `cleared_total`). Each change records one event for the flags it raised, cleared or reopened (`ledger.flags_raised`, `ledger.flags_cleared`, `ledger.flags_reopened`), listing as many as 500 with their count; the session's reviews read the flags an agent's change raised or cleared as one item per change, and raised flags alone make no review due.

**Reviews (CR-2, CR-9, CR-10).** The session's consistency reviews read the ledger: each revision an agent of the session makes is an observation of kind `ledger`, the entry as it reads at that revision (statement, fields, links, evidence, author and reason), which the reviewer reads as it reads other evidence. The revision's new title and statement count toward the 2,000-character trigger, and a new claim or result is a structural block; the user's revisions are not reviewed. The reviewer reads the ledger's events in pages of 200 at each safe point, and drains them before a terminal review; a review's coverage is complete only when it has read them all. A finding anchors to an entry revision, and to one of its fields (`title`, `statement`, `status`, `fields`, `links` or `evidence`) when it concerns one (LG-25, CR-17); an entry's read lists the findings anchored to it, math findings on its statement among them, each with its own status, which a change to the entry never resolves. When the next review is dispatched, an anchor counts as replaced only when a later revision changed what a decision rests on (the statement, fields, `assumes` links and evidence that can count), and, when it names a field, that field; a new title, status or other links replace nothing, and an open finding whose anchors are all replaced becomes `superseded` (CR-28 as amended). The main agent claims a fix of a finding on an entry with `review_respond`, citing the changed entry revisions (`entry_revisions`: a later revision of an entry the finding is anchored to, which changes the field the anchor names, and what a decision rests on unless that field is the title, status or links); the confirmation review's snapshot pins each, with the entry as it reads now when it has moved on, and the reviewer confirms only once it has read them whole (CR-22, CR-24).

**Mutations (LG-30, LG-31).** A change names an operation ID, a reason, and up to 32 entry changes, each creating an entry (its type, title, statement, fields and links) or revising one (its ID or handle and the revision it expects). Entries the same change creates are named `new:<key>`. All of it commits, with its events and its receipt, or none of it does. A stale expected revision is a conflict that names the current one; nothing is rebased. An operation ID names one change in its project, whoever sends it: the same operation ID with the same change returns the first result (`replayed`), and with another change is refused; a change is compared by a digest of its JSON without the fields it leaves unset, so a field a later version adds does not turn a retry into a conflict. An entry is `superseded` exactly while a current revision supersedes it, so a supersedes link and its target becoming `superseded` commit together, and so do the link's removal and the target's leaving `superseded`; an entry that is `superseded` supersedes nothing new, though one that supersedes another may later be superseded. An issue is `split` exactly while it holds `split_into` links, so it names the issues it was split into in the same change. Neither `supersedes` nor `split_into` links ever lead back to their holder.

**Frontier categories (LG-18, LG-19).** A frontier category, named in its project (such as `key-recovery`), states the target and the kind of result it compares, its measures, each with a unit and a direction (`lower` or `higher` is better), and its condition keys, such as attack model or cost model. The user or the main agent defines one, and revises it by naming the revision read (`expected`; a stale one is a conflict that names the current revision); a delegated agent defines none. Every revision is kept, under its operation ID, which names one change in the project as an entry change's does, and records `ledger.category_defined`. An agent's category text, its target, kind, reason and units, holds no character the user may not see (`check_agent_text`, threat model A3); the user's is kept as written. A result that names a category in its fields gives a value for each of its condition keys and no others, each once, and only its measures, as numbers in its units or as given, such as an asymptotic expression; a measure may be missing. The ledger checks this when a result is made or its fields change, against the category's current revision, so a category revised later holds up no other change to its results. Condition keys, and the frontier's condition values, are compared in compatibility form (NFKC, so a no-break space is a space), case folded, with each run of white space one space: `Model` is the key `model`. An agent's condition values hold no hidden character, as all its fields do, and are printable ASCII, so that a letter of another script that looks Latin, a Unicode dash or slash, or other digits do not make a group of their own; the user's are free. The agent reads categories with `ledger_frontier` and defines them with `ledger_category`; the GUI reads them, and the user defines them, through the workspace ([workspace](WORKSPACE.md)).

**The best known results (LG-20, LG-21, LG-23).** A category's frontier is read from its results' current revisions when asked for: every result that is or was eligible, and the 500 newest `proposed` ones, with the number the next 500 begin before (`next_candidates_before`, read with `candidates_before`). Published results that are `recorded` and project results that are `established` are eligible. One that becomes `disputed` stays so, marked as disputed, only when the revision before it became disputed was eligible, and the frontier shows that revision, so measures rewritten on the way to `disputed` are not shown; results in other statuses are not eligible. A published result an agent recorded is eligible only once the user confirmed it as the revision shown reads: the user's latest revision of it holds the material shown, and the user wrote that material, by recording the entry or by a revision that brought it in, or checked it (`ledger check`, or the workspace's); a user's other edits, such as a title or a dropped link, confirm nothing. Until then it is a candidate marked `unverified` (LG-16, LG-20 as amended). The consistency reviewer confirms it too (CR-4): when every quote the revision shown holds, at least one, has a `supported` citation check, the latest of each, of that revision's statement, fields, assumptions and evidence; a revision that changes them needs checks of its own, and a later `unsupported` check of any revision stands until a newer `supported` one, so returning to checked material does not return to its check. A quote of a reference that is refuted, withdrawn or superseded, or of a PDF the user has not vouched for, confirms nothing. Each published result says who confirmed it (`confirmed_by`: `citation check` or `user`, the user's first when both confirm it; only the user's check of the entry itself counts as the user's, never an `independent_check` of another target, such as a delegation's outcome). Each result names who wrote the revision shown, and an agent's role. Results are grouped by their conditions, a value for each of the category's condition keys, compared as written in compatibility form, case folded and with white space collapsed, and compared only within a group. Groups whose conditions differ only in characters that look alike, such as a Cyrillic letter, a Unicode dash or another script's digits in the user's spelling, stay apart and are listed as a warning (`lookalike`, from a partial table): one dominates another when every measure of the category is a number for both, it is at least as good on each, in its direction, and better on one. The best known are the eligible results no other eligible result dominates, so conflicting measures, such as time against memory, keep several; each dominated result names those that dominate it. An eligible result with a measure missing or not a number is listed beside them as not compared, and one whose conditions lack a key the category gained since is listed apart, as unplaced. Project results that are `proposed`, or `disputed` when they were not eligible before, and unverified published results are candidates, each with the best known results it would dominate if it were eligible. When the main agent wrote the category's current revision, the frontier says so first, with its reason and what it changed since the user's latest revision (`agent_revised`). Each result shows its statement, conditions, measures, origin, status, evidence types, the references it cites, the artifacts its evidence pins, and how many open findings and flags it has. The agent reads a category's frontier with `ledger_frontier`, a group of conditions at a time within its output budget; the GUI reads it with `GET …/frontier/{category}`, as many as `limit` groups (20 by default, at most 100) in the order of their folded conditions key (`key`), from `groups_after_key` on (or `groups_after`, a position, for a release), with the first 100 results of each kind in a group (the newest candidates, newest first) and how many more (`more`).

**Dominates links (LG-22).** Where the rule cannot compare two results of a category, because their conditions differ or a measure is missing or not a number, the user or the main agent records that one dominates the other with a `dominates` link and its reason; a delegated agent records none. Both results must be eligible as the change leaves them and in one category, and a link between results the rule compares itself (equal conditions, numeric measures) is refused, since the rule decides those. While both are eligible, the link takes the dominated result from the best known, or from those not compared, into the dominated, naming the result that holds the link; a result that is no longer eligible, such as a refuted one, dominates nothing. A link between two results the rule has come to compare, since one's measures became numbers, counts for nothing, and the rule decides. A change that adds a link on a cycle, a result dominating one that already dominates it, by links or by the rule, through any results between, is refused; the cycle is read as the frontier reads its results, a disputed one as the revision before and only those eligible. A cycle a later change makes, by a dispute, a revision of the category or of a result, or an entry back from set aside, voids its links at read: they count for nothing, and the frontier lists them, with why, among the links that count for nothing (`void_links`), until the user drops one. The frontier shows each link that takes a result, with its reason, who recorded it and in which revision of its holder (`linked_by`). The user drops one, with a reason, as a change to the holder at the revision read that keeps its other links: through the workspace (`POST …/ledger/{entry}/dominates/dropped`) or the harness's `ledger drop` command; it shows in the holder's history.

**The history (LG-24).** Each change that alters a category's best known results under one set of conditions is recorded with them as it leaves them, what it added and removed, and its cause: the ledger change (its operation ID, author, reason cut to 500 characters, the results it made or revised, and the `dominates` links it added, each with its reason cut short, or dropped) or the category's revision. A set of conditions is kept as the frontier compares it (compatibility form, case folded, white space collapsed), so a group keeps its key whichever result's spelling it shows; past the history's 8192 bytes its values are cut and `#` holds a digest of the whole set, and a cause past 16384 bytes loses its reason and links, so recording never refuses a change. A result taken from the best known stays in the history and keeps its status: a published result another dominates is still `recorded`. The best known results at any past time are those the last change recorded by then left. Each change that alters a category's frontier records one `ledger.frontier_changed` event, with the groups it changed. The agent reads the history with `ledger_frontier`'s `history`, newest first; the GUI reads it with `GET …/frontier/{category}/history`, and the best known at a time with `GET …/frontier/{category}/past?at=`. The history begins with migration 27. A category whose history holds nothing yet, such as one defined before it, first records the best known it had, caused by `{"baseline": "frontier history begins"}`, in the change that first touches it; every eligible result is read, so the best known is never cut short. Within a group, the best known are found from the best on, so a change takes as many comparisons as the group's results times its best known; a dominated result names the best known results that dominate it. The agent's read shows a change too large for its budget cut, with the counts; the GUI's lists the first 100 of a change's best known, added and removed, and of each past group's best known, with how many more (`more`).

**Events (LG-33).** Each new revision records `ledger.entry_created` or `ledger.entry_revised` (with the status before and the parts changed) in the control store's event log, under the entry.

**Who may change what (LG-13).** The user may make any change; the main agent may create and revise any entry; a delegated agent may create entries, in their first status, and add evidence to entries, but change nothing else. Other agent roles, the platform, imports and code in the sandbox change nothing; refusals say `not_permitted_for_role`. An agent's session must belong to the project, and an entry of another project is not found.

**The agent's tools.** A run reads with `ledger_list` (by type or current status, a page at a time), `ledger_read` (an entry at a revision, with its links and the links to it), `ledger_history` and `ledger_work` (an entry's work records), and changes with `ledger_change` (entries, work records and flag clearances), a mutation whose operation ID defaults to the tool call's. An artifact's ID, revision and SHA-256, which pin it as evidence, come from `find_artifacts` in any run, not only from the `publish` that made the revision ([artifacts](ARTIFACTS.md#finding-artifacts-from-a-later-run)). The change tool's schema lists the values the ledger takes: each type's statuses, a claim's or result's kinds, a reference's identifier schemes, and the evidence roles and types, so a model need not guess them. The reads are `read` tools; `ledger_change` and `ledger_import` are effects, which the plan fence gates. Every change is the run's: its session, role (`main`, or `delegated` for a delegated run), model, alias and tool call; the arguments name no author, and each tool refuses arguments it does not take. Every answer fits the tool's output budget (20,000 characters): a long list or history comes a page at a time, and a long entry in parts, its statement, links, evidence, incoming links, findings and flags each going on where `more` says, with notes and scopes shortened. Entry text and results files are untrusted data, and the system prompt says so.

**Results files (LG-41).** Code in the sandbox has no route to the ledger. It writes a results file, JSON Lines with one mutation per line (its operation ID, reason and changes), at most 256 lines and 1 MiB, and the agent imports it with `ledger_import`, naming its path in the workspace and the SHA-256 it read; the import is refused if the file is no longer what the agent read, or if the bytes the worker sent do not match the digest it sent with them. Lines end at a newline only; a line repeats no key and holds no NaN or infinity. Every line is checked as a mutation before anything is recorded; the mutations are then applied in one change, all or none, with the agent's authority, and a refusal names its line. Each revision records the file's path, the SHA-256 of the bytes applied, the session's environment and the line; a line imported before replays its first result, so importing a file again, from any session of the project, records nothing. The answer counts the lines recorded and replayed and lists the first 20, with the handles each made.

**The workspace's reads.** Three read-only routes answer typed models (`LedgerListing`, `LedgerEntry`, `LedgerHistory` in `api-types.ts`) for the GUI's ledger and board views: a page of entries, an entry at a revision, and an entry's history ([workspace](WORKSPACE.md)). The views' own tables of the types' statuses, the link kinds and the field names are tested against `web/workspace/src/lib/ledger.fixtures.json`, which `scripts/generate_ledger_fixture.py` writes from `ledger/models.py`; a workspace test fails when it is stale.
