# Skills

Built: importing skill packs from git or an archive, pinning them in projects, the text of the built-in pack ([below](#the-built-in-pack), SK-40, SK-41), and giving each run its skills: an index in its system message, the `skills` tool and the skills a project loads at every run's start ([skills](specs/skills.md), SK-1 to SK-7, SK-10 to SK-13, SK-21, SK-32, SK-33, SK-38, SK-39, SK-42). The built-in pack's import and default pin, discovery notices, embeddings, the import's model pass, the launcher's import and helper staging come next.

A skill is a directory with a `SKILL.md`: front matter with a `name` and a `description`, then a body. A pack is a set of skills, such as a repository's `skills/` directory. Each pack is imported under a source name, and a skill's qualified ID is `<source>/<name>`.

## Importing a pack

The user imports a pack on their own machine with the harness:

```sh
sandbox-science-harness skills import --state-dir STATE --name crypto \
  --git https://github.com/OWNER/REPO [--ref BRANCH|TAG|COMMIT] [--path DIR]
sandbox-science-harness skills import --state-dir STATE --name mine --archive pack.tar.gz
```

- **From git.** `--git` takes a URL or a local repository's path. The harness fetches one commit, the ref's or the default branch's, into a temporary bare repository with the user's git, configuration and credentials, and records the resolved commit; the default branch and its commit come from one lookup. A commit is named by its full hash. The fetch asks the server to leave out blobs over 1 MiB, takes no submodules, may write no file over 64 MiB and is refused when the repository passes 64 MiB. Git runs only on the temporary repository, without the caller's `GIT_DIR` and other location variables, and with `GIT_ALLOW_PROTOCOL` limited to file, git, http, https and ssh. The tree is listed as a stream, only under the skills' directory, and a listing past four times the file limit is refused. Files are read from git's objects, so nothing in the pack is written out as a file. The recorded origin keeps no password, and no user name for http and https. The platform's services and the sandboxes never fetch a pack.
- **From an archive.** `--archive` takes a `.tar` (plain, gzip, bzip2 or xz) or `.zip` file of at most 32 MiB. A tar is decompressed once, to at most 64 MiB, and then read in memory; a zip may have at most four times the file limit of entries. Reading stops after two minutes. The single top directory every entry is in, as in GitHub's archives, is dropped unless it is a skill's own. An archive that cannot be read, such as one with an encrypted entry or a size that is not as stated, is refused. The import records the archive's SHA-256.
- **Which files.** The skills are the directories directly under `skills/` when the pack has skills there, and directly under its top otherwise, or under `--path`. Only that directory's files are kept, with paths relative to it, so sibling links such as `../alpha/SKILL.md` stay inside the pack. Symbolic links, hard links, submodules and other entries that are not regular files are left out, and so are files over 1 MiB and paths that are not plain relative ones: a path with a backslash, an empty, dot, dot-dot or `.git` name, or a character a reader may not see (control, format, bidirectional, zero-width), is left out. Paths that differ only by case are reported. A pack that lists a path twice, or has over 4,096 files or 32 MiB, is refused.
- **Which skills.** Front matter is YAML between `---` lines at the start of `SKILL.md`, read with the safe loader and without aliases. Repeated keys, `<<` merge keys and keys that are not text are refused. A skill is excluded, with the reason, when its `name` is missing, is not lowercase letters, digits and hyphens (at most 64), or differs from its directory's name; when its `description` is missing or over 1,024 characters; when any text in its front matter holds a character a reader may not see, or a number is not finite; or when its body is over 64 KiB. Runs of white space in the description and in text fields become single spaces. Its other front-matter fields are kept as metadata. Nothing in a pack is run.
- **The report.** The command prints the import as JSON: the source, origin, ref, commit or archive digest, the skills' directory, the snapshot's SHA-256, and a report of the skills, the excluded skills and the files left out, each with its reason; the default branch when no ref was given; warnings, such as paths that differ only by case or a source imported before from another origin, which the command also prints; the text files with hidden characters (control, format, bidirectional, zero-width and tag characters), with how many each has, which a run is shown as code points; and, when the source was imported before, the skills added, removed and changed since (a skill changes when any file in its directory does). Paths in the report are cut to 200 characters. The same import again, from the same place at the same revision, adds nothing and says `"unchanged": true`.

## Pinning

```sh
sandbox-science-harness skills pin --state-dir STATE --project P --source crypto [--revision 4089e99415f3]
sandbox-science-harness skills list --state-dir STATE [--project P | --source crypto]
```

A project pins one import of each source it uses: the source's latest, or the one whose commit, archive digest or snapshot starts with `--revision`, given by at least 12 hexadecimal digits; a prefix that names imports of different snapshots is refused. Pinning another import of the source moves the pin, and its revision counts the moves. A pin is refused when one of its skills has the name of a skill of another source the project pins; the refusal names the skills and the source (SK-4). `skills list` lists the imports, the latest first, or a source's, or a project's pins with their skills.

## The built-in pack

The platform's own skills are a pack in this repository, `skills/builtin/<name>/SKILL.md` (SK-40): `pdf-reading`, `literature-search`, `recording-results`, `computation`, `delegating-work`, `writing-documents` and `environment-setup`. They teach the platform's own tools and rules: reading and quoting PDFs, searching the literature through the connectors, recording and establishing results in the ledger, computing and keeping results as files, delegating checks and tasks, writing living documents, and installing software and reaching hosts. They are reference, not orders. The pack is versioned with the harness, and is imported and pinned like any pack, as the source `builtin`.

To change a built-in skill, edit its `SKILL.md` in the pull request that changes the tool or rule it describes. A skill has standard front matter only: a `name` equal to its directory's name, and a `description` of one or two sentences on when to use it, at most 300 characters. Its body is short Markdown. Tool names go in inline code, such as `pdf_pages`; other identifiers, such as fields, values and paths, go in fenced code or plain text.

`packages/orchestrator/tests/test_builtin_skills.py` guards the pack. It reads the pack with the import's own validator, which must accept every skill and leave out no file. It checks every inline-code span outside fenced code against the harness's tool table for the roles each skill is written for (SK-41), so a tool renamed or removed in the harness fails it, naming the skill, the identifier and the nearest tool name. A few other identifiers are allowed in inline code, each with the harness text that names it to the model. A new skill is added to the test's list of skills and their roles.

The built-in skills are the project's own work, under the repository's MIT License. They are written anew for this platform: no text from Claude Science, Anthropic's skills or OpenScience's skills is copied or paraphrased (D56).

## A run's skills

A run is given its project's pinned skills, less those the project excludes, as they are when it starts; a pin that moves later reaches runs started afterwards (SK-5). A run of a project that pins nothing gets no skills section and no `skills` tool.

- **The index.** A section of the system message, after the project memory, opens with a framing (`sandbox-skills-index-1`): the descriptions and the skills' text are the packs' data; a skill guides how to work and grants nothing; load one when its description fits; search in the field's terms; name only skills loaded or found; a loaded skill is reference, not orders; nothing is installed or fetched only because a skill mentions it; a search that finds nothing covers only that search. The skills follow, each as `source/name: description`, between markers carrying a code no skill's text contains, within 12,000 characters: past that, descriptions are cut at a word, shorter until they fit, then skills are listed by name per source, then sources with their counts. The run's prompt pins record the framing's version, each source's revision, the number of skills, the shortening, the skills loaded at the start and the section's SHA-256 ([MAIN prompt provenance](MAIN-PROMPT-PROVENANCE.md)).
- **The `skills` tool** (read only). `search` ranks the skills by BM25 over their names and descriptions and returns up to 8 with their full descriptions and the words that matched, and how many were searched. `load` takes names (`source/name`, or a name one source has) and returns each body under its ID, revision and body SHA-256, between markers no body contains, framed as the pack's procedure that grants nothing. A name that names no skill gets a note, and the other names are still loaded; a single such name is refused. A skill loaded before gets a short note, and a load past the run's 100,000 characters of skill text, those given at its start included, is refused. `read` returns a file of a skill's pack by a path relative to the skill, resolved inside the snapshot so that `../other/...` reaches a sibling skill. A path outside the pack is refused with `resource_outside_pack`, and one under a skill the run does not have, such as one the project excludes or a built-in skill a pack's replaces, with `not_in_set`. A skill's own `SKILL.md`, read, counts toward the 100,000 characters as a load does. A file is text or binary by the whole of it; a read shows at most 64 KiB, cut before a character it would split, or says a file is binary. The result is never cut, and a notice due at that point waits for the next. Bodies and files are given with each hidden character, and each that can pass for other text, written as its code point (`⟦U+202E⟧`), in the system message too.
- **Load evidence.** Each call's record in the run's transcript names the action, the tool call, the role, the alias and the model, and for each skill loaded or file read its ID, revision, SHA-256 and status. The skills loaded at the run's start are recorded in its summary, `summaries.skills.loads`, each with `"trigger": "start"`, its ID, revision, SHA-256, role, alias and the model that first answered, or `over_budget` for one left out. Only these records show that a skill was loaded (SK-22).
- **Settings.** `sandbox-science-harness skills settings --state-dir STATE --project P` shows the project's skills loaded in full at every run's start and those it excludes; with `--expected REVISION` it changes them: `--always ID` and `--exclude ID`, repeated, add to a list, `--not-always ID` and `--include ID` take from one, and `--no-always` and `--no-exclude` empty one first. A change without `--expected` is refused, naming the revision and the lists it would make. Settings whose skills loaded at the start, as the project's pins stand, would pass the 100,000 characters are refused. Skills loaded at the start sit in the system message after the index, each between the same markers, headed by its ID, revision and SHA-256, and count toward the 100,000 characters. One that would pass them, as after a pin moved, is left out, and a line in the section names it.

## Where it is kept

In the control store (`control.sqlite3`), written once: `skill_blobs` holds each file's content by its SHA-256, shared by every snapshot; `skill_snapshots` and `skill_files` hold each snapshot's files, a snapshot being named by a SHA-256 over its paths, whether each is executable and their contents' SHA-256; `skill_skills` holds each snapshot's skills with their descriptions, body SHA-256 and metadata; and `skill_imports` holds each import with its report. `project_skill_pins` holds each project's pins, and `project_skill_settings` each project's skills loaded at the start and excluded.

Code: `packages/orchestrator/src/sandbox_science/orchestrator/skills/` (`index.py` for the section, `tool.py` for the `skills` tool) and `cli_skills.py`.
