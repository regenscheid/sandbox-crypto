# Skills

Built: importing skill packs from git or an archive, pinning them in projects, the built-in pack with its import and default pin ([below](#the-built-in-pack), SK-40, SK-41), and giving each run its skills: an index in its system message, the `skills` tool and the skills a project loads at every run's start ([skills](specs/skills.md), SK-1 to SK-7, SK-10 to SK-13, SK-21, SK-29, SK-32, SK-33, SK-35 to SK-39, SK-42), with discovery notices. Search and discovery compare by meaning as well as words when the user names an embedding model ([below](#embeddings)), and the launcher's import, pins and updates from its config ([below](#from-the-launcher), SK-28). The import's model pass, per-pack thresholds and helper staging come next.

A skill is a directory with a `SKILL.md`: front matter with a `name` and a `description`, then a body. A pack is a set of skills, such as a repository's `skills/` directory. Each pack is imported under a source name, and a skill's qualified ID is `<source>/<name>`.

## Importing a pack

The user imports a pack on their own machine with the harness:

```sh
sandbox-science-harness skills import --state-dir STATE --name crypto \
  --git https://github.com/OWNER/REPO [--ref BRANCH|TAG|COMMIT] [--path DIR]
sandbox-science-harness skills import --state-dir STATE --name mine --archive pack.tar.gz
```

- **From git.** `--git` takes a URL or a local repository's path. The harness fetches one commit, the ref's or the default branch's, into a temporary bare repository with the user's git, configuration and credentials, and records the resolved commit; the default branch and its commit come from one lookup. A commit is named by its full hash. The fetch asks the server to leave out blobs over 1 MiB, takes no submodules, may write no file over 64 MiB and is refused when the repository passes 64 MiB. Git runs only on the temporary repository, without the caller's `GIT_DIR` and other location variables, and with `GIT_ALLOW_PROTOCOL` limited to file, git, http, https and ssh. The tree is listed as a stream, only under the skills' directory, and a listing past four times the file limit is refused. Files are read from git's objects, so nothing in the pack is written out as a file. The recorded origin keeps no password, and no user name for http and https. The platform's services and the sandboxes never fetch a pack.
- **From an archive.** `--archive` takes a `.tar` (plain, gzip, bzip2 or xz) or `.zip` file of at most 32 MiB. A tar is decompressed once, to at most 64 MiB, and then read in memory; a zip may have at most four times the file limit of entries. Reading stops after two minutes. The single top directory every entry is in, as in GitHub's archives, is dropped unless it is a skill's own. An archive that cannot be read, such as one with an encrypted entry or a size that is not as stated, is refused. The import records the archive's SHA-256.
- **Which files.** The skills are the directories directly under `skills/` when the pack has skills there, and directly under its top otherwise, or under `--path`. Only that directory's files are kept, with paths relative to it, so sibling links such as `../alpha/SKILL.md` stay inside the pack. Symbolic links, hard links, submodules and other entries that are not regular files are left out, and so are files over 1 MiB and paths that are not plain relative ones: a path with a backslash, an empty, dot, dot-dot or `.git` name, or a character a reader may not see (control, format, bidirectional, zero-width), is left out. Paths that differ only by case are reported. A pack that lists a path twice, or has over 4,096 files or 32 MiB, is refused.
- **Which skills.** Front matter is YAML between `---` lines at the start of `SKILL.md`, read with the safe loader and without aliases. Repeated keys, `<<` merge keys and keys that are not text are refused. A skill is excluded, with the reason, when its `name` is missing, is not lowercase letters, digits and hyphens (at most 64), or differs from its directory's name; when its `description` is missing or over 1,024 characters; when any text in its front matter holds a character a reader may not see, or a number is not finite; or when its body is over 64 KiB. Runs of white space in the description and in text fields become single spaces. Its other front-matter fields are kept as metadata. Nothing in a pack is run.
- **The report.** The command prints the import as JSON: the source, origin, ref, commit or archive digest, the skills' directory, the snapshot's SHA-256, and a report of the skills, the excluded skills and the files left out, each with its reason; the default branch when no ref was given; warnings, such as paths that differ only by case or a source imported before from another origin, which the command also prints; the relative links in the pack's Markdown that name no file of the snapshot, a link with any URI scheme left aside, as written, with the file that has them and, where only case differs, the file a case-blind loader would find (`broken_links`); the text files with hidden characters (control, format, bidirectional, zero-width and tag characters), with how many each has, which a run is shown as code points; and, when the source was imported before, the skills added, removed and changed since (a skill changes when any file in its directory does). Paths in the report are cut to 200 characters. The same import again, from the same place at the same revision, adds nothing and says `"unchanged": true`.

### From the launcher

The launcher's config names the packs, `[skills.packs.NAME]` with `git` (and optionally `ref`) or `archive`, and optionally `path`, and each project's `skills` ([quickstart](QUICKSTART.md#skill-packs)). `up` runs these commands for it, after it makes the projects and before it starts the run service. It imports a pack that has no import yet and pins it in each project that names it and does not pin it. `skills pin` first pins the built-in skills the harness ships, as a run's start does, so a pack beside a built-in skill is refused at the first `up`, not only after the project's first run. Otherwise `up` fetches nothing, keeps the pins and says at which revision each project pins the pack. It notes a config that names another place, ref or directory than the import records. `up --update-skills` and `sandbox-science skills update [--pack NAME]` import each pack again from its ref and pin the import in its projects. A pin that moves says what changed since the import it left (`changes` in `skills pin`'s output). The launcher says, for each project, the skills added, removed and changed, or that nothing changed. A pack that cannot be imported is reported and left as it was. One that a project cannot pin is reported for that project, and the others still pin it. An import that failed after it was kept is reported as kept with no pin moved. `up` goes on without them, and `skills update` exits 1. With `[skills] embedding_model`, the launcher's imports pass `--embedding-model` with the gateway's URL and the model key file's path, and the run service gets `--skills-embedding-model`. With `[skills] metadata_model`, they pass `--metadata-model` the same way. The import's model calls count for the first project in the config that names the pack (`--project`). An import whose embedding fails is kept: the command warns, its `embeddings` says `failed`, and the run service makes the vectors in the background.

## Pinning

```sh
sandbox-science-harness skills pin --state-dir STATE --project P --source crypto [--revision 4089e99415f3]
sandbox-science-harness skills list --state-dir STATE [--project P | --source crypto]
```

A project pins one import of each source it uses: the source's latest, or the one whose commit, archive digest or snapshot starts with `--revision`, given by at least 12 hexadecimal digits; a prefix that names imports of different snapshots is refused. Pinning another import of the source moves the pin, and its revision counts the moves; the output's `changes` then names the revision it left and the skills added, removed and changed since. A pin is refused when one of its skills has the name of a skill of another source the project pins; the refusal names the skills and the source (SK-4). `skills list` lists the imports, the latest first, or a source's, or a project's pins with their skills.

## The built-in pack

The platform's own skills are a pack in this repository, `skills/builtin/<name>/SKILL.md` (SK-40): `pdf-reading`, `literature-search`, `recording-results`, `computation`, `delegating-work`, `writing-documents` and `environment-setup`. They teach the platform's own tools and rules: reading and quoting PDFs, searching the literature through the connectors, recording and establishing results in the ledger, computing and keeping results as files, delegating checks and tasks, writing living documents, and installing software and reaching hosts. They are reference, not orders. The pack is versioned with the harness, and is imported and pinned like any pack, as the source `builtin`.

At a run's start the harness imports the pack as the source `builtin`, with the platform as author and a ref naming the harness version and the snapshot (it has no commit), when it differs from the last import, and moves the project's `builtin` pin to it; the run and those after it get the skills (SK-40). An installed harness reads the pack as its package data: the wheel carries `skills/builtin/` as `sandbox_science/orchestrator/skills/builtin_pack/`. A checkout reads the repository's directory. A harness that finds no pack logs an error, and runs keep the pin they had. A main run gets every built-in skill. A delegated run gets those whose tools it has, as `skills/builtin.py`'s `ROLES` lists them: `delegating-work`, for now. A run without the delegate tools, such as a check or a task at the last level, does not get `delegating-work`.

The user excludes any built-in skill with `skills settings --expected N --exclude builtin/<name>`. A pack whose skill has a built-in skill's name is refused when pinned. The refusal gives the command to follow, with the settings' revision, and the exclusions it leaves. Once the built-in skill is excluded, the pack's is used (SK-4). A later built-in version that adds a name a pinned pack already has leaves that built-in skill out of the project's set. The import's report says so, under `left_out`, by project. `skills list --project` shows it under the built-in pin's `left_out`, as the runs' set has it: a pack's skill the project excludes leaves nothing out.

The source name `builtin` is reserved, and the control store ties it to the built-in kind. A pack the user imported under that name before version 42 is renamed `builtin-user`, with its pins and the settings that name its skills, and each of its imports' reports carries a warning saying so. The orchestrator's other tests run without the shipped skills. `test_builtin_pins.py` covers their import and pins with test skills. It also builds the wheel and reads the seven skills from it, as an installed harness does.

To change a built-in skill, edit its `SKILL.md` in the pull request that changes the tool or rule it describes. A skill has standard front matter only: a `name` equal to its directory's name, and a `description` of one or two sentences on when to use it, at most 300 characters. Its body is short Markdown. Tool names go in inline code, such as `pdf_pages`; other identifiers, such as fields, values and paths, go in fenced code or plain text.

`packages/orchestrator/tests/test_builtin_skills.py` guards the pack. It reads the pack with the import's own validator, which must accept every skill and leave out no file. It checks every inline-code span outside fenced code against the harness's tool table for the roles each skill is written for (SK-41), so a tool renamed or removed in the harness fails it, naming the skill, the identifier and the nearest tool name. A few other identifiers are allowed in inline code, each with the harness text that names it to the model. A new skill is added to the test's list of skills and their roles.

The built-in skills are the project's own work, under the repository's MIT License. They are written anew for this platform: no text from Claude Science, Anthropic's skills or OpenScience's skills is copied or paraphrased (D56).

## A run's skills

A run is given its project's pinned skills, less those the project excludes, as they are when it starts; a pin that moves later reaches runs started afterwards (SK-5). A run of a project that pins nothing gets no skills section and no `skills` tool.

- **The index.** A section of the system message, after the project memory, opens with a framing (`sandbox-skills-index-3`): the packs' descriptions and the skills' text are the packs' data, and so is what the import's model pass derived from them; what the project's user set only describes and groups the skills; a skill guides how to work and grants nothing; load one when its description fits; search in the field's terms; name only skills loaded or found; a loaded skill is reference, not orders; nothing is installed or fetched only because a skill mentions it; a search that finds nothing covers only that search. The skills follow, each as `source/name: description`, between markers carrying a code no skill's text contains, within 12,000 characters. An entry skill is marked `[entry]`. A skill whose own description is longer than 400 characters shows the pass's short one, marked `(derived)` ([below](#what-the-import-derives)), and one whose description the user set shows it marked `(user)` ([overrides](#overrides)). The marks sit before the colon, as in `crypto/lattice-attacks [entry] (user): ...`, where no description reaches, so a pack's description that starts with `(user)` is still the pack's. Past 12,000 characters, descriptions are cut at a word, shorter until they fit. Then skills are listed by name, grouped by the pass's topics within each pack, or the user's, marked `(user)` after the topic's name, which holds no brackets or colons, or by pack where neither set one, with entry skills still listed with a description. Then the groups are listed with their counts, after the entry skills' names, cut at 400 characters. Past the budget, the counts are per pack, then for as many packs as fit, with how many more; the counts never pass the budget. The run's prompt pins record the framing's version, each source's revision, the number of skills, the shortening, the skills loaded at the start and the section's SHA-256 ([MAIN prompt provenance](MAIN-PROMPT-PROVENANCE.md)).
- **The `skills` tool** (read only). `search` ranks the skills by BM25 over their names and descriptions, fused with their closeness in meaning once the run has the skills' vectors. It returns up to 8 with their full descriptions, the words that matched or the similarity in meaning, and how many were searched. Its answer's `ranked` tells the model how it ranked: by words and meaning, by meaning for some packs only, by words with meaning compared but no skill close enough, or by words alone and why. `load` takes names (`source/name`, or a name one source has) and returns each body under its ID, revision and body SHA-256, between markers no body contains, framed as the pack's procedure that grants nothing. A name that names no skill gets a note, and the other names are still loaded; a single such name is refused. A skill loaded before gets a short note, and a load past the run's 100,000 characters of skill text, those given at its start included, is refused. Both count the bodies the run's view of its session holds, whichever run loaded them ([context management](specs/context-management.md), CM-29b). `read` returns a file of a skill's pack by a path relative to the skill, resolved inside the snapshot so that `../other/...` reaches a sibling skill. A path outside the pack is refused with `resource_outside_pack`, and one under a skill the run does not have, such as one the project excludes or a built-in skill a pack's replaces, with `not_in_set`. A skill's own `SKILL.md`, read, counts toward the 100,000 characters as a load does. A file is text or binary by the whole of it; a read shows at most 64 KiB, cut before a character it would split, or says a file is binary. The result is never cut, and a notice due at that point waits for the next. Bodies, files and descriptions are given with line feeds for line ends, and with each hidden character, and each that can pass for other text, written as its code point (`⟦U+202E⟧`), in the system message too. The cap counts the text as given.
- **Discovery.** Before a run's first model call its task is scored against its skills, and so is each user message that arrives during the run, before the call that carries it (SK-35). A message of fewer than three distinct words is not scored, by words or by meaning, and waits for nothing. A skill is shown when it shares at least two of the message's words and scores at least half the best, or, once the run has the skills' vectors, when its cosine similarity to the message reaches the embedding model's cutoff ([below](#embeddings)). The message's embedding counts toward the wait. A notice shows at most five, by ID and description, framed `sandbox-notice-skills-3` when meaning was compared and `sandbox-notice-skills-words-2`, which says the skills matched by words alone, when it was not, with the entry skills of their packs that the run has not loaded or been shown, under `entry`. The framing says the skills matched the message by its words or its meaning, as candidates rather than requirements, in the packs' words, except a description whose `description_by` says the pass or the user wrote it. It says one strong match is usually enough, to load one only if it fits, and that a skill shown once is not shown again. The notice for a message sits just before it. A run started by a comment answers the comment's own text, not its stand-in task, with the notice just before the work request, and its record names the requests (`answered: comment`). The call waits for the score at most 5 seconds of the run's clock, and goes out without a notice if scoring fails or runs over. Scoring is quick and keeps no state, so one that runs over ends on its own and nothing waits for it. Nothing is blocked and no load is forced (SK-36). Skills the run has loaded, or was shown in a notice a model call saw, are not shown again, and neither are those whose bodies or notices the run's view of its session holds (CM-29b). A notice the run dropped, as at a closing with no room left, does not count as shown. The run's record keeps each discovery under `summaries.skills.discoveries`. Each record has its notice's ID, which the record's `delivered.skills` names once a model call saw it, and what it answered: the task, or the user's messages by their IDs. It also has the skills shown with their revisions, and whether scoring used embeddings (`hybrid`), for some packs only (`partial`), or words alone (`lexical`), with `embedding` saying why: `pending`, a model change, or the failure; or whether it timed out or failed. A delegated run gets discovery on its own task.
- **In the chat.** Each `skills` call shows what it did: the skills found, loaded, already loaded or left out with why, or the file read, or what refused the call.
- **Load evidence.** Each call's record in the run's transcript names the action, the tool call, the role, the alias and the model, and for each skill loaded or file read its ID, revision and status. It has two SHA-256s: the pack's own text's (`body_sha256`, or `file_sha256` for the part of a file read), and the text as the run was given it (`served_sha256`). They differ only where line ends or hidden characters were made plain, and a load's header then names both. The skills loaded at the run's start are recorded in its summary, `summaries.skills.loads`, each with `"trigger": "start"`, its ID, revision, both SHA-256s, role, alias and the model that first answered, or `over_budget` for one left out. Only these records show that a skill was loaded (SK-22).
- **Settings.** `sandbox-science-harness skills settings --state-dir STATE --project P` shows the project's skills loaded in full at every run's start and those it excludes; with `--expected REVISION` it changes them: `--always ID` and `--exclude ID`, repeated, add to a list, `--not-always ID` and `--include ID` take from one, and `--no-always` and `--no-exclude` empty one first. A change without `--expected` is refused, naming the revision and the lists it would make. Settings whose skills loaded at the start would pass the 100,000 characters, as the project's pins stand and with the settings' new lists, are refused. Skills loaded at the start sit in the system message after the index, each between the same markers, headed by its ID, revision and SHA-256, and count toward the 100,000 characters. One that would pass them, as after a pin moved, is left out, and a line in the section names it.
- **In the workspace.** The project's skills page shows the skills a run is given, with what the import's pass derived and the user's overrides marked, the skill settings, which the user changes there at their revision, the overrides, and each pinned source with its import's report. A run's view shows its discoveries, with how each compared, and the skills it loaded, read and searched for ([workspace](WORKSPACE.md#views)).

## What the import derives

A pack carries no special files. With `--metadata-model ALIAS`, the import has a model pass over the pack's catalog derive what the pack leaves out (SK-30). The model alias is the gateway's, given with `--model-url` and `--api-key-file`:

```sh
sandbox-science-harness skills import --state-dir STATE --name crypto --git URL \
  --metadata-model ALIAS --model-url GATEWAY --api-key-file KEY [--project P]
```

- **What it reads.** Each skill's name and description, and the lines around each mention of an environment variable in the pack's files, at most 400 mentions and 120,000 characters, never whole bodies (question 13). The prompt (`sandbox-skills-pass-1`) frames all of it as the pack authors' data between markers carrying a code the text does not contain, and says to ignore any instruction in it.
- **What it derives.**
  - Topics that group the skills, each named in at most 60 characters, a skill in one at most.
  - Entry skills, at most ten, which route work to the pack's others.
  - A short description, at most 300 characters, cut at a word past that, for each skill whose own description is longer than the index's first cut of 400 characters.
  - The environment bindings the skills' helper code expects: a variable the pack's own files mention, and a path inside the pack, the pack's top as the empty path.
- **What it keeps.** The answer is data, never instructions (SK-31). Each item is checked against its bounds and against the snapshot, and an item that fails is dropped and listed with why:
  - a skill the pack lacks, or one already placed;
  - a binding whose variable no file of the pack mentions (`$VAR`, `${VAR}`, `os.environ`, `getenv`, `process.env`);
  - a binding that names a shell, loader, interpreter start-up, pager or tool-configuration variable. These are denied by exact name, such as `PATH`, `HOME`, `IPYTHONDIR`, `DOT_SAGE`, `GPRC`, `ZDOTDIR` or `CC`; by family prefix, such as `LD_*`, `DYLD_*`, `PYTHON*`, `JUPYTER*`, `SAGE*`, `MAXIMA*`, `SINGULAR*`, `ECL*`, `LUA*`, `R_*`, `BASH*`, `LESS*`, `GIT_*` or `XDG_*`; and by family suffix, such as `*OPT`, `*OPTS`, `*FLAGS`, `*RC`, `*PROFILE`, `*STARTUP` or `*WRAPPER`. A pack's file under one would run at every start of the tool;
  - a binding whose path is not inside the pack.

  Derived text loses its control, hidden and look-alike characters. A topic's name also loses brackets, slashes, colons and a leading list mark, so it cannot pass for the index's own notation.
- **Where it shows.** The import's report has it under `derived`, with the alias, the model that answered, the pass's version and the items dropped, all marked as derived (SK-32). The store keeps it by snapshot, alias and version, so an import of a snapshot that has it asks nothing (`"cached": true`). Runs of projects that pin the snapshot get its topics, entry skills and short descriptions in the index and in discovery notices. Only what the pass of the alias the run service is given derived is served (`--skills-metadata-model`, which the launcher passes from `[skills] metadata_model`), and only what this harness's version of the pass derived. Without the alias, runs get none. The workspace's skills page shows what runs get: the launcher gives it the same alias (`sandbox-science-workspace serve --skills-metadata-model`). The import's report lists, under `held`, each binding not namespaced to the pack, with why ([which bindings are set](#which-bindings-are-set)). Runs set them when they stage the pack ([helper staging](#helper-staging)). A call the gateway answers with a 5xx, as Cloudflare's 524, or that times out, is tried once more. A pass that still fails, or that the gateway refuses or answers with something other than its data, leaves the import as it is, with a warning that says the same import, or `sandbox-science skills update`, runs it again, and stores nothing. A call the gateway answered and charged for still counts, whatever its answer held.
- **Cost.** The pass's call counts, with its tokens and the cost the gateway reported, for the project `--project` names. It shows under the role `metadata` with the others (RS-6a). Without `--project` the import only reports it. `--project` counts the import's embedding calls for the project too. A project that does not exist yet, as one new in the launcher's config before `up` makes it, counts nothing, with a warning, and the import goes on.

### Overrides

The user sets, per project, what wins over the pass (SK-33): a skill's short description, its topic and whether it is an entry skill, and the derived bindings a pack may not have. `sandbox-science-harness skills override --state-dir STATE --project P` shows them; with `--expected REVISION`, the skill settings' revision, it changes them:

```sh
sandbox-science-harness skills override --state-dir STATE --project P --expected 3 \
  --skill crypto/lattice-attacks --description "Lattice reduction for key recovery." \
  --topic Lattices --entry
sandbox-science-harness skills override --state-dir STATE --project P --expected 4 \
  --source crypto --unbind CRYPTO_DATA --approve SKILL_DIR --confirm
```

- **Fields.** `--description` (1 to 300 characters) and `--topic` (1 to 60) lose control, hidden and look-alike characters as derived text does, and a topic also brackets, slashes and colons. `--entry` or `--not-entry` sets whether the skill routes work to its pack's others. `--clear description`, `topic`, `entry` or `all`, repeated, gives a field back to the pass. `--unbind VAR` and `--rebind VAR`, with `--source`, take a derived binding away and give it back; `--approve VAR` and `--unapprove VAR` set a binding not namespaced to the pack, and take that back (an approval without `--confirm` says what is known of the variable and is refused); `--prefix PFX_` gives the source a namespace of its own, and `--no-prefix` takes it back ([which bindings are set](#which-bindings-are-set)). A change without `--expected` is refused, naming the revision and the overrides it would make. A project overrides at most 500 skills, and takes away and approves at most 500 bindings each.
- **What wins.** The user's field wins over what any pass derived, and applies without a pass, as when no `--skills-metadata-model` is given. The index marks the user's description and topic `(user)`, where the pass's description is marked `(derived)`, and a discovery notice gives `description_by`, `user` or `derived`, beside a description its pack did not write. The bindings a project's runs set are the pass's that are namespaced to the pack or approved, less those it took away.
- **What shows.** Overrides sit in the project's skill settings, with the skills loaded at the start and those excluded, under the same revision and author: `skills settings` and `skills override` show them all, and neither changes the other's. `skills list --project` shows each pin's under `user_set`, and an import's report shows each project's under `user_set`, with those of skills the snapshot lacks named under `kept_for_absent_skills`. A report lists the projects' overrides up to 256 KiB and counts the rest under `user_set_more`.
- **Pins.** Overrides name a skill by its qualified ID, not by snapshot, so they survive a new pin or import that keeps the skill, and come back with one that brings it back.

### Which bindings are set

A pack's own files can mention any variable, so neither the mention rule nor a deny-list can stop a hostile pack: the variables that make some tool load a file, as `GST_PLUGIN_PATH` or `NLTK_DATA` do, are too many to list. The owner decided (2026-10-16) that a derived binding is set only when (SK-31):

- it is **namespaced to the pack**: its name starts with the source's name in capitals, `-` as `_` (the source `crypto-tools` sets `CRYPTO_TOOLS_DATA` without asking), or with a prefix the project's user gave the source with `skills override --source S --prefix PFX_` (capitals, digits and `_`, 3 to 32 characters, ending in `_`, and no prefix of the deny-list's families); or
- the project's **user approved it**, with `skills override --source S --approve VAR`, which prints what is known of the variable (the pack's file the pass binds it to, and whether its name says a tool finds files or programs under it) and is refused until given `--confirm` as well.

A namespace grants nothing when it belongs to something else (security review of #486, which proved a pack named `gap` binding `GAP_ROOT_PATHS`, whose `init.g` Sage's libgap ran, and one named `gcc` binding `GCC_EXEC_PREFIX`, whose `cc1` ran):

- it is shorter than 3 characters, its `_` included;
- it is a family on the deny-list, which holds the shell, loader and start-up families and tools' own, such as `GAP_`, `GCC_`, `HDF5_`, `GLIBC_`, `OMPI_`, `OPAL_`, `PHP_`, `SYSTEMD_`, `SUDO_`, `GS_`, `GH_`, `TERMINFO`, `SESSION_`, `PROJECT_`, `GUILE_`, `COVERAGE_`, gcc's (`COMPILER_`, `COLLECT_`, `GFORTRAN_`), Sage's components (`KENZO_`, `CREMONA_`, `FOURTITWO_`, `JMOL_`, `NTL_`, `FLINT_`, `LIE_` and others), and unixODBC's, Vim's, Tix's and OCaml's (`ODBC`, `VIM`, `TIX_`, `CAML_`, `OCAML`);
- it starts a name or family on the deny-list, which a tool reads: the list holds every variable Sage 10.9's `sage/env.py` reads, gcc's (`COMPILER_PATH`, `DEPENDENCIES_OUTPUT`, `SUNPRO_DEPENDENCIES`) and the extension builds' (`LDSHARED`, `LDCXXSHARED`, `CCSHARED`), so the source `kenzo` gets no `KENZO_` for `KENZO_FAS`, nor `graphs` `GRAPHS_` for `GRAPHS_DATA_DIR`, whether or not the families name the tool (security re-check of #486, which proved `kenzo` binding `KENZO_FAS`, which Sage's ECL loaded as Lisp, and `compiler` binding `COMPILER_PATH`, whose `cc1`, `as` and `ld` gcc ran);
- it would claim another pinned source's namespace, as `SS_` would `SS_TEST_`'s.

A prefix the user sets is refused for the same reasons. A variable two pinned sources bind is held for both. Any other is **held**: the import's report lists it under `derived.held`, with its path and why, the import's output says how to approve one, and the project's skills page lists it with the bindings it sets. A load's answer names it as held until the project's user approves it, without the command: the model is not handed one. The deny-list ([above](#what-the-import-derives)) stays as the backstop: a variable on it is never set, namespaced, prefixed or approved, and an approval or prefix of one is refused. A binding the project took away with `--unbind` is held whatever its name. An import refuses a pack with a file named as one of git's own, `HEAD`, `commondir`, `gitdir` or `config.worktree`, in any case and at any depth (as it leaves out a `.git` name, in any case): git run in its folder would take it for a repository and read a config, whose `core.fsmonitor` or hooks run code. A folder with `HEAD` and `config` is a bare repository; the re-check of #493 proved a split one, `HEAD`, `commondir` and `config.worktree` in one folder and `config` in the other, whose fsmonitor git 2.53 ran. The images also set `safe.bareRepository=explicit` in git's system config (rebuild the images to have it). Approvals and prefixes are the project's, in its overrides, at the settings' revision; they survive new imports. `SkillStore.bindings` gives a project's set and held bindings, checked against today's deny-list, as an older pass may have kept a variable it now refuses.

## Helper staging

When a run loads a skill whose folder holds more than Markdown, such as a script, the run service stages the skill's pack in the session's environment (SK-16), through the worker ([worker](WORKER.md)):

- **Where.** At `<project root>/.skills/<source>/<snapshot>` in the environment, one folder a pack revision, shared by the environment's sessions. The worker writes the snapshot's files in batches, then makes them read-only (files 0444, or 0555 if executable, folders 0555) once each file's SHA-256 is as expected.
- **Checked at each load, not at each use.** The read-only modes are advisory: sandbox code runs as the same user and can change them and the files (D48). So each load that names the pack checks every file's size and SHA-256 first, and a file that differs, is missing or is more than expected, a FIFO, a symlink or a tree deeper than 32 folders or larger than 8,192 entries has the snapshot staged again, from nothing. Between two loads nothing is checked: an execution that runs a helper after sandbox code changed it runs the changed file. A body a run's view holds from a past run is checked at its first load in the run.
- **Bindings.** The run's shell, job and cell executions then get the pack's bindings the project sets ([which bindings are set](#which-bindings-are-set)) as paths in the staged folder, the pack's top for the empty path. Each staging asks the worker which of the pinned sources' namespaces, in lower case, are commands on the environment's `PATH`; such a namespace is that command's, and grants nothing. A binding never replaces a variable the environment sets itself, such as `SESSION_WORKSPACE`, `PROJECT_SHARED`, `HOME` or `PATH`: the executor refuses the execution. A model that sends `bindings` in a tool call is refused. A staging that fails takes the pack's bindings out of the run's executions. Those held are named in the load's answer, with why, and never set. A cell's bindings are the whole set its kernel's next start takes: a kernel already running keeps those it started with, and the cell's result says to restart it; a restart takes the latest, so a binding taken away leaves the kernel too. Without the pass alias (`--skills-metadata-model`) a run has no bindings, and the pack is still staged.
- **What the model is told.** The load's answer ends with where the pack is staged, the variables the executions get and those held.
- **Records.** The load's record in the run's transcript has `staging`, one item a pack: the skill, source, revision and snapshot, the number of files, the location, and the state: `unchanged`, `staged` or `restaged` with the attempt and the paths that differed (up to 20, with their count), or `failed` with the worker's error. A failed staging leaves the load as it is, and the answer says to run nothing from the pack.

## Embeddings

With an embedding model, search and discovery find a skill by what a message means as well as by its words, so "how many rows" finds a skill that "counts the lines" (SK-29, SK-35). The model is an alias of the model gateway, which serves OpenAI-compatible `/embeddings`:

```sh
sandbox-science-harness skills import --state-dir STATE --name crypto --git URL \
  --embedding-model ALIAS --model-url GATEWAY --api-key-file KEY
sandbox-science-harness run ... --model-url GATEWAY --api-key-file KEY --skills-embedding-model ALIAS
```

- **What is embedded.** Each skill's name, description and the first 1,500 characters of its body. The vectors are kept with the snapshot, unit length, under the model the gateway reported and their dimensions, the vectors' space. An import of a snapshot whose vectors are in the space the alias last answered in asks the gateway nothing. Otherwise one skill's embedding tells the space, and the others are made in it. The import's output says, under `embeddings`, the alias, model and dimensions, how many vectors it computed and reused, and the cost the gateway reported. When embedding fails the import is kept: the command warns, `embeddings` says `failed`, and the same import again embeds the skills.
- **In a run.** No run waits for the skills' vectors. At its start a run reads those the store has in the alias's last space. The others are made in the background, one task per snapshot in the process, which later runs share. Until they exist the run compares by words, and its records say `pending`. Two runs starting at once share one task. A failure is tried again after a backoff that doubles from a minute to an hour, and the records say the failure meanwhile. Search and each discovery embed their text (its first 2,000 characters). Discovery's 5 seconds and search's own 5 seconds, both on the run's clock, cover that embedding.
- **Reading answers.** An answer is read to its end, up to 64 MiB, however the gateway sends it, not in one read of what has arrived. A gateway's error page that is not JSON or plain text, such as a proxy's HTML, is named by its type and size, never quoted.
- **One space.** Every answer is checked against the vectors' space. A pack whose vectors are of another model, as when the alias was pointed at another one, is not compared, and its vectors are made again in the new space at once, in the background, and by a run in another process too. When no pack can be compared, that is an embedding failure, never a score. When only some can, the record says `partial` and why. A gateway that reports the alias itself as the model's name cannot be told apart this way from one whose alias now names another model of the same size.
- **Scoring.** A search ranks by reciprocal rank fusion of the BM25 order and the order by cosine similarity. A skill counts as close in meaning at the cutoff for the embedding model's family, found in the name of the model the gateway reports, which may be an alias: 0.34 for OpenAI's `text-embedding-3-` models, and 0.45 for any other, defaults until per-pack thresholds (SK-34). The third OpenAI models put unrelated texts near 0.3. In lab 43, with `text-embedding-3-small` on the crypto pack, a paraphrase found the right skill at 0.358, and the best unrelated or weaker ones scored 0.317, 0.310 and 0.309. Each search and discovery that compared by meaning records the `cutoff` and how many skills came `close`. The run's summary says, under `summaries.skills.embeddings`, the alias, the spaces of the vectors the run had by its end, and why any were missing.
- **Cost.** Each embedding call the gateway answered counts for the project under the role `embeddings`, with the cost it reported, beside the main agent's, delegated runs', the reviewer's and the job watcher's (RS-6a). The background's calls count for the project whose run started them, those of a build that failed later included. A call the run's cancellation or a timeout ended before its answer costs nothing, as the call is cancelled with it. An import from the command line reports its cost. An alias longer than 200 bytes, which the store cannot keep, is refused when the command's arguments are read.

## Where it is kept

In the control store (`control.sqlite3`), written once: `skill_blobs` holds each file's content by its SHA-256, shared by every snapshot; `skill_snapshots` and `skill_files` hold each snapshot's files, a snapshot being named by a SHA-256 over its paths, whether each is executable and their contents' SHA-256; `skill_skills` holds each snapshot's skills with their descriptions, body SHA-256 and metadata; and `skill_imports` holds each import with its report, of kind `git`, `archive` or `builtin`. `project_skill_pins` holds each project's pins, and `project_skill_settings` each project's skills loaded at the start and excluded, and its overrides of what the pass derives. `skill_vectors` holds each snapshot's skills' embeddings, written once, by model and dimensions, as little-endian float32. `skill_vector_spaces` holds the space each alias last answered in, by snapshot, and `skill_embedding_calls` each embedding call, by project, with its cost. `skill_metadata` holds what each pass derived, by snapshot, alias and version, with what it dropped, and `skill_metadata_calls` each pass's call.

Code: `packages/orchestrator/src/sandbox_science/orchestrator/skills/` (`index.py` for the section, `tool.py` for the `skills` tool, `discovery.py` for the notices, `embeddings.py` for the vectors, `derive.py` for the import's pass) and `cli_skills.py`.
