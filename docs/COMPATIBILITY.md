# Compatibility

How the orchestrator, the workspace and the worker stay compatible, and how a request keeps its identity across releases. Owner decision 8 of the [refactoring plan](../.agents/refactor-plan/PLAN.md) sets the policy until M3.

## Lockstep releases

The orchestrator, the workspace and the worker of one release are upgraded together, with the shared `contracts` and `policy` libraries. Nothing negotiates versions. Every contract model refuses fields it does not know, in requests and responses alike (`Contract` in `packages/contracts`, `extra="forbid"`), so a new field breaks whichever side does not know it, in either direction. The version check turns that into one clear error on the first request:

- `PROTOCOL_VERSION` in `contracts/worker.py` is the worker API's version (14). It changes with any change to an existing request or response ([changing a contract](#changing-a-contract)). Version 14 adds `DriftAcceptance.listings`, the drifted listings a re-acceptance accepts, which the worker requires to match those unaccepted, and `DriftSummary.drifts`, every unaccepted listing (D98 review). Version 13 adds job sandboxes (`JobRequest.profile` and `inputs`, job manifests and profile grants in `Capabilities`; [job sandboxes](specs/job-sandboxes.md)) and the operator's permission-request routes with the per-project `confirm` route the direct MCP path uses ([MCP connectors](MCP-CONNECTORS.md)). Version 12 adds `Capabilities.kernel_reason`, the executor's bounded reason for offering no Python kernel. Version 9 accepts file writes up to 100 MiB, while read ranges and executor replies retain their limits. Version 8 adds generated binding inventory projections and execution digest fencing ([binding inventory](specs/skill-binding-inventory.md)). Version 7 adds the PDF request's `draw` operation, which draws a recorded figure as a PNG for `view_image` ([figures](specs/figures.md), FG-35). Version 6 adds `bindings` to shell, job and cell requests, the skill packs' environment variables ([skills](SKILLS.md#helper-staging), SK-16). Version 5 adds `deleted_files` and `deleted_files_truncated` to execution results ([research artifacts](specs/research-artifacts.md), RA-33). Version 4 gave delegated runs kernels of their own ([plans and delegation](specs/plans-and-delegation.md), PD-37): `CellRequest`, `KernelRestartRequest` and `SessionCloseRequest` name a run, `KernelInfo` says whose kernel it is, and a session's kernel listing holds its runs' kernels too.
- Every response from the worker's application carries it in the `X-Worker-Protocol` header, errors and event streams included. `Capabilities.protocol` carries the same number. Errors that never reach the application carry no header: aiohttp's own refusals of a malformed request, and answers from a proxy or TLS terminator in front of the worker.
- The worker client (`orchestrator/worker_client.py`), which the harness and the workspace both use, the workspace's provisioning observer and the launcher's client for the research sandboxes (`launcher/sandboxes.py`) refuse a response with another version, or a successful one without the header. The error is a `WorkerProtocolError` of kind `unsupported` ("version mismatch: the worker reports protocol '9', this client speaks protocol 10; upgrade the orchestrator, workspace and worker together"). The client does not retry it, and no caller reads it as a feature the worker lacks. An error status without the header is reported as that HTTP error instead: `unavailable` for 502, 503 and 504, `internal` otherwise.
- The clients send the header too. The worker refuses a request that names another version with the same `unsupported` error (HTTP 422), before it reads the body. A request without the header, such as one written by hand, is served.

New routes with new contracts leave the version as it is ([changing a contract](#changing-a-contract)): the file tools' `POST /v1/files/edit`, `/v1/files/glob` and `/v1/files/grep` (`EditFileRequest`, `GlobRequest`, `GrepRequest` and their results) came at version 13, as did `POST /v1/mcp-listings` (`ListingReport`, `ListingReported`), the agent runtime's listing reports (D98). The worker client turns a 404 without the worker's own error body on those routes, an older worker's answer, into `unsupported` ("this worker predates edit_file, glob and grep"), never an unknown effect, since nothing ran.

The executor ships inside the worker package, so its protocol with the worker is internal to one release. An optional `hello` field the worker reads with a default, such as `kernel_reason`, needs no executor protocol change: an older executor omits it and the worker then reports none. So does `file_tools`: an executor started before the file tools, in a sandbox that lives on, omits it, and the worker answers an edit or a search there `unsupported`, naming the environment's recreation, before sending it. Executor protocol 3 enforces current generated binding restrictions and surviving-kernel inventory digests; earlier executors must be recycled before binding-bearing calls or cells are admitted. A policy that uses a new policy field, such as `packages.agpl_exceptions`, needs a policy library that knows it in the worker, the policy middleware and the MCP proxy, so they are upgraded together too.

Worker protocol 8 also carries optional host-built execution authority, scoped operation lookup, and recovery epoch installation ([worker recovery authority](specs/worker-recovery-authority.md)). Missing authority preserves legacy context serialization; once a session is fenced, unowned agent mutations are denied. Authenticated operator permission is independent of the context's actor name.

## Request identity

A client names each operation with an ID of its own. The worker stores the request's digest with the operation; the same ID sent again with the same request returns the same execution or provisioning operation, and with a different request it is a `conflict` ([tools spec](specs/tools.md#lifecycle-idempotency-and-reconnection)).

The digest is `request_digest` in `contracts/canonical.py`: SHA-256 over a domain naming the request type (`worker.execution.<kind>`, `worker.provision`) and the sorted-key JSON of the fields whose values differ from their defaults. Therefore:

- A field added with a default leaves every stored identity unchanged, as long as the default means what omitting the field meant before.
- A value equal to the default is the same request as omitting it. A choice such as "use the policy's default" is therefore its own value: `JobRequest.timeout_seconds` is `None` for the policy's default, which differs from asking for 24 hours.
- Operations stored before protocol 2 hold the older digest, pydantic's JSON of the whole request. The worker still accepts it (`worker/identity.py`), so they replay across the upgrade. That fallback goes once no worker state from before protocol 2 remains.

## Changing a contract

- Any change to an existing request or response raises `PROTOCOL_VERSION`: a field added, removed or changed, a status or an error kind. A new route with new contracts, which no existing client sends, does not, as the admissions, revisions and environment list and suspend routes did not.
- A new request field gets a default that means the old behavior.
- Changing a default's meaning, or how a field is written in JSON, changes the identity of stored operations. Such a change keeps accepting the old digest for one release, as `worker/identity.py` does now.
- The worker stores contract JSON as its records and validates it again on read, so a stricter validator can make stored records unreadable. The worker's store is versioned ([worker](WORKER.md#sandbox-daemon-and-recovery)), and its admission tables check their values when they are written. Executions, events and provisioning records are still contract JSON validated on read. Plan item C-08 covers the rest.

## Before independent upgrades

When components must be upgraded independently (M3 placement), the policy changes: responses accept unknown fields (`extra="ignore"`), requests stay strict, changes are additive only, new behavior is gated by `Capabilities.features`, and the version check accepts a range. None of this is built.

## The worker-side unit

The [unit](UNIT.md) runs the worker, the policy middleware and the package cache from one config file whose sections are those services' own settings. Their settings keep this document's rules where they have them; the unit adds none to a service's settings, and refuses unknown sections and unknown `[unit]` keys. A new `[unit]` option has a default that keeps the old behavior. A service's `serve --settings` command and its settings file stay valid as long as the unit runs them (a `settings_file` section names one as it is), so moving a deployment to the unit changes no setting. Running the three as separate units from separate files is deprecated for one release.
