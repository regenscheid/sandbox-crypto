# Project memory

The project memory as built, against its specification, [project memory](specs/project-memory.md). It keeps what a project has learned about how to work, as short entries in the control store (`orchestrator/memory.py`), which agents propose and the user decides.

## What is built

**Entries (PM-1).** A project's memory is a list of entries, each with an ID unique in its project (`mem-1`, `mem-2`: one counter per project), its text and a revision. Text is Markdown with LaTeX, 1 to 1,000 characters after surrounding white space is taken off. Every agent role receives an accepted entry, so what the user approves must be all an agent reads (threat model, A3): a proposal's text and reason and the user's own text are refused, never stripped, when they hold a character the user may not see, as it is or as a character reference such as `&#x202E;` (`check_agent_text`: controls but tabs and line feeds, format characters such as zero-width, bidirectional and tag characters, separators, private-use and unassigned code points, and every Default_Ignorable code point such as a variation selector); the refusal names the code point and where it is. Markdown and math that a rendering would hide, such as a link reference definition or `\phantom`, are kept as written; the Memory page shows the exact text. A memory holds at most 100 entries; to add more, the user removes or merges some. Every change of an entry appends a version, written once (triggers refuse updates and deletions): the memory's version it made, the entry's revision after it, what changed (`added`, `edited`, `removed` or `moved`), the text, the entry's place, who applied it and when, and the proposal it came from, if any, whose record says who proposed it (the run, its role and session, the model alias and the model that answered), when and why. A removed entry keeps its history. The memory's **version** counts the changes of its accepted entries; each change raises it by one, and a decline leaves it.

**Order (PM-7).** The entries are in the Memory page's order: oldest accepted first, unless the user moved one. A move swaps an entry with the one before or after it, and appends a version to both that keeps their revisions: an entry's revision counts the changes of its text, so a move leaves a proposal or an edit that names a revision current. Every version keeps the entry's place, so the memory at an earlier version can be rebuilt in its order then, for an agent that must work from the same memory as the run it belongs to (PM-8).

**Proposals (PM-2, PM-3).** An agent run proposes one action with a reason of 1 to 500 characters: `add` with text, `change` with an entry, the revision it read and the new text, or `remove` with an entry and the revision it read. A proposal against an entry that changed since, or was removed, is refused, naming the current revision. A proposal waits (`prop-1`, `prop-2`: one counter per project) until the user accepts or declines it; nothing an agent does changes an entry. A project holds at most 50 waiting proposals and a run makes at most 10, waiting or decided; beyond them a proposal is refused, saying the user has not caught up. A project keeps at most 10,000 proposals and 50,000 changes, its history included.

**Decisions (PM-2, PM-4).** Only the user changes the memory: accepting a proposal applies it as a new version, attributed to the proposing run with the user's acceptance recorded; declining applies nothing. Accepting a change or a removal names the entry's revision the user saw beside the proposal: when the entry changed after the proposal was made, the user has seen the current text, and the accepted change becomes the next revision with both authors in its history (PM-F6). The user also adds, edits, removes and moves entries directly, naming the revision seen; a stale revision is a conflict that names the current one, and an edit that keeps the text changes nothing and is refused.

**The agent tools (PM-3).** Main and delegated runs have `memory_list` and `memory_propose` (`orchestrator/memory_tools.py`); the consistency reviewer and the job watcher have neither, since they get no tools of the run's. `memory_list` answers the memory's version and the accepted entries in order, with their IDs, revisions, provenance and text (see Provenance in recall below), within the run's output budget: a long memory comes in parts, each giving `next_from`, where the next begins. `memory_propose` takes one action, as above, with a `basis` and `anchors` (see below), and answers the proposal's ID and that it waits for the user. A proposal is the run's: its session, role, model alias, the model that answered and the tool call; the arguments cannot name another author, and the operation ID is the tool call's, so a repeated call returns the first answer. Listing is a read. A proposal changes nothing until the user accepts it, so it has an effect class of its own, `proposal`, which the plan fence lets pass even while the session's plan is a draft, unlike `ledger_change`; a run that no longer holds its session may still not propose.

**The Memory page (PM-4, PM-7, PM-13).** The GUI's Memory page (`#/projects/<project>/memory`) lists the waiting proposals, each with its text beside the entry as it is now, the run that proposed it, its role and model, when and why, the basis it was proposed with and its anchors, with Accept and Decline; then the accepted entries, each with its basis (and that the user accepted an agent's proposal), the date its text was recorded, its scope and its anchors, and Edit, Move up, Move down, Remove and the history one click away, which shows the basis and anchors of each version; then a form for a new entry. Accepting a change or a removal sends the revision shown beside it, so a proposal whose entry changed since is accepted only against the text the user saw; a proposal whose entry was removed can only be declined. The page flags entries past the 16,000 characters agents receive and the overflow, with the total. The project page links to it, with how many entries the memory has and how many proposals wait. Every text, a proposal's, an entry's and each version's, is shown first as the exact string every agent reads, each character the user may not see as its code point, with a change proposal's differences from the entry now word by word; a rendering, which can hide a link reference definition, a link's title or `\phantom` math, comes apart, labelled as a preview, with the links it holds listed (`ApprovalText`; threat model, A3; [workspace](WORKSPACE.md#showing-untrusted-text)). A move's version says the text did not change.

**Provenance in recall (PM-3, PM-6, PM-13; control store version 83).** Each item `memory_list` returns, and each entry of the system message's section, says what kind of record it is. `memory_list` gives, besides `entry_id`, `revision` and `text`: `prefix`, `basis`, `accepted`, `recorded_at` (UTC), `scope` and, when the version has them, `anchors`. The **basis** is `user` for an entry whose text the user added or edited (the versions already record it), and for an accepted agent proposal the basis it was proposed with: `user_quoted`, `observed` or `interpreted`; an agent's entry accepted before version 83 is `not recorded`, and so is a proposal made before, if accepted later. The user's acceptance never makes an agent's text `user`. The text of an entry is that of the version that wrote its revision: a move changes neither the basis, the anchors nor the date. The **scope** is `project` for every item; `session` and `run` are reserved for a store of session or run notes, which the platform does not keep (bounded run memory stores a run's history, not notes a memory tool recalls). The **prefix**, at most 80 characters, comes before the text, such as `[2 h ago] [observed, accepted] [mem-3@2 · project]`: the age at the call (`just now`, `N min ago`, `N h ago`, `N d ago`, the date in UTC past 30 days), the basis (`[user]`, `[user, quoted]`, `[observed]`, `[interpreted]`, `[not recorded]`; `accepted` is added after `user, quoted`, `observed` or `interpreted` for an accepted agent proposal), and the ID, revision and scope. The anchors follow the text, by name (`msg-…`, with `[start:end]` for a range of a tool's output, `artifact@revision`, `document#block@revision`, `entry@revision`, or `mem-3@2`). The system message's section shows the same prefix with the date in place of the age, on the entry's first line, and the anchors on a line after the text (`Anchors: …`), so the section is the same for the same memory version; prefixes and anchors count toward the 16,000 characters. `memory_propose` takes `basis` (`user_quoted`, `observed` or `interpreted`, the default) and up to 10 `anchors`, of the kinds the ledger accepts (`message`, `call`, `artifact`, `document`, `entry`, and `memory` as `mem-3@2`; [ledger](LEDGER.md)). Code checks them at the proposal with the ledger's own check (`ledger/provenance.py`: `resolve` and `check`), where the author may look (a main run's session, a delegated run's own run and the messages its brief names): every anchor must exist, `user_quoted` needs a quote of the user's own words found verbatim in a message the user wrote, and `observed` needs an observation (a tool result or a range of one, or an artifact revision) that holds every number of the text. A proposal the basis does not bear out is refused with `provenance_required`, naming what failed, and nothing is stored; a proposal with the default basis needs no anchor. The proposal and the version that accepting it makes keep the basis and the anchors, as the names they resolved to: a quote is checked and not kept. The tables are `memory_versions` and `memory_proposals`, which gained `basis` and `anchors` in version 83: a version written without a proposal got `user`, the others and the earlier proposals `not recorded`, and the rows stay unchangeable. A **ledger change** may name a memory entry at a revision, `{"memory": "mem-3@2"}`, as an anchor: the entry and revision must exist (a removed entry's earlier revisions do), and it is never an observation, so a memory anchor alone never makes a change `observed`. Nothing in a note's text, basis or anchors is an instruction or a permission; the basis says what kind of record a note is, never that it is true.

**Changes and events (PM-11).** Every proposal, decision and direct change is one change of the control store, with its operation receipt (scope `memory`; an agent's receipts are its run's, the user's are the user's) and its events on the event log (subject `memory`): `memory.proposed` and `memory.decided` under the proposal, with the proposing session, and `memory.changed` under the entry. A retry with the same operation ID returns the first result, and the same ID with another request is refused. The tables check their values when they are written, and the memory's version and its counters never go back (control store version 24).

**In a run's system message (PM-5 to PM-9).** Every main and delegated run is given the accepted entries as a section of its system message, after the MAIN base and any research framing and before the planning guidance (`orchestrator/memory_prompt.py`). The section is a framing, `sandbox-memory-run-2`, which says the entries are notes the user accepted, to follow as guidance, which grant no tool, path, network access or approval, that changes go through `memory_propose`, what the prefix before each note says, to prefer `user` and `observed` notes to `interpreted` and `not recorded` ones and to name a note's ID when relying on one; then the memory's version and the entries in order, each between markers that carry a code no entry contains (`<entry-CODE id="mem-N" revision="R">` … `</entry-CODE>`, inside `<memory-CODE>`), and inside them the entry's prefix and text, then its anchors, so that no text inside an entry can end it or the memory and fake what follows; the code is derived from the entries, so the same version always gives the same section; then, when the memory is longer than the bound, a line saying how many entries were left out and that `memory_list` lists them all; and an end line. Entries are given whole while the whole section as sent, framing and markers included, stays within 16,000 characters: 2,000 of them are kept for the framing and the other lines, and the entries' blocks, which count their prefixes and anchors, take the rest, about 12 entries of 1,000 characters. That is roughly 4,000 to 8,000 tokens, more for math and scripts other than Latin. The bound counts characters (Unicode code points, as Python's `len` does); the pin records the section's UTF-8 byte count (`bytes`), which is larger for text outside ASCII. The markers and the framing keep an entry from imitating the section's own structure in its text; they do not protect against a model server that parses chat-template tokens inside message content, such as `<|im_end|>` on some self-hosted backends, where an entry could end the system message itself. Such a backend must treat those tokens in content as text. Waiting and declined proposals and the entries' histories are never given. A memory without entries gives no section. The memory is read once, when the run starts, and kept to its end: an entry accepted meanwhile reaches the next run. A run of a tree is given the version its root was given (`RunRequest.memory_version`, which delegation will set from the root run's own pin, never from an agent's arguments; nothing starts delegated runs yet), rebuilt in its order then even if entries changed since. The run's record pins it (`PromptPins.memory`): the framing's version, the memory's version, the entries given as `mem-N@R`, how many were left out, and the section's byte count and SHA-256; the section is also among the record's section pins, with no version, since its text is not from the catalog ([MAIN prompt provenance](MAIN-PROMPT-PROVENANCE.md)).

**The reviewer and the watcher (PM-5, PM-6, PM-8).** The consistency reviewer is given the memory the reviewed run was given when it started, after its rubric, under the framing `sandbox-memory-reviewer-2`: guidance on how the work should be done, not evidence, so a claim is not supported because a note states it. The job watcher is given the memory as it is at each check, since a job can outlive its run, after its system text, under the framing `sandbox-memory-watcher-2`: guidance, not instructions to act. Each records what it was given in its call's envelope, format 2, with the same memory pin as a run's record ([reviewer](REVIEWER-PROMPT-PROVENANCE.md) and [watcher](WATCHER-PROMPT-PROVENANCE.md) provenance). Neither has the memory tools.

**The workspace (PM-4).** `GET /api/v0/projects/{project}/memory` answers the entries in order, the version, their characters, how many of them an agent would receive within the bound of 16,000 characters for the whole section as sent, its framing and the markers around each entry included (PM-7) and how many proposals wait; `GET …/memory/proposals` the waiting proposals, oldest first, each with the entry it would change as the entry is now; `GET …/memory/{entry}/history` an entry's versions, newest first, 50 at a time before the memory's version `?before=`; `POST …/memory` the user's change, under the workspace's same-origin guard ([workspace](WORKSPACE.md)).
