# MCP connectors and authentication

Confirmed: D64, D66 and D98, which retired D67's MCP proxy on 2026-10-26 (the owner). **The agent's MCP calls are made by the agent runtime's own client, from its sandbox, and decided by OpenShell's native `protocol: mcp` rules and the policy middleware** ([the direct path](#the-direct-path), [prototype](specs/mcp-middleware-prototype.md)). The babbage lab against the owner's portal, with the production wiring, passed proofs 1 to 4 live; proof 5 (binary results) is covered by tests, since none of the portal's servers returns an inline binary. Research code has no MCP access. The MCP proxy, its package and its image are deleted; `[mcp_proxy]` is refused, and `sandbox-science migrate-mcp-config` rewrites it ([migrating](#migrating-from-mcp_proxy)). What the proxy alone did is kept or listed as a loss ([below](#what-the-proxy-did-that-the-direct-path-does-not)). Tools are classified by effect, with hints for unmentioned tools and a drift test (D96, built: [classification files](#classification-files)); grants are per class, server and project under admin ceilings (D97); and MCP lockdown is `declared` or `locked` per project (D95, built). See the [decisions](DECISIONS.md). The connector auth service is not built, and the OAuth design below predates the retirement: it was written for the proxy. The text below describes the connectors as built.

- crypto-research-mcp is the phase 1 connector; others are added later.
- MCP services authenticate mainly with OAuth.
- `Authorization` and custom-header authentication should also be supported.
- A secrets manager should keep raw credentials away from agents.

**crypto-research-mcp uses a Cloudflare Access service token, not OAuth** (agreed by the owner, 2026-10-14). It is a `headers` server: its two header values reference two credentials of one OpenShell provider, which the owner creates. No secret passes through an agent, the harness or this repository ([below](#crypto-research-mcp-a-cloudflare-access-service-token)). The server is at `https://research-mcp-api.npages.org/mcp`, and the service token alone is enough: no OAuth bearer is needed behind Access ([checked on 2026-10-14](#what-the-server-offers)). The connector auth service and the OAuth flow stay the design for later OAuth servers, off M2's path.

Sources: the [MCP authorization specification, 2025-11-25](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/basic/authorization.mdx) and the OpenShell v0.1.5 [providers](https://github.com/NVIDIA/OpenShell/blob/v0.1.5/docs/how-it-works/providers/overview.mdx) and [profiles](https://github.com/NVIDIA/OpenShell/blob/v0.1.5/docs/how-it-works/providers/profiles.mdx) documentation. The direct path was run on babbage against the owner's portal on 2026-10-26 ([prototype](specs/mcp-middleware-prototype.md#recommendation)); the MCP proxy before it in labs 2, 13, 15, 17 and 39 ([lab 39](../.agents/docs/agent-reports/babbage-openshell-lab-39-2026-10-15.md)). The connector auth service, the OAuth flow and the checks for the spike below are not built or tested.

## Goals

1. **No agent-reachable process holds a raw MCP credential.** That covers the harness, delegated agents and research workers.
2. **Research code never connects to MCP services** (user requirement; since 2026-10-26 it has no MCP access at all). The agent's calls go from the agent runtime's sandbox, through OpenShell's native rules and the policy middleware, which apply the project's policy.
3. **One registry for all servers.** Each server is a `mcp.servers` entry in the project policy plus an OpenShell provider. There are no server-specific code paths, so adding a server later is configuration.
4. **The same tool-level policy applies to every call.**

## Components

| Component | Zone | Role |
| --- | --- | --- |
| Connector auth service (later; not for crypto-research-mcp) | Z1 (trusted) | Runs the interactive OAuth flow with the user, registers clients, stores tokens in OpenShell providers, and performs refreshes when the gateway cannot (below). Python, MIT, built on the MCP Python SDK's OAuth client support where it fits. Needed only for OAuth servers; crypto-research-mcp uses a service token the owner registers |
| **The agent runtime's MCP client** (`mcp_direct.DirectClient`) | Z2, in the agent runtime's sandbox | Makes the requests the host's toolbox admitted, to each server's own URL through OpenShell's proxy; holds only placeholders, filters listings by the compiled native rules and reports them for the drift check |
| OpenShell's `protocol: mcp` endpoints and the policy middleware | Z1 | Admit and deny tools by name (native rules), then decide the rest by the project's policy, hold escalated calls as permission requests and record every request ([policy middleware](POLICY-MIDDLEWARE.md)) |
| OpenShell gateway and providers | Z1 | Credential storage (encrypted database, Kubernetes Secrets or OpenBao), placeholder resolution, gateway-managed refresh where possible |

## The MCP proxy (retired 2026-10-26)

From 2026-10-11 to 2026-10-26 every MCP call went through the MCP proxy (D67, D75): a thin Python service in an OpenShell sandbox of its own (`packages/mcp-proxy`, command `sandbox-science-mcp-proxy`, the `mcp-proxy` image), which authenticated each caller by a token, applied the project's tool policy with the policy library, held escalated calls as permission requests, re-serialized what it forwarded, and recorded each message (`mcp-call` records with source `mcp-proxy`, [event store](EVENT-STORE.md)). The launcher ran it from `[mcp_proxy]`, compiled its sandbox's fence (`compile_mcp_proxy`) and forwarded a loopback address to it. D98 moved enforcement to OpenShell's native rules and the policy middleware, and the owner retired the proxy once the babbage lab passed. Its design and how it ran are in this file's history (before 2026-10-26) and the lab reports.

### What the proxy did that the direct path does not

The [prototype](specs/mcp-middleware-prototype.md#what-the-proxy-still-does-that-this-path-does-not) listed what the proxy did that the direct path did not. For each, as retired:

- **Only advertised tools.** The proxy refused a `tools/call` for a name missing from the server's latest complete listing (`tool_not_advertised`). *Lost:* the native rules and the middleware decide by name alone, compared exactly and case-sensitively, by the policy's tool rules and the classification in force; a tool the server does not advertise is decided as any other name. A server that folds case cannot be reached through a variant spelling the policy did not name, since an unnamed, unclassified name is denied at the fence.
- **Its own bytes upstream.** The proxy re-serialized what it decided. *Lost:* the server gets the client's bytes, which the middleware has read strictly (one JSON-RPC message, no duplicate keys, only the parameters MCP defines, no placeholders in the body).
- **Answer bounds.** The proxy bounded answers by the policy's `mcp.proxy.max_response_bytes` (the section is `mcp.limits` now, without it). *Kept, differently:* the client bounds every answer at 8 MiB (`MAX_ANSWER_BYTES`), whatever the policy says; `max_response_bytes` is read by nothing.
- **`ping` and server requests in a stream.** The proxy answered a server's `ping` and refused its other requests within an answer's event stream. *Lost:* the client declares no capabilities (which the middleware requires), and reads only the response to its own request from a stream; a server request in a stream goes unanswered, and a server that needs one gets none.
- **Each call's outcome.** The proxy recorded the outcome and the answer's size. *Lost:* the middleware sees requests, and only listing answers; the run's tool record keeps the outcome as the agent saw it.
- **Callers: `worker_access` and `worker_tools`.** The proxy let research code reach MCP servers when the policy said so. *Lost, on purpose:* research code has no MCP access. A policy that sets `worker_access: true` or a `worker_tools` list is refused ([policy](POLICY.md#mcp-calls)); none of the examples, test policies or documents relied on it but the proxy's own.
- **Listings without denied tools, binary results, approvals, canaries, the tool index.** *Kept:* the middleware rewrites the listings it reads whole and the client filters the rest by the native rules; binary items become artifacts over `publish_mcp_binary`; the workspace answers the middleware's requests through the worker; canaries and the user's availability check list through the runtime's client (`list_mcp_tools`); the index is the harness's.

### Migrating from [mcp_proxy]

A launcher config with `[mcp_proxy]` is refused when it is loaded: "[mcp_proxy] is retired ... Run sandbox-science migrate-mcp-config CONFIG". The helper rewrites the table in place, keeping the original beside it as `CONFIG.mcp-proxy.bak`:

```bash
sandbox-science migrate-mcp-config ~/.config/sandbox-science/personal.toml --print   # look first
sandbox-science migrate-mcp-config ~/.config/sandbox-science/personal.toml
```

- `servers` become `[mcp_direct.servers.NAME]` tables without a `url` (the project policy's is used); each server's credential headers come from the policy's `headers` entry, each header whose value is one `${provider:NAME.KEY}` mapped to the variable `[mcp_proxy.credentials]` gave `NAME.KEY`.
- `project`, `providers`, `about`, `index`, `provider_env_file` (the same path) and `provider_profile` are kept as written.
- The proxy's own keys (`image`, `credentials`, `sandbox`, `listen`, `approvals`, `policy`, `targets`, `ceiling`) are dropped, and the helper says so: the direct path compiles from the worker's policy, targets file and pool ceiling. `[canaries]` and everything else in the file stay as they were.
- What it cannot carry over it names, for the owner to set by hand: a `bearer` or `oauth` server, whose token goes out as `Bearer <token>`, which `credentials` cannot name; a header with text around its placeholder; a header whose variable `[mcp_proxy.credentials]` does not give. It also says when the policy still sets `worker_access` or `worker_tools`, which `up` now refuses.
- The result must load as a config, `[orchestrator]` included (the direct path's client runs in the agent runtime), or nothing is written.

By hand, the same: delete the `[mcp_proxy]` tables and add, for crypto-research-mcp,

```toml
[mcp_direct]
providers = ["crypto-research-mcp"]
provider_env_file = "/path/to/the/owners/cloudflare.env"   # the same file as before
provider_profile = "/path/to/examples/openshell/profiles/cloudflare-access.yaml"

[mcp_direct.servers.crypto-research-mcp]
credentials = { "CF-Access-Client-Id" = "CF_ACCESS_CLIENT_ID", "CF-Access-Client-Secret" = "CF_ACCESS_CLIENT_SECRET" }
```

The policy middleware's settings need `mcp_listings = true`. `scripts/personal_up.sh` stops before starting the launcher when the config still has `[mcp_proxy]`. A proxy sandbox an earlier launcher made and did not delete is deleted by the next `up` or `down`.

## The connectors as built

### The harness's client

Agents use connectors through the harness (`orchestrator/connectors.py`, D-08): the confined runtime's host keeps a run's connectors (the index, the loads, the gates, the waits and the records), and the agent runtime's own client makes every request ([the direct path](#the-direct-path)). Main and delegated runs get them alike, through one client per harness (DA-3): a child's tools are listed, indexed and loaded as its root's, under the same policy, and a delegated check is offered only the tools a classifying client classes `read`, which the runtime's client does not (below). A task's brief may narrow its connectors to some of its parent's (`connectors`: servers, servers behind a portal, tools or name patterns), never more: the child lists only the servers it names and is offered only the tools every narrowing above it admits, and loading another is `not_permitted_for_role` ([DA-6](specs/delegated-agents.md)). The control service takes them from `control.json`'s `direct` (the project, the servers, `about` and `index`), which the launcher writes from `[mcp_direct]`; the host-side `sandbox-science-harness run` and `serve` have no connectors since the MCP proxy, which they called, retired.

- **One project.** The policy middleware applies one project's policy and approvals to the runtime sandbox's calls (its binding), so only runs of that project get the servers' tools.
- **Listing.** At a run's start, the harness lists each server's tools through the runtime's client, within 15 s a server, under the names the server lists. crypto-research-mcp lists 72 tools by bare names, such as `e-print-mcp_search_eprint` (lab 39, 2026-10-15). It shows only the tools the compiled native rules admit. A name a run's records cannot hold (a letter or digit, then letters, digits, `_` and `-`, at most 64), or one the harness gives a tool of its own, whether the run has it or not (`python`, `restart_kernel`, `admit_hosts`, `document_reply`, `plan_read`, …), is left out and logged, and takes no place in the server's count. A name two configured servers list is neither's, whichever was listed first, so one server cannot stand in for another's tool; the run's record names it. A server that offers no tools is logged as offering none, "none listed, or the policy denies all (check tool_prefix)", since a wrong `tool_prefix` leaves every tool denied. A server offers at most 128 tools, and a run at most 256, with at most 512 KiB of descriptions and schemas. A listing that fails at once is tried again twice, a second and then two seconds later; one with no answer in 15 s is not. A server whose listing still failed is unavailable, not empty (lab 41, B4: one failed listing left a run without connectors, and nothing said so): `mcp_tools` is offered all the same, its index names the server as unavailable with the reason, and the first `mcp_tools` call, with or without arguments, lists it once more, so that its tools join the index from the next turn and can be loaded by name at once; while it stays unavailable, the call's answer says so (`unavailable`), and that its tools are unavailable in this run, not missing. The run's record keeps the servers that stayed unavailable (`summaries.connectors.unavailable`, with the reason) and those a later listing reached (`relisted`), and the run's `started` event names the unavailable ones, which the chat shows. The run goes on either way.
- **An index, and tools loaded on demand** (lab 39, B5). Every connector tool's schema at every model call cost about 17,000 tokens for crypto-research-mcp's 72 tools, and a research session could not fit its budget. So MAIN first gets an index, in the description of the harness's own `mcp_tools` tool, with each tool's full name and the first sentence of the server's description of it, at most 60 characters, framed as the server's. Tools are indexed by the configured server, and, behind a portal, by the server their names start with (a prefix with a hyphen), shown as `e-print-mcp (via crypto-research-mcp)`: a server names its own tools, so the index always says which configured server they came from. The operator's word on what a server is for (`--mcp-about KEY=TEXT`, at most 200 characters) is marked `operator:`, and `--mcp-index KEY`, repeated, lists those servers' tools one by one and the others by their count alone. A key is a configured server (`--mcp-server`), or `SERVER/BEHIND` for one behind it, such as `crypto-research-mcp/e-print-mcp`, so what the operator says about one server never reaches another's tools; a key no server matches is logged. The index names at most 32 servers behind one configured server and holds at most 16,000 characters of tool lines; the rest are found with a query. `mcp_tools` loads tools by `names` (at most 16) into the run's tools for the rest of the run, and answers which it loaded, which were loaded before, which no listed tool has, which are the harness's own tools (`harness_tools`, which need no loading) and which it did not load. A `query` (at most 200 characters) lists the tools that match it well, at most 8, each with its server, purpose and whether it is loaded, and loads none (lab 40, B4: loading a query's best matches loaded ten unrelated schemas for a search for the ledger's tools, which every later call carried). A tool matches when its name, purpose or server holds each word of a query of one or two words, or two thirds of a longer one's, leaving out words such as "the" and "tool", and one of them is in its name or purpose; a query that matches nothing so well says so, and that the harness's own tools, such as `ledger_*`, are not connector tools. The description says a connector tool runs on its server through the platform, so it needs no `shell` or `admit_hosts` (lab 40's run 1 tried both before its first connector call). A run loads at most 100,000 characters of descriptions and schemas, past which a load is refused and the run goes on with the tools it has. A connector tool called before it is loaded is loaded then, and called. Loaded schemas count toward the run's context as any tool's do, from the next model call. The run's record keeps, under `summaries.connectors`, how many tools were listed, how many each configured server offered, the names refused for being listed twice, and each tool loaded, in order, with the SHA-256 of the spec the model was given; each `mcp_tools` call's record says what it loaded, with those SHA-256s. Measured with lab 39's tool list: 67,303 characters before; 7,257 after with every server's tools listed one by one, and 3,193 with three (`packages/orchestrator/tests/test_connectors.py`).
- **Purpose** ([tools spec](specs/tools.md#purpose-of-each-call), B9). Each connector tool is offered with the required `purpose_note` the harness adds to every tool's schema, and the harness takes it out of the arguments before the call goes out, so no server, middleware record or approval's arguments carry it. A tool whose own schema defines a top-level `purpose_note` is not loaded: it is left out of the index, logged, and `mcp_tools` names it under `not_loadable` with that reason. The name was chosen so that no server's tool collides with it.
- **Effects.** Every connector tool has the effect class `effect`, so the main run's plan gate applies to it. `mcp_tools` is a `read`: it changes only what the run's model calls carry. A delegated run's fence reads a classifying client's class of each listed tool and its escalation mark (`sandbox-science/escalates`): a `read` passes it, and under a draft or user-edited plan a call held for the user still goes out, its card naming the child, while one the policy would pass unasked is refused (D99, DA-7). The MCP proxy classified its listings; the runtime's client passes the server's own, whose classes are not taken, so a delegated check gets no connector tool and the child fence treats every connector call as outward (fails closed) until direct listings carry classes the host trusts.
- **Untrusted text.** A tool's description, and the index's line for it, lose every character a person may not see (but line breaks and tabs): controls, format, private-use and unassigned characters, line and paragraph separators and every Default_Ignorable code point, as `agent_text.hidden_characters` finds them, stripped rather than refused since the server wrote them. It is bounded to 2,000 characters and is framed as the server's. Its input schema is rebuilt from JSON Schema's structural keywords only (`type`, `properties`, `required`, `items`, `additionalProperties` as a boolean, `anyOf`/`oneOf`/`allOf`, `enum`/`const` with bounded and cleaned values, at most 1,024 characters of them a tool, past which they are dropped, and numeric and length limits); titles, descriptions, defaults, examples, patterns and references are dropped. A schema that is larger than 16 KiB, malformed, or not an object becomes an empty object schema, so a model API never refuses it.
- **Calls.** Each call names the run's session in `Sandbox-Science-Session` and the run in `Sandbox-Science-Run`, which the policy middleware records with the call; listings name them too. A child's session is its root's. The client keeps one MCP session per server, shared by its runs and started once for concurrent callers, and starts it again once if the server no longer knows it; callers that find it forgotten together share one new start. It sends every message with its keys sorted, so a call made again after its approval matches the request the user approved. A call has 330 s.
- **Refusals.** A refusal is the tool's error, with its reason code. A call held for approval comes back as `approval_required`, naming the permission request; the user answers it in the workspace's chat ([approvals in the workspace](#approvals-in-the-workspace)), or the operator with the policy middleware's `pending` and `approve`. With the run service, the call waits in place, retried as it was made, until it is answered or times out; without it, the agent calls again with the same arguments. The runtime's fence admits the tools the policy escalates by name, so an approval takes effect; one escalated only by the default action stays denied there. An error a server answered is framed as the server's. Arguments JSON cannot hold are `not_sent`, and nothing reaches the server. A call whose answer is lost or unreadable is `no_usable_answer`: the server may have done the work, so the harness retains its tool intent and stops the attempt for reconciliation instead of asking the agent to call it again.
- **Results** are the text the server returned, read whole up to 8 MiB and bounded as any tool result. Binary items arrive as the server sent them, and the harness withholds them (`policy.mcp_answers`, the rule by which the retired proxy dropped them) and keeps each as an artifact (`mcp_binaries.ArtifactBinaries`): it writes the decoded bytes to `mcp-results/<server>/<digest>.<ext>` in the session's workspace through the worker and publishes the file with the run's publisher, so the inventory's budget and retention apply. The model sees a note naming the artifact, its path and its SHA-256 instead, never the base64; an item that cannot be kept (not base64, over 16 MiB, the worker unavailable) is withheld with a note saying so. In the confined runtime the direct client runs in the agent runtime's sandbox and the publisher on the host: the runtime sends each item over the attempt's `publish_mcp_binary` capability with the model's call ID, its media type and SHA-256, and the host keeps it the same way and answers the artifact, revision and note. The host refuses a digest mismatch, an item over 8 MiB or a call over 8 MiB or 100 items, a media type other than `image/*`, `audio/*` or `application/*`, and a call ID that is not the attempt's pending connector call; a retry of the same item is answered, not kept again, and the items are recorded with the call ([prototype](specs/mcp-middleware-prototype.md#where-the-client-runs-binaries-and-canaries)).
- **The direct client** (D98, `mcp_direct.DirectClient`; in the confined runtime it runs in the agent runtime's sandbox, where it makes the agent's connector requests on [the direct path](#the-direct-path) and serves the canaries and the workspace's availability checks). It shows only the tools its server's compiled native rules admit (`DirectServer.tools`, from `policy.openshell.tool_admission`; none without them), so a listing the middleware let pass unread (an event stream, which OpenShell 0.1.5 never offers it whole) shows no denied tool, and it reports each complete listing, as the server sent it, over `report_mcp_listing`; the worker records any drift from the project's pin as the middleware would ([prototype](specs/mcp-middleware-prototype.md#where-the-client-runs-binaries-and-canaries)). A listing the control side does not take is not shown. It trusts a refusal that names a permission request only when the control side confirms it, since a server can write OpenShell's denial body: the production check (`WorkerRequestCheck`) asks the worker, which holds the middleware's event store, with the client's own token (`POST /v1/permission-requests/{seq}/confirm`, [worker](WORKER.md)), and gets yes or no about one request; in the confined runtime, which holds no worker token, the check is the attempt's `confirm_request` capability, which the host answers for the attempt's project only ([confinement](specs/orchestrator-confinement.md)). It reads results from JSON and event-stream answers only, the two the middleware rewrites.

Tested with the direct client through a fake OpenShell with the real policy middleware in front of the fake server (`packages/orchestrator/tests/test_connectors.py`, `test_mcp_direct.py`), with synthetic tokens.

### The direct path

`[mcp_direct]` in the launcher's config (or the Kubernetes bundle's, [KUBERNETES-BUNDLE](KUBERNETES-BUNDLE.md#the-direct-mcp-path-opt-in)) is a deployment's MCP configuration: the agent's connector calls made by the agent runtime's own client (D98). It needs `[orchestrator]`, the confined runtime. Without it the agent has no connectors.

```toml
[mcp_direct]
project = "crypto"                         # by default the only project
providers = ["crypto-research-mcp"]        # attached to the agent runtime's sandbox
provider_env_file = "~/.config/sandbox-science/secrets/cloudflare.env"  # optional
provider_profile = "examples/openshell/profiles/cloudflare-access.yaml"
# index = ["crypto-research-mcp/e-print-mcp"]

[mcp_direct.servers.crypto-research-mcp]   # a server of the project policy, at its URL
credentials = { "CF-Access-Client-Id" = "CF_ACCESS_CLIENT_ID", "CF-Access-Client-Secret" = "CF_ACCESS_CLIENT_SECRET" }

[mcp_direct.about]
"crypto-research-mcp/e-print-mcp" = "IACR ePrint papers: search, records, full text and PDFs"
```

A server's `url` may be left out: it is the project policy's, and a given one must equal it. The policy middleware's settings need `mcp_listings = true`. On `up`, the launcher:

1. registers the provider from `provider_env_file` by its path when the gateway lacks it, or with `--refresh-provider` ([below](#crypto-research-mcp-a-cloudflare-access-service-token)), and refuses to start without each of `providers`;
2. compiles the agent runtime sandbox's egress for the project's policy, pool ceiling and targets (`launcher.direct_mcp`, `compile_agent_mcp`): one inspected `protocol: mcp` endpoint per configured server, whose native rules allow and deny its tools by name, bound to its provider's credentials and admitting only the runtime's interpreter, and the policy middleware (the targets file's registration) for those hosts, with the project and the caller `agent-runtime`; it merges them beside the sandbox's platform services, and refuses a server the policy does not declare, the floor or ceiling rule out, or whose URL differs;
3. creates the sandbox with the providers attached, so its processes see placeholders only, and binds it to the project's policy revision through the worker once it is Ready (`POST /v1/runtime-sandboxes`), so the middleware decides its requests;
4. gives the runtime each server's URL, credential headers and the tools the compiled endpoint admits (`runtime.json`'s `mcp`, `tool_admission`), and control the run service's direct access (`control.json`'s `direct`: the servers, `about`, `index`) and the digest of the workspace's token for the availability check (`check_token_sha256_file`);
5. gives the workspace the servers' names and purposes (`--mcp-service`), and the control service's address with that token (`--mcp-check`, `--mcp-check-token-file`).

**How a call is authorized.** The run service lists each server at a run's start and indexes the tools; every request leaves from the runtime. For a call, the host's toolbox decides first, as for any tool: the model must have been offered it, the plan fence and the other gates pass its effect class, and a server the user turned off takes no call; then the host relays the request to the runtime over the attempt's `mcp_request` capability ([confinement](specs/orchestrator-confinement.md#capability-operations), `confinement.connector_calls`). The runtime's client sends it to the server's URL through OpenShell's proxy, where the compiled native rules refuse a tool not admitted by name (`policy_denied`) and the policy middleware decides the rest by the project's tool rules, holds an escalated call as a permission request, and records every request (`mcp-call`) with the project, session and run. A held call's refusal names its request; the runtime confirms it over `confirm_request`, which the host answers for the attempt's project from the middleware's records through the worker, recording the server, method, tool and parameters' digest it confirmed; the host takes the hold only when the request was confirmed for the very call it relayed (its own server, tool and parameters' digest), and otherwise the answer is the server's error, with no wait and no card; the call then waits for the user's answer in the workspace, retried. A listing shows only the admitted tools and is reported for the drift check (`report_mcp_listing`); a result's binary items come back over `publish_mcp_binary` as artifacts of the run, while the host relays that call. The host's tool record names the connector, any permission request and the kept items. The tool admission the runtime gets only narrows what the model sees: a runtime that widened it would see its calls refused by OpenShell's rules, which it cannot change.

**Inspected traffic.** On this path the policy middleware also records each call's arguments and each answer, bounded and redacted, and checks the answers for the policy's patterns (`mcp.inspection`), alerting or, for a `block` pattern, refusing a whole answer or cutting an event stream with an error that names the finding ([MCP traffic inspection](POLICY-MIDDLEWARE.md#mcp-traffic-inspection)). The workspace shows them on the run page and in each MCP tool row of the chat.

**Effect classes and classification revisions.** The direct client passes the server's own listing, whose classes are not taken (`classifies` is false), so direct-path tools carry no effect class: a delegated check, offered only the tools classed `read`, gets no connector tools, and the D99 child fence treats every connector call as outward (it fails closed) until direct listings carry classes the host trusts. The compiled native rules admit tools by the project's classification in force when they were compiled, and the middleware decides each call by the one in force at that call; how a revision reaches the fence is under [project revisions](#project-revisions).

**Project IDs and the sandbox's label.** The runtime's sandbox is labelled with the project ID (`sandbox-science.io/project`, which the worker reads before it binds the sandbox), and a Kubernetes label value is at most 63 characters of letters, digits, `.`, `_` and `-`, starting and ending with a letter or digit. So every project's ID must be one, whether or not the deployment uses the direct path ([projects](PROJECTS-AND-SESSIONS.md#as-built-the-harnesss-project-records)): a config's `[[projects]]` (the launcher's and the Kubernetes site's) is refused at load, and `project create` at creation, with the reason. As a second guard the runtime owner and a bundle's `[mcp_direct]` project refuse one that is not.

### Canaries

A canary is a scheduled, bounded `tools/list` of each configured server, so that a server that stopped answering is noticed before a run needs it (D103). The launcher runs them when its config has `[canaries] enabled = true` (off by default) with `[mcp_direct]`; `interval` is the seconds between runs, 900 (15 minutes) by default, at least 60. No trusted service can reach a server, so the control service asks the connected agent runtime, over the control connection, to list each `[mcp_direct]` server through the runtime's own `DirectClient` (the host-to-runtime `list_mcp_tools` request, as control asks the runtime for model completions).

- **The same path as the user's check.** Each run lists every server, one after another, with the session `mcp-canary`: an `initialize`, then `tools/list` page by page, at most 32 pages within 15 s, each request within 10 s (`mcp_canaries.list_tools`, which the workspace's **Check availability** asks for too, through the control service's `POST /mcp-check`). Each listing, a canary's or a check's, has a client and an MCP session of its own, closed when it ends, so it lists the tools the server offers now: a portal fixes a session's tools when it starts, and a kept session went on listing three tools after the portal offered 72 (2026-10-27). The session is not ended with a `DELETE`, which the policy middleware refuses (it takes only POSTs to the endpoint); the server expires it. It never calls a tool and never tries a listing again within a run. The runtime answers the outcome only (its count is of the tools the native rules admit); its client reports the server's whole listing over `report_mcp_listing` for the canaries' project, so a canary listing records drift as a run's does, whether or not the middleware read it.
- **Results.** The status is `listed`, `unavailable`, `denied` (the policy refused) or `timeout`. Each result is a row of the control store's `mcp_canaries` (schema version 86): server, time, status, the tool count and the listing's digest (SHA-256 over each tool's canonical JSON, one a line, in order) when listed, the elapsed milliseconds, and an error kind otherwise (`malformed_listing`, `cursor_loop`, `too_many_pages`, `timeout`, `client_error`, `internal_error`, a refusal such as `policy_denied`, and from the control service `runtime_unavailable` with no runtime connected, `runtime_refused` for a runtime without a client, `undeclared_server`; no answer within 20 s is `timeout`). After each run the runner prunes every server's rows, those of servers no longer configured too, to 30 days and at most 10,000 rows per server. Control stores them from the runtime's first handshake.
- **Log events.** Every result is one record, `event: mcp_canary`, with `server`, `status`, `tool_count`, `elapsed_ms` and `error_kind` (service `mcp-canary`; a warning when not listed). A move from `listed` to any other status, or back, is a second record, `event: mcp_canary_changed`, with `status` and `previous`; a server's first result that is not `listed` counts as one, with no `previous`. The bundle's alert rules read it ([alert rules](KUBERNETES-BUNDLE.md#alert-rules)).
- **In the workspace** the MCP services view shows each service's latest canary beside the user's own check, "Canary: listed 12 minutes ago" ([workspace](WORKSPACE.md)), and the Monitor view lists every configured service's with its status and age; the user's check is kept in the workspace process's memory only. The runtime's word on a canary is a monitor's: a lying runtime hides only an outage.
- **The agent's sandbox is bound for the middleware.** The policy middleware decides only sandboxes that its store binds to a policy revision, and refuses any other as `sandbox_unbound`. When the launcher's runtime owner (the host) or the Kubernetes runtime manager has the agent runtime's sandbox Ready, it asks the worker to bind the sandbox's gateway ID to the MCP project's policy revision (`POST /v1/runtime-sandboxes`: the revision the store binds to the project, else the one granted to it last), and unbinds it once the sandbox is confirmed deleted (`DELETE /v1/runtime-sandboxes/{id}`); a replacement is bound as a new sandbox. A bind that fails fails the creation, with the record kept for the owner; an unbind that fails only says so, since an ID is never reused. The launcher never writes the store.

In a Kubernetes deployment the site generator writes control's canaries (`[mcp_direct.canaries]`, on by default, every 900 seconds unless `interval` says otherwise; [bundle](KUBERNETES-BUNDLE.md)), and they run on the direct path as above. Tested with a fake listing client and a fake source (`packages/orchestrator/tests/test_canaries.py`), and with a fake runtime client and the control service's runner and check route (`test_confinement_canaries.py`).

## Classification files

A server's tools are classified by effect (D96) in checked-in files that the policy names with `mcp.servers.<server>.classification: <name>`: every `*.yaml` under `packages/policy/src/sandbox_science/policy/classifications/<name>/`, read in the policy files' strict dialect. A portal gets one file per server behind it, each for the tools whose names start with its `prefix`; no tool may be in two files. The admin reviews each file, and only the accepted file decides calls ([effect classes](POLICY.md#effect-classes-d96-d97)).

```yaml
apiVersion: sandbox-science/v0alpha1
kind: ToolClassification
server: crypto-research-mcp
prefix: firecrawl-mcp_
pinned: "2026-10-24"
tools:
  firecrawl-mcp_firecrawl_scrape:
    class: read
    reason: "Fetches one page's content; browser actions and profile saves are effects (H1)."
    sha256: 867de81d8da507fb45731a6423e9a6a431a44d063bce75773880507f5aedf748
    significant: {url: url}
    rules:
      - {argument: actions, present: true, class: browse}
      - {argument: profile.saveChanges, equals: true, class: write}
```

- **Entries.** Each tool has its `class`, a one-line `reason`, its `sha256` pin, argument `rules`, and its `significant` arguments by kind (`url`, `host`, `recipient`, `title`, `size`, `query`), which the approval cards summarize a call by ([approvals](#approvals-in-the-workspace)).
- **crypto-research-mcp** has a file for each of `attack-catalog`, `e-print`, `firecrawl`, `nist-csrc`, `nist`, `paper-search`, `patent-search` and `web-fetch`, and one for the portal's own tools, from the pinned schemas and the 2026-10-23 audit's H1. Firecrawl `scrape`, `crawl` and `search` are reads whose page `actions` are `browse`, whose `profile.saveChanges: true` is `write`, and whose `webhook` (crawl) is `communicate`; `agent`, `interact` and `interact_stop` are `browse`; monitors that notify later (`monitor_create`, `monitor_update`) are `communicate`, and `monitor_run` and `monitor_delete` are `write`; both feedback tools are `write`; the ePrint and NIST corpus refreshes and the portal's toggles are `admin`. Every other tool is a `read`, including the billed searches (cost is the services' to control) and the fetches that fill a server's cache (D95).
- **Pins and drift.** A pin is the SHA-256 of a tool's name, description and input schema as sorted compact JSON (`mcp_wire.tool_digest`), the description with its whitespace collapsed (each run of spaces, tabs and newlines one space, none leading or trailing); annotations and `outputSchema` are not pinned. The collapse is there because clients show the same server text differently: the pins of 2026-10-24 were made from a claude.ai connector's view of the portal, which shows a docstring's newlines as spaces (and lacked `firecrawl_monitor_delete`, which the raw listing has), while the agent runtime's client and the middleware digest the raw `tools/list`, so the lab of 2026-10-26 saw 58 of 71 tools "changed" with no word changed (the 59th was the lab's deliberate wrong pin). A change to the name, the input schema or any word or punctuation of the description still changes the pin; a change only to the description's spacing does not. The pinned listings are test fixtures (`packages/policy/tests/fixtures/mcp-tools/<server>/<group>.json`), each a raw `tools/list` cut to name, description and input schema, and `test_classification.py` fails, with a diff, when a file's pins differ from them, and when a rule or significant argument names an argument the pinned schema lacks. A tool classified from an earlier listing that the pinned one lacks has no `sha256` and is not pinned. At run time the policy middleware, with `mcp_listings = true` in its settings, reads the JSON answers to the `tools/list` requests of sandboxes that call servers directly (an event stream OpenShell does not offer it whole passes unread; the agent runtime's client reports that listing and the worker compares it, with the same code and record, source `runtime`: [prototype](specs/mcp-middleware-prototype.md#where-the-client-runs-binaries-and-canaries)), keeps their tools' hints, and records a `tool_list_drift` finding (an `mcp-tools-drift` record naming the tools added, removed and changed) when a complete listing differs from the pins of the classification in force for the project (a [project revision](#project-revisions) or the catalog's), or from the operator's `mcp_tool_pins`, which names tools only and wins where it names a server. The record also gives each added and changed tool's digest (`digests`) and each added tool's hint class (`hints`), for the same tools its name lists hold, at most 100 of each. The record also carries the digest of the whole listing (`listing`). A drift blocks no read: the tool's class still decides it, but the server's non-read calls ask, in every project whose classification in force has the pin it drifted from (drifts are kept per server and pin), until the classification is accepted again or a new pin is in force for that project, and a changed tool is reviewed and pinned again ([detect and hold](POLICY-MIDDLEWARE.md#detect-and-hold-d103), D103). The operator's `accept-tools` (an `mcp-tools-accepted` record with only the server) ends the hold for every project; the user's re-acceptance through the worker (with the project, the pin and listing it accepts, a reason and the actor `user`) or an `mcp-classification-accepted` record ends it for that project. A later listing with the same digest is no new drift and records nothing, so the acceptance stands; a listing with another digest is a new drift, held again.
- **Refreshing the pins.** Take the listing raw, from a lab or the runtime's client, never from an assistant's connector view: the direct MCP lab's listing-only run (`direct_mcp.py prepare` and `up`, one `tools/list` through the runtime's `DirectSettings.client`, the raw result saved under `/var/tmp/ss-direct-mcp-*`, then `abort`) is how the 2026-10-26 listing was taken. Write each group's tools to its fixture (name, description and input schema, sorted by name, `captured` the day), set `pinned` in the classification files, and pin each tool with `tool_digest` or a `classify-draft` of the listing, keeping the checked-in classes: a tool whose description words or schema changed is reviewed by the owner before its class is kept, and a new tool is classified and reviewed. `test_classification.py` then shows any pin that disagrees. A change to how the digest is computed is itself a one-time drift for any listing accepted under the old digest (a project's revision pinned from a raw listing with newlines, a re-accepted listing digest): its non-read calls ask until it is accepted again, and the orchestrator image must be rebuilt, since the runtime's client computes the digests it reports.
- **Drafting a file.** `sandbox-science-harness classify-draft SERVER --tools tools.json --prefix firecrawl-mcp_ --model-url URL --model ALIAS --api-key-file KEY --out draft.yaml` asks the gateway's model once to propose each tool's class, reason, rules and significant arguments, and writes a draft pinned to the listing's digests. The tool list is the server's text, so the prompt frames it as data, and the answer is read as data: a class outside the closed set, a rule or argument the tool's schema lacks, and a tool the list lacks are dropped, and a tool the answer leaves out is `unclassified`. With `--project P --policy-store DIR` (the policy middleware's state directory) the draft is stored as the project's instead of, or as well as, written to `--out`: `classification-drafts/<project>/<server>/<hex>.yaml`, named by its SHA-256, with its creation time and the model alias beside it, once it loads as a classification file of that server would. The draft is a convenience, the model's text, marked DRAFT; it decides nothing until a user accepts it (below) or it is checked in.

### Project revisions

A project's own classification of a server (D96, CL-3) is a revision in the policy store, the file store the worker and the policy middleware share (`policy_store` in the worker's settings, the middleware's `state_dir`): `classifications/<project>/<server>/<hex>.yaml`, one classification file named by the SHA-256 of its bytes, read in the same strict dialect and refused unless its `server` is that server; `<hex>.json` beside it records who accepted it (`user`), when, the reason, the draft it came from, the revision it replaced and its diff (tools added, removed and changed, and the widenings); and `current.json` names the revision in force for that project and server.

- **Resolution.** Where the project's policy names a classification for a server, the project's revision in force replaces the catalog's files for that project, whatever their name: one file stands for the whole server, so a revision drafted for one group of a portal's tools leaves the others unclassified (and counts them as widenings where their hints could make them reads). The catalog stays every other project's default and the drift fixtures' pin source. The policy middleware reads `current.json` at every MCP call, and decides the call, rewrites the listing, summarizes the card and compares the pins with the revision in force, so an acceptance applies to the next call; a binding it cannot read refuses the call. Loaded classifications are cached by their content's digest. (The retired MCP proxy decided with the catalog; CL-5 is moot.)
- **The fence.** The agent runtime's native rules (`compile_agent_mcp`) admit tools by the classification in force for the project when they are compiled: the launcher reads each configured server's binding from the policy store it shares with the worker and the middleware (`[openshell.environments] policy_store`, `PolicyStore.fence_classifications`) and compiles with the revision it names, else with the catalog's, and logs, for each configured server, which classification its fence uses: the accepted revision, or the checked-in one ("admitted by the checked-in classification", with or without a warning above it that says why a revision did not apply), in the same log line form and at the same level, on a host and in the Kubernetes runtime manager. The runtime's tool admission (`runtime.json`'s `tools`) comes from the same compiled endpoint, so the model is offered what the fence admits. The fence is compiled on `up` and on every replacement of the runtime (`sandbox-science replace-orchestrator`, or the launcher's own after the runtime fails), never pushed into a running sandbox: OpenShell 0.1.5 can replace a live sandbox's policy (`openshell policy set`), but the runtime's tool admission was given at its start, so a pushed widening would still not be offered, and a replacement changes both at once. A revision accepted while a runtime runs therefore reaches its fence at the next replacement. The middleware stays the authority meanwhile, since it reads the binding at every call: a widening is refused at the stale fence by name (`policy_denied`) until then, which is stricter, and a narrowing applies to the next call, the middleware asking or refusing as the revision classes the tool whatever the stale fence admits. So a stale fence is never wider than the middleware's decision. A server with no binding (`current.json` absent) is compiled with the catalog's. A binding or revision that cannot be read (not JSON, naming a revision the store lacks, a file whose digest differs) leaves that server's fence on the catalog's, with a warning on `up`, rather than failing the start: the middleware refuses every call of that server (`policy_unavailable`) while the binding cannot be read, so the fallback admits nothing that passes. A revision that loads but does not compile into a fence (more tools than a fence may name, say) leaves its server's fence on the catalog's too, with a warning, and the middleware decides each call by the revision; the fence is compiled before the old runtime is deleted, so a site whose own files do not compile leaves the running runtime alone. The Kubernetes runtime manager follows the same rules at each creation of the runtime's sandbox, bootstrap and replacement alike (`runtime_manager.fence`): its Secret carries the site's project policy, pool ceiling and targets, and it reads each configured server's revision in force through the worker (`GET /v1/runtime-classifications?project=&server=`), which answers the revision and its file as stored, or why the binding cannot be read. That route is the one read its `binding_only` client has, for its own project and the servers it names, and shows no draft, acceptance record or drift; it was chosen over mounting the store into the manager's Pod because the store is on the pool's volume, which another Pod cannot share, and a read-only route keeps the manager from every other file there. The worker answers a binding or revision it cannot read with a kind (`binding` or `revision`) and a short reason without its paths, and logs the details. The manager checks each file against its revision's digest and loads it as the store would. Every failure leaves the servers concerned on the checked-in file with a warning that says what the middleware does: it refuses their calls when the binding or revision cannot be read, and decides by the classification in force when only the manager's read failed (the worker did not answer, a file arrived changed). The manager records the servers' tool admission compiled with each sandbox's fence (`runtime-mcp.json` in its state, naming the sandbox) once the sandbox exists, for every attach to it; a sandbox it has no record for is offered the checked-in admission. Tested in `test_classification_revisions.py` (the store's reads), `test_direct_mcp.py` (the launcher's compile before and after an acceptance, and an unreadable binding), `test_fence_revisions.py` (the policy middleware: a widening admitted by the recompiled fence and allowed, a narrowing refused at once by the middleware whatever the stale fence admits), `test_runtime_manager.py` (the manager's compile from a bound revision, its fallback without one or with an unreadable one, and its recompile at replacement after an acceptance) and `test_environments.py` (the worker's route and its scope).
- **Widenings.** Under any combination of the argument conditions either classification's rules for a tool name, a call of it widens when it would pass (`allow` or `alert`) under the new classification where the current one escalates or denies it; when it still escalates but under a wider grant ceiling; or when it still escalates under a class it did not have whose ceiling lets a session or project grant cover it, since a grant the project holds of that class would then answer it (`classification.widening_reasons`, which says which). A tool the current classification does not mention has the class decision time gives it, its hint's from the latest drift record, else `unclassified`; a tool the new one leaves out takes its hints' most permissive class, `read`. They are computed under the project's policy as the policy store binds it to the project (`projects/<project>.json`), else the revision granted to it last; the worker cannot read the grants themselves (they are in the control store), so it names the class a grant would need. The policy's `classify` entries win over both; its tool lists are not consulted, so a tool they decide may be listed though its calls would not change.
- **Acceptance.** The workspace's review view reads the classifications in force and the drafts through the worker and relays the user's acceptances to it ([worker](WORKER.md), `/v1/classifications`): accepting a draft, edited or not, checks the YAML as the loader does, refuses a tool the server is not known to have (not in the draft, the classification in force or the latest drift) or a pin no listing gave it, writes the revision, its record and the binding, then an `mcp-classification-accepted` event (source `workspace`; project, server, revision, draft, the revision it replaced, reason, widenings, diff, actor `user`), and puts the replaced revision back if the event cannot be written. Each acceptance carries the workspace's `operation_id`; the worker keeps its first answer, so a retry accepts nothing twice. An accepted revision exports as its file exactly as stored, to check in (`GET /v1/classifications/{server}/revisions/{revision}/export`). Re-accepting a drift writes `mcp-tools-accepted` with the project, server, reason and actor. The workspace has one user, who holds the worker's operator token, so accepting is that user's: there are no roles.

## Approvals in the workspace

The owner decided on 2026-10-21 that the policy may route a tool call to the user: a tool the policy escalates waits for the user's answer in the workspace's chat. The policy still decides which calls are asked about; the user can never allow a tool the policy denies.

- The policy middleware holds an escalated call as a permission request (D98), keyed by the project, caller, policy revision, server, method, tool and the parameters' digest. The workspace reads and answers the project's requests through the worker, which holds the middleware's event store, with its operator client (`GET /v1/permission-requests`, `POST /v1/permission-requests/{seq}/answer`, [worker](WORKER.md)). The runtime's fence admits the tools the policy escalates by name, so an approved call passes it. (Until 2026-10-26 the MCP proxy held such calls too, and the workspace answered them as an operator caller of the proxy; that source is gone.)
- The run service's call waits in place while its request is unanswered, retrying it every 3 seconds for a minute and every 10 after, and its run records a `waiting` event with the request's number, server and tool, and another when the wait ends.
- **The card** (D97). The chat shows each held call of its session as a card: the tool and its server, its effect class, its significant arguments as the server's classification names them (URL and its host, recipient, title, size, query; [classification files](#classification-files)), which the middleware recorded with the request, the agent's own words from that step (marked as the agent's), for a delegated agent's call the child and its parent's brief ([delegated agents](specs/delegated-agents.md)), and folded away the call's raw arguments from the session's transcript (the middleware keeps only their digest). Research code's network and package requests get cards of their own ([policy middleware](POLICY-MIDDLEWARE.md#permission-requests)).
- **The requests' source.** The worker lists the middleware's held calls beside research code's requests (`kind: mcp`, `source: worker`, the only source; an answer that names `proxy` is refused). The answer goes back with the `call` scope, and the relay answers the middleware's later calls a class grant covers. A child's call carries its run in the middleware's record; the child's wait records the request as the child's (`child_requests`, under the middleware's number) and tells its parent, and its card takes the child's own words from that record, matched by the request's number, run, server and tool, so an older record under the retired proxy's numbering never stands for a middleware request. A parent's withdrawal refuses: the request is not listed, cannot be approved, and the relay denies it at the middleware, so the child's retry ends denied ([DA-10](specs/delegated-agents.md)).
- **Answers.** Allow **once** (this call, with its exact arguments, for an hour), **this session** or **this project** (a grant, below), or Deny. The card offers only the scopes the call's ceiling allows, and the workspace refuses any other, whatever the page sent: `communicate` at most for the session, `admin` and `unclassified` once only, and a call from research code (a worker caller) once only. The middleware's ledger has the scopes `call` and `tool`; `server`, which covered every tool of a server including ones it adds later (the 2026-10-23 audit's H2), is gone, and its old answers no longer apply.
- Network destinations are not held: the policy middleware cannot hold a connection, and its escalations stay deny-then-retry (D69). Their cards are answered the same way ([policy middleware](POLICY-MIDDLEWARE.md#permission-requests)).

## Grants

A grant is the user's standing answer (D97), kept in the control store (`project_grants`, [living documents](LIVING-DOCUMENTS.md)) and listed on the project's Connectors page in its Grants panel, with what it covers, its scope, its expiry if the user gave one, and when it was last used; Revoke ends it in one click.

- **What a grant names.** An effect class on one MCP server (`write` calls to crypto-research-mcp), a host for research code's reads (GET and HEAD), or a package source (an ecosystem, and for conda a channel), for one **session** or the **project**. Grants last until revoked unless given an expiry (`hours`). A tool the server adds later is covered only when the policy classifies it into a granted class; `unclassified` is never granted wider than once.
- **Within the ceiling.** A grant covers a held request only if its scope is within the ceiling the request itself carries (the policy's `max_grant` for its class and server, recorded by the middleware, or `project` for research code's reads and package installs), checked again at every use, so a policy revision that lowers a ceiling ends wider grants' effect at once.
- **No research code on agent grants.** Every request records its caller's kind. A class grant covers only the agent's calls (the run service's), never research code's MCP calls; a host grant covers only research code's HTTP and git requests, never an agent's call naming that host.
- **How grants reach the middleware.** The workspace's relay answers each new request a grant covers, every 3 seconds, and notes the grant's use: a tool call with the `call` scope for 15 minutes (its exact arguments: an argument rule can give another call of the same tool another class, so a grant never stretches to the whole tool), a host's reads with the middleware's `host` scope for an hour, for that sandbox and policy revision, and a package request for its own files. A revoked grant answers nothing new at once; the answers it already gave end within those times. Answers in the stores stay bound to sandbox (or project and caller) and policy revision, since a revision can change what escalates; grants are not, since they answer only what the current policy escalates, under the ceiling the request carries.
- **Migration** (control store version 81). Each remembered tool approval became a project grant of the tool's class on its server, as the checked-in classification of the server's name classifies the tool, where that class may be granted for a project (`write` under the shipped ceilings); an approval of a tool it does not classify (`unclassified`), of a class with a narrower ceiling, or of a whole server was dropped, and its calls ask again.

## Authentication modes

Each server entry declares one mode:

| Mode | Use | How credentials reach the request |
| --- | --- | --- |
| `oauth` (primary) | Servers that follow MCP authorization | The access token is stored as an OpenShell provider credential with `auth_style: bearer`. The client sends `Authorization: Bearer <placeholder>`, and the OpenShell proxy substitutes the real token on every request (the spec requires the header on every request and forbids tokens in query strings) |
| `bearer` | Static API tokens | Provider credential; `Authorization: Bearer <placeholder>` |
| `headers` | Custom header schemes (`X-Api-Key`, `Authorization: Basic …`, several headers), such as crypto-research-mcp's Cloudflare Access service token | One provider credential per secret value, all in one provider (OpenShell binds one provider per endpoint). Header values in the server entry reference them, and the agent runtime's client places the placeholders (`[mcp_direct.servers.NAME] credentials`). OpenShell resolves placeholders in any header value, including Basic auth. The roadmap's "profile-driven placement" is not needed, because the MCP proxy places the placeholder |
| `none` | Public servers | No credential |

Checked on babbage ([lab 2](../.agents/docs/agent-reports/babbage-openshell-lab-2-2026-10-10.md)):
- A provider named by `credential_binding` must be attached to the agent runtime's sandbox (`[mcp_direct] providers`), and its profile must declare no endpoints.
- OpenShell substitutes placeholders in headers, never in a JSON-RPC body, which it forwards unchanged.
- After `initialize`, the client must send `MCP-Protocol-Version` on every request. Without it, OpenShell assumes 2025-03-26 and refuses requests that a policy limits to later revisions.

## crypto-research-mcp: a Cloudflare Access service token

crypto-research-mcp sits behind Cloudflare Access. A request passes Access when it carries a service token's two values in the headers `CF-Access-Client-Id` and `CF-Access-Client-Secret`, and Access then forwards it to the server. The server entry is therefore a `headers` server whose two values reference two credentials of one OpenShell provider, `crypto-research-mcp`:

```yaml
crypto-research-mcp:
  url: https://research-mcp-api.npages.org/mcp   # the Access-protected address of the server
  revision: "2025-11-25"
  auth:
    mode: headers
    headers:
      CF-Access-Client-Id: "${provider:crypto-research-mcp.CF_ACCESS_CLIENT_ID}"
      CF-Access-Client-Secret: "${provider:crypto-research-mcp.CF_ACCESS_CLIENT_SECRET}"
```

- **Where the address lives.** The portal's URL is in the project policy file, as this entry's `url`, and nowhere in the launcher's config: `personal-policy.yaml` for the personal instance ([personal babbage](PERSONAL-BABBAGE.md)), and the deployment's own policy file (the `policy` of the config's `[worker]` table) in general. The launcher config names the policy file and the `[mcp_direct]` servers by name only. The tracked `examples/policy.yaml` holds a placeholder, so a deployment replaces it in its own copy, which is outside the repository.
- **One entry, one listing, name prefixes.** The portal is one MCP server with one URL, and it lists the tools of all its servers together: `attack-catalog-mcp_get_catalog_info`, `e-print-mcp_search_eprint` and the portal's own `portal_list_servers` come in one `tools/list`. A tool's server is the prefix of its name, so the policy has one `crypto-research-mcp` entry, and its [classification](#classification-files) files each carry the `prefix` they apply to. Rules, escalations and denials name tools by their prefixed names.

The policy compiler binds the server's endpoint to that one provider (`credential_binding`), and the agent runtime's client, in its sandbox, reads the two placeholders from `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET` (`[mcp_direct.servers.crypto-research-mcp] credentials`, [the direct path](#the-direct-path)) and sends them as the two headers. OpenShell substitutes the values as the request leaves, only toward the bound host. The runtime holds placeholders only, and nothing an agent or a worker can reach holds the token.

**What the owner does.** The owner creates the token and the Access policy, and registers the secrets with OpenShell, on babbage. No secret passes through an agent, a chat, this repository or a command line:

1. In Cloudflare Zero Trust, create a service token for the harness (Access → Service credentials → Service Tokens), and keep its Client ID and Client Secret until step 4: Cloudflare shows the secret only once. Choose its duration, and note when it expires.
2. In the Access application that protects crypto-research-mcp, add a policy with the action **Service Auth** that includes this service token. A **Service Auth** policy admits a request with the token's headers and no user login.
3. Import the provider profile, which declares the two credentials and no endpoints (OpenShell refuses a `credential_binding` to a provider whose profile has endpoints, lab 2). Profiles are read from the gateway, so this needs the running gateway; `lint` checks the file first:

   ```bash
   openshell provider profile lint -f examples/openshell/profiles/cloudflare-access.yaml
   openshell provider profile import -f examples/openshell/profiles/cloudflare-access.yaml
   ```
4. Create the provider from environment variables, read without echo, so the values appear in no command line or shell history. `--credential KEY` without `=VALUE` takes the value from the environment variable `KEY` (OpenShell 0.1.3, `openshell provider create --help` on babbage, 2026-10-14; unchanged in 0.1.5):

   ```bash
   read -rs -p "Client ID: " CF_ACCESS_CLIENT_ID; echo; export CF_ACCESS_CLIENT_ID
   read -rs -p "Client Secret: " CF_ACCESS_CLIENT_SECRET; echo; export CF_ACCESS_CLIENT_SECRET
   openshell provider create --name crypto-research-mcp --type cloudflare-access \
     --credential CF_ACCESS_CLIENT_ID --credential CF_ACCESS_CLIENT_SECRET
   unset CF_ACCESS_CLIENT_ID CF_ACCESS_CLIENT_SECRET
   ```
5. Name the provider in `[mcp_direct] providers`, which `up` attaches to the agent runtime's sandbox ([the direct path](#the-direct-path)), and put the URL of the server in the project policy's entry.

**From the owner's file** (approved by the owner, 2026-10-15). Instead of typing the values in at steps 3 and 4, the owner keeps them in a file in the owner's secrets directory on babbage, which no agent opens. A helper registers the provider from it:

```bash
uv run python -I -m sandbox_science.launcher.access_provider /path/to/the/owners/cloudflare.env \
  --profile examples/openshell/profiles/cloudflare-access.yaml --openshell "$HOME/.local/opt/openshell-0.1.5/bin/openshell"
```

- **The file.** The helper refuses a file that is not a regular file, that is a symbolic link, that has more than one link, that is not the user's, or that its group or others may read or write. Its directory must be the user's, and its group and others may not write it. A symbolic link is refused by its path alone: name what it links to.
  - It holds `KEY=VALUE` lines, blank lines and `#` comments.
  - The keys are `CF-Access-Client-Id` and `CF-Access-Client-Secret`, or `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET`. Case doesn't matter, nor does `-` against `_`. A `:` may come before the `=`.
  - A value may have spaces and quotes around it. Other keys are ignored.
  - A file missing either value is refused, with the missing key named.
- **What it does.** It runs `openshell provider profile lint` and `import` if the gateway has no `cloudflare-access` profile yet. Then it runs `openshell provider create`, as at step 4, or `provider update … --wait` if the provider exists.
- **What it checks first.** Whoever names the file also names the OpenShell CLI that gets the values, so the helper refuses:
  - to run with a `FAKE_*` variable set, with which the tests' stand-ins record what they are given, or an `LD_*` one, which loads code into a program;
  - an OpenShell CLI that is not an absolute path, is not a regular file the user or root owns, may be written by its group or others, or is inside a git checkout, such as this repository or one of its worktrees. A folder is a checkout when its `.git` is a directory that holds `HEAD`, or a file that begins `gitdir:`; an empty `.git` directory, as the personal instance's home has, is not one (lab, 2026-10-26). `up` passes the CLI as running it would find it: a path made absolute, or a name found on `PATH`.
- **Where the values go.** Only to that one `create` or `update` command, through its environment, and from it to OpenShell's own encrypted store, the gateway's database. OpenShell 0.1.5 takes a credential from a variable or from its command line only (its `--help`), so while that command runs, the user's other processes can read the values in its `/proc/<pid>/environ`. They never appear on a command line, in a log, in the helper's own environment or in its output. Nothing that command says is shown, since it could echo them. Neither the helper nor its children write a core file, and the helper cannot be traced or read through `/proc` by the user's other processes.
- **The default on babbage, for now** (the owner, 2026-10-15). `[mcp_direct] provider_env_file` names the file, in a config outside the repository: the tracked example has a placeholder, and a lab's config, written by the lab setup, is the only one that names the real file ([labs](../.agents/labs/README.md)). `sandbox-science up` then runs the helper itself, in a process of its own, whenever the gateway lacks the provider, as each new lab gateway does. `up --refresh-provider` registers the provider again, as after a rotation ([quickstart](QUICKSTART.md#mcp-servers)). The launcher never opens the file. Steps 3 and 4 remain the alternative.

**Rotation.** A new token goes in the same way with `openshell provider update crypto-research-mcp --credential CF_ACCESS_CLIENT_ID --credential CF_ACCESS_CLIENT_SECRET --wait`, or from the owner's file with `sandbox-science up --refresh-provider`. A running process keeps the placeholder of the credential's revision it started with, so the agent runtime is replaced after the update (`sandbox-science replace-orchestrator`, or the next `up`; [refresh](#oauth-flow-mcp-2025-11-25), the same rule). Revoking the token in Cloudflare stops access at once; deleting the provider (`openshell provider delete crypto-research-mcp`) stops OpenShell from substituting it.

**Checked on babbage, 2026-10-14:** the `openshell provider create`, `update` and `profile` commands and flags above, from the installed 0.1.3's `--help`; no provider, profile or sandbox was created. ## OAuth flow (MCP 2025-11-25)

*Design, not built, written for the MCP proxy before it retired (2026-10-26): where it names the proxy, read the agent runtime's client and OpenShell's provider substitution.*

The connector auth service performs the client side of MCP authorization when the user clicks **Connect** in the GUI:

1. **Discovery.** Call the server unauthenticated, read the `WWW-Authenticate` resource-metadata URL (or fall back to the well-known paths), fetch the protected-resource metadata (RFC 9728), then the authorization-server metadata (RFC 8414 / OpenID discovery).
2. **Client registration**, in the order the spec prefers:
   - *Client ID Metadata Document*: needs an HTTPS-hosted metadata document. Practical once there is a hosted endpoint.
   - *Pre-registration*: a configured `client_id` and secret.
   - *Dynamic Client Registration* (RFC 7591): the spec's fallback. **crypto-research-mcp supports it (confirmed), so phase 1 uses DCR.** The connector auth service registers once per deployment and redirect URI: a `localhost` callback on babbage, a separate HTTPS registration when hosted. It stores the registration response (`client_id`, any `client_secret` or registration access token) as secret refresh material, and re-registers if the authorization server later rejects the client.
3. **Authorization code with PKCE.** Include the `resource` parameter set to the server's canonical URI (RFC 8707). Use the policy's scopes; if the policy lists none, use the spec's scope selection (the `scope` in `WWW-Authenticate`, else `scopes_supported` from the protected-resource metadata), and record the granted scopes. Use a `localhost` redirect on babbage. Hosted deployments use an HTTPS callback, which the spec requires for non-localhost redirects.
4. **Token exchange**, again with `resource`.
5. **Storage.** The access token becomes the provider's injectable credential, with its expiry. The refresh token, `client_id` and any client secret become secret refresh material. The token endpoint goes into a per-server provider profile; OpenShell keeps token URLs profile-owned.

**Refresh.** There are two options, and the spike decides between them per server:

- *Gateway-managed* (`oauth2_refresh_token`). OpenShell refreshes the token and stores rotated refresh tokens automatically. Its documented refresh configuration has a token URL and scopes, but **no `resource` parameter**, which the MCP spec requires on every token request. This works only if the authorization server accepts refreshes without `resource`.
- *External* (`external` strategy). The connector auth service refreshes with `resource` and pushes the new access token to the provider through the OpenShell API. Refresh material then lives in the connector auth service's secret storage (Kubernetes Secrets/OpenBao, or the gateway's store if the API allows).

  **Reloading the running proxy.** OpenShell documents that after a static credential update, a process that is already running keeps its *revision-scoped* placeholder, and that placeholder does not resolve to the new value; a new process is needed. Gateway-managed refresh uses stable refresh handles, so later rotations need no restart. With external refresh, the MCP proxy must therefore replace its upstream client for that server on every token update. Design:
  - The MCP proxy runs one **upstream worker process per MCP server**. The front-end process that accepts callers holds no credential placeholders.
  - The connector auth service updates the provider with `--wait`, which reports per-sandbox application of the change, and then notifies the MCP proxy with the change ID.
  - The proxy starts a new upstream worker, which receives the new revision's placeholder, routes new calls to it, lets in-flight calls on the old worker finish within a grace period, then stops the old worker.
  - Refresh runs ahead of expiry (`refresh_before`) so the switch happens while the old token is still valid. A call that still fails with 401 on an old worker is retried once on the new worker, only for idempotent reads.
  - The spike checks whether the `external` strategy also gets stable handles. If it does, the worker swap becomes unnecessary.

**Scope changes.** If a server answers `403 insufficient_scope`, the proxy does not re-authorize on its own. It raises a permission escalation naming the scopes requested. The user re-consents through the connector auth service. This keeps step-up authorization a human decision.

**Token audience.** Because tokens are audience-bound to one MCP server (RFC 8707) and the OpenShell provider is endpoint-bound to the same host, a token cannot be replayed at another service even inside the proxy.

## Server entry (policy file)

```yaml
mcp:
  servers:
    example-oauth-server:                # later phase; crypto-research-mcp is a headers server (above)
      url: https://…/mcp                 # canonical URI, used as the OAuth resource
      revision: "2025-11-25"             # MCP protocol revisions allowed
      auth:
        mode: oauth
        registration: dcr                # cimd | preregistered | dcr
        scopes: [read]                   # least privilege; server-specific names
        refresh: gateway                 # gateway | external
      tools: { allow: [...], escalate: [...], deny: [...] }

    example-header-server:               # later phase
      url: https://…/mcp
      auth:
        mode: headers
        headers:
          X-Api-Key: "${provider:example-header-server.API_KEY}"
          X-Account: "research"           # non-secret literal
```

`${provider:NAME.KEY}` references resolve to OpenShell placeholders, never to secret values. A literal secret in a header value is rejected by the policy compiler.

## Later phases

- **Local stdio MCP servers** run inside a worker sandbox, with their own providers and egress policy. They are never spawned beside the orchestrator.
- **More remote servers** need only a policy entry and a **Connect** click (OAuth), or a provider created from a token (bearer/headers).
- **Per-project token separation.** The same service connected for two projects can use two providers, so revoking one project's access does not affect the other.
