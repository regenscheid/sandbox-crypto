# Research workspace

The workspace is the research GUI (W4, D80). It shows the harness's records: the projects, their sessions and environments, and each session's runs, with the agent's messages, its tool calls and their results, and the LaTeX in them rendered. It shows the project's living documents, each revision with the server's block IDs and who changed what, and lets the user edit and comment on them ([living documents](#living-documents)). LaTeX that KaTeX rejects is repaired where it can be, by rules or by the reviewer model, and marked ([math repairs](#math-repairs)). It has two parts:

- `web/workspace/`: the app the browser runs. Svelte 5 with TypeScript, built by Vite into static HTML, scripts, stylesheets, KaTeX's fonts and distribution notices.
- `packages/workspace` (`sandbox_science.workspace`): the server, in the project's Python on aiohttp, with the command `sandbox-science-workspace`. It serves the built files and a JSON API, handles login, and asks the reviewer model for math repairs when it is configured to.

Besides runs and documents, the GUI shows a session's plan and progress, with a text editor for the plan ([session plans](#session-plans)); its kernels ([session kernels](#session-kernels)); its background jobs, with cancellation ([background jobs](#background-jobs)); its consistency reviews and math checks, with the user's decisions on findings ([consistency reviews](#consistency-reviews-and-math-checks)); a project's macros; and the recorded provisioning state of a project's environments ([provisioning](#provisioning-observations)). It also shows a session's chat with its main agent and its runs' events as they are written ([chat](#chat)), and a project's published artifacts, with a viewer for PDFs ([the PDF viewer's origin](#the-pdf-viewers-origin)). It shows the project ledger as a searchable list with a selected entry beside it and an optional board, with its entries, issues, evidence, flags, gate and history, the project memory with the proposals that wait for the user, and the project's skills, with their import reports and settings ([views](#views); [ledger](LEDGER.md), [memory](MEMORY.md), [skills](SKILLS.md)). The user answers the permission requests the policy routes to them in the chat, connector tool calls and research code's network and package requests alike, and sees and revokes the project's grants on the Connectors page ([MCP connectors](MCP-CONNECTORS.md#approvals-in-the-workspace)).

## Session layout and file uploads

Project selection, session search, and research navigation live in a collapsible left sidebar. A session keeps chat in the center and offers **Documents**, **Plan**, **Agents**, and **Activity** from its header. The optional right pane resizes with a pointer or the arrow/Home/End keys up to half the browser window; its expand button reaches that width directly. Compact screens use keyboard-contained drawers; Escape closes them. Switching pane tabs preserves the composer and mounted document editors. Documents show a notice when an agent publishes a newer revision, with an explicit refresh that retains an unsaved draft and its original base revision.

Documents has an **All documents** library with search, content-kind, scope, and sort controls above compact rows. It includes the current session workbook, shared project documents, uploaded originals, and published artifacts. Each opened document has a named tab beneath Documents; arrow keys switch tabs, and Delete or the close button closes one. Closing keeps its editor and unsaved draft mounted for reopening within the session view. Search/sort of uploaded originals explicitly covers loaded pages; older pages remain reachable with **More uploads**. Plan keeps the existing plan/progress editor. Agents shows parent/child status, delegation briefs, and a bounded live activity view, with links to full history. Activity keeps recovery-adjacent observations, fold proposals, kernels, jobs, reviews, and run history. Chat and documents share Markdown/KaTeX rendering, including project macros and inline/display math. See the [interaction contract](specs/research-ui.md).

Use **Attach files** or drop files on the attachment area, up to eight per message and 100 MiB per file. A stored file may be attached again. Original hashes, metadata and USER attribution are immutable control records; new original bytes use the verified durable blob store and its optional S3 backing, while existing inline originals remain readable. Limits are 2 GiB/1,024 files per project and 8 GiB/4,096 files per store. Browser uploads send raw file bodies with bounded metadata; the server streams binary originals and downloads in bounded chunks, outside SQL transactions. The legacy JSON/base64 route remains limited to 8 MiB. Upload requests have a 300-second browser deadline and retain their ID for retry. Transfers continue across internal navigation; pending bytes stay in browser memory, with an unload warning. Only attachment metadata is saved in browser draft storage.

Durable upload admission permits four transfers overall and two per project; the workspace additionally serializes its uploads/downloads and sandbox deliveries across tabs. Cancellation drains the actual disk/object-store operation before releasing admission. An interrupted installed upload retains its reservation and exact byte identity for retry. Archived original downloads verify size/hash before sending headers and close an incomplete response on transfer failure. Storage and scratch requirements are in the [durable upload contract](specs/durable-artifact-blobs.md#uploaded-originals-2026-10-20).

Sending with attachments copies each file through the configured worker API, with USER authority, to a server-chosen session path under `shared/uploads/`. The queued message records a JSON manifest with names, paths and hashes. A worker or surviving executor without the larger transfer capacity returns an actionable refusal, retaining the original for retry after upgrade. An unavailable worker leaves the original and draft available for retry; an existing changed sandbox copy is never overwritten. Replaying an already accepted message does not copy again. The workspace stores and serves bytes; it never executes or extracts research content on the host. Arbitrary binary files, including PDFs, can be attached and downloaded as originals. UTF-8 `.md`, `.markdown`, `.txt`, and `.tex` files up to 1 MiB can explicitly become a revisioned document; normalization affects that derivative only. Uploaded PDFs are not automatically imported into the artifact PDF viewer. Upload deletion and automatic document extraction are not built.

## Building and running

```bash
cd web/workspace
npm ci --ignore-scripts      # exactly the packages in package-lock.json; no install scripts
npm run build                # writes dist/, and the PDF viewer's dist/viewer/
cd ../..
uv run sandbox-science-workspace serve --state-dir harness-state --static web/workspace/dist
```

Distribute the complete `dist/` directory, including `THIRD-PARTY-NOTICES.txt`, `LICENSE-Sandbox-Science.txt` and `license-manifest.json`. The build collects the package and helper origins it actually emits and ships their complete primary notices, with attribution and pinned license text for embedded components (React-derived Apache 2 helpers, the MIT is-promise adaptation, and the OFL fonts and glyph-derived SVG assets). The manifest records the notices and each distributed file's SHA-256, excluding the manifest itself. A stylesheet split out with a shared chunk, which has no source file of its own, takes its origins from the component styles and stylesheets of the chunks that import it. Unknown origins or assets, missing or changed notices, changed fonts, and version or license mismatches between the lockfile and the installed packages fail the build; copying a public directory is refused. The server serves these files like any other built file. See [notice inputs and update procedure](../web/workspace/licenses/README.md) and [licensing](LICENSING.md). The [isolated math-check distribution](MATH-CHECKS.md#build-and-configure) uses the same notice inputs for its code-only bundle. The PDF viewer is a third build (`vite.viewer.config.ts`) into `dist/viewer/`, with notices and a manifest of its own: PDF.js, its worker and exactly the PDF.js files the license manifest lists ([PDF viewer](specs/pdf-viewer.md), PV-5). Only the preview origin serves it.

The server prints a login URL once:

```
PDF viewer origin on http://localhost:8201/
Sandbox Science workspace on http://127.0.0.1:8200/
Log in by opening this URL; it works until the server stops:
    http://127.0.0.1:8200/login?token=…
```

Open it in a browser on the same machine. The settings of `serve`:

| Setting | Meaning |
| --- | --- |
| `--state-dir` | Required. The harness's state directory (`sandbox-science-harness … --state-dir`). Its control store, `control.sqlite3`, holds the projects, sessions, runs, documents, plans and reviews |
| `--static` | Required. The web app's build, `web/workspace/dist` |
| `--listen` | `host:port`, default `127.0.0.1:8200`; port 0 picks a free port |
| `--allow-remote` | Accept a listening address that is not loopback (see below) |
| `--preview-listen` | `host:port` of the PDF viewer's own origin; default the same host and the next port, so `--listen` on port 65535 needs it ([the PDF viewer's origin](#the-pdf-viewers-origin)) |
| `--preview-name` | The host name the viewer's origin is given by: on loopback, `localhost` or its listen address. Default `localhost` when it listens on `127.0.0.1` (and the workspace is not itself named `localhost`), which makes it another site; otherwise its listen address |
| `--public-origin`, `--preview-public-origin` | Behind a TLS-terminating reverse proxy: the `https://` origins the browser reaches the workspace and the viewer at. Given together, each exactly `https://host[:port]`, distinct, and only with `--allow-remote`; `--preview-name` is then refused ([behind a reverse proxy](#behind-a-reverse-proxy)) |
| `--trust-proxy-from` | A network in CIDR form (repeatable) whose connections' `X-Forwarded-Proto` and `X-Forwarded-Host` are believed; only with `--allow-remote`; never `/0` ([behind a reverse proxy](#behind-a-reverse-proxy)) |
| `--log-level` | `DEBUG`, `INFO` (default), `WARNING` or `ERROR` |
| `--worker`, `--worker-token-file` | The worker's URL and a file with the workspace's worker token, for job views and cancellation, kernel observations and provisioning observations |
| `--mcp-project`, `--mcp-service NAME=PURPOSE` | Optional project and top-level MCP service identities for the read-only service browser; `sandbox-science up` passes the safe names and purposes from its configuration. These arguments carry no endpoint or credential |
| `--model-url`, `--reviewer-model`, `--api-key-file` | The model gateway for math repairs ([math repairs](#math-repairs)) |

The server refuses an address that is not loopback unless `--allow-remote` is given. It speaks plain HTTP, so on another address the login URL and the session cookie cross the network unencrypted, and it then accepts any host name ([authentication](#authentication)). Placing the GUI on another machine is W5's work. On a cluster, the Kubernetes bundle's opt-in [ingress](KUBERNETES-BUNDLE.md#workspace-through-the-clusters-ingress-opt-in) runs it with `--allow-remote` and its two public origins behind Traefik and Authentik ([behind a reverse proxy](#behind-a-reverse-proxy)).

**The server's network reach.** It listens where `--listen` says, and on `--preview-listen` for the PDF viewer. It can contact the model gateway at `--model-url` for math repairs, and the worker at `--worker` for job views, cancellation, kernel observations and provisioning observations. Without either setting it opens no outbound connection.

For work on the app itself, `npm run dev` serves it with Vite and passes `/api` and `/login` to a server on port 8200. Log in through the dev server's port. Logging out does not work there, since the dev server is another origin, and Vite's pages do not carry the server's headers.

The app is a directory of its own, `web/`, rather than a member under `packages/`: uv takes every directory in `packages/` for a Python project, and pyright and pytest search it, while the app's toolchain is Node's. Each browser app gets its own directory under `web/`.

## Authentication

Login works like Jupyter's, for one user on their own machine (threat model, zone Z4: the GUI is trusted by the user, the content it shows is not).

- **Login token.** At each start the server makes a random token (32 bytes, 43 URL-safe characters) and prints the login URL once, on standard output; it neither logs nor stores the token. A restart makes a new token and ends every session.
- **Login.** `GET /login?token=…` compares the token in constant time. A match sets the session cookie `sandbox_science_workspace-<port>` (32 random bytes; HttpOnly, SameSite=Strict, Path `/`, and Secure over HTTPS) and redirects to `/`, so the token leaves the address bar. Browsers send a host's cookies to every port on it, so the name carries the port, and two workspaces on one machine keep their sessions apart. The server keeps only the cookies' SHA-256 digests, in memory. A session lasts until the server stops or the user logs out (`POST /api/v0/logout`); past 64 sessions, the oldest ends.
- **The API needs the session.** Every route under `/api/` answers 401 without it.
- **Changes need the server's own origin.** A request with any method other than GET or HEAD must carry an `Origin` equal to the server's own (scheme and `Host`); a missing or `null` origin is refused. Nothing answers CORS: no route takes preflights or sets `Access-Control-*` headers. SameSite=Strict also keeps the cookie off requests started by other sites. The routes that take a POST are listed in the [API](#api-v0).
- **The server's own names.** On a loopback address, every request must name the server in `Host`: `localhost`, `127.0.0.1`, `[::1]` or the address it listens on, with its port. A page whose own host name an attacker rebinds to 127.0.0.1 (DNS rebinding) is refused, and could not use the cookie in any case, since the cookie belongs to the name the user logged in with. With `--allow-remote` this check is off, because the names that reach the server are not known, unless a public origin names them ([behind a reverse proxy](#behind-a-reverse-proxy)).
- **User attribution.** Writes are attributed to the USER on the server; a request body cannot choose its author. Plan reads and edits use the same USER identity for every login. Math repairs, which limit each browser session, name the session by the SHA-256 digest of its cookie.
- **What remains.** Cookies are not bound to ports, so any other web server on the same host name receives the session cookie when the browser visits it, as with Jupyter. On the user's own machine only the user's services listen there; research code runs in sandboxes that cannot reach the host's loopback, except on the worker's local backend, which is for tests.

Re-authentication for high-risk approvals (D54) comes with approvals.

### Behind a reverse proxy

The server speaks plain HTTP. To reach it from another machine it runs behind a proxy that terminates TLS, such as the Kubernetes bundle's Traefik with Authentik forward auth ([ingress](KUBERNETES-BUNDLE.md#workspace-through-the-clusters-ingress-opt-in)). Both settings are opt-in and need `--allow-remote`; without them nothing on this page changes, and forwarded headers are never read (`proxy.py`; `test_proxy.py` proves the loopback server unchanged, to the `Set-Cookie` header).

- **Public origins** (`--public-origin https://workspace.example.org --preview-public-origin https://preview.example.org`). They are what the browser sees, and they replace the server's own origin rather than adding to it, since under `--allow-remote` the server's own origin is only `http://<whatever Host arrived>`, an origin no page of the workspace has. With them:
  - the workspace answers only to a `Host` that names its public host (`workspace.example.org`, or with `:443`), and the viewer only to its own, which restores the DNS-rebinding defence that `--allow-remote` otherwise turns off; anything else gets 403. A `kubectl port-forward` to the listener is therefore refused too;
  - a change (any method but GET or HEAD) must carry exactly `Origin: https://workspace.example.org`; `http://` on the same name, another port, the preview origin and `null` are refused;
  - the session cookie is `__Host-sandbox_science_workspace-<port>`: Secure, HttpOnly, SameSite=Strict, Path `/`, no `Domain`. The `__Host-` prefix makes the browser refuse any version of it set by another host, so the preview origin, a sibling under the same parent domain, cannot set or shadow it;
  - the preview origin announced in the workspace's CSP (`frame-src`, `img-src`), its links and the viewer's and figures' `frame-ancestors` and `#w=` fragment are the public origins, so the PDF viewer and figure frames work through the proxy;
  - `serve` prints the public origins, with the addresses served at, and the login URL on the public origin. Redirects (`/login` to `/`) are relative, so they need no origin.
- **Trusted proxies** (`--trust-proxy-from 10.42.0.0/16`, repeatable). Only for a connection whose peer address (the socket's, never a header's) is in one of these networks are `X-Forwarded-Proto` (`http` or `https`) and `X-Forwarded-Host` read, in place of the connection's scheme and `Host`, for the host and origin checks and the cookie's Secure flag. Each must appear at most once with one value; a repeated, comma-separated or malformed one is refused with 403 rather than guessed at. Behind a public origin, a trusted proxy that reports `http` is refused, so a plain-HTTP entry point at the proxy does not reach the app. `Forwarded` (RFC 7239) is never read, because Traefik replaces a client's `X-Forwarded-*` but passes `Forwarded` through; `X-Forwarded-For` is never read or logged, since no decision depends on the client's address. A network with host bits set or of every address (`/0`) is refused. Traefik passes `Host` through by default, so the bundle trusts no proxy: the public origin alone suffices. Trust a proxy only when it rewrites `Host` and sets `X-Forwarded-Host`.
- **What stays trusted, and by whom.** The proxy is trusted for reachability (TLS, Authentik) and, when listed, for the scheme and host it forwards; nothing it sends authenticates. Authentik only gates who reaches the server: the workspace keeps its own login token and session, and Authentik's headers (`X-authentik-username` and the like) open nothing. Logging in to Authentik first and then opening the printed `https://…/login?token=…` works as on loopback. Single sign-on through Authentik (taking its user as the workspace's) is future work.
- **SameSite=Strict holds.** After Authentik's login, the browser returns to `/login?token=…` by a top-level navigation (from Authentik's host, which is the same site under the parent domain the bundle requires); a browser accepts a Strict cookie set in that response from any site, and the page it redirects to, `index.html`, needs no cookie. Only the app's own `fetch` requests, same-origin, carry it. So neither the session cookie nor the login step is loosened to Lax. When Authentik's own session expires, an API request is redirected to Authentik and fails as a cross-origin fetch; reloading the page logs in again.

## What the browser may do

Every response carries these headers, errors and files included:

| Header | Value | Why |
| --- | --- | --- |
| `Content-Security-Policy` | `default-src 'none'; script-src 'self'; style-src 'self'; style-src-attr 'unsafe-inline'; img-src 'self'; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` | Scripts, stylesheets, fonts and fetches only from the server's own files and API. No inline or eval script, no frames, no plugins, no forms. KaTeX lays formulas out with inline `style` attributes, so those are allowed, and nothing else inline |
| `X-Content-Type-Options` | `nosniff` | A file is only what its type says |
| `Referrer-Policy` | `no-referrer` | A followed link does not tell its site where it came from |
| `X-Frame-Options` | `DENY` | No framing, for browsers without `frame-ancestors` |
| `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy` | `same-origin` | Other sites' windows and pages cannot reach the app or embed its files |

The build inlines no asset as a `data:` URL, so the fonts arrive as files the policy admits. API answers are `Cache-Control: no-store`; the app's assets, whose names carry their content's hash, are cached for a year.

**Files.** The server serves only files inside the build directory, with a type from a fixed table (HTML, JavaScript, CSS, JSON, fonts, SVG, PNG, icons, text). A path with an empty, `.` or `..` segment, a dotfile, a backslash or NUL is not found, however it is encoded; so is a symbolic link that leads outside the directory. A GET outside `/api/` for a path that is no file and whose last segment has no `.` is one of the app's routes, and gets `index.html`.

All routes need the session and answer JSON, except original upload downloads. Every route that is a GET also answers HEAD. POST routes also need the server's own origin. ### Document routes

A document revision's answer holds its `document`, its `revision` (author, the user who accepted it, reason, base and parent, warnings, what was normalized, the parsers' versions), its `text`, its front matter's `title`, effective `macros` and `macro_context` (setting revision and hash, anchors, known or held state, warnings and identity), and its `blocks`: each one's `id`, `kind`, `parent`, `depth`, `lines`, `status`, structural kind and attributes, its editable Markdown `source` without its containing block's indentation, and its formulas' `id`, `kind`, `status` and `tex`. `matched` is false when the server could not parse the revision as its block map was made, and the formulas then come without their TeX.

Document writes use `POST …/documents/{document}/changes`, with a strict action (`source`, `patch`, `revert`, `promote`, or `apply_patch`), `base`, `reason` and `operation_id`. The action carries respectively `text`, `operations`, `target`, `name`, or `patch_id`; unknown fields are refused. Results include `outcome`, revision, retained patch ID and structured conflicts. `GET …/patches/{patch}/preview` returns the retained operations, the exact current `base`, current and proposed source, and whether the named operations can safely apply.

Comments use `GET …/comments?revision=N&after=THREAD`, returning `threads` and `next_after` (10 threads or 1 MiB at most). `GET …/comments/{thread}?before=ENTRY_NUMBER` reads up to 50 entries or 256 KiB of projected entries and an `entries_before` cursor, with the anchor projected onto the current document revision. `POST …/comments` takes a strict `create`, `reply`, `edit`, `edit_body`, `resolve` or `reopen` action and an `operation_id`. Create carries `anchor: {revision, block, math? | start?/end?}`, `body` and optional `addressed_to`; reply and edit carry `thread`, `expected`, `body` and an optional target session; `edit_body` carries the original `entry`, the current body's `base` and `sha256`, `thread`, `expected`, the new `body` and `operation_id`, and appends history without changing the original entry or a work request already pinned to it; resolve and reopen carry `thread` and `expected`. Completing a `request_id` is reserved for the addressed session's main agent; a user cannot claim that completion through this route. User attribution and project and session ownership are derived or checked on the server, and unknown fields are refused. Bodies are bounded to 8,192 characters or 16 KiB of UTF-8 within the ordinary 64 KiB request limit; anchors keep immutable context derived on the server. Lists of changed blocks carry explicit totals, truncation and revision links.

### Errors and records

Errors are `{"error": {"kind", "message"}}` (document errors also carry `details`) with the worker API's kinds: 400 `invalid_request` for a malformed ID, run name, document name, revision number or request body, 401 `policy_denied` without a session, 404 `not_found`, 409 for a stale guard (a document, comment, plan or finding revision, or a provisioning pin), 413 for a request body over 64 KiB (document changes allow 8 MiB of escaped JSON, while document text stays bounded to 1 MiB of UTF-8; plan changes allow 128 KiB), 422 `unsupported` for a record over the size limit or an observation without a configured worker, 429 `unavailable` for a session that has asked for as many model repairs as it may for now, 503 `unavailable` when the worker cannot be reached or answers badly, a request times out, or a project or run record is damaged, and 500 `internal` for an unexpected failure. One mapping in `errors.py` gives every route these statuses. A 503 or 500 carries a fixed message that names neither the worker's address nor a record's path. The job routes pass the worker's own refusals (400, 403, 404, 409 and 422) through with their status and message; the kernel and provisioning routes answer them with fixed messages. JSON that a record cannot carry, a NaN from a tool's output say, is sent as a string.

The server reads the harness's records through the orchestrator's `ProjectStore`, and the documents, plans and reviews through its `DocumentStore`, in a thread. Views read through read-only `ProjectStore` and `DocumentStore` connections, and a separate writable connection makes user changes. At startup the command opens that writer to bring the store to the current schema version, and does not start if it cannot. Reading the harness's state directory directly is this stage's arrangement: the workspace runs beside the harness and imports the orchestrator's stores (the one deployable member importing another, in the [conventions](../.agents/CONVENTIONS.md)). W5 gives the control application an API of its own for the GUI to use.

The server registers shared dependencies once, in `WorkspaceContext`: the project reader,
document reader, user writer, worker, timeouts and run-size limit. `requests.py` owns
project-scope checks, explicit read/write store selection, thread execution and JSON
responses. Document-name validation, session ownership, action schemas and cursor rules
remain in their feature modules. The application guard translates raised errors through
`errors.py`, retaining the common status, error details and `no-store` header. The ledger's
adapter retains its typed JSON encoder and read deadline; generic document reads and user
writes retain no request deadline. A deadline cancels only the await of a thread, so it
must not be treated as stopping a write already in progress.

## The client

The app talks to the server through a few shared modules (`web/workspace/src/lib`).

**The client's requests.** Every request goes through one function (`src/lib/http.ts`): to this origin under `/api/v0`, without the cache or redirects, with an optional deadline and byte limit, failing with an `ApiError` that carries the server's error kind and message. The types of the typed answers (the project list, a project, a session, kernels, plans and plan edits, provisioning, chat messages and run events, artifacts and viewer links) are generated from the server's response models into `src/lib/api-types.ts` by `scripts/generate_api_types.py`; a workspace test fails when the file is stale. Answers from this server are trusted as the server's own: the client checks only that a polled answer belongs to the project, session or environment the view shows. The panels that refresh (plans, kernels, jobs, provisioning, the session's runs and chat) share one poller (`src/lib/poller.ts`): it reads only while the page is visible, never overlaps its own reads, gives up on a read after eight seconds, waits three seconds between reads (a second and a half for chat) and backs off to thirty after failures, and stops for good on a 401, and, for a panel that reads its own scope's record, on a 404 or a 409. The jobs panel retries a 404 or 409, since the jobs route passes the worker's refusals through. A read that hiding the page interrupted is read again when the page is shown. A 401 from any request, or the Log out button, ends the page's session (`src/lib/session.ts`): every panel stops and no request starts until the page is reloaded after a new login.

**Saving.** Every editor saves the same way (`src/lib/mutation.ts`): the document, comment, reply, comment-body, finding-response, macro, plan and chat editors each keep a typed draft, with the revision it was based on, in memory across views and in the tab's session storage across reloads (a stored draft that is unreadable or invalid is left untouched). Except in the plan editor, a save sends the change with a random operation ID kept under the change's kind, scope and body until a result: after any failure (no answer, a 5xx, a sign-out, or a refusal), saving the same change again reuses the ID, so the server replays its first answer instead of applying the change twice. The plan editor instead makes a random `plan-edit-<uuid>` ID for each new save, keeps it in its draft with the exact request, and drops it after a definitive refusal ([plan editor](SESSION-PLAN-EDITOR.md#unknown-save-outcomes)). A failure does not prove that an earlier attempt of the same change was not applied. A 409 is a conflict with the current revision, which the editor shows; a changed draft is a new change, with a new ID. A draft that cannot be stored for a reload is kept in memory only, and an older stored copy of it is removed. On the server, every write route, math repair included, reads its body with `context.json_body`, or with `context.read_body` when it validates the JSON strictly itself (the plan edit route): UTF-8 (or the declared charset) JSON within the route's byte limit, refused with 400, or with a JSON 413 over the limit.

**Views and their decisions.** A view's decisions live in a plain TypeScript module beside it, tested without a browser: what a draft holds, the change it sends, when a save is done and how a conflict resolves (`documentEdit.ts` for the document editor, `commentAnchors.ts` for a new comment, `commentThreads.ts` for a thread's replies, status changes and body corrections, `macroSettings.ts` for the macro setting, `documentHistory.ts` for a document's history and its patch reviews, `reviewBrowser.ts` and `reviewText.ts` for the consistency reviews panel, `findingView.ts` for a finding's status, anchors, history and decisions, `findings.ts` for a response to a finding, `provisionView.ts` for the Environments panel's labels and its paging through comparisons and packages, `planEdits.ts` for the plan editor). Four shared pieces carry what the views repeat. `pagedList.ts` reads a list a page at a time (a document's comment threads; a session's reviews, findings and math checks; a review's evidence and audit records; the slices of an evidence text; a project's published artifacts); a reload drops any page still on its way, so a late answer never mixes an older list into a newer one, and what a first page brings besides its items (the windows left unreviewed, the math-check queue) is applied only when that page is shown. `earlier.ts` reads a history backwards a page at a time, on `pagedList.ts`: a comment thread's entries before the oldest one shown, or a finding's transitions from the newest. It starts again when the thread or the finding changes. `detail.ts` reads one thing by its key and shows only the latest choice (a document's history, a patch's preview, a finding's mechanical math evidence): another key's value is cleared at once, and a late answer for an earlier key is dropped. `submit.ts` runs a view's write one at a time (posting a comment or a reply, correcting a comment's body, responding to a finding, applying a patch, saving the macros, sending a chat message, resuming or cancelling a run), keeps its failure for the view, and may then read the current revision beside the retained draft (the macro editor). Each takes a state object the view makes with `$state` and changes it in place; a reload or a new key reads none of that state first, so a view's effect may start one without depending on it.

## Living documents

The project's living documents and its sessions' workbooks show each revision and who changed what. The document view shows rendered text beside comments; selecting Edit source hides the rendering and gives the editor the full document width. Switching back to Comments restores the rendering without discarding an unsaved source draft. The current revision offers source and block editing, and workbook documents can move to project scope. Earlier live revisions offer an explicit revert. History previews retained patches against the current text and lets the user apply them with that exact revision as the guard. Documents live in the harness's control store; see [living documents as built](LIVING-DOCUMENTS.md) and [the reconciliation rules](LIVING-DOCUMENTS.md#changes).

Drafts keep their base revision in memory across views and in this browser tab's session storage across reloads. Conflicts show the newer text and author while keeping the draft. Resolving a whole-source conflict starts with the current text and keeps the old draft separately; block resolution touches only the named block. A browser without storage keeps the in-memory draft and warns before closing. Inputs are disabled while a save is pending.

**Comments and addressed work requests.** Each document revision offers a block, formula or quoted-range comment composer, its original quote and context and its attachment status (`current`, `moved`, `stale`, `orphaned`). Threads show attributed append-only history, requests' queued, delivered and responded states, revision links and changes outside the anchor. Replies, opening-comment edits and resolve and reopen actions guard the expected thread revision. Drafts survive navigation and reload independently of source edits; retry IDs for an exact payload survive uncertain responses. Large thread histories and thread lists are paged.

Choose a recorded session's main agent to queue a work request. Workbook documents default to their own session; project documents have no default. An active main run receives it at a model safe point, and it ends a job wait. For an idle session, the run service starts a run for it, as for a chat message ([chat](#chat)); without the service, it waits for the session's next main run. The full comment body is the instruction, and the anchor, quoted document and other comments grant no authority. Delivery is acknowledged only after the run transcript is durable; a crash between saving the transcript and acknowledging can replay the stable request ID. Agent replies do not resolve user threads. See [the annotation and delivery rules](LIVING-DOCUMENTS.md#comments-and-work-requests).

**Comment body math.** [Comment and reply math](COMMENT-MATH.md) shares the bounded isolated checker and closing-only notices with document math. Original bodies and every correcting actor stay immutable; project-wide checks identify the original comment entry, body revision, pinned parent document macro revision and exact check context. The comments route accepts a body correction (`edit_body`) only for USER-owned source, guarded by thread, body and hash. Body drafts and retry IDs survive conflicts independently of reply drafts; adopting current guards keeps unsaved text. Legacy identities that are bound to an older parser or unknown stay visible as held checks while ordinary edits stay usable.

**One parse on both sides** (LD-5, LD-9). A document is parsed by the text renderer's parser with two rules more, as the server parses it: YAML front matter at the very start of the text, and theorem-like containers, `::: lemma (label)` to `:::` (`src/lib/documentrules.ts`, ports of mdit-py-plugins' `front_matter` and `container`, MIT, credited in the file). The rules are registered in the server's order, and each block rule records where the blocks it makes lie and where their own text begins on each line (`src/lib/blockmap.ts`), from which the browser derives its block map as the server does: each block's kind, depth and lines, without trailing blank lines, and each formula's block, kind and TeX. The shared cases in `src/lib/documents.fixtures.json` pin both, and run through both parsers in CI, with the dollar and delimiter cases run through the document parser too.

**The server's IDs** (`src/lib/attach.ts`). The revision's block map comes from the server with each block's ID, kind, depth, lines and status, and each formula's ID, kind and TeX. A block of the browser's parse takes the ID of the server's block of the same kind, depth and lines, in order, and its formulas take the server's span IDs when both read the same kinds and TeX. Each block's element carries its ID as `data-block`, shown at its top right while the pointer is over it, and each formula's carries `data-math`. Where the parsers disagree, the view says where and why, and that part keeps no ID and is outlined: it never guesses which block is which. Revisions parsed with table profile 1 keep their original maps and can show the Unicode table trim mismatch that profile 2 corrects ([table profiles](TABLE-PARSER-PARITY.md)). A revision whose block map a parser of another version made comes without its formulas' TeX; its blocks still take their IDs, and its formulas theirs in order.

**What a revision changed.** A block the revision changed, added or moved is marked at its left, in the colors of its status; a first revision marks none. A displayed equation in a quote is rendered without the quote's markers, which its TeX keeps as the plugin reads it.

**Macros** (LD-28; `src/lib/macros.ts`). A document's math renders with the server's effective context: bounded project definitions, overridden by its front matter. KaTeX expands a macro wherever a formula uses it, and a few short macros that use one another can expand into a great many characters: three of them, written inside a formula, once froze a page for 39 s. So, on both sides:

- the effective context has at most 200 macros, each a control sequence defined in at most 1,000 characters;
- a macro whose definition defines another, as `\def` does, or uses one of its arguments more than once, which would let it multiply what it is given, is left out;
- the server also leaves out a macro that expands into itself, or to more than 2,000 characters with the macros it uses expanded, and warns of each on the revision;
- and as KaTeX renders a formula, each expansion of one of the document's macros counts its definition's characters: a formula whose macros expand to more than 2,000 characters in all is shown as written, with why.

Render and repair caches carry project scope, effective context identity and definitions, so one project or context cannot reuse another's result. The project view offers a USER editor for the JSON setting; exact revision guards and persisted drafts and retry IDs keep concurrent edits. The same setting is available through the [USER CLI and scoped API](PROJECT-MACROS.md#changing-the-setting). Settings admit at most 16 KiB of canonical definitions; unsafe settings are refused, while unsafe document front matter keeps its source and a warning. A formula that defines a macro is still shown as written ([math repairs](#math-repairs)).

An unnumbered current document uses the current project setting. An explicitly numbered revision uses the setting pinned when it was saved; older history without a pin stays unknown. Comments use the selected document's effective context; thread history is diagnostic rather than a claim about each body's rendering when it was saved. Anchored findings resolve a unique agreed context from their document anchors; contradictory or unproved contexts are visibly held, with project-only rendering labelled diagnostic. See [context and lifecycle boundaries](PROJECT-MACROS.md#exact-contexts-and-uncertainty).

**Limits.** A document holds up to 1 MiB of text and 20,000 formulas, as the server keeps them; its math renders in goes as a text's does ([showing untrusted text](#showing-untrusted-text)), so a long document takes more goes, not longer ones. The same renderer shows it, with the same rules for links, images, raw HTML and math.

## Chat

The user can write to a session's main agent ([run service](specs/run-service.md)). A message is queued in the control store with its state. A run of the session delivers it before its next model call, as the user's own message, and a message waiting when the run is about to answer makes it go on. Once the run's record is saved, the message is `delivered` with that run. A message a failed model call saw stays `queued` for the next run. While the agent waits on jobs, a message, or a work request addressed to the agent, ends the wait. While it waits for the user's answer to a question it asked, a message answers the oldest such question in the user's own words instead of being queued ([questions to the user](QUESTIONS.md)). One run holds a session at a time: a run started while another holds it is refused (`busy`).

Each run writes its events as it goes, in the control store: `started`, `user`, `model` (a model call began), `assistant`, `tool`, `notice`, `waiting` and `stopped`. Each is at most 64 KiB, with long text cut to its head and tail; the record keeps the whole text. The events are for display; deliveries are acknowledged only after the record is saved. The workspace reads them by cursor.

The normal launcher runs the agent model loops in a separate restricted OpenShell VM. The trusted host control service owns durable state and scoped capabilities; research code runs in worker sandboxes. The workspace writes authenticated USER inputs and recovery requests, and receives status through the control store. Fresh chat or an unoffered addressed comment can start work in the session's environment within its current budgets. Session and worker authority are rechecked before admission; a lost lease stops new effects.

LiteLLM's budget is the only cost enforcement by default (D102); a project tracks its spending per session, run and role. A project limit is an optional daily cost from canonical model observations and explicitly linked legacy usage. An unpriced call stays visible as unknown spending but does not by itself exhaust a configured cost limit; observed costs and explicit reservations still count toward it. The model-call journal alone checks a configured limit, before each paid call; a spent limit or a run's optional share stops the run with `gateway_budget`, as a gateway refusal does, with the local reason in its record's `summaries.budget`. Original offered inputs remain attached to unfinished work. A retry delay, new service or fresh chat never authorizes repeating the old paid request.

The chat panel exposes explicit Resume and blocked reasons even when no message is held. One durable Resume request recovers the selected tree leaf-first, preserving original policy, prompts, budgets and effect identities. The claim atomically requeues only that tree's unconsumed held input; completed/stopped branches, other trees and canonical receipts are excluded. Unknown model charges stay visible and do not alone block Resume; an uncertain paid call is never replayed as a new request. Unknown worker or MCP effects retain their original identities for reconciliation before continuation. The authenticated recovery API supplies paged work and unresolved identities and explicit operator resolutions; a full graphical reconciliation editor remains future work ([recovery controls](specs/recovery-controls.md)).

**Permission cards** (D76, D97). Below the conversation, the chat shows each request that waits for the user's answer as a card (`ChatPermission.svelte`, `src/lib/permissionCards.ts`), polled every 2 seconds: a connector tool call the MCP proxy or, on the direct path (D98), the policy middleware holds, alike, research code's HTTP or git request the policy middleware escalated, or a package request (a provisioning file set, or a file research code fetched through the package cache). A card shows a structured summary, never the payload: the tool, its server and effect class and its significant arguments, or the method, host and port, path, content type and size; who asked when it was not the agent (research code, or the user); the agent's own words, marked as the agent's, and for a delegated agent's call its brief (the direct path's cards name the call's run and, for a delegated run, the child and its brief, read from the session's delegation records by the run the middleware recorded; the middleware keeps no words of the child's, so those show only for the proxy's); and folded away a tool call's raw arguments from the transcript, or a JSON body's top-level fields with long values cut. Allow offers only the scopes the server says the request's ceiling allows (once, this session, this project), and the server refuses any other; Deny refuses. Network and package requests that name no session show in every session of the project. A **hold** of the session's outward calls by a detection rule (D103, `ChatHold.svelte`) is a card of its own: what the rule saw, in words, and the latest calls folded away, with **Clear hold**, which resumes the calls, and **Stop session**, which stops the session's run ([detect and hold](POLICY-MIDDLEWARE.md#detect-and-hold-d103)); research code's hold shows in every session of the project, and stopping it stops the run of the session it is answered in. The project's **Grants panel** (`GrantsPanel.svelte`, at the top of the Connectors page) lists the project's grants with what each covers (an effect class on a server, a host's reads, or a package source), its scope, its expiry and its last use, with Revoke, which ends one at once ([grants](MCP-CONNECTORS.md#grants)).

**Research check-ins** in chat show each soft-cap or loop check-in ([adaptive resources](specs/adaptive-research-resources.md)) with the branch's task, its use at the check-in, the loop heuristic's detail, the archived checkpoint and the decision: a parent's, the user's, or an automatic one. Older check-ins remain pageable; completed or superseded attempts are labeled historical. A root that paused after repeated extensions without new evidence offers **Review resource allowance**: one step, recorded with the user's reason against the exact paused attempt; it does not itself resume work or relax a spending limit. The root's automatic check-ins appear in the chat as notices. The root's turn limit (`max_turns`, 2,000 by default) is the user's: the research pauses there without further model calls and the chat shows a card, with the root's latest answer and use, offering **Continue for N more turns** (one more block as large as the limit, then it asks again) or **Stop the research** (an explicit Stop that Resume does not undo); Resume continues it too. A run started without a state directory has no records to pause on and still stops at its limit with a report round. There are no token approvals (D102).

Recovery and history routes pass their read-only or explicit-user writer document store to public orchestrator repositories. They never access control-store transactions or connections directly; the repository retains the supplied store's read-only boundary.

Canonical response receipts mark incorporated input delivered before final-record materialization, so a crash cannot silently repeat it. Unconsumed input stays held for recovery. A `research_state` stop preserves consolidation guidance through Resume and service replacement; fresh chat may request consolidation, while a ledger change alone never restarts unfinished research. Cancel stops the active run while background jobs retain their own lifetime. Without a healthy control-service heartbeat, new inputs wait.

## Run records

With `--state-dir`, the harness keeps every run that reaches the tool loop, including ordinary failures. It keeps the same record `--transcript` writes, in the control store's `runs` table beside the projects and sessions, named `<started>-<run-id>`. `<started>` is the start time in UTC, such as `20261011T130102345678Z`, so names sort in order of starting, and a run ID used again adds a record rather than replacing one. With `--state-dir`, a `--run-id` must therefore be an identifier. Each record is written once, in one transaction; a trigger refuses to change or delete it. A record holds:

| Field | Contents |
| --- | --- |
| `run_id` | The run's ID, which starts the operation IDs of its tool calls |
| `role`, `parent`, `delegation` | The run's place in its session's tree of runs: `main` for the root, which answers the user, or `delegated` with its parent's record name and its delegation ([plans and delegation](specs/plans-and-delegation.md), PD-32). A delegated run's record is saved before its parent's; older records are `main` |
| `alias`, `limits` | The model alias its calls named, and the limits it ran under: its turns (`max_turns`), the longest conversation it sent (`max_input_chars`), and its token limit (`tokens`, a delegated run's) or its part of the project's daily cost limit (`run_share`, under the run service with `--run-share`); older records have neither ([plans and delegation](specs/plans-and-delegation.md), PD-29) |
| `context` | Project, session, environment and policy revision |
| `task` | The task as given |

For archived tool records over 64 KiB, the saved run keeps at most 16 KiB per preview,
including its project/message reference. Full evidence remains available through the
tool-record API and its byte pages. The tool view labels these as **Record preview**,
with the reference and an omission notice. Model messages still hold their original
arguments and sampled results. The skills view marks omitted skill-use details as
archived. Runs without a journal keep the original full records inline. Exporting the
run JSON preserves these references; it does not bundle the journal's full payloads.

Model, tool-loop, harness and cleanup exceptions keep the messages and completed tool outcomes observed so far. A failed record has `stopped="error"` and no final answer; the GUI labels it a failed run and shows its partial transcript. The command still exits 1. The failure field holds only a fixed phase, never exception text, an upstream error body or a traceback. Checked with the CLI and a browser ([report](../.agents/docs/agent-reports/failed-run-records-2026-10-12.md)).

Only notices delivered through a successful model call may be acknowledged, and only after the run is durably saved. A failed record cannot finalize staged ignored-math outcomes. Scientific decisions already completed stay recorded. A refusal during setup or isolation before the loop, an interrupted command-line run, process death and an unwritable state directory leave no failed record. A cancel by the user through the run service saves a `cancelled` record; any other cancellation propagates through later cleanup failures without saving a run or acknowledging notices.

The harness writes `--transcript` first. A record it cannot keep, such as one whose tool output is nested deeper than its schema follows, is reported, and the command exits 1.

## Showing untrusted text

Everything the views show was written by an agent, a user, a paper or a program, so it is untrusted (threat T6). One renderer shows all text, the `Markdown` component (`src/lib/markdown.ts`), and the rest of the app shows text only as text.

- **Markdown** is markdown-it's default dialect (CommonMark, tables and strikethrough) with raw HTML off: tags in the text show as written.
- **Links** are kept only for absolute `http` and `https` addresses and `mailto`. Any other link, `javascript:` or relative, stays text. Links open in a new tab, without a referrer and without access to the app (`noopener noreferrer nofollow`). Bare addresses are not turned into links.
- **Images** become links and are never loaded, so text cannot make the browser fetch an address.
- **Math** is written with dollars, or with LaTeX's own delimiters: `\(…\)`, `\[…\]`, and display environments such as `\begin{align}…\end{align}` written without delimiters ([where math begins and ends](#where-math-begins-and-ends)). It goes to KaTeX in its untrusted mode (`trust: false`: `\href`, `\url`, `\includegraphics` and `\html…` show in red as written, and do nothing), with positive sizes capped at 20 em and at most 1,000 macro expansions. A formula that defines a macro (`\def`, `\gdef`, `\let`, `\newcommand` and the like) is shown as written: macros come from the bounded project setting with document front matter overriding it ([project macros](PROJECT-MACROS.md), LD-28), and a definition can multiply KaTeX's work far beyond the formula's length within that limit (a formula of 480 characters took KaTeX 35 s). Commands are read token by token with KaTeX's own token pattern, so a `\verb|…|` body or a `%` comment defines nothing. A comment starts only at a token that is `%` alone, as in KaTeX: `%` with a combining mark is another token, which a macro such as `\@secondoftwo` can skip unparsed. Where KaTeX's lexer would stop with an error, the reading goes on, finding more rather than less. KaTeX reads a `%` in the link of `\href`, `\url` or `\includegraphics` as a character, and which `%` that is depends on how it parses the formula, so in a formula with one of them and a `%`, every name after a backslash counts. LD-28 has the GUI apply such a definition to its own span, with a warning; this differs ([below](#differences-from-the-specification)). A formula KaTeX cannot parse is repaired if it can be, and otherwise shown as a plain-text approximation; either way it is marked, and its LaTeX as written is behind the mark ([math repairs](#math-repairs)). Rendering never changes the text. KaTeX's MathML remains available to assistive technology.
- **Copying math.** Selecting and copying a formula puts its original LaTeX, with the parser's original delimiters, on the plain-text clipboard (LD-44), including when the view shows a repair or Unicode approximation. A partial formula selection copies the whole expression without moving the visible selection. Mixed selections keep surrounding text and block boundaries; display-only repair marks and diagnostics are left out of the formula's plain text. HTML copying keeps the rendered view. Editor, code-only and non-math copying keep their ordinary behavior.
- **Nothing a text draws leaves its own box.** KaTeX caps only positive sizes, so `\smash` and a negative `\raisebox` could draw an agent's text over the tool call below it; the stylesheet clips each rendered text to its box (`contain: paint`).
- **Limits.** Text over 200,000 characters is shown as written. One text sends KaTeX at most 1,000 formulas and 20,000 characters of math, and no formula over 5,000 characters, since KaTeX's output is about 150 times its input; math beyond that is shown as written. The repairs of one text's formulas send KaTeX at most 20,000 characters more; beyond that, its formulas are approximated without them. Texts render in goes of 250 ms, each a task of the page's thread, with the Markdown, KaTeX and the page's update all counted, as when a page first shows all its texts. Within a go, texts render one after another. Once its time is spent, no further text starts: one that comes later shows as it was last rendered, or as written if it never was, and waits for its turn in a later go. KaTeX stops too, between formulas, and the math it had no time for shows as written, marked *not rendered yet*, until a later go renders the text again, starting where it stopped. The first text and the first formula of a go always render, so each go gets further, and a go can run over by one text's Markdown and one formula. So however much text and math a page has, its first view holds the page's thread about a quarter of a second, and the browser draws and takes input between goes. A formula whose repairs had no time waits for a later go too, and the model is not asked for it before the rules have been tried. Without definitions, the slowest formula of 5,000 characters found takes KaTeX about 60 to 80 ms (alternating `\Huge` and `\tiny`). KaTeX renders on the page's own thread, so one formula cannot be interrupted. The page keeps KaTeX's result for each formula, and the repairs' candidates and approximations, each within a count and a size, so a text rendered again sends KaTeX only what is new. The macros in force are part of what these results, and the model repairs, are kept by (LD-28).
- **Tool calls** show their arguments and results as plain text, each hidden character as its code point (a result's colour codes dropped, as code's are), as do a document's raw text in a conflict and a block's source. A result's rich outputs (HTML, SVG, images) are not rendered.
- **Code**, in tool calls and in Markdown, shows hidden characters as their code points, such as `⟦U+202E⟧`, so that code cannot read differently from what ran: controls but the tab and the line feed, format characters (zero-width, bidirectional and tag characters among them), surrogates, private-use and unassigned code points, line and paragraph separators, and every Default_Ignorable code point (`text.ts`, `visible`; the set is `hidden.fixtures.json`, which the server's check shares). Spaces other than U+0020, the blank Braille pattern and the object replacement character show as code points too, since they can pass for other text, though the server does not refuse them. Program output and code drop terminal colour and style sequences and read a carriage return as a line end (`visibleOutput`), so a progress bar reads line by line; every other hidden character stays a code point.
- **Text the user approves and agents then read** (threat model, A3) is shown by `ApprovalText` as the exact string agents receive, in a `<pre>` that holds the whole text above the controls the user decides with (never a scrolled box), each hidden character a chip naming its code point, with a count above when there are any and a warning when more than two blank lines in a row could hide what follows; against the text it replaces, word by word (line by line for long texts); and, when asked, a rendering apart, labelled as a preview, with every link address, title and reference definition the rendering would hide. A rendering can hide text that is plainly there: a link reference definition shows as nothing, a link's address and title show only on hover, and `\phantom`, `\color{transparent}` and a `%` comment in math draw nothing. The server refuses hidden characters in such text, written as they are or as character references of any number of digits or by name (`documents/agent_text.py`, `check_agent_text`), and more than two blank lines in a row between lines of text. U+FE0F is text right after an emoji or in a keycap (a warning sign or a check mark in its emoji form, a keycap digit), on both sides; an agent's line ends become line feeds before the check (`agent_text`).
- **A rendering or a text box that may hide something**, where the user reads text agents wrote or writes text agents read (a finding's statement, remedy and explanations, comments, the chat's messages, and the text boxes of plans, documents, comments, replies and chat messages), has a banner beside it (`HiddenBanner`) naming each hidden character with its line and column and, beside a rendering, every link address, title and reference definition the rendering hides, and what else it hides: math that draws nothing (`\phantom`, `\hphantom`, `\vphantom`, a transparent colour, a `%` comment), a character reference that shows as a hidden character, and a code fence's words after its language (`renderingHides`). A plain link, with no title, to the web, an email address or a page of the workspace, whose words name no address but its own (`plainLink`), hides only its address, which shows on hover: such links fold into a closed list, "Links (n)", which alone is all that shows when the text hides nothing else; every other link is listed openly. `ApprovalText` names these too. The run view's texts and a ledger entry's statement have the banner as well, and a comment has its exact text under its rendering. A rendered document has it too, but only when the document hides something (a character, math that draws nothing, a reference, a fence's extra words, or a link's title), so a document whose links show their address on hover has none; it lists every link only for a document under 4,000 characters, and otherwise only the links with a title, at most twenty of them. It shows nothing when there is nothing hidden.

D54 puts previews of untrusted artifacts (HTML, SVG, notebook output, PDFs, and agent-written Markdown) on a separate origin, in sandboxed frames. The workspace shows only text, in the app's own origin, under the rules above and the policy that admits no inline script. PDFs open on a separate origin ([below](#the-pdf-viewers-origin)); other rich artifacts wait for theirs. The [figures](specs/figures.md) spec (approved, not built) adds the preview origin's figure frame, the figure files it serves by capability, and `img-src` and `frame-src` for that origin in the workspace's policy.

### The PDF viewer's origin

PDFs are untrusted content, so the viewer has an origin of its own ([PDF viewer](specs/pdf-viewer.md), PV-1 to PV-3; [threat model](THREAT-MODEL.md), T6). The same process listens on a second port, `--preview-listen` (by default the next port on the same host; loopback unless `--allow-remote`), with a second application (`preview.py`) that serves only the viewer's bundle (`/viewer/`, from the build's `viewer/` directory) and PDF bytes for a capability (`/pdf/<capability>`). The workspace's own listener refuses `/viewer/`, so the renderer never runs on the workspace's origin. Behind a reverse proxy, `--preview-public-origin` gives it its `https://` origin instead of a name ([behind a reverse proxy](#behind-a-reverse-proxy)). The preview origin has no API and no login, takes only GET and HEAD, answers on loopback only to a `Host` that names it, and never reads a cookie: a request carrying the workspace's cookie, which the browser sends to every port on the host, gets exactly what one without it gets.

By default the viewer listens on `127.0.0.1` too, at the next port, but is given by the name `localhost` (`--preview-name`): the workspace is `http://127.0.0.1:8200`, the viewer `http://localhost:8201`. An IP address and a name are different *sites*, so the browser keeps them apart for scripts and storage, does not send the workspace's cookie to the viewer, and may run the viewer's and the figures' frames in a process of their own (FG-17). This works on every system and through an SSH tunnel that forwards both ports, with no second address; the listener answers to `localhost` as to its address. Given by `localhost`, it also listens on `[::1]` at the same port where this computer has an IPv6 loopback, so a browser that tries `::1` first reaches the viewer and no other program; `serve` warns when another program already holds that port. The browser must reach `localhost` at the listener, as browsers do (they resolve it to loopback, and try `127.0.0.1` when `::1` does not answer); a hosts file or proxy that sends `localhost` elsewhere breaks the viewer, and `--preview-name 127.0.0.1` gives the viewer by its address again, on the same site, with a warning at start. Another loopback address, such as `--preview-listen 127.0.0.2:8201`, is another site too, on Linux, which answers on all of `127.0.0.0/8`; macOS answers only on `127.0.0.1` until an alias is added (`sudo ifconfig lo0 alias 127.0.0.2`).

The workspace mints a capability when the logged-in user asks to view a published PDF: an HMAC-SHA-256 over the project, the artifact, the revision, its SHA-256 and an expiry 10 minutes ahead, under a key made at random when the process starts and kept only in memory, so a restart ends every capability; the expiry runs on a monotonic clock. A capability has exactly one spelling, unpadded base64url. The preview origin compares MACs in constant time, refuses a malformed, forged or expired capability (403), reads the bytes through the artifact inventory, which checks their size and SHA-256 (another revision's hash is not found, 404), refuses an artifact that is not `application/pdf` (415) or larger than 64 MiB (413), and answers with `Content-Disposition: attachment`, `nosniff` and a CSP that adds `sandbox`: PDF.js fetches the bytes, and a visit to the URL itself downloads them rather than rendering them in the browser's own viewer. It reads and hashes the bytes in a worker thread, at most four PDFs at once, so the event loop the two listeners share keeps serving the workspace.

Every preview response carries `Content-Security-Policy: default-src 'none'; script-src 'self'; worker-src 'self'; style-src 'self'; font-src 'self'; img-src 'self' data: blob:; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors <the workspace's origin>`, so only the workspace may frame it and a compromised frame cannot even send a request to the workspace's port, and `Cache-Control: no-store`. The workspace's own policy then adds `frame-src <the preview origin>`, and only that. Both origins are the ones the server prints (`http://127.0.0.1:8200` and `http://localhost:8201` by default), so open the workspace at the printed address: under another name for the same host, such as `localhost`, the viewer refuses to be framed (and would be the same site as the viewer).

The PDF view frames the viewer with `<iframe sandbox="allow-scripts allow-same-origin">` and `referrerpolicy="no-referrer"`. The link's fragment carries the capability and the workspace's origin (`#c=…&w=…`), and, for a page to open at, `p` (a number from 1; anything else opens the first page), and never reaches a server. The viewer shows one page at a time with selectable text, moves by page number or printed label, and zooms; **Copy anchor** posts the selection's anchor to the workspace's origin only, and the viewer takes no messages. Where the browser lists the origins that frame a page (`location.ancestorOrigins`), the viewer opens only when the nearest is the workspace the link names. The workspace accepts a message only from the preview origin and from that frame's own window, about the PDF it shows, and only in an anchor's exact shape (`src/lib/pdfAnchors.ts`); it adds the PDF's path, which the link names, and shows each control or bidirectional formatting character in the quote and the label as `⟨U+…⟩`, so the anchor reads as it is. Opening the PDF again changes only the fragment, and the viewer reloads itself for it.

**Figure files** ([figures](specs/figures.md), FG-12, FG-13). The preview origin also serves a pinned PNG or JPEG for a page's `<img>` (`/file/<capability>`), for a capability the workspace mints as it mints the viewer's (`GET …/revisions/{revision}/figure?sha256=`), so the workspace's own origin draws no figure. It serves the file only as the type it is recorded as, and only when its first bytes are that type's: a `.png` that holds HTML is refused (415), and so is an image over 8 MiB or, by its header, over 50 megapixels or 16,384 pixels on a side (413). A capability names the route it was minted for, `pdf` or `file`, under its MAC, so a PDF's capability opens nothing on `/file/` and a figure file's nothing on `/pdf/`. The answer has the file's media type, `nosniff`, `no-store`, `Content-Disposition: attachment` and the preview origin's CSP with `sandbox`; only an image served is marked `Cross-Origin-Resource-Policy: cross-origin`, so that the workspace's page, another origin, may load it, and every refusal stays `same-origin`. With the preview origin on, the workspace's CSP adds it to `img-src` as well as `frame-src`, and nothing else. The artifact list offers "Show the image" on a kept PNG or JPEG within the size (`FigureImage.svelte`, `src/lib/figures.ts`), which mints the link when opened; an image the server or the preview origin refuses shows its path and the reason. **References in text** (FG-6 to FG-9, FG-17). The renderer (`Markdown.svelte`, `src/lib/figureRefs.ts`, `FigureRef.svelte`) draws a text's references to recorded files where the text writes them: a document revision's (its view's `pins`, with a newer revision as `latest`), a ledger statement's and a chat message's. Each path image the rendering shows outside code, math and links is matched in order to the pin of its path, and its place, made with the DOM, never from markup, is given to the figure: a PNG or JPEG as an image, an SVG, HTML file or PDF in a frame, any other type as a link, or a broken reference with its path and why (no recorded file, deleted, its bytes not kept, a relative path without a session). Beside it, its pinned revision and a newer one (`r3, newer: r5`); on a document's current revision, "Move the pin to r5" saves a `repin` patch, which makes a revision whose text is unchanged, and the document is read again. A text draws at most 20 figures; the rest show their source and "Draw this figure". At most eight frames draw at once on the page.

**The figure frame** (FG-14, FG-17, FG-18). The preview origin serves a bundle of its own under `/figures/` (`src/figures/`, built into `dist/figures` by `vite.figures.config.ts`), which the workspace's listener never serves. Its CSP is the preview origin's with `style-src 'self' 'unsafe-inline'`, for the libraries that come with F5 and F6, and never `'unsafe-eval'`. Its URL's fragment names the workspace's origin; framed by another, it draws nothing. It takes one message, from that origin and its parent window only, in an exact shape (`src/figures/protocol.ts`): the figure's kind, a fence's text and one capability for each file it shows; anything else is ignored, and a second request is ignored too. It fetches only that figure's capability from its own origin, decodes an SVG as an image (so it runs no script and loads nothing, whatever it holds) and paints it once onto a canvas fitted to the frame's width, each side at most 4,096 CSS pixels and 2^24 canvas pixels, so nothing in it animates and the browser never repaints it, and answers the workspace's origin only with its size and `rendered`, or an error with a code from a fixed set (`refused`, `type`, `size`, `unreadable`, `framing`), which the page words itself: no text from the frame reaches the workspace's page. What a library draws (F5, F6) goes through `src/figures/sanitize.ts`, an allowlist: the markup is parsed as XML into a document of its own, and only listed SVG elements and attributes survive, with no value that could reach an address (`url(#id)` within the figure is kept); animation (`animate`, `set`, `animateMotion`, `animateTransform`), `style`, `a`, `image`, `use`, `feImage`, `script`, `foreignObject` and every other element are dropped, and so are `href`, `src`, `srcset`, `poster`, `background`, `action`, `formaction`, every event attribute and any style that loads or imports. It is not DOMPurify, whose output rests on the browser's HTML parser, which the tests' DOM does not reproduce for SVG. The preview origin serves an SVG figure only when it is UTF-8 and begins, past its prolog, with `<svg`, as an attachment for the frame's fetch; an HTML figure only as UTF-8 text without a NUL, `inline`, with the CSP's `sandbox` and no allowances, so it runs no script even opened by itself, framed by the workspace only. The page (`FigureFrame.svelte`) frames the figure frame and the viewer with `sandbox="allow-scripts allow-same-origin"` and `referrerpolicy="no-referrer"`, and an HTML figure with `sandbox=""` at a fixed 400 px with its own scrolling. It makes a frame when the figure comes within 200 px of the view, draws at most eight at once, and removes a frame not drawn within 5 seconds, showing the figure's path and why; it takes a status only in the exact shape, from that frame's window and the preview origin, and sizes the frame by it, at least 20 and at most 4,000 px. A frame of another site in a page the browser is not showing (a hidden pane, a background tab) may have no width at first: the figure frame and the viewer's figure mode wait for a width before they draw, up to 1.5 seconds, then draw at the figure's own size (`src/figures/layout.ts`), and send their size again whenever it changes, the viewer fitting its page again; once a figure is drawn, the page takes a later size too, one at most every 200 ms, so a figure drawn while hidden is sized when it is shown. A PDF figure is the viewer in its figure mode (`m=figure` in the fragment): one page fitted to the frame's width, without the controls, its size sent to the workspace. The artifact list offers "Show the figure" on a kept SVG, HTML file or PDF of at most 8 MiB.

**Charts** (FG-4, FG-15, FG-17; `src/figures/chart.ts`, `vegaChart.ts`). A `vega-lite` fence is drawn in the figure frame where the text writes it (`FigureChart.svelte`), from the data files its text pins: the page asks `GET /api/v0/projects/{project}/figures/chart?data=ARTIFACT:REVISION:SHA256` (each data path's pin, in order, at most 16 CSV, TSV or JSON files of 8 MiB in all) for the frame's URL and a capability for each, and posts the frame the fence's text with each data path and its capability. The preview origin serves a data file as its type, UTF-8 text only. The frame refuses a chart whose JSON does not parse or passes 64 KiB, that names a Vega-Lite version other than 6 (`$schema` is a label, never fetched), holds inline `values` or `datasets` or other generated data than a `sequence` of at most 10,000 values, or names any address but its pinned paths, an image mark or a link; it compiles the chart with Vega-Lite 6.4.3, parses it with Vega 6.4.0 for the interpreter (`vega-interpreter` 2.3.2), and runs it with a loader of its own that answers only the pinned paths, at most 8 MiB in all, then refuses more than 20,000 marks; its SVG goes through the sanitizer before it is shown, named by the chart's description or title. Vega's delimited reader builds each row with generated code, which the frame's CSP refuses, so the frame gives Vega its own readers for CSV, TSV, DSV and JSON (other formats, such as TopoJSON, are refused), which stop past 100,000 rows whatever ends a line, and a `sequence()` in an expression is bounded as a data `sequence` is. Vega swallows what its loader and readers throw and draws without the data; the frame notes each refusal and refuses the chart after the run, so an expired capability, a refused file or too many rows is shown, never a chart drawn without them. Compiling, running and drawing happen in a worker the frame starts from its own bundle for each chart, which it terminates after 4 seconds (`time`), before the page's 5: the frame may share the workspace page's thread, but the chart's work does not (review of #500, M1). A chart takes the pins of its own block, one for each time it names a path, so one chart never draws another's revision. Memory is bounded too, since frames of the same site share the page's process (and a browser may still put the default preview origin, another site, in the page's process): no transform may output more than 100,000 rows (a `flatten` of one long array, an `impute`), nor any dataset hold more after its transforms; the drawn scene's text is at most 1 Mi characters, checked before the SVG is made; the SVG is at most 3 Mi characters, checked in the worker before it is sent and again in the page before it is parsed; and the page draws at most two charts at once (`charting`), each also holding one of the eight frames' turns. What the chart's expressions make is bounded as it is made: an expression's text is at most 1 KiB; every value Vega's interpreter gives, and every string or array its string and array functions (`pad`, `truncate`, `upper`, `lower`, `trim`, `substring`, `replace`, `split`, `slice`, `join`, `reverse`, `sequence`) build, is at most 64 Ki characters a string and is spent against the run's 16 Mi characters and 1 M array elements; and no transform's output holds a string field past 64 Ki characters or more than 1 M array elements, so grouping long strings or doubling one by concatenation is refused (`size`) before it can exhaust the page's memory. These checks read into a value's arrays and plain objects at any depth, so a string doubled inside an object (`{v: datum.o.v + datum.o.v}`) is caught too (review of #500, L1). Every function an expression calls, the interpreter's own (`indexof`, `test`, `parseFloat`, …) as well as Vega's, first has each argument checked, a string at most 64 Ki characters, so none reads a string built past its limit. A function whose result could pass the limits is refused before it builds it, from its arguments (L2): `pad` to its length, `join` by its elements and separator, `truncate` with its ellipsis, `replace` by its matches and replacement, a number `format` by its width (also in a specification's `format`), and `timeSequence` and `utcSequence` at most 10,000 steps, as `sequence`. A chart whose data path is not pinned shows why, with its source; every chart offers its source. A text draws at most 20 figures, charts among them.

The preview origin's SVG check is a linear scan (`svg_begins`): a regular expression with a lazy comment in a repeated group backtracked for hours on 40 comments, holding the interpreter's lock, which would have frozen both listeners (review of #492, H1).

Known limits and trade-offs (review of #487 and #492):

- **One thread.** A preview origin that differs from the workspace's only in port is the same site, and a browser may run its frames on the workspace page's own thread. A figure's draw is bounded (one paint of a canvas of bounded size; a frame not drawn in 5 seconds is removed), but an HTML figure is the browser's own page, and its CSS (animation, heavy layout) is not bounded: on the same thread it can slow the workspace's page for as long as it is shown. By default the preview origin is `localhost` and the workspace `127.0.0.1`, two sites, so the frames may have a process of their own; `serve` warns when the preview origin is given by the workspace's own host (`--listen localhost:…`, or `--preview-name 127.0.0.1`). Whether the browser does give them a process of its own is its choice (site isolation); a static rendering of HTML figures would remove the risk; it is not built.
- **One preview origin for every figure** (I2). Every frame of every project is on the same origin, so one compromised frame could read another's DOM. Each frame holds only what its own capabilities open, for 10 minutes, and nothing in a frame runs a figure's own script; an origin per figure is not built.
- **Bearer capabilities** (I3). A capability opens its file for anyone who has it, for 10 minutes; under `--allow-remote`, over plain HTTP, it travels in the clear with every request. It names one route (`pdf` or `file`) under its MAC.

### Where math begins and ends

Comments and anchors address math spans, so the browser and the server must agree where each formula begins and ends (D65). The browser's rules (`src/lib/dollarmath.ts`) are a port of the `dollarmath` plugin of mdit-py-plugins 0.6.1, which the server uses with markdown-it-py ([living documents as built](LIVING-DOCUMENTS.md#parsing)), with these settings on both sides, and one rule of this project's own:

| Setting | Value | Effect |
| --- | --- | --- |
| `allow_space` | false | `$ x$` and `$x $` are not math, so amounts such as "$5 and $10" stay text |
| `allow_digits` | true | A digit may touch a dollar sign. The plugin's check for the other setting has no exact JavaScript twin |
| `double_inline` | true | `$$…$$` inside a paragraph is displayed math, as agents often write it |
| `allow_blank_lines` | false | A blank line ends a `$$` block, so a stray `$$` cannot swallow the rest of a text |
| `allow_labels` | true | `$$…$$ (eq:1)` labels an equation |
| A `$$` block ends within 200 lines of its opening line (this project's own) | | The plugin looks to the end of the text from every `$$` that does not close, which makes some texts take quadratic time; past the limit, `$$` is ordinary text, so such math is displayed within its paragraph |

The dialect is markdown-it's default (markdown-it-py: `js-default`) with HTML off. The cases in `src/lib/dollarmath.fixtures.json` pin the spans, and the server's parser passes every one, the line limit applied to the plugin's block rule ([living documents as built](LIVING-DOCUMENTS.md#parsing)). Table parsing has two profiles: profile 2 matches the browser's row and cell trim, and a seeded whole-document comparison checks complete blocks, math and source offsets and attached IDs; profile 1 keeps its original reading for older revisions ([table profiles](TABLE-PARSER-PARITY.md)). The port keeps the plugin's quirks, which the cases record: a `$$` block in a block quote keeps the quote markers in its content (a document's view renders it without them), a block can end in the next list item, the text is the plugin's (stripped of all Unicode whitespace, except an image's description, which neither side strips), and a backslash that ends a text escapes a dollar sign that starts it.

**LaTeX's own delimiters** (`src/lib/mathdelimiters.ts`). Agents often write `\(…\)`, `\[…\]` and bare display environments (`equation`, `align`, `alignat`, `gather`, `multline`, `flalign` and `eqnarray`, starred or not, and `displaymath`). markdown-it reads them as rules of its own, which give the same tokens as dollar math and follow its rules: a delimiter after an odd number of backslashes is escaped, counted as for dollars (so a backslash that ends a text escapes a delimiter that starts it, the plugin's quirk); inline, a formula ends at the first closing delimiter in its paragraph, and one of only whitespace, Python's as for dollars, is not math; a block begins a line and its closing delimiter ends one, within 200 lines and with no blank line between. Code blocks are read as code wherever they are, indented or fenced, in lists and quotes too, so nothing in them becomes math. Code spans are read as dollar math reads them: a span that starts before a formula keeps it, but a formula that starts before a span runs over its opening backtick (`\(a `b \) c` d` makes "a `b " math). The rules differ from `$$` in four ways: a `\[` or `\begin{…}` line may begin a block right after a line of a paragraph, as a code fence may, since it can only be math; a block stops, as a fence does, at a line outside its list item or quote, where `$$` reads on into the next item or a lazy line; a block whose closing delimiter has more text after it on its line is read within its paragraph, where `$$` would look further for a line that ends with `$$`; and a block's content leaves out the markers of the quotes it is in. An environment is its own delimiter, so KaTeX gets the whole environment, except `displaymath`, whose body it gets. Adding these rules changes no dollar case. The cases in `src/lib/mathdelimiters.fixtures.json` pin the spans; the server's parser passes them too. The rules come from the user's own `cscience-crypto`, which converts these delimiters to dollars before parsing; reading them while parsing keeps code as written in indented code and in fences inside lists and quotes, which a conversion before parsing rewrote, keeps a displayed formula in its list item, and pairs no delimiter with a stray dollar sign.

**Escaped brackets.** Markdown writers escape brackets that are not links (`See \[1\]`, `\[sic\]`, `- \[x\] done`, and Pandoc's `\[@smith2020\]`, `\[^1\]` and `\[path\_to\_dir\]`), which is also LaTeX's displayed math. Within a paragraph, `\[…\]` is displayed math in two cases:
- its content is padded with a space, a tab or a line feed just inside both brackets (`\[ a - b \]`), as TeX writers pad and Markdown writers' escapes do not;
- unpadded, it holds what math uses and bracketed prose seldom does: a command (a backslash and a letter), a brace, one of `= + < >`, or `^` or `_` after its first character (`^1` alone is a footnote's reference).

A backslash before ASCII punctuation is a Markdown escape, and it and the character it escapes count as neither. Anything else stays text, as the escapes make it.

So "See \[1, 2\]", "we \[...\] agree", "pages \[3-5\]", "version \[1.2\]", `\[path\_to\_dir\]`, `\[\*\]`, `\[\#1\]` and Pandoc's citations and footnotes stay as written. "so \[x^2\] holds", `\[\alpha\]`, `\[a = b\]`, and every padded formula, such as `\[ f(x) \]`, `\[ |x| \]`, `\[ n! \]` or `\[ -1 \]`, display. A line that is only `\[n\]` is a displayed formula, since the rule is for brackets within a paragraph.

The trade-off goes both ways:
- unpadded displayed math within a sentence with nothing of the rule, such as `\[n\]`, `\[2\]`, `\[f(x)\]` or `\[a - b\]`, shows as bracketed text, as `\[1\]` and `\[x\]` must;
- escaped brackets around prose with one of `= + < >` or an underscore inside a word, such as `\[debug=true\]`, `\[C++\]`, `\[<tag>\]` or `\[my_var\]`, show as math.

The content is read character by character, a line break as any other, since Pandoc wraps lines inside brackets too. The shared cases pin all of these. The server's port reads the content the same way, character by character, with no pattern.

## Math repairs

When KaTeX rejects a formula, the renderer tries three things in turn (`src/lib/mathrepair.ts`, with the rules in `texRepairs.ts` and the approximation in `texUnicode.ts`; the browser-only model client is `modelRepairs.ts`, which the server-side math checker does not bundle), and shows what it got with a mark that says which:

1. **Rules** (*auto-repaired*). Deterministic repairs, chosen by KaTeX's error: commands KaTeX lacks (`\mbox`, `\emph`, `\abs`, `\norm`, `\eqref`, `\R`, `\eps`, `tabular`, `eqnarray`, …), labels, references and spacing commands dropped, `\text{…}` arguments escaped, braces and `\left`/`\right` balanced, bare `%`, `#` and `&` escaped, double scripts nested (`x_i_j` as `x_{i_j}`), dangling `_` and `^` dropped, `&` and `\\` outside an environment wrapped in `aligned` or `gathered`, display-only environments made inline ones in inline math, and an unknown command shown as an operator's name (`\Tr` as `\operatorname{Tr}`). The first candidate KaTeX renders is shown. A rule changes a command only where its backslash starts one (in `\\R`, a line break and an R, nothing changes), a removal never joins a command to the letters after it (`\d\label{x}ef` becomes `\d ef`, not `\def`), and a candidate that brings in a definition, or a command KaTeX gates by trust that the formula did not have, is dropped.
2. **The reviewer model** (*model-repaired*), when the server has one. The page asks the server once for each formula, in the background, and keeps up to 2,000 answers until it reloads (the server keeps them too, so asking again for one the page dropped costs no model call): one request at a time until the server says it has a model, then two. When the server says it has none, or the session ends or reaches its limit, the requests still waiting are dropped at once, and so is any answered `busy` after that. An answer of `busy` is asked again after 2, 4 and 8 s, then given up for the page. Meanwhile the formula is approximated, and its mark is dashed. When answers come, KaTeX checks them, and the texts that show those formulas render again, at most once a frame (once a second in a hidden tab). An answer that brings in a definition, or a command KaTeX gates by trust, is not shown.
3. **An approximation** (*approximated*). The formula in Unicode, as nearly as plain text allows: Greek letters and operators, sub- and superscript digits and letters, blackboard bold, fractions as `a/b`, matrices and cases flattened, and unknown commands by their names.

Pressing a mark shows why (KaTeX's error, and who repaired it or why nothing did) and the formula as written, with its delimiters, to read and copy; bidirectional controls in it, and in KaTeX's error, which quotes it, show as their code points, as in code, in the mark's title too. The text never changes: repairs are a view, as the rendering is. The marks are buttons, and the app's own script opens them, so the page needs no inline script. A mark and what it shows sit above anything a formula draws, so `\rlap{\colorbox{white}{…}}` cannot hide them. A repair is rendered within the text's math limits ([showing untrusted text](#showing-untrusted-text)), and a formula over 5,000 characters is not repaired.

Copying uses the renderer's original formula body before trimming, repair or macro expansion, with its parser delimiters. In living-document display math, the markers of quotes and lists are left out by the same source extraction used for rendering. Bidirectional controls stay visible as code points in the diagnostic panel; the copy-only escaped metadata keeps their original characters. No source revision is changed. The one copy handler of the app runs only for a single nonempty selection inside the app that contains formula metadata, uses a cloned range, and needs no asynchronous clipboard permission, route or content-policy exception. Table copying keeps the selected DOM's outer newlines and tab-separated cells; code-only copying keeps the browser's own newline handling. Checked with native copy and paste in a browser ([report](../.agents/docs/agent-reports/workspace-copy-latex-2026-10-12.md)).

**The endpoint.** `POST /api/v0/math-repair` takes `{"tex", "display", "error"}`: one formula without its delimiters, at most 4,000 characters, whether it is displayed, and KaTeX's error, cut to 500 characters. Optional `project` and `macro_context` identities must appear together; the project is validated and both identities are bounded. They isolate the repair cache, grant no authority to read sources and do not go to the model. Requests without them are still accepted. Like every API route it needs the session, and like every POST the server's own origin. It answers `{"enabled": false, "tex": null, "reason"}` when the server has no reviewer model, and the page then asks no more; otherwise `{"enabled": true, "model", "tex", "reason", "cached"}`, where `tex` is the repair or null and `reason` says why there is none (`no usable repair`, `busy`, a gateway failure).

**The model.** Requests go to the reviewer model the settings name, through the model gateway, and to no other model: never a session's or a subagent's, whose output is what is being repaired. Settings, as for the harness's `run`:

| Setting | Meaning |
| --- | --- |
| `--model-url` | The model gateway's OpenAI-compatible base URL (the LiteLLM proxy, D61), as the gateway answers it: no redirect is followed |
| `--reviewer-model` | The reviewer model's alias at the gateway; `off`, `none`, `false`, `0` or `disabled` turn model repairs off |
| `--api-key-file` | A file holding the workspace's key for the gateway |

Without the three, or with `--reviewer-model off`, model repairs are off and the server never connects to the gateway. The key is a secret: the server sends it only in the gateway's `Authorization` header, and never returns it. Its log lines about failed repairs hold only the gateway's status or the kind of failure, never the gateway's text, which can quote the key; any other line that would hold the key holds `[the gateway key]` instead. The key file must hold one line of visible ASCII characters, or the server does not start, and it warns when others can read the file. Give the workspace a LiteLLM virtual key of its own, with its own spending limit. The server follows no redirect from the gateway, which would carry the formula elsewhere, takes any answer but a 2xx as an error, and reads at most 1 MiB of an answer. Unlike the harness's calls, a repair is not tried again after a rate limit or an unavailable upstream: someone is waiting, and can ask again. The rest are rules of the orchestrator's model client, so they hold for the harness's own calls too: a `--model-url` that the gateway redirects, such as an `http://` address it sends on to `https://`, fails both the workspace's repairs and `run`, which then needs the address the redirect names.

**Limits** (`packages/workspace`, `mathrepair.py`):

| Limit | Value |
| --- | --- |
| A formula sent | 4,000 characters, with KaTeX's error cut to 500 |
| An answer | 512 tokens, within 25 s, and 1 MiB from the gateway |
| Requests to the model at once | 2, with 8 more waiting; beyond that the answer is `busy`, which the page asks again later |
| Answers kept | 512, the least recently used dropped first; a repair or a refusal until the server stops, a failure (a timeout, the gateway's error, an answer it cannot read, anything else) for an hour, as the user settled for living documents (LD-46) |
| Requests to the model for one browser session | 60 in any hour; beyond that the endpoint answers 429, and the page asks no more |

A formula the server has answered costs nothing more, whichever session asks. The model's answer is cleaned of code fences, with an info string such as `latex` (on a fence of one line, only a known one: `latex`, `tex`, `math` or `katex`), and of delimiters, and refused if it is empty, the formula unchanged, more than three times as long plus 200 characters, or `UNFIXABLE`, the model's word for a formula it cannot repair without changing its meaning. It is untrusted LaTeX like any other: KaTeX renders it in its untrusted mode, and the page shows it marked as the model's.

**What leaves the machine.** With model repairs on, each formula that neither KaTeX nor the rules can render, with KaTeX's error and whether it is displayed, goes to the model gateway, and from there to the provider behind the reviewer alias. Nothing else of the text goes: not the sentence around the formula, nor the project, session or run. A formula from embargoed or restricted work goes too, so leave model repairs off, or point the reviewer alias at a model the data may reach, when such work is shown.

The repairs, the approximation and the endpoint are adapted from the user's own `cscience-crypto` (`src/web/cscience-math.js` and `pkg/platform/lib/math-repair.mjs`, with their tests), contributed under the MIT License; each file says so. Its patches to the upstream Web UI are not part of it.

### Differences from the specification

The [living documents](specs/living-documents.md) spec states this behavior for the platform (LD-41 to LD-48). The workspace differs from it in three ways:
- it reads LaTeX's delimiters while parsing, where LD-41 drafts a conversion before parsing, and saves a living document's text in the dollar form with a conversion checked against that parse ([living documents as built](LIVING-DOCUMENTS.md#changes));
- the repair endpoint is the workspace server's, with cache isolation by project and effective context and a limit for each browser session, where LD-45 and LD-46 put it in the control API with records of each call and the project's model budget;
- a formula that defines a macro is shown as written, where LD-28 has the GUI apply a definition made inside a span to that span alone, with a warning. The GUI refuses definitions because one can multiply KaTeX's work many times over within its limit on expansions (the 480 characters that took 35 s), and because macros belong in the project's settings and the document's front matter, which LD-28 provides. Whether to keep the refusal, or apply definitions within a span under a tighter limit, is a point for the user.

Document revision saves schedule durable math checks with this KaTeX and these settings. Rejected formulas in eligible agent and worker blocks create mechanical `warn`/`math` findings with exact provenance, suggested deterministic remedies and delivery only when a run closes ([document math checks](MATH-CHECKS.md)). The operator must configure the renderer; without it, checks stay inconclusive.

## Checks

```bash
cd web/workspace
python3 ../../scripts/check_licenses.py --npm package-lock.json
npm ci --ignore-scripts
python3 ../../scripts/check_licenses.py --npm package-lock.json --installed
npm run format:check    # prettier; npm run format rewrites src

```

CI runs these in the `web` job, and then the math checker's and the figure checker's tests. The license check reads the lockfile before anything is installed: a version 3 lockfile, in which every package must declare a tier 1 license ([licensing](LICENSING.md)), come from the npm registry with a SHA-512 integrity hash, and, unless it is optional, need no install script. License expressions are read with their precedence, so `(MIT OR Apache-2.0) AND GPL-3.0-only` fails. After `npm ci`, `--installed` also checks each installed package's own `package.json`, which the integrity hashes cover, against the lockfile's license and version.

The notice tests compare two builds byte for byte, check every emitted file against the notice manifest, and check the primary notice texts, the runtime helpers, all sixty fonts and embedded copyright and reserved names. Negative cases cover missing or changed licenses, lockfile and install mismatches, unknown modules, helpers, styles and assets, modified fonts, outside origins and public-directory copying. SIL OFL applies to the unmodified font assets and embedded glyph-derived SVG assets; the Apache 2 and MIT embedded helpers fit the platform-code allowlist.

The app's tests (vitest, next to each module in `src/lib`; those named `*.dom.test.ts` mount a view in happy-dom, with Svelte's browser runtime, and click through it) cover the shared parser cases through both parsers, the attachment of the server's IDs, macros and their bounds, the Markdown component's escaping, links, images and math budgets, the math delimiters, repairs and approximation, the caches, the requests for model repairs, the routes and the polling panels. The server's tests (`packages/workspace/tests`) cover login and sessions, the origin and host checks, the headers, the static files, every API route against stores the orchestrator's own code wrote, the worker proxies against fake peers, the math repair service against a scripted model and a fake gateway, the command end to end, and that the API table above matches the registered routes. Clipping a text to its box is a stylesheet rule, so it is checked in a browser.

Packages are untrusted downloads. `web/workspace/.npmrc` turns install scripts off, saves exact versions and refuses a Node version the tools do not support. To add or update one, pick a version some weeks old and resolve with a cutoff date a little after it, then run the license check:

```bash
npm install --ignore-scripts --before=2026-10-07T00:00:00Z some-package@1.2.3
```

### Stored run evidence download

`GET /api/v0/projects/{project}/sessions/{session}/runs/{run}/evidence` downloads
`sandbox-run-evidence-v3` NDJSON under the workspace's normal login and project
scope. It takes no query/body, supports unfinished runs with stored evidence,
and returns 404 for an unknown run. Two downloads may be active; further requests
receive 429. The route is read-only and leaves no server-side export file.

The snapshot includes the final run JSON when present, archive messages and native
provider bytes, saved text samples, tool intents, full structured tool records,
starting inputs and observed model usage.
It does not include external worker files or referenced document revisions. Each
text/blob field has its storage type, byte count, base64 chunks of at most 64 KiB
and a SHA-256. A final checksum covers every preceding byte of the download.
Rows appended after the snapshot are excluded. Existing omissions and truncation
metadata remain unchanged; a missing final checksum means an incomplete download.

Verify a downloaded file offline, without loading it all into memory:

```bash
uv run python -m sandbox_science.orchestrator.context.history.verify_export run.evidence.ndjson
```

The manifest names the project/session/run and per-table row cutoffs and counts.
`row`/`row_end` delimit a stored row. `value` holds scalar/null fields;
`field`/`chunk`/`field_end` delimit exact text/blob bytes. Join a field's decoded
chunks before UTF-8 or JSON decoding. Checksums detect corruption, not authenticity.
See the [continuity contract](specs/research-continuity.md#stored-evidence-download-contract).
The verifier also accepts v1/v2 bundles with their original table field sets.

### Context inspection across continuations

The saved-run history and individual run event pages offer **Context management**.
The timeline follows journaled answers and fold events for the selected saved or
live attempt; auxiliary reviewer/fold usage refreshes as a bounded intent snapshot.
Original history and captured-input listings can select that attempt or all
attempts with its immutable work identity; children and siblings have their own
conversations. Continuation links identify epoch and predecessor, and unsaved
attempts remain inspectable without requiring a final run record.

**Search all pages** scans bounded pages automatically, pausing after 100 pages
or 200 new matches. **Continue automatic search** resumes at the cursor. Stop
and dialog dismissal abort the pending request. The latest 200 snippets remain
in memory; earlier originals remain archived and can be found again. Indexed
search reports pending coverage and offers explicit bounded backfill. Composition
uses separately captured adapter-input messages and tool schemas from the original
model intent; it never reconstructs a hypothetical prompt from run previews.
Provider-native replay, hidden reasoning and uncaptured legacy inputs remain
unavailable.
